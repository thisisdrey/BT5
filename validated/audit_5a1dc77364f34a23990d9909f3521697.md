### Title
Vault `deposit` can mint `0` zTokens while consuming a depositor's underlying — mirrors ACO's "mint 0 tokens" bug ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Every asset vault's `deposit` function (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`, and their `local-testing` mirrors) computes the shares to mint via `convert-to-shares-preview`, but — unlike `redeem`, which explicitly guards against a zero output — `deposit` never asserts that the computed share amount is non-zero before pulling in the user's underlying and minting shares.

### Finding Description
`deposit` computes `inkind` from `convert-to-shares-preview(amount)`: [1](#0-0) 

```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

When `total-supply-preview` (`ts`) is non-zero and `total-assets-preview` (`ta`) exceeds `ts` (i.e., the vault's share price is > 1, which happens naturally as interest accrues over time), `mul-div-down amount ts ta` rounds down. For sufficiently small `amount` values relative to the exchange rate, this returns `u0` even though `amount` itself is strictly positive. It also returns `u0` outright whenever `ta` is `u0` while `ts` is non-zero (e.g., after all underlying has been borrowed out / socialized as bad debt but shares still exist).

`deposit` then proceeds with this zero `inkind`: [2](#0-1) 

The only guards present are `(asserts! (> amount u0) ERR-AMOUNT-ZERO)` and `(asserts! (>= inkind min-out) ERR-SLIPPAGE)`. Neither prevents `inkind == 0`: `amount` (the underlying being deposited) is non-zero, and if the caller passes `min-out = 0` (the default/naive value used by most integrators and by `supply-collateral-add` callers who don't anticipate rounding), the slippage check trivially passes for `inkind = 0`. The function then calls `receive-underlying` (pulling the user's real tokens into the vault) and `ft-mint? zft inkind recipient` (minting `0` shares), permanently absorbing the depositor's underlying into vault assets with no corresponding claim issued to them.

By contrast, `redeem` in the very same contract explicitly guards this exact class of bug: [3](#0-2) 

```
(asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
(asserts! (not (get redeem states)) ERR-PAUSED)
(asserts! (> amount u0) ERR-AMOUNT-ZERO)
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
(asserts! (>= inkind min-out) ERR-SLIPPAGE)
```

`ERR-OUTPUT-ZERO` (`err u803012`) exists as a constant precisely for this purpose but is never applied on the `deposit` path — the exact asymmetry that caused the referenced ACO `ACOToken._mintToken` bug (mint functions allowing `getTokenAmount` to return `0` for a non-zero input, silently consuming collateral with no token issued).

This affects the direct entry point (`vault-usdc.deposit`, etc., callable by any unprivileged principal) as well as the indirect path through `market.clar`'s `supply-collateral-add`, which calls `vault-deposit` with a `min-shares` parameter fully controllable by the caller: [4](#0-3) 

### Impact Explanation
This is a direct loss of user principal: the depositor's underlying tokens are transferred into the vault and increase `assets`, but they receive `0` zTokens, meaning no claim on the vault whatsoever. Their deposited value is effectively donated to existing zToken holders. This is unclaimable by the depositor (no shares exist to redeem against), constituting theft of user funds at rest — the depositor's funds are irretrievably lost to them and redistributed to other users. This maps to the in-scope Critical impact: **direct theft of user funds at rest**.

### Likelihood Explanation
The rounding condition (`ta > ts`, share price above 1:1) is the normal, expected steady-state of any vault once any interest has accrued — it is not a rare edge case. Any user (or automated integrator) who deposits a small `amount` relative to the vault's assets-to-shares ratio, using `min-out = 0` or a low slippage tolerance, will trigger this without any special privilege or malicious intent required, though it can also be deliberately engineered by an attacker who front-runs/observes a favorable exchange rate and induces another user (or their own second address) to deposit a small dust amount to test/confirm zero-share minting, or simply exploits it against their own funds to grief the observed accounting (donating value to inflate other holders' shares, which itself can be a precursor to griefing other users' expected redemption value).

### Recommendation
Add `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` to `deposit` in every vault contract (`v0-vault-usdc.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`, and the `local-testing` equivalents), mirroring the existing check already present in `redeem`, so that a deposit which would mint zero shares reverts instead of silently consuming the user's underlying.

### Proof of Concept
1. Let a vault reach a state where `total-assets-preview() = TA` and `total-supply-preview() = TS` with `TA > TS` (share price > 1), e.g., after normal interest accrual over time.
2. An attacker (or unwitting user) calls `deposit(amount, 0, recipient)` where `amount` is small enough that `mul-div-down(amount, TS, TA) == 0` (e.g., `amount < TA/TS`).
3. `deposit`'s checks pass: `amount > 0` ✓, `inkind (=0) >= min-out (=0)` ✓, supply cap check passes.
4. `receive-underlying` pulls `amount` of real underlying tokens from the caller into the vault, `var-set assets` increases by `amount`.
5. `ft-mint? zft 0 recipient` mints zero zTokens — the caller receives nothing representing their deposited `amount`, which is now unrecoverable by them and has been absorbed into the vault's asset base for the benefit of existing shareholders.
