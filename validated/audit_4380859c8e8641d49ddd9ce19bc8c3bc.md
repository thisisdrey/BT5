## Title
Active-permission holder can escalate to full Owner control via `AccountPermissionUpdateContract`, and can front-run the legitimate owner's revocation to permanently seize the account - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
This is a valid analog. The Drips `Caller.authorize()`/`unauthorize()` bug (a delegated/lower-trust key can re-grant itself authority and front-run its own revocation) maps to java-tron's account multi-signature permission system. A signer holding only an `Active` permission that has the `AccountPermissionUpdateContract` operation bit enabled can submit an `AccountPermissionUpdateContract` transaction that unconditionally overwrites the account's `Owner`, `Witness`, and `Active` permissions - with no check that the resulting permission set is consistent with, or subordinate to, the permission that authorized the change. This lets a delegated key escalate itself to full `Owner` control and lock out the legitimate owner, and it can front-run any attempt by the real owner to revoke it.

### Finding Description
Signature verification for any transaction is delegated to `TransactionCapsule.checkPermission`/`validateSignature`, which only verifies that (a) the referenced permission exists, (b) if it is a non-zero `permissionId` it must be of type `Active`, and (c) the operations bitmask of that `Active` permission includes the bit for the contract's `ContractType`: [1](#0-0) 

This check is purely "does this Active permission's bitmask allow this ContractType", with no notion of permission hierarchy (Owner vs Active). Because `AccountPermissionUpdateContract` (type 46) is one of the generally-allowed contract types in the default/available-contract-type mask, an owner can (intentionally or via a mis-scoped grant) enable this bit in an `Active` permission: [2](#0-1) 

Once that bit is set, any key in that `Active` permission (which may have a very low threshold, e.g. weight 1 of 1) can sign an `AccountPermissionUpdateContract` transaction. The actuator's `execute()` unconditionally overwrites the account's owner/witness/active permissions with whatever is supplied in the contract, without verifying that the new permission set is consistent with, or authorized at a level equal to or higher than, the permission that signed the transaction: [3](#0-2) 

The underlying capsule method performs a full, unconditional replace of `OwnerPermission`, `WitnessPermission`, and all `ActivePermission` entries: [4](#0-3) 

`validate()` only checks the *shape* of the new permissions (key counts, thresholds, operations bitmask correctness) - never whether the caller's authorization level (`Owner` vs a scoped `Active` permission) is sufficient to replace the `Owner` permission itself: [5](#0-4) 

Because a single `Active`-permission signer with the `AccountPermissionUpdateContract` bit can rewrite `Owner` unilaterally, the exact front-running pattern from the report applies:
1. Alice (owner) grants Bob an `Active` permission that includes `AccountPermissionUpdateContract` in its operations bitmask (e.g., to let Bob rotate operational keys without going through Owner-level multisig).
2. Alice later wants to revoke Bob and submits an `AccountPermissionUpdateContract` transaction (signed with `Owner` permission) removing Bob's active permission.
3. Bob observes this pending transaction and front-runs it with his own `AccountPermissionUpdateContract` transaction (signed with his own `Active` key, which already satisfies the bitmask+weight check), overwriting the `Owner` permission to consist solely of Bob's key.
4. Once Bob's transaction lands first, he now holds full `Owner` authority over Alice's account, and Alice's own subsequent revocation transaction is executed by an account that Alice no longer controls (or is now invalid/ineffective since Bob has already replaced Owner).

This is worse than the original Drips finding: Drips-authorized users could only add other authorized addresses (the original owner retained ultimate authority), whereas here an `Active`-permission holder can outright replace `Owner`, permanently and irrevocably seizing full control of the account in a single transaction.

### Impact Explanation
An account owner who grants a scoped, low-trust `Active` permission that includes the `AccountPermissionUpdateContract` capability effectively grants that key holder unbounded, `Owner`-equivalent authority, contrary to the intended purpose of the tiered Owner/Active/Witness permission model. A compromised or malicious `Active` key can permanently lock out the true owner (unauthorized account takeover) and then use the seized `Owner` permission to authorize transfers, freeze/unfreeze balances, vote, or otherwise drain and control all assets held by the account, resulting in theft of funds and permanent loss of account control for the legitimate owner.

### Likelihood Explanation
Any account that uses java-tron's multi-signature/permission feature (`AccountPermissionUpdateContract`, requires `AllowMultiSign`) and grants an `Active` permission the `AccountPermissionUpdateContract` operation bit is affected. This is not a hypothetical corner case - the operation bit is available by default in the contract-type mask and there is no code path preventing an owner from enabling it for a scoped/operational key. Any holder of such a key (whether malicious from the outset or compromised later) can trigger the escalation with a single self-authored transaction requiring only their own low-threshold signature, and can time it to front-run any revocation attempt by the legitimate owner.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`/`execute()`, restrict the ability to modify `OwnerPermission` (and to add/modify `Active` permissions with equal or higher combined weight/scope) to signers whose transaction `permission_id == 0` (i.e., signed by the `Owner` permission), independent of whether an `Active` permission's operations bitmask happens to include `AccountPermissionUpdateContract`. If delegated permission rotation is a desired feature, it should be scoped so that an `Active` permission holder can only modify permissions of equal-or-lower privilege (e.g., its own `Active` entry), never the `Owner` permission, and the actuator should have access to the signing `permission_id`/`permission` type to enforce this hierarchy.

### Proof of Concept
1. Owner Alice enables `AccountPermissionUpdateContract` in the operations bitmask of an `Active` permission and adds Bob's key with weight ≥ threshold of that Active permission, via `AccountPermissionUpdateActuator`/`AccountCapsule.updatePermissions` (as exercised in `AccountPermissionUpdateActuatorTest.successUpdatePermissionKey`) [6](#0-5) .
2. Bob crafts a new `AccountPermissionUpdateContract` transaction for Alice's `owner_address`, setting `owner` permission to a threshold-1 permission containing only Bob's key, sets `permission_id = 2` (Bob's Active permission id), and signs it with only his Active key.
3. `TransactionCapsule.checkPermission` passes because `permission.getType() == Active` and the `AccountPermissionUpdateContract` bit is set in its operations [1](#0-0) .
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, unconditionally replacing `OwnerPermission` with Bob's supplied permission [7](#0-6) , [8](#0-7) .
5. Bob broadcasts this transaction ahead of (or in place of) Alice's own revocation transaction; once mined, Bob is the sole `Owner` of Alice's account and Alice's subsequent unauthorize/revoke transaction can no longer regain control.

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule result = (TransactionResultCapsule) object;
    if (Objects.isNull(result)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fee = calcFee();
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);

      byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
      AccountCapsule account = accountStore.get(ownerAddress);
      account.updatePermissions(accountPermissionUpdateContract.getOwner(),
          accountPermissionUpdateContract.getWitness(),
          accountPermissionUpdateContract.getActivesList());
      accountStore.put(ownerAddress, account);

      adjustBalance(accountStore, ownerAddress, -fee);
      if (chainBaseManager.getDynamicPropertiesStore().supportBlackHoleOptimization()) {
        chainBaseManager.getDynamicPropertiesStore().burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
