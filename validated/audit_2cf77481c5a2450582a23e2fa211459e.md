Audit Report

## Title
Unbounded, attacker-supplied `gas` value in `Command::CallContract` is trusted as the dispatch-gas estimate for Snowbridge outbound queue v2 fee/weight accounting - ([File: bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs])

## Summary
`Command::CallContract` carries a fully caller-controlled `gas: u64` field [1](#0-0) , and `ConstantGasMeter::maximum_dispatch_gas_used_at_most` — which every other command variant prices with a fixed, benchmarked constant — simply echoes this value back unmodified for `CallContract` [2](#0-1) . This uncapped value is written verbatim into the committed, merkle-rooted outbound message in `do_process_message` [3](#0-2) , while the `fee` stored in `PendingOrders` comes from an entirely independent XCM `PayFees`/`WithdrawAsset` amount that is never checked against the declared `gas` [4](#0-3) .

## Finding Description
The XCM converter for v2 outbound messages decodes an unprivileged, signer-supplied `Transact` payload containing `ContractCall::V1 { target, calldata, gas, value }` and pushes it directly into `Command::CallContract { target, calldata, gas, value }` with no bounds check on `gas` [5](#0-4) . The fee is extracted separately, from `WithdrawAsset`/`PayFees` instructions that precede the `Transact`, and is only checked for internal consistency (`reserved_fee_amount >= fee_amount`) and that the asset is Ether — never against the declared `gas` [6](#0-5) . `SendMessage::validate` for the v2 pallet only checks payload size, with no fee/gas relationship enforcement [7](#0-6) . By contrast, the v1 pipeline derives the fee charged to the sender directly from `GasMeter::maximum_gas_used_at_most`, making an inflated gas figure self-taxing [8](#0-7) ; no equivalent derivation/validation exists in v2. This confirms the claimed root cause and exploit path exist as described, with no additional cap or fee-gas consistency check found elsewhere in the outbound-queue-v2 pallet or primitives.

## Impact Explanation
Any unprivileged account able to construct an XCM `Transact` with `ContractCall::V1{ gas: u64::MAX, .. }` can commit a message into `Messages`/`MessageLeaves` whose ABI-encoded, merkle-rooted `gas` field is arbitrarily large while paying an unrelated, minimal `fee`. This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category: relayers either bear unbounded/uncompensated Ethereum-side gas risk or refuse delivery, causing messages to remain stuck in `PendingOrders`, degrading bridge throughput. The corrupted value is the on-chain committed `gas` field in `OutboundCommandWrapper`/`CommandWrapper`, which is never bound to or validated against the `fee` in `PendingOrder`.

## Likelihood Explanation
Constructing this XCM requires no special privilege — only a signed account routing a `Transact` through the standard v2 converter/exporter path, exactly as already exercised (with a benign `gas: 100_000`) in the existing emulated test `snowbridge_v2_outbound_edge_case.rs:457-462`. Substituting `gas: u64::MAX` requires no additional capability, making this readily and repeatably triggerable by any unprivileged actor.

## Recommendation
Cap `Command::CallContract`'s `gas` field in `ConstantGasMeter::maximum_dispatch_gas_used_at_most` (e.g., `min(gas_limit, MAX_CALL_CONTRACT_GAS)`), and/or enforce the cap during XCM conversion in `convert.rs`. Additionally, derive or validate the sender-supplied `fee` against the actual committed `gas` (mirroring v1's `calculate_fee`) in `SendMessage::validate`, rejecting messages whose `fee` is insufficient relative to the declared `gas` at submission time.

## Proof of Concept
1. As any signed account, submit `pallet-xcm::execute` with `WithdrawAsset`/`PayFees`/`InitiateTransfer` to Ethereum embedding `Transact { call: ContractCall::V1{ target, calldata, value: 0, gas: u64::MAX }.encode() }` (structurally identical to `snowbridge_v2_outbound_edge_case.rs:457-462` but with `gas: u64::MAX`), paired with a small `fee`.
2. `XcmConverter::convert` in `convert.rs` accepts this unchecked, producing `Command::CallContract { gas: u64::MAX, .. }` [9](#0-8) .
3. `do_process_message` calls `T::GasMeter::maximum_dispatch_gas_used_at_most(&command)`, which returns `u64::MAX` unmodified and commits it into `Messages`/`MessageLeaves`, while `PendingOrders[nonce].fee` stores only the attacker's small fee [10](#0-9) .
4. The mismatched gas/fee message is now permanently committed in the merkle root with no downstream re-validation, demonstrating the queue-stall/underpriced-work impact.
