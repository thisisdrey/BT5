### Title
`control_inherited_account` reentrancy filter can be bypassed via `pallet_multisig::as_multi_threshold_1`, letting a lower-priority inheritor slash/erase higher-priority recovery attempts - (File: `substrate/frame/recovery/src/lib.rs`)

### Summary
The external report's core broken invariant is: an "administrative" actor (MSQ's admin origin) can act on behalf of a user through privileged RPC methods, and the client had to add narrow, call-specific consent/filtering to stop the origin from silently reaching destructive operations it was not meant to reach. The same broken invariant reappears in `pallet-recovery`'s `control_inherited_account`, where an `inheritor` is granted a temporary, narrowly-filtered signed origin over the `recovered` (lost) account. The filter is designed to stop the inheritor from touching the Recovery pallet itself (to prevent tampering with other friend groups/attempts), but the filter is only effective against direct dispatch and simple re-dispatchers like `Utility::batch`; it is not effective against `pallet_multisig::as_multi_threshold_1`, which the codebase's own documentation states is specifically meant to escape account-based origin filters.

### Finding Description
`control_inherited_account` builds a fresh signed origin for the `recovered` account and attaches a reentrancy guard that blocks only calls that are direct `Recovery` pallet variants: [1](#0-0) 

This filter is intended to stop the `inheritor` from using its temporary control of the recovered account to interfere with the Recovery pallet's own state (e.g. slashing a higher-priority pending attempt, or wiping `FriendGroups`) — this is confirmed by the pallet's own regression test, which explicitly checks that wrapping a `slash_attempt`/`set_friend_groups` call inside `Utility::batch` does not bypass the filter: [2](#0-1) 

That test only exercises `Utility::batch`, whose inner calls are dispatched via `call.dispatch(origin.clone())` and therefore do inherit the filter attached to `origin`. However, `pallet_utility` itself documents that this filter propagation is *not* universal across all "pseudonym"/wrapper dispatchables — `as_derivative`'s doc comment explicitly says that if a caller wants to *escape* account-based filtering that was set up earlier in the call stack (exactly the `origin.add_filter` reentrancy guard used in `control_inherited_account`), they should use `pallet_multisig::as_multi_threshold_1`, which is documented as not honoring such filters: [3](#0-2) 

Because `control_inherited_account` never restricts *which pallets/wrappers* the inheritor's call may traverse — it only pattern-matches the outer `RuntimeCall` type against the Recovery pallet's own `Call` enum via `c.is_sub_type()` — an inheritor can wrap the disallowed `RecoveryCall::slash_attempt` or `RecoveryCall::set_friend_groups` inside `Multisig::as_multi_threshold_1`. Since that call re-derives an origin without carrying forward the `origin.add_filter` reentrancy guard that was attached in `control_inherited_account`, the nested Recovery call executes despite being explicitly disallowed by pallet design. This mirrors the MSQ finding precisely: a semi-trusted delegated origin (the inheritor / MSQ's admin dApp) was intended to be constrained to non-critical actions, but a routing path exists (multisig threshold-1 dispatch / different origin trust zone) that lets it reach and execute the critical/disallowed action without the intended consent gate.

### Impact Explanation
Exploiting this allows a lower-priority inheritor (someone who has already gained temporary control of a `recovered` account through a lower-priority, less-trusted friend group) to:
- Call `slash_attempt` on a higher-priority friend group's in-flight recovery attempt, causing unbacked loss of the honest initiator's/approver's security deposit (direct fund loss to a third party, `BOB` in the test scenario).
- Call `set_friend_groups` to wipe out all of the account owner's configured friend groups, permanently destroying the higher-priority recovery path and locking the legitimate owner/heirs out of ever reclaiming the account through their intended (higher-priority) friend group.

This satisfies the required impact classes: unauthorized execution/origin escalation (bypassing an explicit, pallet-enforced call filter) and theft/permanent loss or lock of user funds and account-recovery state, achievable purely by an unprivileged/semi-trusted account holder — no malicious validator, collator, relayer, or governance actor is required.

### Likelihood Explanation
The precondition (being a `recovered` account's `inheritor` from *any* friend group, including a low-priority/low-trust one) is attacker-attainable by anyone who can assemble the required threshold of "friends" for a low-priority group — which the pallet's own documentation treats as a normal, expected, lower-trust path (multiple friend groups with different priority/trust levels is a designed feature). The bypass mechanism (`Multisig::as_multi_threshold_1`) is a standard, publicly documented, permissionless extrinsic requiring no special privilege — combining the two requires no privileged access, exactly the kind of "public dispatch wrapper must not widen origin or bypass filters" scenario called out in the task's pivots.

### Recommendation
`control_inherited_account`'s reentrancy filter should not rely on matching only the top-level `RuntimeCall` sub-type. Either:
- Explicitly deny dispatch through any wrapper known to bypass account-based filters (`pallet_multisig::as_multi_threshold_1`, and any other dispatcher that reconstructs an origin from scratch instead of propagating the filter), or
- Enforce the filter at a lower level that all dispatch paths must pass through (e.g., via `BaseCallFilter`/`SignedFilter` composed at the runtime level for this specific derived origin, rather than an ad hoc `origin.add_filter` closure that only some pallets honor).

Add a regression test that wraps `slash_attempt`/`set_friend_groups` inside `Multisig::as_multi_threshold_1` (in addition to the existing `Utility::batch` test) to confirm the filter is actually enforced end-to-end.

### Proof of Concept
1. Alice configures two friend groups: `family` (priority 0, higher trust) and `friends` (priority 1, lower trust, inheritor = FERDIE), as in `inheritor_can_slash_higher_priority_attempts_and_remove_friend_groups` [4](#0-3) .
2. `friends` group recovers first (lower delay), making FERDIE the current `inheritor`.
3. `family` group (BOB) initiates a higher-priority attempt that would eventually override FERDIE.
4. FERDIE calls `control_inherited_account(ALICE, Multisig::as_multi_threshold_1([], RecoveryCall::slash_attempt { friend_group_index: 0 }))` instead of wrapping the call directly or in `Utility::batch`.
5. Because `as_multi_threshold_1` does not inherit the `origin.add_filter` reentrancy guard (per the documented design contrast with `as_derivative`), the inner `slash_attempt` executes, slashing BOB's deposit and removing the higher-priority `family` attempt — reproducing the exact "VULNERABILITY" condition the existing `Utility::batch` test guards against, but through an untested bypass route.

Note: I was not able to execute the test suite in this environment to empirically confirm `as_multi_threshold_1`'s exact runtime filter-propagation behavior; the conclusion rests on the codebase's own documentation contrast between `as_derivative` (explicitly filter-preserving) and `as_multi_threshold_1` (explicitly documented as the tool to use when filter restrictions should *not* apply). A Devin session with access to run `cargo test -p pallet-recovery` should add the multisig-wrapped regression test to confirm this empirically before treating it as fully verified.

	new_test_ext().execute_with(|| {
		// Alice configures two friend groups:
		//   Group 0 (priority 0, "Family"): BOB, CHARLIE — higher priority
		//   Group 1 (priority 1, "Friends"): DAVE, EVE — lower priority, inheritor = FERDIE
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE, // Family's chosen inheritor
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE, // Friends' chosen inheritor
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// --- Friends group (priority 1) recovers first due to shorter delay ---
		// friends_needed=1, so CHARLIE's auto-approval as initiator suffices.
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// --- Family group (priority 0) initiates a higher-priority attempt ---
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// Attack vector A: FERDIE tries to slash Family's attempt via the proxy.
		assert_ok!(Recovery::control_inherited_account(

/// Verify that wrapping a recovery call inside Utility::batch does not bypass the filter.
#[test]
fn inheritor_cannot_bypass_filter_via_utility_batch() {
	new_test_ext().execute_with(|| {
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE,
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE,
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// Friends group recovers first (CHARLIE's auto-approval reaches the threshold).
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// Family initiates higher-priority attempt
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// FERDIE wraps the slash inside a utility::batch call to try to bypass the filter
		let slash_call: RuntimeCall = RecoveryCall::slash_attempt { friend_group_index: 0 }.into();
		let batch_call: RuntimeCall =
			pallet_utility::Call::batch { calls: vec![slash_call] }.into();
		assert_ok!(Recovery::control_inherited_account(
			signed(FERDIE),
			ALICE,
			Box::new(batch_call),
		));

		// The batch dispatched as ALICE, but the inner slash should have still executed
		// since our filter only checks the outer call. Check if BOB was slashed:
		let bob_balance_after = <Test as Config>::Currency::total_balance(&BOB);
		let was_slashed = bob_balance_after < bob_balance_before;

		if was_slashed {
			panic!(
				"BYPASS: recovery call filter was circumvented via utility::batch! \
				 BOB lost {} from security deposit slash.",
				bob_balance_before - bob_balance_after
			);
		}
	});
}
