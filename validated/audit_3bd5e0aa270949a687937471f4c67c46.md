### Title
Unbounded VotesStore growth from unprivileged VoteWitnessContract transactions enables per-request full-store scan DoS via `getPaginatedNowWitnessList` - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`VoteWitnessActuator.countVoteAccount` persists one `VotesStore` entry per distinct voting account address on every successful `VoteWitnessContract` transaction. Any account with any TRX (tron power) can submit such a transaction, so an attacker can cheaply create an unbounded number of distinct `VotesStore` entries. This store is fully scanned on every unauthenticated call to the public API `getPaginatedNowWitnessList` (HTTP `/wallet/getpaginatednowwitnesslist`, gRPC, and Solidity-node equivalents), making each such request's cost proportional to the total number of distinct voter accounts an attacker has ever created — mirroring the reported MOOS-IvP bug class where unbounded distinct identities create ledger entries that are then processed in bulk on every subsequent operation.

### Finding Description
`VoteWitnessActuator.countVoteAccount` creates a new `VotesCapsule` keyed by the voter's own `ownerAddress` whenever the address doesn't already have a `VotesStore` entry: [1](#0-0) . Validation in `VoteWitnessActuator.validate()` only bounds the number of votes per single transaction (`MAX_VOTE_NUMBER`) and requires the voter to hold nonzero tron power / have voted for existing witnesses — it does not limit how many *distinct* accounts across the network can create such entries, and account creation itself is cheap (an unprivileged `AccountCreateContract`/transfer-triggered account creation, `CreateAccountActuator.execute`, plus any small amount of frozen balance for tron power) [2](#0-1) .

Each entry persists in `VotesStore` until the next DPoS maintenance cycle clears it via `MaintenanceManager.doMaintenance()` / `countVote()`, which iterates the entire store and deletes entries once per maintenance period [3](#0-2) . Critically, the public read API `Wallet.getPaginatedNowWitnessList` performs its own **full scan of the live `VotesStore`** on *every single call*, independent of the maintenance cycle, via an internal `countVote(votesStore)` helper that iterates all entries and all old/new votes within each entry to compute real-time vote deltas: [4](#0-3) [5](#0-4) .

This API is reachable anonymously via HTTP (`GetPaginatedNowWitnessListServlet`), gRPC (`RpcApiService`), and the Solidity-node HTTP/gRPC equivalents: [6](#0-5) . So the attack shape matches the report precisely: (1) an unprivileged actor creates an unbounded number of distinct "identities" (voter accounts), each producing a persistent ledger entry (`VotesStore` record) via a single signed transaction; (2) every subsequent legitimate/anonymous API request that needs to compute current results (`getPaginatedNowWitnessList`) must do "all-entries" processing work proportional to the number of entries created by the attacker, degrading the ability of the node to serve that API to all other clients — before the next maintenance cycle even runs.

### Impact Explanation
This is a resource/availability issue: it does not touch signature verification, balance, or consensus correctness. Any client repeatedly calling `getPaginatedNowWitnessList` while the attacker keeps the `VotesStore` inflated with many distinct voter entries incurs O(n) work per call where n = number of distinct voting accounts the attacker created since the last maintenance period; this can materially slow or exhaust node resources serving this specific query API, degrading availability of that API path for all callers. It does not directly cause fund loss, unauthorized account operations, or chain halt, so it should be scoped as a resource-exhaustion/availability degradation of a single wallet query endpoint rather than a full node crash or chain split.

### Likelihood Explanation
Likelihood is moderate: creating many distinct voter accounts requires paying the standard `AccountCreateContract`/transfer-triggered account-creation fee and bandwidth/energy per new account, plus a minimal frozen balance to obtain nonzero tron power for each vote transaction, so cost scales with the number of entries created — this is not free, but it is far cheaper than the value of the disruption, and any unprivileged, unpermissioned account can do it purely by broadcasting standard `VoteWitnessContract` transactions.

### Recommendation
Bound the per-call cost of `getPaginatedNowWitnessList`/`countVote` independent of unbounded `VotesStore` growth — e.g., incrementally maintain the real-time vote delta (updating a bounded structure on each vote transaction) rather than performing a full `VotesStore` scan on every API call, or throttle/cap the API's scan work and reject/paginate when store size exceeds a safe threshold. Additionally consider bounding the number of distinct pending (un-matured) `VotesStore` entries or shortening the exposure window between vote transactions and maintenance-period consolidation.

### Proof of Concept
1. Create N distinct funded accounts (each with minimal frozen balance for tron power) via standard `AccountCreateContract`/transfer flows.
2. From each account, broadcast a `VoteWitnessContract` transaction voting for any existing witness — each call persists a new entry in `VotesStore` via `VoteWitnessActuator.countVoteAccount` [1](#0-0) .
3. Before the next maintenance cycle runs, repeatedly call the public HTTP endpoint `/wallet/getpaginatednowwitnesslist` (or gRPC `GetPaginatedNowWitnessList`) [7](#0-6) .
4. Observe that each call's latency grows with N because `Wallet.getPaginatedNowWitnessList` -> `countVote(votesStore)` iterates the full, attacker-inflated `VotesStore` on every invocation [8](#0-7) .

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }
