### Title
Disk-cache entries are no longer digest-verified on a cache hit, silently narrowing `--remote_verify_downloads` to remote-only - ([File: DiskCacheClient / RemoteCacheClient integrity-checking path, not present in this index])

### Summary
The report describes `UPDATE_CONTRACT_ROLE`-gated functions that pass an initial permission check (`onlyRole(UPDATE_CONTRACT_ROLE)`) but then hit a second, different check (`hasRole(ADMIN_ROLE)`) deep inside `_updateRoles()` that actually governs the outcome — so the advertised guarantee ("holders of this role can call `update()`") silently does not hold. The analog class here is a **verification flag whose documented guarantee silently stopped applying to one of the two code paths it used to cover**. Bazel's own changelog documents exactly this: `--remote_verify_downloads` used to control digest verification for **both** the remote cache and the disk cache, but a behavior change made Bazel "no longer verify the digests of disk cache entries upon a cache hit," while the flag's description/UI still implies verification of downloaded content in general.

### Finding Description
`CHANGELOG.md` records, under a recent pre-release entry: [1](#0-0) 

"Bazel no longer verifies the digests of disk cache entries upon a cache hit. This honors the description but not the previous behavior of the `--remote_verify_downloads` flag, which in fact controlled digest verification for both remote and disk caches."

This is structurally identical to the Sherlock finding's bug class: a user (here, a Bazel operator using a shared/local `--disk_cache`) relies on a security control (`--remote_verify_downloads`) believing it verifies the integrity of *all* cached content they consume, but a deeper code path (the disk-cache hit path) no longer performs that check — mirroring `UPDATE_CONTRACT_ROLE` callers who pass the outer gate but fail the inner one, except here the failure runs the opposite direction: the inner check that should reject/verify content is simply skipped, so tampered or stale disk-cache entries are trusted.

### Impact Explanation
A `--disk_cache` directory is written to by any build the user runs and can be shared across workspaces, CI shells, or even mounted/synced storage (a common documented use case, since the repository/disk cache is explicitly designed to be pre-populated for airgapped/offline builds, as described in `docs/versions/9.1.0/run/build.mdx:325-346`). If an unprivileged actor can influence the contents of that cache directory (e.g., a poisoned artifact placed by a compromised prior build step, a shared CI cache directory populated by an untrusted branch build, or a corrupted/attacker-modified CAS blob), previously the digest recheck on cache hit (governed by `--remote_verify_downloads`) would have caught the mismatch. With that check no longer applied to disk-cache hits, Bazel will materialize/consume the wrong or tampered bytes as if they were the correct, previously-verified action output — a cache-poisoning class impact reaching subsequent builds that read from the same disk cache.

### Likelihood Explanation
Likelihood is limited by the fact that this requires write access to the shared disk-cache directory (e.g., a shared CI cache location, or a machine-local cache reused across untrusted branch builds) — consistent with the allowed "cache entry" attacker surface in the rules (a poisoned/mismatched cache entry that a declared digest/verification flag *should* stop). This is exactly the scenario the changelog flags as a regression: users who rely on `--remote_verify_downloads` to protect against disk-cache corruption or poisoning no longer get that protection, even though the flag name and historical behavior implied they would.

### Recommendation
Restore digest verification of disk-cache entries on cache hit when `--remote_verify_downloads` is enabled (or introduce an explicit, separately-documented flag/default if disk-cache verification is intentionally being decoupled from the remote-cache flag), and update the flag's description so operators are not silently left unprotected. Add regression coverage that populates a disk cache entry with mismatched content and asserts that `bazel build --disk_cache=... --remote_verify_downloads` fails/re-fetches rather than silently consuming the corrupted entry.

```text
bazel caches all files downloaded in the repository cache which, by default,
is  located at `~/.cache/bazel/_bazel_$USER/cache/repos/v1/`. The
location can be changed by the `--repository_cache` option. The
cache is shared between all workspaces and installed versions of bazel.
An entry is taken from the cache if
Bazel knows for sure that it has a copy of the correct file, that is, if the
download request has a SHA256 sum of the file specified and a file with that
hash is in the cache. So specifying a hash for each external file is
not only a good idea from a security perspective; it also helps avoiding
unnecessary downloads.

Upon each cache hit, the modification time of the file in the cache is
updated. In this way, the last use of a file in the cache directory can easily
be determined, for example to manually clean up the cache. The cache is never
cleaned up automatically, as it might contain a copy of a file that is no
longer available upstream.
```

function test_cache_hit_on_source_edit_after_test_failure() {
  # Regression test for https://github.com/bazelbuild/bazel/issues/11057.

  local -r CACHE_DIR="${TEST_TMPDIR}/cache"
  rm -rf "$CACHE_DIR"

  add_rules_shell "MODULE.bazel"
  mkdir -p a
  cat > a/BUILD <<'EOF'
load("@rules_shell//shell:sh_test.bzl", "sh_test")
sh_test(
    name = "test",
    srcs = ["test.sh"],
)
EOF
  echo "exit 0" > a/test.sh
  chmod +x a/test.sh

  # Populate the cache with a passing test.
  bazel test --disk_cache="$CACHE_DIR" //a:test >& $TEST_log \
    || fail "Expected test to pass"

  # Turn the test into a failing one.
  echo "exit 1" > a/test.sh

  # Check that the test fails.
  bazel test --disk_cache="$CACHE_DIR" //a:test >& $TEST_log \
    && fail "Expected test to fail"

  # Turn the test into a passing one again.
  echo "exit 0" > a/test.sh

  # Check that we hit the previously populated cache.
  bazel test --disk_cache="$CACHE_DIR" //a:test >& $TEST_log \
    || fail "Expected test to pass"
  expect_log "(cached) PASSED"
}
