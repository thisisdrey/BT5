### Title
`FetchIntoObjectPool` does not verify that `origin` is an authorized member of the target object pool - ([File: internal/gitaly/service/objectpool/fetch_into_object_pool.go])

### Summary
`FetchIntoObjectPoolRequest` accepts an arbitrary `origin` repository and a target `object_pool`, but the handler never verifies that `origin` is actually a linked member of that pool before fetching all of its refs/objects into it. This mirrors the reported bug class: a destination-side operation trusts a caller-supplied "source" without checking a supposed-to-exist authorization/membership relationship (`allowMessagesFrom` in the report, pool-membership here).

### Finding Description
`validateFetchIntoObjectPoolRequest` only checks that `origin` and `object_pool` are non-nil and that they share the same storage name — it performs no check that `origin` is a repository which has actually been linked to that object pool via `LinkRepositoryToObjectPool`: [1](#0-0) 

The handler then builds a `localrepo.Repo` directly from the attacker/caller-supplied `origin` and unconditionally fetches `+refs/*` from it into the pool: [2](#0-1) 

The actual git-level fetch performed by `FetchFromOrigin` only checks that the pool repository exists — it has no notion of "is this origin allowed to feed this pool": [3](#0-2) 

By contrast, membership is supposed to be an explicit, deliberate relationship established only through `LinkRepositoryToObjectPool`, which writes the pool's `objects/info/alternates` pointer into the *member* repository: [4](#0-3) 

Nothing in `FetchIntoObjectPool` consults that link/membership state (there is no membership store lookup, unlike e.g. the `PoolMetadataStore` used purely for informational scanning in `subcmd_pool_test.go`). This means any repository on the same storage can be supplied as `origin`, regardless of whether it was ever linked to the destination pool — directly analogous to the reported issue where the destination chain accepted messages without checking whether the source chain was actually configured (`allowMessagesFrom`) to send them.

### Impact Explanation
An actor who is authorized to call `FetchIntoObjectPool` with `target_repository` write access to some object pool `P`, but who does not own/administer the `origin` repository `R` (e.g. a private repository they merely have `additional_repository`-level read access to, per the gRPC field annotations), can force Gitaly to fetch all of `R`'s refs and objects into `P`. If the caller also controls a member of `P` (or later links their own repository to `P`), the objects that were fetched — including from a private repository they were never fully authorized to fully replicate — become reachable via `refs/remotes/origin/*` and via alternates from that other repository, resulting in **cross-repository object disclosure**. It also allows corrupting an object pool's ref namespace/state (dangling refs, D/F conflicts, disk bloat) by repeatedly pulling from unrelated origins, a resource-abuse/DoS vector against the pool's housekeeping.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the caller to have RPC-level authorization to invoke `FetchIntoObjectPool` for a target pool while supplying an `origin` repository outside that pool's legitimate membership set — a scenario plausible in multi-tenant GitLab-Gitaly deployments where access checks are storage/repository-scoped rather than pool-membership-scoped, since nothing in the RPC path enforces the membership invariant.

### Recommendation
Before performing the fetch, `FetchIntoObjectPool` (or `validateFetchIntoObjectPoolRequest`) should verify that `origin`'s object directory is actually configured as an alternate of, or otherwise registered as a member of, the target `object_pool` (e.g. by checking the origin's `objects/info/alternates` resolves to the pool's path, or by consulting a durable pool-membership store) before allowing the fetch to proceed, analogous to checking `allowMessagesFrom` before accepting a cross-chain message.

### Proof of Concept
1. Caller has access to invoke `FetchIntoObjectPool` for object pool `P` (e.g., they administer a project whose pool is `P`) but does not own private repository `R`, which they can merely reference by relative path.
2. Caller issues `FetchIntoObjectPool(origin=R, object_pool=P)`.
3. `validateFetchIntoObjectPoolRequest` passes because only storage names are compared: [5](#0-4) 
4. `objectPool.FetchFromOrigin` runs `git fetch <R path> +refs/*:refs/remotes/origin/*` unconditionally, pulling `R`'s objects and refs into `P`: [6](#0-5) 
5. Caller links their own repository to `P` via `LinkRepositoryToObjectPool`, or already has a repository sharing `P`'s alternates, and can now resolve/read `R`'s objects that were fetched into `P`, disclosing private repository content they were never authorized to fully access.

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}
