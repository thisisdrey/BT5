Audit Report

## Title
Unauthenticated deposits to the DAP staging account are trusted as legitimate burns, letting anyone deflate `InactiveIssuance`/active issuance at will - (File: `substrate/frame/dap/src/lib.rs`)

## Summary
`pallet-dap`'s `on_idle` hook (`substrate/frame/dap/src/lib.rs` lines 214-256) drains whatever `reducible_balance` is present in the deterministic `staging_account()` (lines 351-357) and calls `Unbalanced::deactivate()` on the entire amount (line 361) without verifying that the balance actually originated from a legitimate `OnUnbalanced::on_nonzero_unbalanced` credit (lines 512-529). Because `staging_account()` is a plain, publicly-derivable `AccountId` (also exposed via the `staging()` view function at line 337), any unprivileged account can send an ordinary `balances::transfer_keep_alive` to it and have the funds counted as "deactivated" issuance.

## Finding Description
The legitimate flow deposits slash/burn credits into `staging_account()` via `OnUnbalanced::on_nonzero_unbalanced` (`substrate/frame/dap/src/lib.rs` lines 512-529), which simply resolves the `Credit` into that account with `T::Currency::resolve`. Separately, `on_idle` reads `reducible_balance(&staging_account, Preservation::Preserve, Fortitude::Polite)` (lines 222-227) and, if non-zero, transfers the *entire* amount to the buffer account and calls `Self::deactivate_buffer_funds(available)` (line 247), which invokes `Unbalanced::deactivate` (line 361), lowering `active_issuance` while `total_issuance` stays fixed — confirmed by the conformance test in `substrate/frame/support/src/traits/tokens/fungible/conformance_tests/regular/unbalanced.rs` lines 247-260, and the pallet's own integration test in `substrate/frame/dap/src/tests/on_unbalanced.rs` lines 85-144 showing the exact `active_issuance` decrease.

Nothing in `on_idle` distinguishes funds credited via the trusted `OnUnbalanced` path from funds sent via an ordinary transfer by any signed account, since `staging_account()` is derived deterministically with `into_sub_account_truncating` (line 356) and is a normal `AccountId` capable of receiving standard transfers. This mirrors a balance-presence-as-proof-of-event flaw: the pallet treats "balance present in staging account" as equivalent to "a real slash/burn occurred," with no provenance check on the deposit.

`active_issuance` (`total_issuance - InactiveIssuance`) is read by `pallet-referenda`'s servicing logic per the storage-access annotations on `nudge_referendum_continue_not_confirming`/`_continue_confirming` weight files (e.g. `substrate/frame/staking-async/runtimes/parachain/src/weights/pallet_referenda.rs` lines 427-442, confirmed present in this repo along with numerous other runtime weight files referencing the same call), making active issuance a governance-critical figure used in referenda tally computations, consistent with the pallet's own doc comment at lines 29-32 ("Incoming funds are deactivated to exclude them from governance voting").

## Impact Explanation
Any unprivileged account holding a small balance can transfer an arbitrary self-chosen amount to the publicly-known `staging_account()` address and have the runtime record it as "deactivated" issuance on the next `on_idle`, without any real slash, burn, or wired `OnUnbalanced` event occurring. This lets an attacker artificially and repeatedly deflate active issuance — the value used as input to OpenGov referenda support/approval threshold calculations — degrading the correctness of governance-threshold accounting. This is a runtime bug compromising intended accounting/governance behavior, reachable by any unprivileged actor, matching the "runtime bugs that compromise intended behavior" impact criteria.

## Likelihood Explanation
Feasibility is high and the barrier to entry is low: `staging_account()` is deterministic and also directly exposed via the `staging()` view function (line 337), so no address-guessing is required. The only prerequisites are an ordinary signed account and a standard `balances::transfer`/`transfer_keep_alive` call — no governance, validator, collator, or relayer privilege is needed. The attack is mechanical, repeatable at will, and processed automatically by `on_idle` on the next idle block; the primary cost to the attacker is the transferred funds themselves, which move irrecoverably into the buffer account.

## Recommendation
Do not treat the raw balance sitting in `staging_account()` as ground truth for the deactivation amount. Track the amount to deactivate explicitly at the point of `OnUnbalanced::on_nonzero_unbalanced` (e.g., an internal `PendingDeactivation` counter incremented only by the trusted burn/slash callback), and have `on_idle` drain/deactivate exactly that tracked amount rather than whatever `reducible_balance` happens to be present. Alternatively, prevent ordinary transfers from landing in the staging account (e.g., use an account type/filter that rejects normal `transfer` extrinsics targeting it), so only the pallet's own `OnUnbalanced` credit path can fund it.

## Proof of Concept
1. Query `pallet_dap::Pallet::<Runtime>::staging()` (or independently derive `sp_dap::DAP_PALLET_ID.into_sub_account_truncating(sp_dap::DAP_STAGING_ACCOUNT_ID)`).
2. From any funded, unprivileged account, submit `Balances::transfer_keep_alive(staging_account, X)` for an arbitrary `X`.
3. Allow the chain to reach an idle block (triggers `pallet_dap::on_idle` in `substrate/frame/dap/src/lib.rs` lines 214-256).
4. Observe: `buffer_account` balance increases by `X`, and `Balances::InactiveIssuance` increases by `X` (per `deactivate_buffer_funds` at line 361 and the semantics validated in `substrate/frame/support/src/traits/tokens/fungible/conformance_tests/regular/unbalanced.rs` lines 247-260) — even though no slash, burn, or wired `OnUnbalanced` event occurred; the deposit was an ordinary user-initiated transfer indistinguishable in `on_idle` from a legitimate credit. 		fn on_idle(_block: BlockNumberFor<T>, remaining_weight: Weight) -> Weight {
			let mut meter = WeightMeter::with_limit(remaining_weight);

			// Need at least one read (staging account balance).
			if meter.try_consume(T::DbWeight::get().reads(1)).is_err() {
				return meter.consumed();
			}

			let staging_account = Self::staging_account();
			let available = T::Currency::reducible_balance(
				&staging_account,
				Preservation::Preserve,
				Fortitude::Polite,
			);

			if available.is_zero() {
				return meter.consumed();
			}

			// Need 1 read and 2 writes for the transfer, plus 1 read and 1 write for
			// deactivate (InactiveIssuance) and 1 read for TotalIssuance.
			if meter.try_consume(T::DbWeight::get().reads_writes(3, 3)).is_err() {
				return meter.consumed();
			}

			let buffer = Self::buffer_account();
			if T::Currency::transfer(&staging_account, &buffer, available, Preservation::Preserve)
				.is_err()
			{
				defensive!("DAP: staging account transfer to buffer failed");
				return meter.consumed();
			}

			Self::deactivate_buffer_funds(available);
			Self::deposit_event(Event::StagingDrained { amount: available });

			log::debug!(
				target: LOG_TARGET,
				"DAP: drained {available:?} from staging account to DAP buffer"
			);

			meter.consumed()
		}

impl<T: Config> OnUnbalanced<CreditOf<T>> for Pallet<T> {
	fn on_nonzero_unbalanced(amount: CreditOf<T>) {
		let staging = Self::staging_account();
		let numeric_amount = amount.peek();

		// Funds land in the staging account; `on_idle` will drain them into the buffer and
		// deactivate them there.  Deactivation is intentionally deferred so that active issuance
		// does not flicker down-then-up within the same block.
		let _ = T::Currency::resolve(&staging, amount).inspect_err(|_| {
			defensive!(
				"🚨 Failed to deposit slash to DAP staging account - funds burned, it should never happen!"
			);
		});
		log::debug!(
			target: LOG_TARGET,
			"💸 Deposited {numeric_amount:?} to DAP staging account"
		);
	}

#[test]
fn slash_to_dap_accumulates_to_staging_then_deactivates_on_idle() {
	build_and_execute(true, || {
		set_default_budget_allocation();

		let buffer = DapPallet::buffer_account();
		let staging = DapPallet::staging_account();
		let ed = <Balances as Inspect<_>>::minimum_balance();

		let alice = account_id(1);
		let bob = account_id(2);
		let charlie = account_id(3);

		// Given: buffer and staging each have ED; users have balances.
		assert_eq!(Balances::free_balance(&buffer), ed);
		assert_eq!(Balances::free_balance(&staging), ed);
		let initial_active = <Balances as Inspect<_>>::active_issuance();
		let initial_total = <Balances as Inspect<_>>::total_issuance();

		// When: multiple slashes occur via OnUnbalanced (simulating staking slashes).
		for (who, amount) in [(&alice, 30u64), (&bob, 20), (&charlie, 50)] {
			let credit = <Balances as Balanced<_>>::withdraw(
				who,
				amount,
				Precision::Exact,
				Preservation::Preserve,
				Fortitude::Force,
			)
			.unwrap();
			DapPallet::on_unbalanced(credit);
		}

		// Then: funds land in staging, not buffer.
		assert_eq!(Balances::free_balance(&staging), ed + 100);
		assert_eq!(Balances::free_balance(&buffer), ed);

		// And: users lost their slashed amounts.
		assert_eq!(Balances::free_balance(&alice), 100 - 30);
		assert_eq!(Balances::free_balance(&bob), 200 - 20);
		assert_eq!(Balances::free_balance(&charlie), 300 - 50);

		// And: active issuance is NOT yet decreased (deactivation is deferred to on_idle).
		assert_eq!(<Balances as Inspect<_>>::active_issuance(), initial_active);

		// And: total issuance unchanged (funds moved, not destroyed).
		assert_eq!(<Balances as Inspect<_>>::total_issuance(), initial_total);

		// When: on_idle drains staging into buffer and deactivates.
		DapPallet::on_idle(1, Weight::MAX);

		// Then: staging retains only ED; buffer gained all slashed funds.
		assert_eq!(Balances::free_balance(&staging), ed);
		assert_eq!(Balances::free_balance(&buffer), ed + 100);

		// And: active issuance decreased by 100 (funds deactivated in DAP buffer).
		assert_eq!(<Balances as Inspect<_>>::active_issuance(), initial_active - 100);

		// And: total issuance still unchanged.
		assert_eq!(<Balances as Inspect<_>>::total_issuance(), initial_total);
	});
