Audit Report

## Title
Delivery receipt `success` flag is ignored, allowing reward payout and order settlement on failed Ethereum execution - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` — which carries a `success: bool` field decoded directly from the Ethereum `InboundMessageDispatched` event — but never inspects that field before paying the relayer reward and removing the `PendingOrder`. As a result, a message whose execution reverted on Ethereum (`success = false`) is settled and rewarded identically to a genuinely successful delivery.

## Finding Description
The public extrinsic `submit_delivery_receipt` verifies the event proof via `T::Verifier::verify`, decodes the log into a `DeliveryReceipt` via `DeliveryReceipt::try_from`, and immediately forwards it to `process_delivery_receipt` without any success check: [1](#0-0) 

`DeliveryReceipt` is decoded from the Solidity `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` event and explicitly carries the `success` field from the raw log: [2](#0-1) 

`process_delivery_receipt` only validates the gateway address and the existence of a `PendingOrder` for the nonce — `receipt.success` is never read anywhere in the function body: [3](#0-2) 

The existing guards — `T::Verifier::verify` (proves the log genuinely originated from the configured Ethereum chain/gateway), the gateway-address equality check, and the `PendingOrders::get(nonce)` existence check — only establish that a real event occurred for a known nonce. None of them substitute for checking whether the command execution the event describes actually succeeded. Integration test fixtures confirm `success` is meant to reflect the real outcome, always setting it explicitly (`success: true`) when constructing valid receipts, reinforcing that the field is a meaningful signal that is simply discarded in production logic: [4](#0-3) 

## Impact Explanation
This breaks the settlement invariant that bridge receipts and payout state must only advance after execution actually succeeds. A relayer can be paid the full `order.fee` reward and have the `PendingOrder` removed for a message whose Ethereum-side command reverted, provided the Gateway contract emits a valid `InboundMessageDispatched` log with `success = false`. This is an unbacked payout: reward accounting is settled disconnected from genuine successful delivery, matching the "duplicate settlement or payout" / "theft or unbacked mint" class in the impact gate.

## Likelihood Explanation
The path is reachable by any signed account via the public `submit_delivery_receipt` extrinsic, requiring only a legitimate proof for a real Gateway event flagged `success = false` — no privileged origin, malicious validator, or leaked key is required. Any command execution that legitimately reverts on Ethereum (e.g., insufficient gas at execution time on a sub-command, a reentrancy guard, an asset transfer failure) would organically produce such an event, making exploitation both feasible and repeatable.

## Recommendation
Check `receipt.success` in `process_delivery_receipt` before crediting `T::RewardPayment::register_reward` and before removing the `PendingOrder`. On `success == false`, take an alternate path (e.g., a distinct `MessageDeliveryFailed` event) that still settles/clears the pending order bookkeeping but withholds or reduces the reward, rather than unconditionally paying full `order.fee`.

## Proof of Concept
1. `do_process_message` queues a message, creating `PendingOrder { nonce, fee, .. }` in storage.
2. The corresponding command is delivered to Ethereum but reverts; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains the proof for this real log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false` along with valid `nonce`/`gateway`/`reward_address`.
5. `process_delivery_receipt` checks only `gateway` and `PendingOrders::get(nonce)`, then unconditionally calls `T::RewardPayment::register_reward(&reward_account, .., order.fee)` and removes the order — confirmed by reading [5](#0-4)  where no branch on `receipt.success` exists between fetching `order` and paying/removing it.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
