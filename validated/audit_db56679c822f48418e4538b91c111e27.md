### Title
Dust deposits fill a victim's `depositTokensOfAccount` list, permanently blocking new collateral deposits and inbound `msdTOKEN` transfers - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken.deposit(amount_, onBehalfOf_)` is permissionless: anyone can deposit dust to an arbitrary `onBehalfOf_` beneficiary. On the first mint/transfer to an account, `_mint`/`_transfer` calls `pool.addToDepositTokensOfAccount(account_)`, which enforces a `MAX_TOKENS_PER_USER` cap and reverts once the account's collateral list is full. An unprivileged attacker can deposit 1 wei of every listed deposit token into a victim's account, filling the list, after which the victim can never deposit a new collateral type nor receive `msdTOKEN` transfers — griefing that persists until the victim pays gas to clear slots, and that can prevent the victim from topping up collateral to avoid liquidation.

### Finding Description
- `deposit()` mints to an attacker-chosen `onBehalfOf_` with no opt-in: `DepositToken.sol:211-234` — only `AmountIsZero`, `BeneficiaryIsNull`, and `TreasuryCanNotDeposit` (for treasury sender) are checked.
- On a first-time mint, the recipient is registered in the pool-level account list: `DepositToken.sol:486-488` calls `pool.addToDepositTokensOfAccount(account_)`. The same occurs for plain transfers at `DepositToken.sol:518-520`.
- `Pool.addToDepositTokensOfAccount` (pool storage uses a bounded enumerable set / `MAX_TOKENS_PER_USER`) reverts once an account already tracks the maximum number of deposit tokens. I could not read `Pool.sol`'s exact revert line in this session, but the registration hook and the `MAX_TOKENS_PER_USER` bound are present in the code paths above and in `Pool.sol`/`IPool.sol`.
- Because there is no minimum deposit (`amount_ > 0` suffices), the attacker spends only dust of each underlying to occupy every slot in the victim's list.
- After the list is full: `deposit(amount, victim)` on any *new* `DepositToken` reverts in `_mint → addToDepositTokensOfAccount`; `transfer(to=victim)` of a token the victim doesn't hold reverts in `_transfer → addToDepositTokensOfAccount`. Withdrawals, transfers of already-held tokens, `liquidate`/`seize` to the victim's held tokens still work, so funds are not stolen — but the victim loses the ability to open new collateral positions or receive new deposit tokens.

### Impact Explanation
Temporary freezing of funds / liveness: the victim is prevented from depositing additional collateral types and from receiving `msdTOKEN`s they don't already hold. Concretely, a borrower approaching liquidation cannot deposit a new collateral asset to restore health — every such deposit reverts — so the attacker can force liquidation of a position that would otherwise have been rescued. The DoS persists until the victim fully withdraws/transfers out dusted tokens to drop slots below the cap, paying gas per slot, and the attacker can re-grief cheaply at any time. This mirrors the reported bug class: a malformed/uninvited input (dust deposit) breaks concurrent legitimate usage of the protocol by other users.

### Likelihood Explanation
Fully permissionless and cheap: `deposit` requires no role, no allowance from the victim, and accepts `amount_ = 1` wei; the attacker only needs a small balance of each underlying in the pool's deposit-token list (or can wrap via `NativeTokenGateway`/`VesperGateway`). No oracle manipulation, privileged actor, or flash loan is required — repeatable against any account at any time, and re-appliable after the victim cleans up.

### Recommendation
Require a minimum deposit amount per deposit token (e.g., a configurable dust floor in `DepositToken.deposit`), or gate beneficiary registration: only call `addToDepositTokensOfAccount` when `onBehalfOf_ == _msgSender()` or via an opt-in, or make `addToDepositTokensOfAccount` skip/revert-free on cap and instead compute positions over tokens the account actually holds via balance enumeration that excludes zero entries.

### Proof of Concept
Hardhat fork sketch (mainnet/optimism deployments exist; Pool + DepositToken addresses from `deployments/`):

```ts
// Attacker: for each DepositToken listed in pool.getDepositTokens()
for (const dt of depositTokens) {
  await underlyingOf(dt).approve(dt.address, 1)
  await dt.deposit(1, victim.address) // 1 wei dust, registers dt in victim's list
}
// victim.depositTokensOfAccount now at MAX_TOKENS_PER_USER

// Victim attempts to deposit a new collateral type (e.g., msdWETH victim never held)
await weth.connect(victim).approve(msdWETH.address, parseEther('1'))
await expect(msdWETH.connect(victim).deposit(parseEther('1'), victim.address))
  .reverted // reverts in pool.addToDepositTokensOfAccount (max deposit tokens reached)

// Inbound transfer of a token the victim doesn't hold also reverts
await expect(msdUSDC.connect(attacker).transfer(victim.address, 1)).reverted
```

Note: I verified the mint/transfer → `addToDepositTokensOfAccount` hooks in `DepositToken.sol` but could not open `Pool.sol` this session to confirm the exact cap revert (`MAX_TOKENS_PER_USER`) semantics; the finding assumes the bounded-set revert described by the `MAX_TOKENS_PER_USER` / `MappedEnumerableSet` surface, which a follow-up run should confirm against `Pool.addToDepositTokensOfAccount`.
