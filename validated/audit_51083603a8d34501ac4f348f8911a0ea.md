### Title
Reward-cycle desync between `GetNakamotoInv` request and reply causes `NakamotoInv` bits to be merged into the wrong `tenures_inv` slot - ([File: stackslib/src/net/inv/nakamoto.rs])

### Summary
`NakamotoTenureInv::getnakamotoinv_try_finish` merges an inbound `NakamotoInv` reply using `self.reward_cycle()` (i.e. `self.cur_reward_cycle`) read *at reply-processing time*, not the reward cycle that was actually embedded in the `GetNakamotoInv` request that produced this reply. Because `process_getnakamotoinv_begins` can mutate `cur_reward_cycle` via `try_reset_comms`/`reset_comms` *before* checking whether a request is already in flight for that peer, a slow-to-reply peer's outstanding response can be merged into a different (already-reset) reward-cycle bucket than the one it was actually answering.

### Finding Description
The equality the code is supposed to preserve is: *the reward cycle recorded when `GetNakamotoInv` was sent to a peer == the reward cycle used to store that peer's `NakamotoInv` reply in `tenures_inv`.*

- When a request is sent, `process_getnakamotoinv_begins` computes `inv_rc = inv.reward_cycle()` and issues `GetNakamotoInv` for the consensus hash of that cycle: [1](#0-0) 
- No reward-cycle identifier travels back in the `NakamotoInv` payload; when the reply arrives, `getnakamotoinv_try_finish` blindly re-reads `self.reward_cycle()` at the time of processing and merges into that bucket: [2](#0-1) 
- Crucially, on every call to `process_getnakamotoinv_begins`, `getnakamotoinv_begin` is invoked (which can call `try_reset_comms` → `reset_comms`, mutating `self.cur_reward_cycle` back to an earlier `start_rc`) **before** the code checks `self.comms.has_inflight(&naddr)`: [3](#0-2) [4](#0-3) 
- `try_reset_comms` fires whenever `self.cur_reward_cycle >= max_rc || !self.online` and enough time (`inv_sync_interval`) has passed, resetting `cur_reward_cycle` to `start_rc = max_rc.saturating_sub(inv_reward_cycles)`: [5](#0-4) 
- `merge_tenure_inv` unconditionally overwrites whatever bit vector currently occupies the given reward-cycle key with the attacker-controlled tenure bitmap: [6](#0-5) 

Exploit flow: a malicious peer is asked for the last cycle it needs to sync (`cur_reward_cycle == max_rc` at request time). The peer withholds its `NakamotoInv` reply past one `inv_sync_interval`. On the node's next periodic `process_getnakamotoinv_begins` pass, `getnakamotoinv_begin` observes `cur_reward_cycle >= max_rc` and resets `cur_reward_cycle` to an earlier `start_rc`, even though the original request for `max_rc` is still outstanding (the `has_inflight` check only prevents sending a *new* request — it doesn't stop the reward-cycle counter from being rewound). The peer then finally sends its (adversary-chosen) `NakamotoInv` reply. `getnakamotoinv_try_finish` merges this bitmap using the *new*, stale `self.reward_cycle()` (`start_rc`), overwriting the bit vector for a cycle the peer never actually answered for, breaking the sortition-height ↔ bit ↔ reward-cycle correspondence relied on by `has_ith_tenure`/`find_available_tenures`.

Existing guards do not prevent this: `has_inflight` only gates whether a *new outbound* GetNakamotoInv is sent, not whether the in-flight reply's target reward cycle is still valid; there is no per-request reward-cycle/nonce echoed back and checked against `self.cur_reward_cycle` at send time.

### Impact Explanation
A malicious peer can cause the local node to attribute an attacker-chosen tenure-presence bitmap to a reward cycle it did not actually describe, corrupting `NakamotoTenureInv::tenures_inv` for that peer. Downstream consumers (`has_ith_tenure`, tenure-download scheduling / `find_available_tenures`) will then believe the peer has (or lacks) tenures at sortitions in that cycle that don't match reality, which can steer the download-inventory logic away from fetching real tenures or waste attempts fetching nonexistent ones from that peer — matching the "High: steering a node off the tip via false inventory" category. It is per-peer state only (does not corrupt other peers' inventories or the node's own chainstate), and is repeatable each time the timing window recurs for that connection.

### Likelihood Explanation
This requires a fairly narrow timing precondition: the attacker's peer must be the one currently being asked for exactly its last pending reward cycle (`cur_reward_cycle == max_rc`), and must delay its reply across at least one `inv_sync_interval` tick without the connection/request being timed out or dropped first. I was not able to fully verify, within the available iterations, whether `NeighborComms`/RPC-layer request timeouts (in `stackslib/src/net/neighbors/comms.rs` / `rpc.rs`) would sever the connection or drop the in-flight request before this window elapses — if such a timeout is shorter than `inv_sync_interval`, the race would not be reachable. This is an open uncertainty in this analysis. The attacker needs no privileged role, secret, or crypto break — only control over their own reply timing, which is achievable by any peer that can complete a normal P2P handshake and receive a `GetNakamotoInv` request.

### Recommendation
Have `getnakamotoinv_try_finish` validate the reply against the reward cycle that was actually requested (e.g., record the requested reward cycle/consensus-hash alongside the in-flight request and pass it explicitly into `getnakamotoinv_try_finish`/`merge_tenure_inv`, instead of re-reading the possibly-mutated `self.cur_reward_cycle`), and/or prevent `try_reset_comms`/`reset_comms` from mutating `cur_reward_cycle` while `self.comms.has_inflight(&naddr)` is true for that peer.

### Proof of Concept
1. Construct a `NakamotoInvStateMachine` with a mock `NeighborComms` allowing manual control of `has_inflight` and reply delivery timing.
2. Register one peer's `NakamotoTenureInv` with `cur_reward_cycle == max_rc` (simulating that its last-needed cycle was just requested), and hold the corresponding request as "in flight."
3. Call `process_getnakamotoinv_begins` again after advancing the clock past `inv_sync_interval` (or directly call `inv.getnakamotoinv_begin(network, max_rc)`), and observe `cur_reward_cycle` reset to `start_rc = max_rc - inv_reward_cycles` via `try_reset_comms`/`reset_comms`, while the original request is still marked in-flight.
4. Deliver the delayed `StacksMessageType::NakamotoInv` reply (crafted with an attacker-chosen `BitVec<2100>`) via `getnakamotoinv_try_finish`.
5. Assert `inv.tenures_inv.get(&start_rc)` now equals the attacker-supplied bitmap (i.e., the reply meant for `max_rc` was stored under `start_rc`), demonstrating the reward-cycle/bit misattribution described above.

    /// Returns false if not.
    pub fn merge_tenure_inv(&mut self, tenure_inv: BitVec<2100>, reward_cycle: u64) -> bool {
        // populate the tenures bitmap to we can fit this tenures inv
        let learned = self
            .tenures_inv
            .get(&reward_cycle)
            .map(|cur_inv| cur_inv != &tenure_inv)
