### Title
Non-hardened exchange calculation path skips negative/overflow balance validation, allowing incorrect exchange balances and reserve accounting - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
This is the java-tron analog of the Code4rena finding where an asset's `price()` function can return sentinel/degenerate values `(0, FIX_MAX)` that a downstream consumer (`collateralShortfall()`) fails to validate before using in further arithmetic, producing an incorrect shortfall. In java-tron, the analogous pattern occurs in the TRC10 Bancor-style exchange system: `ExchangeCapsule.transaction()` computes a new pair of token balances using a `Processor` (either the legacy floating-point `ExchangeProcessor` or the newer `SafeExchangeProcessor`), but the sanity check that rejects negative resulting balances is applied **only** when `hardenedCalc` is `true`.

### Finding Description
`ExchangeCapsule.transaction()` computes `buyTokenQuant` via `processor.exchange(...)` and then computes `newFirstTokenBalance`/`newSecondTokenBalance`. The correctness check:
```java
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [1](#0-0) 
is gated by `hardenedCalc`, which is only `true` when the chain parameter `allowHardenExchangeCalculation()` has been activated via SR proposal. Whether this is enabled is decided by `AbstractExchangeActuator.allowHarden()`, which simply proxies `DynamicPropertiesStore.allowHardenExchangeCalculation()`: [2](#0-1) 

When `hardenedCalc` is `false` (i.e., on any network/period where the hardening proposal has not been enabled — the default/legacy state), `transaction()` uses the legacy `ExchangeProcessor`, which performs the Bancor-formula math in `double` floating point: [3](#0-2) 
This floating-point computation, combined with the unchecked balance update path (`firstTokenBalance + sellTokenQuant`, `secondTokenBalance - buyTokenQuant` using plain `+`/`-` instead of `StrictMathWrapper`), means:
1. `buyTokenQuant` returned by the legacy processor can, due to floating-point precision loss/edge cases (e.g., extremely small `newBalance` supply relative to `quant`, or repeated near-zero-balance trades), diverge from the true integer Bancor result — analogous to `price()` returning a degenerate `(0, FIX_MAX)` sentinel that the caller trusts blindly.
2. Because the `< 0` guard is skipped when `hardenedCalc == false`, a resulting negative balance for either token side of the exchange pool is **not rejected** — the malformed capsule is persisted directly:
```java
this.exchange = this.exchange.toBuilder()
    .setFirstTokenBalance(newFirstTokenBalance)
    .setSecondTokenBalance(newSecondTokenBalance)
    .build();
``` [4](#0-3) 

This is invoked directly from `ExchangeTransactionActuator.execute()`, which is reachable by any account submitting a signed `ExchangeTransactionContract` (an ordinary, unprivileged transaction type): [5](#0-4) 
`validate()` re-derives `anotherTokenQuant` via the same unchecked `transaction()` call only to compare against `tokenExpected`, but this is the same double-precision, unchecked computation reused in `execute()`: [6](#0-5) 

### Impact Explanation
If the legacy (non-hardened) path produces a negative pool balance for one side of the pair, the exchange's internal token-balance capsule (persisted via `Commons.putExchangeCapsule`) becomes inconsistent with actual backing assets held by the exchange creator's account. Because subsequent trades against this exchange (`ExchangeInjectActuator`, `ExchangeTransactionActuator`, `ExchangeWithdrawActuator`) all trust `getFirstTokenBalance()`/`getSecondTokenBalance()` as the source of truth for further Bancor-formula math, a corrupted (negative or precision-drifted) balance can propagate into subsequent buy/sell quantity calculations, letting a trader receive more tokens than the pool's true backing supports — an unbacked-balance / theft-of-funds condition for other participants in that exchange pair.

### Likelihood Explanation
This requires the target TRC10 exchange to be operating with `allowHardenExchangeCalculation` disabled (the legacy default before that parameter is voted on by SRs), and requires crafting sell quantities/exchange balances that push the floating-point Bancor calculation into a regime producing precision loss or a negative result — the same "hard corner case" acknowledgment given by the original protocol team for the analogous Reserve Protocol issue. It is not trivial to trigger on a well-hardened, fully-upgraded mainnet, but it is a real, reachable code path for any user submitting an ordinary `ExchangeTransactionContract` on a chain/period where the harden proposal has not (yet) been activated.

### Recommendation
Apply the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` validation (and, ideally, the overflow-safe integer arithmetic in `SafeExchangeProcessor`) unconditionally, regardless of `hardenedCalc`/`allowHardenExchangeCalculation`, rather than gating the safety check behind a governance flag. At minimum, `ExchangeCapsule.transaction()` should reject any computed balance that is negative before persisting `this.exchange`, in both the legacy and hardened code paths.

### Proof of Concept
1. Deploy/observe a TRC10 exchange pair (`ExchangeCreateContract`) on a network/period where `allowHardenExchangeCalculation` is not yet enabled (`hardenedCalc == false`, the default until the SR proposal activates it) — confirmed by `AbstractExchangeActuator.allowHarden()` proxying the mutable chain parameter [2](#0-1) .
2. Submit repeated `ExchangeTransactionContract` trades with sell quantities engineered to stress the floating-point Bancor formula in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [3](#0-2)  such that `buyTokenQuant` diverges from the exact value or a resulting balance goes negative.
3. Because `hardenedCalc` is `false`, the negative-balance guard at `ExchangeCapsule.transaction()` line 160 is skipped and the corrupted balances are persisted [7](#0-6) .
4. Subsequent trades against the same exchange pair compute further buy/sell quantities from these corrupted balances, allowing extraction of tokens beyond the pool's true backing.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
