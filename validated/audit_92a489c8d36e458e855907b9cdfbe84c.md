### Title
`RewardsDistributor` computes reward deltas on `DebtToken.balanceOf`, which includes continuously accrued interest, so interest not outstanding during the accrual interval inflates a user's rewards and drains `rewardToken` owed to other stakers - (contracts/RewardsDistributor.sol)

### Summary
The Rubicon `BathBuddy` bug is a reward-allocation accounting mismatch: `vestedAmount` used `balanceOf(this) + released(token)`, where both terms included retained fees, so rewards were computed on value that was not part of the vested base. Metronome's `RewardsDistributor` has the same structural flaw when a `DebtToken` is a reward-bearing token: `_calculateTokenDelta` multiplies the *current* `token_.balanceOf(account_)` — which for `DebtToken` is `principal * currentDebtIndex / debtIndexOf[account_]` and therefore includes all interest accrued since the account's last reward checkpoint — by an index delta that spans the entire elapsed interval. Rewards are credited on debt (interest) that did not exist for most of that interval.

### Finding Description
- `RewardsDistributor._calculateTokenDelta` computes `_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex)` (`contracts/RewardsDistributor.sol:230`), where `_deltaIndex` is the change in the per-token reward index since the account's last update (`contracts/RewardsDistributor.sol:197-231`).
- `DebtToken.balanceOf` is not a static ERC20 balance: it returns `principalOf[account_] * _debtIndex / debtIndexOf[account_]` using a freshly computed interest accrual (`contracts/DebtToken.sol:196-206`, `_calculateInterestAccrual` at `contracts/DebtToken.sol:551-566`). An account's balance grows every block without any `updateBeforeMintOrBurn` call.
- So when `updateBeforeMintOrBurn` / `updateBeforeTransfer` / `claimRewards` (all permissionless, `contracts/RewardsDistributor.sol:150-192`) finally run for a debt token, the interest accrued over the whole elapsed window is retroactively treated as outstanding debt for reward purposes — identical in effect to BathBuddy counting retained fees in the reward base.
- Symmetrically, `_calculateTokenIndex` uses `token_.totalSupply()` (which also includes accrued interest, `contracts/DebtToken.sol:500-503`) as the divisor at update time, so the per-unit index increment does not match the effective average supply either; an attacker can exploit the asymmetry by keeping their own checkpoint stale while their balance grows.

### Impact Explanation
Direct theft of unclaimed yield: `claimRewards` pays out real `rewardToken` via `_transferRewardIfEnoughTokens` (`contracts/RewardsDistributor.sol:248-256`). Every wei over-credited to a holder whose `balanceOf` was inflated by retroactively-counted interest is `rewardToken` that belongs to other accounts' accrued rewards — the distributor is funded with a finite reward budget and pays out whatever `tokensAccruedOf` says. This matches the judge-accepted severity framing of the original report (leaked reward value, no stolen principal).

### Likelihood Explanation
- Requires a `RewardsDistributor` configured with nonzero `tokenSpeeds` on a `DebtToken` — a supported configuration (`onlyIfTokenExists` explicitly accepts debt tokens, `contracts/RewardsDistributor.sol:91-97`), and interest-bearing debt tokens are exactly where balance drift is largest (`interestRate > 0` is the normal case).
- No privileged action needed: anyone can call `updateBeforeMintOrBurn`, `updateBeforeTransfer`, and `claimRewards`. An attacker mints debt, avoids touching reward functions, lets interest accrue, then claims — receiving rewards on interest that was outstanding for only a fraction of the index window. The longer between updates and the higher the interest rate, the larger the over-credit.
- No guard stops this: `nonReentrant` doesn't apply to the accounting itself, there is no checkpoint of balance-at-index-time, and `updateBeforeMintOrBurn` is only invoked on mint/burn, not on passive interest accrual.

### Recommendation
Do not use the live `balanceOf` in reward-delta math for tokens whose balances grow outside the reward system's checkpoints. For `DebtToken`, either:
- maintain a reward-accounting principal snapshot per account in `RewardsDistributor` (store `balanceOf` at each `_updateTokensAccruedOf` and use the *stored* balance for the delta, updating it on every hook), or
- accrue rewards on `principalOf[account_]` normalized by `debtIndexOf` rather than the interest-inclusive `balanceOf`, and align `totalSupply()` used in `_calculateTokenIndex` to the same measure.

### Proof of Concept
Fork/Hardhat reproduction sketch:
1. Deploy `Pool`, a `DebtToken` with `interestRate > 0`, and a `RewardsDistributor`; governor calls `updateTokenSpeed(debtToken, speed > 0)` and funds `rewardToken`.
2. Attacker mints debt (`DebtToken.issue`) at `t0` — `accountIndexOf` set, `tokensAccruedOf = 0`.
3. Let `T` seconds pass with no reward hooks: attacker's `balanceOf` grows by `~interestRate * T` while `accountIndexOf` is unchanged.
4. Attacker calls `RewardsDistributor.claimRewards(attacker, [debtToken])`. `_tokensDelta` is computed as `balanceOf(now) * indexDelta(T)` — crediting rewards on the just-accrued interest for the entire window.
5. Compare against a second attacker who calls `updateBeforeMintOrBurn` every block (or compute the analytic entitlement integrating `balanceOf(t)`): the lazy attacker strictly over-accrues, and `tokensAccruedOf` exceeds their time-weighted share, draining `rewardToken` that should vest to other users.

Not fully verified in this pass: whether any deployed `RewardsDistributor` currently has a nonzero speed on a `DebtToken` (deployment JSONs show the contract exists; speed config wasn't confirmed). If no deployed distributor rewards debt tokens, the same class still applies, more weakly, to `DepositToken` (static balance → no drift), so the finding's reachability hinges on that configuration.
