### Title
Frozen per-connection `total_stake` snapshot causes stale, distorted proportional QUIC stream quotas — stake-weighted QoS evasion / unfairness - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
`SwQos::build_connection_context` computes a peer's proportional share of the network's stake (`stake_ratio = stake / total_stake`) exactly once, at QUIC connection establishment, and freezes that `total_stake` value for the entire lifetime of the connection. Every subsequent per-stream quota calculation (`available_load_capacity_in_throttling_duration`) keeps dividing by this stale, connection-time `total_stake` instead of the current cluster-wide stake. This is structurally the same class of bug as the referenced report: a proportional "share / total" ratio is computed once and never re-based against the live denominator, so as the denominator (total stake) drifts over time, the computed shares for different connections become internally inconsistent — some peers get a persistently over- or under-sized fraction of the shared QUIC throughput budget relative to their true, current stake weight.

### Finding Description
`SwQosConnectionContext` stores a `total_stake: u64` field that is populated once in `build_connection_context`: [1](#0-0) 

This same context (and its frozen `total_stake`) is reused for the whole connection's life in two places:
1. Setting the initial QUIC `max_concurrent_uni_streams` transport parameter when the connection is admitted: [2](#0-1) 
2. Computing the per-stream throttling quota on every new stream via `max_streams_per_throttling_interval` → `available_load_capacity_in_throttling_duration`: [3](#0-2) [4](#0-3) 

The quota formula is `max_staked_load_in_throttling_window * stake / total_stake` — a direct proportional-share calculation, structurally identical to the vault's `depositShares = depositAmount * share / underlying` pattern from the report: a numerator/denominator ratio that is expected to stay consistent across all participants, but whose denominator (`total_stake`) is captured at different points in time for different connections and never refreshed for long-lived ones. `staked_nodes` (the source of `total_stake`) is a live, periodically-updated structure (`StakedNodesUpdaterService`), so the true total stake changes continuously as validators activate/deactivate stake — but only newly-established connections observe the updated value; existing connections keep using their original denominator indefinitely (there is no re-fetch/refresh path in `try_add_connection`, `on_new_stream`, `on_stream_accepted`, etc.).

### Impact Explanation
Because the global stream-load EMA (`StakedStreamLoadEMA`) and its capacity budget are shared across all staked connections, but each connection's fractional entitlement is computed against a different, frozen snapshot of `total_stake`, the proportional allocation across connections becomes internally inconsistent:
- A connection opened while total stake was low locks in a comparatively large `stake / total_stake` fraction and keeps consuming that oversized share of the shared throttling budget even after total stake grows — this is a stake-weighted QoS evasion: the peer's enforced quota no longer reflects its true, current proportional stake weight, letting it out-consume its fair share relative to peers whose connections (or reconnections) observe the updated, larger denominator.
- Conversely, a connection opened when total stake was high is permanently under-quota'd relative to its true current share if total stake later drops (e.g., large validators deactivate), unfairly starving that peer's throughput for the life of the connection.
Since `max_streams_per_ms`/EMA capacity is a shared, finite resource, one connection consuming more than its rightful share directly reduces the fair-share throughput available to honestly-weighted peers — this is the "QoS evasion" impact category explicitly permitted by the rules.

### Likelihood Explanation
This is reachable by any unprivileged staked node simply by establishing (and keeping alive) a QUIC TPU/TPU-forward connection — no special validator/operator role or elevated privilege is required beyond having a stake account, which is a normal, permissionless network participant action. QUIC connections to the TPU are commonly long-lived (bounded by connection timeout/keep-alive settings), and `staked_nodes`/total-stake naturally fluctuates every epoch as delegations activate/deactivate, so the staleness condition arises organically rather than requiring an unusual or contrived scenario. The distortion is deterministic and persists for the full connection lifetime, not a rare timing race.

### Recommendation
Recompute (or periodically refresh) `total_stake` from `staked_nodes` at stream-quota calculation time (in `max_streams_per_throttling_interval`/`on_new_stream`) rather than relying solely on the value frozen in `SwQosConnectionContext` at connection admission. At minimum, `available_load_capacity_in_throttling_duration` should be passed the current `total_stake` read from the live `staked_nodes` map on each throttling check, mirroring how per-connection quotas are re-derived rather than cached for the connection's full lifetime.

### Proof of Concept
1. At time T0, total staked lamports in `staked_nodes` = 100. Validator A (stake = 10) opens a QUIC connection; `build_connection_context` computes `total_stake = 100`, giving A a quota fraction of `10/100 = 10%` of `max_staked_load_in_throttling_window`.
2. Between T0 and T1, additional validators activate stake, and cluster total stake grows to 1,000 (A's stake unchanged at 10). `StakedNodesUpdaterService` updates `staked_nodes` to reflect this.
3. Validator B opens a new connection at T1; `build_connection_context` computes `total_stake = 1,000` for B, and if B also has stake = 10, B's fraction is `10/1,000 = 1%`.
4. A's long-lived connection from T0 never re-evaluates `build_connection_context`; every subsequent stream on A's connection still calls `available_load_capacity_in_throttling_duration(Staked(10), total_stake=100)` (the value cached in `conn_context.total_stake`), yielding a 10× larger share of the shared throttling budget than B, despite both peers holding identical current stake — demonstrating a persistent, stake-disproportionate QoS advantage for the earlier-connecting peer purely due to the frozen denominator, at the expense of the shared streaming capacity available to fairly-weighted, newly-connecting peers like B.

impl QosController<SwQosConnectionContext> for SwQos {
    fn build_connection_context(&self, connection: &Connection) -> SwQosConnectionContext {
        let remote_address = connection.remote_address();
        get_connection_stake(connection, &self.staked_nodes).map_or(
            SwQosConnectionContext {
                peer_type: ConnectionPeerType::Unstaked,
                total_stake: 0,
                remote_pubkey: None,
                in_staked_table: false,
                remote_address,
                stream_counter: None,
                last_update: Arc::new(AtomicU64::new(timing::timestamp())),
            },
            |(pubkey, stake, total_stake)| {
                // The heuristic is that the stake should be large enough to have 1 stream pass through within one throttle
                // interval during which we allow max (MAX_STREAMS_PER_MS * STREAM_THROTTLING_INTERVAL_MS) streams.

                let peer_type = {
                    let max_streams_per_ms = self.staked_stream_load_ema.max_streams_per_ms();
                    let min_stake_ratio =
                        1_f64 / (max_streams_per_ms * STREAM_THROTTLING_INTERVAL_MS) as f64;
                    let stake_ratio = stake as f64 / total_stake as f64;
                    if stake_ratio < min_stake_ratio {
                        // If it is a staked connection with ultra low stake ratio, treat it as unstaked.
                        ConnectionPeerType::Unstaked
                    } else {
                        ConnectionPeerType::Staked(stake)
                    }
                };

                SwQosConnectionContext {
                    peer_type,
                    total_stake,
                    remote_pubkey: Some(pubkey),
                    in_staked_table: false,
                    remote_address,
                    last_update: Arc::new(AtomicU64::new(timing::timestamp())),
                    stream_counter: None,
                }
            },
        )

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
