### Title
Out-of-bounds read in ZIP central directory entry parsing — (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's ZIP reader parses per-entry length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) straight out of attacker-controlled bytes and advances the cursor without ever checking those lengths against the actual size of the mapped central-directory buffer, unlike the local-file-header parser which explicitly calls `EnsureRemaining()` before every variable-length field.

### Finding Description
`FindZipCentralDirectory` (lines 704-778) validates only that the *aggregate* central directory (`cd.central_dir_offset + cd.central_dir_size`) fits within the file, and hands back a `central_dir` pointer plus that aggregate size. [1](#0-0) 

Per-entry iteration happens in `ProcessCentralDirEntry` (called from `ProcessNext` and `CalculateOutputLength`), which reads `file_name_length`, `extra_field_length`, `file_comment_length` from the entry and then does:
```
memcpy(filename, p, len);      // len derived from file_name_length, no bounds check on p
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  extra_p += data_size;        // data_size unchecked against extra_field_length or buffer end
  ...
}
p += file_comment_length;
``` [2](#0-1) 

None of `file_name_length`, `extra_field_length`, `file_comment_length`, or the inner ZIP64 extra-field `data_size` are checked against the remaining bytes in the mapped central directory (or the mapped file at all). This contrasts directly with the local file header parser, `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before reading `file_name_length`/`extra_field_length` bytes: [3](#0-2) 
and with `EnsureRemaining` itself, which is the only bounds-check primitive defined in this file: [4](#0-3) 

`ProcessNext`, the driver used for every entry during a real extraction/ijar pass, calls `ProcessCentralDirEntry` unconditionally with no surrounding bounds check: [5](#0-4) 

A crafted JAR/ZIP whose central-directory entry declares an oversized `file_name_length`/`extra_field_length`/`file_comment_length` (or a ZIP64 extra field with an oversized `data_size`) causes `p`/`extra_p` to walk past the end of the memory-mapped input file into adjacent process memory, and the `memcpy` into `filename` copies whatever bytes lie there. Because the input is `mmap`'d (`MappedInputFile`), this is a read into unmapped or unrelated memory content — the same "boundary condition" class as the reported libXpm bug (`XpmCreateXpmImageFromBuffer` trusting length fields without validating them against the actual buffer).

### Impact Explanation
ijar (`third_party/ijar`) is Bazel's own native tool for producing interface JARs from `.jar` inputs, and is invoked as part of ordinary Java compilation/build actions on JAR files that originate from external, attacker-influenced sources (e.g., a JAR fetched via `http_jar`/`http_archive`, or supplied by a dependency in an untrusted branch that CI builds). Because the length fields are fully attacker-controlled and unchecked, the copied `filename` bytes (adjacent process memory content) can flow into the interface-jar's own emitted entry names/attributes, i.e., into a build artifact — an information disclosure of process memory content, matching the CVSS vector of the analog report (`C:H/I:N/A:N`). Depending on where the mapped region ends relative to page boundaries, the same defect can also cause a crash (SIGSEGV) reading unmapped memory, which is a secondary DoS effect but not the primary claim here.

### Likelihood Explanation
High for any build that processes a JAR the attacker fully controls (a plausible and common scenario: any external Java dependency, a JAR built from a malicious/compromised third-party repo consumed via `http_jar`/`http_archive`/Maven rules). No credentials, MITM, or checksum bypass is required — the attacker simply authors the JAR bytes that a victim's build legitimately downloads and hashes/matches, then bazel's own ijar tool parses the malformed central directory during normal build actions.

### Recommendation
Add the same `EnsureRemaining()`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: validate `file_name_length`, `extra_field_length`, `file_comment_length`, and each ZIP64 extra-field `data_size` against the remaining bytes of the mapped central directory buffer before advancing `p`/`extra_p` or performing the `memcpy`, failing the parse with an error instead of reading out of bounds.

### Proof of Concept
Construct a minimal ZIP/JAR file where:
1. The central directory contains one valid-looking entry header (correct `CENTRAL_FILE_HEADER_SIGNATURE`).
2. Set `file_name_length` (or `extra_field_length`/`file_comment_length`) to a value (e.g., `0xFFFF`) that extends past the end of the actual mapped file/central directory region.
3. Run `ijar <crafted.jar> <output.jar>` (or trigger via a `java_library`/`java_import` build depending on such a JAR fetched through `http_jar`).
4. Observe via ASan/Valgrind that `memcpy(filename, p, len)` in `ProcessCentralDirEntry` (third_party/ijar/zip.cc:520) reads past the mapped file boundary, and that the resulting `filename` bytes (containing adjacent memory content) appear in the produced interface JAR's entry table — or that the process crashes with a heap-buffer-overflow/SEGV report.

A `src/test/shell/bazel/`-style regression test or a targeted C++ unit test (in `third_party/ijar/`) feeding a hand-crafted malformed central directory buffer directly to `ProcessCentralDirEntry`/`ProcessNext` under ASan would deterministically reproduce and confirm the out-of-bounds read.

    return false;

      return false;
    }

  return true;
