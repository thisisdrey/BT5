### Title
Unvalidated attacker-controlled array length in `BatchValidateSign`/`ValidateMultiSign` precompile leads to uncontrolled memory allocation / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`extractBytes32Array` and `extractBytesArray` in `PrecompiledContracts.java` read a 32-byte "array length" word directly from smart-contract calldata and use it to allocate a Java array (`new byte[len][]`), then loop `len` times reading from the `words` array, without validating that `len` (or the derived offsets) is consistent with the actual size of `words`/`data`.

### Finding Description
`extractBytes32Array` takes `len` straight from `words[offset].intValueSafe()` and immediately allocates `new byte[len][]`, then indexes `words[offset + i + 1]` for `i` in `[0, len)` with no check that `offset + len` is within `words.length`: [1](#0-0) 

`extractBytesArray` only guards the initial `offset` against `words.length`, but never validates `len` before allocating `new byte[len][]` or before deriving `bytesOffset`/`bytesLen` used to slice `data`: [2](#0-1) 

Both are invoked from the `BatchValidateSign` precompile's `doExecute`, which is reachable by any contract that issues a `CALL`/`STATICCALL` to this precompile with crafted calldata (e.g. via `batchValidateSign` from Solidity). A size cap (`MAX_SIZE`) is applied to `sigArraySize`/`addrArraySize` only when `VMConfig.allowTvmSelfdestructRestriction()` is active; on the `extractBytesArray`/legacy branch (or when that config flag is off) no upper bound is enforced on the attacker-supplied length before the array is allocated: [3](#0-2) 

Because `len` comes from `intValueSafe()` on a full 32-byte word, it can be as large as `Integer.MAX_VALUE`. `new byte[Integer.MAX_VALUE][]` (an 8-byte reference array of that length) requests roughly 16 GB, which throws `java.lang.OutOfMemoryError` — an `Error`, not a `RuntimeException`/`Exception`. This differs qualitatively from a normal `ArrayIndexOutOfBoundsException`, which the VM's per-opcode/precompile exception handling is designed to catch and convert into a reverted call; an `Error` is not reliably caught by such handlers and can propagate up and destabilize or crash the node process. This mirrors the CVE's root cause: an attacker-controlled count/length field (`RowsPerStrip` in the TIFF analog, `len`/array-length words here) is used directly to size and index buffers without validating it against the real bounds of the input.

### Impact Explanation
If the `OutOfMemoryError` is not caught by the JVM/thread-level exception handling surrounding VM execution, this can crash or destabilize the full node from a single crafted transaction/contract call, which is a denial-of-service against block production/serving — a concrete "node crash or halt" outcome under the validation criteria. Even in the best case where an outer handler converts it into a failed transaction, this at minimum makes an unbounded memory-allocation primitive reachable from unauthenticated contract calldata, which is inconsistent with hardened input handling elsewhere in the codebase (e.g. `RLP.java`'s explicit `OutOfMemoryError` catch/guard patterns and `verifyLength` bounds checks) that were evidently added specifically to prevent this exact bug class: [4](#0-3) [5](#0-4) 

### Likelihood Explanation
Trivially reachable: any account can deploy or call a contract that invokes the `BatchValidateSign`/`ValidateMultiSign` precompile address with a crafted `len` word, requiring no special privilege, stake, or prior state.

### Recommendation
Add explicit bounds validation before allocation in `extractBytes32Array` and `extractBytesArray`: check `len` against a sane maximum (consistent with the existing `MAX_SIZE` check) and validate `offset + len` against `words.length` unconditionally (not only when `allowTvmSelfdestructRestriction()` is enabled), analogous to `RLP.verifyLength`.

### Proof of Concept
Craft a `CALL` to the `BatchValidateSign`/`ValidateMultiSign` precompile address with calldata whose sig/address-array offset word points to a length word set to a large value (e.g. `0x7fffffff`). On the legacy/`extractBytesArray` path, `doExecute` allocates `new byte[0x7fffffff][]` before any subsequent bound checks, requesting multi-gigabyte memory from a single external call.

**Uncertainty note:** I was not able to fully verify, within the available tool calls, whether the JVM-level VM opcode dispatcher (e.g. the `CALL`/`STATICCALL` handling in `Program`) wraps precompile execution in a `catch (Throwable)`/`catch (Error)` block that would prevent an `OutOfMemoryError` from propagating and crashing the node process. If such a `Throwable`-level catch exists, actual node-crash impact would be reduced to a more limited effect (failed call/local resource pressure) rather than a full node crash; I recommend a background agent confirm the exact exception-handling boundary around precompiled-contract `execute()` invocation in `Program.java` before treating this as fully confirmed at Critical/High severity.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
