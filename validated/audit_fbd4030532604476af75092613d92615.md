## Title
Non-reverting `ZKProofStore` permanently blacklists a `ShieldedTransferContract` txid after a single transient validation failure - ([File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java])

### Summary
`ShieldedTransferActuator.validate()` caches the outcome of the expensive zk-SNARK proof/pool-balance check in `ZKProofStore`, keyed by transaction id, so it isn't recomputed if the same transaction is validated again (mempool re-check, re-broadcast, block application). However, `ZKProofStore` is a plain `TronDatabase`, not a `TronStoreWithRevoking`, so writes to it bypass the checkpoint/session revoke mechanism that protects every other actuator-touched store. A single transient validation failure (e.g. the pool-balance snapshot check that depends on *current* dynamic-store state) permanently writes `false` for that txid, and this record survives session rollback, mempool re-push, and even chain-fork reverts — unlike `NullifierStore`, which is properly revoked.

### Finding Description
`checkProof()` short-circuits on a cached result:

```java
ZKProofStore proofStore = chainBaseManager.getProofStore();
if (proofStore.has(tx.getTransactionId().getBytes())) {
  if (proofStore.get(tx.getTransactionId().getBytes())) {
    return;
  } else {
    throw new ZkProofValidateException("record is fail, skip proof", false);
  }
}
``` [1](#0-0) 

If the real check fails for *any* reason — including the pool-value check that depends on the mutable `totalShieldedPoolValue`, which can differ between mempool state, a soon-to-be-reverted fork branch, and the eventual canonical chain — the failure is persisted with `isFirstValidated=true` and recorded via:

```java

`ZKProofStore` writes directly to the raw DB source with no revoking/session wrapper:

```java
@Component

  ...
  @Override

    dbSource.putData(key, b);

``` [4](#0-3) 

Contrast this with `NullifierStore`, which correctly extends `TronStoreWithRevoking` and therefore participates in the checkpoint/session mechanism used by `pushTransaction`'s `try (ISession tmpSession = revokingStore.buildSession())` block: [5](#0-4) [6](#0-5) 

`processTransaction()` — which invokes the actuator's `validate()`/`execute()` — is the single code path shared by both mempool submission (`pushTransaction`, `blockCap == null`) and block application (`applyBlock`, `blockCap != null`): [7](#0-6) 

Because `ZKProofStore` is never rolled back on session revoke or on `switchFork`'s branch reversion (see the fork-switch session handling that only wraps revoking stores) [8](#0-7) 
, a node that once evaluated a transaction on a branch that gets reverted (or under a transiently different pool-value/mempool state) keeps a stale `false` record for that exact txid. If the same transaction is later included in the canonical chain by other nodes, this node's `checkProof()` will immediately throw `ZkProofValidateException("record is fail, skip proof")` during block application, without ever re-running the actual snark/pool checks — causing `ContractValidateException` to propagate out of `processTransaction`, and preventing this node from applying an otherwise-valid block.

### Impact Explanation
This is the same bug class as the reported TOTP-reuse lock: an idempotency/dedup marker keyed by a stable identifier (txid) is written irreversibly on the very first (possibly transient/incorrect) attempt, and every subsequent legitimate re-evaluation of that identical transaction is permanently short-circuited to the cached negative result instead of being retried. In java-tron this manifests as:
- Permanent denial-of-validation for a specific, signed `ShieldedTransferContract` transaction on any node whose local state happened to produce a transient failure once.
- Because the record is not covered by the revoking/checkpoint system, a node can end up with a stale invalid record after a fork-branch revert, and subsequently fail to apply a valid block containing that transaction — a node halt/chain-divergence scenario reachable purely by an unprivileged user broadcasting a normal shielded transfer transaction.

### Likelihood Explanation
Any unprivileged broadcaster of a `ShieldedTransferContract` can trigger the recording path — the pool-value/balance check inside `checkProof()` depends on `dynamicStore.getTotalShieldedPoolValue()`, which fluctuates with concurrent pending shielded transactions, and on a temporary fork branch during a fork switch. No special privileges, malicious SR/witness behavior, or non-standard node configuration are required; ordinary network conditions (mempool contention, brief forks) are sufficient to produce a first, incorrect `false` verdict for a txid.

### Recommendation
Make `ZKProofStore` a `TronStoreWithRevoking` (like `NullifierStore`) so cached proof results participate in the same session/checkpoint revert semantics as all other consensus-relevant state, and/or stop treating a first validation failure as permanently authoritative — only cache/short-circuit on a definitive positive result, and let negative-but-transient outcomes (e.g., pool-value insufficiency, which can change block to block) be re-evaluated on every attempt rather than being memoized forever.

### Proof of Concept
1. Broadcast a well-formed `ShieldedTransferContract` transaction `T` (txid `X`) at a moment where `totalShieldedPoolValue` transiently makes the balance check fail (e.g., another pending shielded tx has not yet been dropped from the pool) — `checkProof` throws `ZkProofValidateException("shieldedPoolValue error", true)`, and `recordProof(X, false)` permanently stores `false` for `X`.
2. Once the transient condition clears, other nodes/SRs successfully validate and include `T` in a canonical block.
3. On the node that recorded the stale entry, when it receives and applies that block via `applyBlock` → `processTransaction` → `ShieldedTransferActuator.validate()` → `checkProof()`, `proofStore.has(X)` is true and `proofStore.get(X)` is false, so it immediately throws `ZkProofValidateException("record is fail, skip proof", false)` without re-checking the (now valid) proof, causing `ContractValidateException` to bubble out of block application and the node to fail to apply an otherwise valid canonical block.
