Audit Report

## Title
Unbalanced token donation to the deterministic pool account can DoS or under-mint LP tokens in `pallet-asset-conversion::do_add_liquidity` - (`substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`do_add_liquidity` computes `reserve1`/`reserve2` directly from `Self::get_balance(&pool_account, ...)`, i.e. the pool account's live, external token balance, rather than from an internally tracked invariant that is only mutated by `add_liquidity`/`remove_liquidity`/`swap`. Because the pool account address is fully deterministic and computable off-chain via `T::PoolLocator::address`, any unprivileged account can transfer pool-asset tokens directly to it, skewing the ratio used by `Self::quote` for the next legitimate `add_liquidity` call.

## Finding Description
In `do_add_liquidity`, reserves are read as raw balances: [1](#0-0) 

These reserves feed directly into `Self::quote`, which is a simple ratio calculation with no manipulation resistance: [2](#0-1) 

The optimal-amount branch enforces `amount1_min`/`amount2_min`/`OptimalAmountLessThanDesired` against this skewed quote: [3](#0-2) 

Further downstream, when `total_supply` is non-zero, the LP-token amount minted is `min(amount1*total_supply/reserve1, amount2*total_supply/reserve2)`: [4](#0-3) 

Since `reserve1`/`reserve2` are inflated by a raw, unsolicited transfer that never mints LP tokens or updates `total_supply`, both the ratio quote and the LP-minting division are corrupted by third-party donations. Existing tests confirm the pool account is externally computable and can be pre-funded before any real liquidity exists, and that the existing mitigation only covers *unrelated* non-sufficient assets used for price quoting — not the actual pool assets used by `do_add_liquidity`'s reserve math: [5](#0-4) [6](#0-5) 

I confirmed via `grep_search` that there is no separate `Reserves` storage item or invariant-tracking mechanism in `substrate/frame/asset-conversion/src/lib.rs` — `get_balance` is the sole source of reserve figures used in `do_add_liquidity`, `do_remove_liquidity`, and swap math, matching the report's central claim.

## Impact Explanation
An unprivileged attacker can grief the public `add_liquidity` extrinsic for any pool by donating an unbalanced amount of a pool asset to the pool account, causing legitimate LPs' transactions to revert (`AssetOneDepositDidNotMeetMinimum`, `AssetTwoDepositDidNotMeetMinimum`, `OptimalAmountLessThanDesired`) or to receive fewer LP tokens than the fair share for their deposit (since `side1`/`side2` are computed against the corrupted reserves). This is a public-entrypoint degradation of intended AMM behavior triggerable without any privileged role, aligning with the "public underpriced work that degrades... processing" and "runtime bugs that compromise intended behavior" categories.

## Likelihood Explanation
High. The pool account address is a pure function of the asset pair via `T::PoolLocator::address`, computable by anyone before or after pool creation, and the donation requires only an ordinary `Assets::transfer`/`Balances::transfer` call with no special permission. The existing `cannot_block_pool_creation` test already demonstrates the exact pre-funding technique working against the pool account for unrelated assets; extending it to the real pool assets to corrupt `add_liquidity`'s ratio math is a straightforward variation, requiring no unusual capital or timing constraints, and is repeatable across any pool.

## Recommendation
Do not derive `reserve1`/`reserve2` for `do_add_liquidity`'s ratio and LP-mint calculations purely from the pool account's live external balance. Track reserves as pallet storage updated atomically and only within `do_add_liquidity`/`do_remove_liquidity`/swap execution paths (Uniswap V2-style reserve state decoupled from raw balance, with an explicit `sync` only if intentionally allowed and proportionally reconciled with LP supply), so unsolicited external transfers to the pool account cannot influence minting or optimal-amount calculations.

## Proof of Concept
1. Create a pool for `(asset1, asset2)` via `create_pool`; compute the deterministic pool account via `T::PoolLocator::address(&pool_id)`.
2. Attacker calls `Assets::transfer` to send a large amount of `asset1` directly to the pool account (no `add_liquidity` call, mirroring `cannot_block_pool_creation` but targeting an actual pool asset instead of an unrelated one).
3. A legitimate LP calls `add_liquidity` with `amount1_desired`/`amount2_desired` matching the pre-donation market ratio and reasonable `amount1_min`/`amount2_min`.
4. `Self::quote` in `do_add_liquidity` (lines 822/832) recomputes `amount2_optimal`/`amount1_optimal` against the now-skewed `reserve1`, causing `AssetTwoDepositDidNotMeetMinimum`, `AssetOneDepositDidNotMeetMinimum`, or `OptimalAmountLessThanDesired` to fire and revert the legitimate LP's transaction, or (if it does not revert) causing the LP-mint division at lines 869-871 to under-mint LP tokens relative to the deposited value.

#[test]
fn cannot_block_pool_creation() {
	new_test_ext().execute_with(|| {
		// User 1 is the pool creator
		let user = 1;
		// User 2 is the attacker
		let attacker = 2;

		let ed = get_native_ed();
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), attacker, 10000 + ed));

		// The target pool the user wants to create is Native <=> WithId(2)
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		// Attacker computes the still non-existing pool account for the target pair
		let pool_account =
			<Test as Config>::PoolLocator::address(&(token_1.clone(), token_2.clone())).unwrap();
		// And transfers the ED to that pool account
		assert_ok!(Balances::transfer_allow_death(
			RuntimeOrigin::signed(attacker),
			pool_account,
			ed
		));
		// Then, the attacker creates 14 tokens and sends one of each to the pool account
		for i in 10..25 {
			create_tokens(attacker, vec![NativeOrWithId::WithId(i)]);
			assert_ok!(Assets::mint(RuntimeOrigin::signed(attacker), i, attacker, 1000));
			assert_ok!(Assets::transfer(RuntimeOrigin::signed(attacker), i, pool_account, 1));
		}

		// User can still create the pool
		create_tokens(user, vec![token_2.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));

		// User has to transfer one WithId(2) token to the pool account (otherwise add_liquidity
		// will fail with `AssetTwoDepositDidNotMeetMinimum`)
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), user, 10000 + ed));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 10000));
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(user), 2, pool_account, 1));

		// add_liquidity shouldn't fail because of the number of consumers
		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			10000,
			100,
			10000,
			10,
			user,
		));
	});
}
