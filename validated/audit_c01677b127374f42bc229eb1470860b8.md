### Title
Fixed (non-sliding) per-source stream throttling window allows precisely-timed clients to burst up to ~2x `max_streams_per_throttling_interval` across a window boundary - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a lazily-reset *fixed* window counter rather than a true sliding window, and `throttle_stream` only inspects the counter at the moment a new stream is requested. A client that precisely times stream opens can place a near-max batch just before a window reset and another near-max batch immediately after the reset, producing an admitted-stream burst close to `2 * max_streams_per_throttling_interval` within a single `STREAM_THROTTLING_INTERVAL`-sized sliding window, without ever hitting the `sleep(throttle_duration)` branch.

### Finding Description
The per-source (IP/pubkey-keyed, shared across all connections from that key — see `try_add_connection` in `streamer/src/nonblocking/quic.rs:1027-1039`) throttle state is a single `(stream_count, last_throttling_instant)` pair reset lazily: [1](#0-0) 

`throttle_stream` reads the current `stream_count` against `max_streams_per_throttling_interval` and only sleeps when the count has already reached the cap: [2](#0-1) 

Because the window boundary (`last_throttling_instant`) is only advanced the first time a check occurs *after* the interval has elapsed, and because the counter that is compared against the cap is unconditionally reset to `0` at that moment, an attacker who controls exact stream-open timing (fully within reach of an unstaked remote client dialing QUIC streams to the TPU port) can:

1. Open `max_streams_per_throttling_interval - 1` streams late in window *k* (all pass, no sleep, since `stream_count < max`).
2. Immediately after crossing the boundary, open `max_streams_per_throttling_interval` more streams; the first of these triggers `reset_throttling_params_if_needed` to reset `stream_count` to `0` and move `last_throttling_instant` forward, so none of this new batch is throttled either.

Both batches occur within an arbitrarily small epsilon of the boundary, so a sliding window of size `STREAM_THROTTLING_INTERVAL` that straddles this boundary contains close to `2 * max_streams_per_throttling_interval` admitted streams — never invoking `sleep`. This violates the intended invariant that no `STREAM_THROTTLING_INTERVAL`-sized window should admit more than `max_streams_per_throttling_interval` streams from a given source.

Note that connection churn itself does not defeat this limiter, since the `stream_counter` is shared per `ConnectionTableKey` across all connections from the same source (`streamer/src/nonblocking/quic.rs:1027-1030`, `streamer/src/nonblocking/swqos.rs:209-219`). The exposure is purely a timing/window-alignment artifact of the fixed-window design, not connection churn.

However, because `stream_count` for a given window is hard-capped at `max_streams_per_throttling_interval` before further increments trigger `sleep`, this doubling can only be realized once per crafted boundary; sustaining it on every consecutive boundary requires deliberately under-using the budget in intervening windows, so this is a bounded, recurring burst amplification (up to ~2x for a short overlap), not an unbounded/indefinite rate escape.

### Impact Explanation
This is a QoS-enforcement evasion: an unstaked/staked-but-low-stake source can momentarily double its admitted-stream throughput at engineered window boundaries relative to its configured `max_streams_per_throttling_interval`, which can transiently starve fair-share capacity for co-tenant IPs sharing the unstaked connection pool during those burst instants. It falls under the QoS-evasion bounty category rather than a memory-safety or consensus-safety issue, since it does not bypass sigverify, corrupt state, or cause unbounded memory growth — the achievable amplification is bounded to roughly 2x for a short overlapping window, not sustained indefinitely.

### Likelihood Explanation
Exploitability requires only that the attacker precisely control the wall-clock timing of stream opens on connections they already control — no special privileges, stake, or peer control needed, matching the unstaked-attacker threat model. It is fully reproducible against `ConnectionStreamCounter`/`throttle_stream` in isolation as shown below, though achieving the doubling on *every* successive boundary (rather than a single boundary) additionally requires the attacker to forgo using their budget elsewhere in the window, which is a mild but nontrivial extra timing constraint.

### Recommendation
Replace the lazy fixed-window reset in `ConnectionStreamCounter` with a true sliding-window or token-bucket scheme (e.g., decay `stream_count` continuously, or track timestamps of the last N stream opens and enforce that no more than `max_streams_per_throttling_interval` fall within any trailing `STREAM_THROTTLING_INTERVAL`), eliminating the ability to double-count near a reset boundary.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test]
async fn test_boundary_straddle_doubles_admitted_streams() {
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max = 10u64; // max_streams_per_throttling_interval
    let stats = Arc::new(StreamerStats::default());

    // Phase 1: admit max-1 streams late in the current window (simulated by
    // directly manipulating stream_count as on_stream_accepted would).
    for _ in 0..max - 1 {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    assert_eq!(stats.throttled_streams.load(Ordering::Relaxed), 0);

    // Wait until just past STREAM_THROTTLING_INTERVAL to cross the boundary.
    tokio::time::sleep(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Phase 2: admit another `max` streams immediately after the reset.
    for _ in 0..max {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }

    // No sleep was ever triggered, yet (max-1) + max streams were admitted
    // within a single STREAM_THROTTLING_INTERVAL-sized sliding window ending
    // just after phase 2 — nearly 2x max_streams_per_throttling_interval.
    assert_eq!(stats.throttled_streams.load(Ordering::Relaxed), 0);
}
```
Expected result: the assertion that no sliding `STREAM_THROTTLING_INTERVAL` window admits more than `max` streams fails — the test above admits `2*max - 1` streams while `throttled_streams` remains `0`, confirming `sleep(throttle_duration)` is never invoked despite the effective rate exceeding the configured cap.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
