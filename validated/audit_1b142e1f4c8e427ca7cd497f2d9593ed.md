### Title
Stale StackerDB signer authorization retained on-disk when a signer set is replaced with an empty set - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` in `stackslib/src/net/stackerdb/mod.rs` only calls `reconfigure_stackerdb()` — the routine that rewrites each slot's authorized `signer` in the on-disk `chunks` table — when the newly computed config differs from the old one **and** the new signer list is non-empty. When the freshly-evaluated config for a StackerDB smart contract collapses to an empty signer set (e.g. a `.signers-N-M` boot contract reporting no participation for the current reward cycle, or `StackerDBConfig::from_smart_contract`/`::noop()` falling back to `signers: vec![]` on a transient evaluation failure), the reconfiguration step is skipped entirely, and the previous cycle's signer-to-slot bindings remain valid in the database.

### Finding Description
The relevant logic is: [1](#0-0) 

```rust
if !existing_contract_ids.contains(&stackerdb_contract_id) {
    if let Err(e) = self.create_stackerdb(&stackerdb_contract_id, &new_config) { ... }
} else if (new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config
        && new_config.signers.len()
            != self.get_slot_versions(&stackerdb_contract_id)?.len())
{
    // only reconfigure if the config has changed
    if let Err(e) = self.reconfigure_stackerdb(&stackerdb_contract_id, &new_config) { ... }
}
```

`reconfigure_stackerdb()` (in `stackslib/src/net/stackerdb/db.rs`) is the only code path that updates the `signer` column bound to each slot in the persisted `chunks` table: [2](#0-1) 

When the new config's `signers` list is empty, the first disjunct's `!new_config.signers.is_empty()` guard evaluates to `false`; the second disjunct only fires when `new_config == stackerdb_config` (i.e., nothing changed), which is not the case here since the config *did* change (non-empty → empty). As a result the whole `else if` is `false`, `reconfigure_stackerdb` is never invoked, and the previous signer(s) remain bound to their slots on disk.

Crucially, the write-path authorization check (`try_replace_chunk` and `validate_received_chunk`) does **not** consult the in-memory `StackerDBConfig.signers` field for authorization — it authenticates purely against the persisted slot record fetched via `get_slot_validation`/`get_slot_signer`: [3](#0-2) [4](#0-3) 

So even though the freshly-evaluated `StackerDBConfig` (now stored in `PeerNetwork.stacker_db_configs` and used e.g. by `stacker_db_sync`) correctly reports an empty signer set for the current epoch, the durable per-slot signer binding used by both the HTTP write handler (`RPCPostStackerDBChunkRequestHandler` → `try_replace_chunk`) and the P2P push-chunk validation (`validate_received_chunk`) is never revoked. The previous signer retains the ability to write (push a new, higher-version, validly-signed chunk) into that StackerDB slot even though the authoritative contract state (and the in-memory config) says there should be no valid signer.

This directly mirrors the reported bug class: an old, previously-authorized principal (the vault's old AMO manager / here, the previous reward-cycle's signer) retains its granted capability (`approve()` allowance / StackerDB slot-write authorization) after the controlling logic intends to replace/void it, because the revocation step is conditionally skipped.

### Impact Explanation
This breaks the equality "authenticated-to-write == currently-authorized-by-contract-state" for a StackerDB slot. A signer that has been dropped from the signer set for a reward cycle (participation failure, `has_participation=false` in `update_signers`) — but who still possesses their private key from the previous cycle — can continue to submit chunks (`POST /v2/stackerdb/<contract>/chunks`, or via the P2P StackerDBPushChunk unsolicited path) that the node will accept as legitimate, because `try_replace_chunk`/`validate_received_chunk` check the stale on-disk `signer` column rather than the freshly recomputed empty signer list. This is an unauthorized write to StackerDB state by a party the protocol has determined should no longer hold write privileges for that slot, and any node applying `create_or_reconfigure_stackerdbs` in this order is affected, causing chunk data (and any consumers such as the signer message pipeline) to trust content that is no longer canonically authorized.

### Likelihood Explanation
This requires no privileged/insider access beyond already having controlled a signer key in a previous reward cycle for the affected StackerDB contract — a condition that recurs naturally as reward cycles rotate and `.signers-0-*`/`.signers-1-*` boot contracts are reused every other cycle. The triggering condition (an evaluated config transitioning to an empty signer list while the contract already exists) is a normal path, not a contrived edge case: it occurs whenever `has_participation` is `false` for the reward cycle in `NakamotoSigners::update_signers` (`stackslib/src/chainstate/nakamoto/signer_set.rs`), or whenever `StackerDBConfig::from_smart_contract` transiently fails and falls back to `StackerDBConfig::noop()` (empty signers) inside `create_or_reconfigure_stackerdbs`.

### Recommendation
Remove the `!new_config.signers.is_empty()` exemption in `create_or_reconfigure_stackerdbs` so that `reconfigure_stackerdb` is always called whenever `new_config != stackerdb_config`, regardless of whether the new signer list is empty. This ensures that when the authoritative signer set shrinks to nothing (or changes), the on-disk `chunks.signer` bindings are wiped/reset immediately, revoking the previous signer's write authorization for that slot, consistent with how a non-empty signer-set change already resets ownership via `INSERT OR REPLACE`.

### Proof of Concept
1. Reward cycle `C`: `.signers-0-<msg>` boot contract is configured with signer `S` (private key `sk_S`) owning slot 0; `create_or_reconfigure_stackerdbs` runs `reconfigure_stackerdb`, binding slot 0's `signer` column to `S`.
2. Reward cycle `C+2` (same boot contract reused, `cycle_mod == 0`): the reward-set computation determines `has_participation = false`, so `update_signers` in `signer_set.rs` writes an empty `stackerdb-signer-slots-0` list into the boot contract.
3. On the node's next refresh (`PeerNetwork::refresh_stacker_db_configs` → `create_or_reconfigure_stackerdbs`), `StackerDBConfig::from_smart_contract` evaluates the contract and returns `new_config.signers == vec![]`. Since `new_config != stackerdb_config` (non-empty → empty) but `new_config.signers.is_empty()` is `true`, the `else if` condition is `false`; `reconfigure_stackerdb` is skipped. The on-disk slot 0 record still has `signer = S`.
4. `S` (holder of `sk_S`, no longer an authorized signer for cycle `C+2`) crafts a `StackerDBChunkData` for slot 0 with an incremented `slot_version`, signs it with `sk_S`, and submits it via `POST /v2/stackerdb/<contract>/chunks` (handled by `RPCPostStackerDBChunkRequestHandler` → `try_replace_chunk`) or pushes it unsolicited over P2P.
5. `try_replace_chunk`/`validate_received_chunk` fetch the stale `slot_validation.signer == S` from the DB, verify the signature against `S`, and accept the write — despite `S` no longer being part of the current, contract-authoritative signer set.

    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
