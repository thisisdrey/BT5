### Title
Exchange Transaction Kill-Switch Bypassed When `allowHardenExchangeCalculation` Is Enabled - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`Manager` gates every `ExchangeTransactionContract` (and related Exchange contracts) behind an `isExchangeTransaction()` check that is used as a circuit-breaker: it rejects the contract from the mempool in `pushTransaction`, skips it while packing new blocks in the block-generation loop, and screens it again in `processBlock` via `rejectExchangeTransaction`. This is functionally the network's "pause" mechanism for the legacy Bancor-formula Exchange feature. The same `isExchangeTransaction()` helper, however, returns `false` (i.e., "not an exchange transaction, do not reject it") whenever `allowHardenExchangeCalculation` is enabled, which silently disables the kill-switch for every user-broadcast exchange trade — the same class of bug as the missing `whenNotPaused` modifier in the reference report, where a state that is supposed to block an action fails to do so.

### Finding Description
Three chokepoints exist specifically to keep `ExchangeTransactionContract` (and sibling Exchange* contracts) from being processed by ordinary nodes:

- In the mempool entry point, any incoming exchange transaction is unconditionally rejected: [1](#0-0) 
- In block production, exchange transactions are skipped while packing pending transactions into a new block: [2](#0-1) 
- In block application, `rejectExchangeTransaction` is invoked for every transaction in an incoming block before execution: [3](#0-2) 

All three of these gates share the same underlying predicate, `isExchangeTransaction(Transaction)`. A test explicitly documents that this predicate is toggled off when the `allowHardenExchangeCalculation` dynamic property is set to `1`: [4](#0-3) 

This means enabling `allowHardenExchangeCalculation` removes the enforcement point entirely for `pushTransaction`, block-packing, and `processBlock`'s `rejectExchangeTransaction`/`isExchangeTransaction` screen simultaneously — analogous to a contract that lacks a `whenNotPaused` check on its user-facing entry point: the "pause"/kill-switch state (`allowHardenExchangeCalculation`) is supposed to gate a sensitive action, but the gating logic inverts and permits the very transaction type it is meant to block.

Corroborating actuator-side evidence: `AbstractExchangeActuator` uses the same `allowHardenExchangeCalculation` flag to switch the Exchange math from ordinary (potentially overflow-safe legacy behavior) to `StrictMathWrapper` arithmetic: [5](#0-4) , and a new `SafeExchangeProcessor` implements a BigDecimal/`pow`-based swap curve: [6](#0-5) . The system was clearly designed so that the "hardened" arithmetic is meant to be a safe replacement path, but the flag that enables it also silently deactivates the pre-existing reject/pending-exclusion safety net for the entire Exchange transaction type, rather than layering the two independently the way the modifier chain in Solidity's `whenPaused`/`whenNotPaused` pattern would.

### Impact Explanation
`ExchangeTransactionContract`, `ExchangeCreateContract`, and other Exchange* transactions are reachable by any unprivileged account via a normally signed and broadcast transaction (Wallet/TronJsonRpc entry points), exactly the actor class in scope ("order placer"). Because `pushTransaction`'s explicit `ContractValidateException("ExchangeTransactionContract is rejected")` guard and the block-producer/`processBlock` skip logic are all keyed off the same bypassable predicate, once `allowHardenExchangeCalculation` is turned on, every node in the network resumes accepting and executing Exchange trades through the historically disabled TRC10 Bancor-relay pool. Any residual precision, rounding, or invariant defect in the exchange formula (the exact defect class that originally justified disabling this feature with a hard block at the mempool/block-production/block-application layers) can again be exploited to mint unbacked token balances or drain a trading pool's reserves — i.e., theft of funds or an unbacked-balance condition, both explicitly in scope as concrete impacts.

### Likelihood Explanation
Triggering this requires only that `allowHardenExchangeCalculation` be set to `1` (a chain-wide, committee-controlled dynamic parameter) and then submitting an ordinary signed `ExchangeTransactionContract` transaction — no special privileges beyond being a normal order/transaction broadcaster are needed once the flag is set. Given that the flag exists specifically to re-enable Exchange functionality, any chain that turns it on to allow "hardened" (safer) exchange math simultaneously and unintentionally removes the unconditional rejection safety net for exchange transactions, making exploitation trivial for any user as soon as the flag is active.

### Recommendation
Decouple the "use hardened math" flag from the "allow exchange transactions at all" kill-switch. `isExchangeTransaction()` (and consequently `pushTransaction`, the block-packing skip, and `rejectExchangeTransaction`) should not be short-circuited by `allowHardenExchangeCalculation`; the rejection/skip logic should be controlled by its own dedicated flag (e.g., an explicit `allowExchangeTransaction`), so that enabling hardened arithmetic does not implicitly re-enable a code path that was deliberately disabled for safety.

### Proof of Concept
The bypass is already codified in a repository test, confirming the predicate's dual role and the exact toggle that disables the reject/skip gates: [7](#0-6) 
1. With `allowHardenExchangeCalculation` at its default (`0`), `isExchangeTransaction()` on an `ExchangeTransactionContract` transaction returns `true`, so `pushTransaction` throws `ContractValidateException("ExchangeTransactionContract is rejected")` (Manager.java:897-899) and the transaction never enters a block.
2. Setting `allowHardenExchangeCalculation` to `1` (chain-wide dynamic property) makes `isExchangeTransaction()` return `false` for the same transaction, per the assertion in `isExchangeTransactionBypassedWhenHardenedEnabled`.
3. With the predicate now false, the transaction is no longer rejected by `pushTransaction`, is no longer skipped in the block-packing loop (Manager.java:1732-1734), and is no longer screened out by `rejectExchangeTransaction` in `processBlock` (Manager.java:1884-1885) — allowing any signed `ExchangeTransactionContract` from an ordinary account to execute against `MarketSellAssetActuator`/`ExchangeTransactionActuator`'s exchange math, which is exactly the previously-disabled functionality.

    // Default: hardened disabled (==0) -> contract is treated as exchange

        (boolean) m.invoke(dbManager, exchange));

    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
    Assert.assertFalse("Exchange tx must be bypassed when hardened enabled",
        (boolean) m.invoke(dbManager, exchange));

    // Reset
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
