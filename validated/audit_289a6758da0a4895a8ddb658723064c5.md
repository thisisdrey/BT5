Based on the code, the binding claimed to be broken does not break — `check_extension_enabled` gates every `w_execute_extension` call correctly, and there is no path from zero enabled extensions to a nonzero state.

**Binding traced:** `w_execute_extension(request)` → `execute_extension` → `self.check_extension_enabled(&env::predecessor_account_id())?` → `self.0.has_extension(account_id)` = `self.0.extensions.contains(account_id)`. [1](#0-0) 

`check_extension_enabled` and `has_extension` only return `Ok`/`true` if the predecessor is already a member of `State::extensions`; if `extensions` is empty, `contains` is `false` for every possible predecessor, so the call fails at `check_extension_enabled` before `execute_request`/`execute_op`/`add_extension` is ever reached, regardless of the `WalletOp` payload. [2](#0-1) [3](#0-2) 

The scenario in the question — a legitimately-added extension later calling `w_execute_extension` with `WalletOp::AddExtension{account_id: <second attacker account>}` — is not a privilege-escalation bug but the documented, intentional design: extensions "have full control over the wallet-contract instance and can be added/removed by the signer **or other installed extensions**." [4](#0-3) 

`add_extension` itself only mutates the `BTreeSet` and emits an event; it does not perform any additional authorization check, but it is only reachable through `execute_op`, which is only reachable through `execute_request`, which is only reachable through `execute_extension`'s enablement gate (or `execute_signed`'s signature/nonce gate for `Actor::SignedRequest`). [5](#0-4) 

So the chain "empty `extensions` → attacker predecessor calls `w_execute_extension` → `AddExtension`" cannot occur: the FIRST extension must already be present in `State::extensions` (via legitimate owner-authorized `AddExtension` op, itself gated by either a valid signature via `w_execute_signed` or another already-enabled extension), which is precisely the "authorised actor" the binding requires. There is no unprivileged, never-enabled account that can reach `add_extension`.

### No vulnerability found for this question.

The claimed escalation path (zero enabled extensions → nonzero) does not exist: `check_extension_enabled`/`has_extension` unconditionally reject any predecessor not already present in `State::extensions`, so `add_extension` is unreachable without a prior legitimate authorization (signature or an already-enabled extension). The described "fan-out" scenario where an already-authorized extension enables a further extension is intentional, documented behavior (extensions have "the same full power ... as the original signer"), not a privilege escalation from an unauthorized state, and does not violate the authorization binding.

    fn set_signature_mode(&mut self, enable: bool, actor: Actor<'_>) -> Result<()> {
        if self.0.signature_enabled == enable {
            return Err(Error::ThisSignatureModeAlreadySet);
        }
        self.0.signature_enabled = enable;
        self.check_lockout()?;

        WalletEvent::SignatureModeSet {
            enabled: enable,
            by: actor,
        }
        .emit();

        Ok(())
    }
