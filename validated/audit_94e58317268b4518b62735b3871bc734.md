### Title
Non-constant-time authorization header comparison enables timing side-channel auth bypass on fast-call-read endpoint - (File: stackslib/src/net/api/fastcallreadonly.rs)

### Summary
`RPCFastCallReadOnlyRequestHandler::try_parse_request` compares the attacker-supplied `Authorization` header against the configured secret using standard `String`/`&str` inequality (`auth_header != password`), which is not constant-time. No `subtle`-style constant-time comparison is used anywhere else in the source tree either (only appears as a transitive `Cargo.lock` dependency), so this leaky comparison pattern is not mitigated at any layer above the handler.

### Finding Description
At `stackslib/src/net/api/fastcallreadonly.rs:105-110`, the handler extracts the `authorization` header from the HTTP preamble and checks it against `self.auth` (`password`) with a plain `!=` comparison: ` [1](#0-0) `. Rust's default `PartialEq` for `String`/`&str` delegates to byte-slice comparison, which typically short-circuits at the first length mismatch or first differing byte rather than always comparing the full buffer in constant time. This route is reachable by any unprivileged remote party who can connect to the node's RPC port and issue `POST /v3/contracts/fast-call-read/<address>/<contract>/<function>` requests with attacker-chosen `Authorization` header values — no prior secret, peer key, or admin role is required. By measuring per-request response-time deltas over many attempts, an attacker can incrementally determine the position of the first mismatching byte and reconstruct `self.auth` byte-by-byte, faster than pure brute force over the secret's keyspace. No other check (length caps, signature checks, canonical-tip resolution) intervenes before this comparison, and the codebase does not use a constant-time comparison primitive (e.g., the `subtle` crate) anywhere in its own source, only as an incidental transitive dependency in `Cargo.lock`.

### Impact Explanation
Successful secret recovery yields a full authentication bypass on the intentionally auth-gated `fast-call-read` endpoint. Once `self.auth` is known, the attacker can freely invoke `try_handle_request`, which runs unbounded read-only Clarity contract-call execution (`chainstate.maybe_read_only_clarity_tx` / `with_readonly_clarity_env`, `stackslib/src/net/api/fastcallreadonly.rs:203-230`) with `LimitedCostTracker::new_free()`, bypassing the endpoint's intended access control. This matches the "auth bypass" Critical-impact category and is repeatable indefinitely once the secret is recovered.

### Likelihood Explanation
The endpoint is reachable by any remote, unprivileged client capable of opening an RPC connection to the node — no peer/config/tip state is required beyond the node having `auth` configured (a precondition of the endpoint being enabled at all). The attack requires the ability to measure timing across many requests; while real-world network jitter raises the practical bar, the underlying comparison provides no constant-time guarantee, so the primitive itself is genuinely exploitable in low-jitter conditions (e.g., attacker colocated on the same LAN/host, or averaging over many samples). Attacker cost is bounded to sending repeated HTTP requests with varying header values — no privileged role, node key, or StackerDB slot is needed.

### Recommendation
Replace the direct `!=` string comparison with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq` (`auth_header.as_bytes().ct_eq(password.as_bytes()).into()`), or an equivalent fixed-time byte comparison that does not short-circuit on length or content mismatch. Apply the same fix to the other endpoints using the identical pattern (`blockreplay.rs`, `blocksimulate.rs`, `postblock_proposal.rs`, `postblock_v3.rs`, `txsimulate.rs`) for consistency.
