### Title
Missing Ownership Verification of `RelayFromAddr` in `handleCreateRelayRequest` Allows Relay State Poisoning - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest()` in `relay_manager.go` never verifies that the `RelayFromAddr` field of an incoming `CreateRelayRequest` control message actually belongs to the certificate-verified identity of the peer (`h`) that sent it. Any authenticated Nebula peer (with a valid CA-signed cert for *their own* address) can claim an arbitrary third-party VPN address as `RelayFromAddr` and cause the receiving node to register that peer's tunnel as the relay path for the claimed (unowned) address, poisoning the receiver's relay state without ever proving ownership of that address via a CA-signed certificate.

As a result, `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` binds the *authenticated tunnel to peer `h`* as the relay path for the *arbitrary claimed address `from`*: [3](#0-2) 

This mirrors the reported bug class exactly: a security invariant (an address may only be associated with the peer that legitimately owns/is certified for it) is enforced along the legitimate path (`StartRelays` always sets `RelayFromAddr = f.myVpnAddrs[0]`, the sender's own certified address): [4](#0-3) 
but is never re-validated when the control message is *received and processed*, allowing the invariant to be bypassed via the network-facing message path — analogous to the LP share requirement being enforced only for one flow and not for the alternate flow (transfers) in the original report.

The Relay/HostInfo abstractions confirm that relay identity is meant to be tied to certificate ownership (`Relay.PeerAddr` is used later by `QueryVpnAddrsRelayFor` for routing decisions and by `handleCreateRelayResponse` to look up `peerHostInfo := rm.hostmap.QueryVpnAddr(relay.PeerAddr)`): [5](#0-4) [6](#0-5) 
None of this logic re-derives or checks `from`/`PeerAddr` against the sending HostInfo's actual certificate-backed `vpnAddrs`.

### Impact Explanation
An attacker holding a valid Nebula certificate for their own address can send a `CreateRelayRequest` claiming to be any other, unrelated VPN address (`RelayFromAddr` = victim's address) to any node willing to act as a relay target/terminal. The victim node (or any relay in the mesh) will then record the attacker's own tunnel as the trusted relay path (`Established` Terminal relay) for that spoofed address, with no certificate proving the attacker actually controls it. Subsequent relay-routing decisions that consult this state (e.g. `QueryVpnAddrsRelayFor`, `handleCreateRelayResponse`) can direct traffic intended for the real address holder toward the attacker's tunnel instead, resulting in remote relay-state poisoning and potential interception/black-holing of relayed traffic for a certificate the attacker does not hold — a hostmap/relay address trust bypass reachable by any peer without needing a CA-signed certificate for the victim address.

### Likelihood Explanation
Exploitation only requires that the attacker be a valid, authenticated Nebula peer able to reach a node acting as (or willing to become) a relay — no possession of the victim's private key or certificate is needed, and no special timing or race condition is required. The control-message path (`header.Control` / `NebulaControl_CreateRelayRequest`) is always reachable once a normal encrypted tunnel exists between attacker and target, making this straightforward to trigger in any deployment that uses relays (`relay.am_relay`/`relay.use_relays`).

### Recommendation
In `handleCreateRelayRequest` (and symmetrically in `handleCreateRelayResponse`), verify that the claimed `RelayFromAddr` (or `RelayToAddr`, depending on role) is actually contained in the sending `HostInfo`'s certificate-derived `vpnAddrs` (`h.vpnAddrs`) before calling `AddRelay`/updating relay state. Reject the control message if the claimed address is not one the sender's certificate authorizes, mirroring the existing self-address check (`f.myVpnAddrsTable.Contains(from)`) but validating ownership against `h`'s certificate instead of only excluding the local node's own addresses.

### Proof of Concept
1. Attacker `A` establishes a normal, legitimately authenticated Nebula tunnel to node `T` (T is reachable as a relay target, e.g. `am_relay` or simply the intended terminal endpoint).
2. Attacker crafts a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: <victim V's address>, RelayToAddr: <T's address>, InitiatorRelayIndex: <attacker-chosen index>}` and sends it over the existing authenticated tunnel via `header.Control` (bypassing `StartRelays`, which normally would only ever set `RelayFromAddr` to the sender's own address).
3. `T.handleCreateRelayRequest` sees `target == T` is itself, and since no existing relay entry maps `from = V` yet, calls `AddRelay(..., h=<A's HostInfo>, ..., from=V, TerminalType, Established)`, registering `A`'s tunnel as the trusted relay path to `V` in `T`'s hostmap — without ever validating that `A`'s certificate covers `V`.
4. Any later relay lookups on `T` for target `V` (`QueryRelayForByIp(V)` / `QueryVpnAddrsRelayFor`) will resolve to attacker `A`'s tunnel, diverting traffic intended for `V`.

		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.

		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return

	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return

func (hm *HostMap) QueryVpnAddrsRelayFor(targetIps []netip.Addr, relayHostIp netip.Addr) (*HostInfo, *Relay, error) {
	hm.RLock()
	defer hm.RUnlock()

	// This runs per relayed packet, so check the primary with a single map probe and only consult
	// moreHosts when the primary can't relay for us.
	h, ok := hm.Hosts[relayHostIp]
	if !ok {
		return nil, nil, errors.New("unable to find host")
	}

	for _, targetIp := range targetIps {
		r, ok := h.relayState.QueryRelayForByIp(targetIp)
		if ok && r.State == Established {
			return h, r, nil
		}
	}

	if list, ok := hm.moreHosts[relayHostIp]; ok {
		// list[0] is the primary we already checked
		for _, h := range list[1:] {
			for _, targetIp := range targetIps {
				r, ok := h.relayState.QueryRelayForByIp(targetIp)
				if ok && r.State == Established {
					return h, r, nil
				}
			}
		}
	}

	return nil, nil, errors.New("unable to find host with relay")
