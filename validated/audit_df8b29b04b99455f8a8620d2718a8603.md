Audit Report

## Title
XCM `ERC20Transactor` credits/moves the requested `amount` instead of the actual ERC20 balance delta, allowing fee-on-transfer/deflationary tokens to desynchronize the shared checking-account backing - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke `IERC20::transfer` on an arbitrary `pallet-revive`-deployed contract and, on a `true` boolean return, unconditionally treat the full requested `amount` as moved, without ever reading the actual balance delta on the shared `TransfersCheckingAccount`. `ERC20Matcher`/`IsLocalAccountKey20` impose no restriction preventing a deflationary/fee-on-transfer contract from being used this way, since matching is purely based on the location being a local `AccountKey20`. [1](#0-0) [2](#0-1) [3](#0-2) 

## Finding Description
In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall { to: checking_address, value: amount }` against the arbitrary ERC20 `asset_id`, and on `is_success == true` unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the full requested `amount` into the XCM holding register with no re-read of `balanceOf(checking_account)` before/after the call. [4](#0-3) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the shared `TransfersCheckingAccount` to the beneficiary and returns `Ok(surplus)` purely based on the boolean `transfer` return value, again without checking that the beneficiary actually received `amount`. [5](#0-4) 

The matcher chain that feeds `asset_id`/`amount` into these functions performs no validation of the ERC20's transfer semantics: `MatchedConvertedConcreteId::matches_fungibles` only checks `MatchAssetId::contains(id)` (i.e., `IsLocalAccountKey20`, which is purely a location-shape check for `(0, [AccountKey20 { .. }])`) and converts the nominal `Fungible(amount)` value from the XCM `Asset` — it never consults on-chain ERC20 state. [6](#0-5) [7](#0-6) 

Because `TransfersCheckingAccount` is a single pooled account shared across all users and all XCM operations touching a given ERC20 (configured once per runtime, e.g. `ERC20TransfersCheckingAccount` in Asset Hub Westend's `xcm_config.rs`), any deflationary/fee-on-transfer token can cause the XCM engine's belief about held value to diverge from the checking account's real balance, and that divergence is paid for out of the pooled balance contributed by other users of the same token. [8](#0-7) 

Existing guards — `ERC20Matcher`/`IsLocalAccountKey20` and `MatchesFungibles::matches_fungibles` — do not mitigate this, as neither performs any balance-delta verification against the ERC20 contract state.

## Impact Explanation
This violates the invariant that contract-held/pooled value transferred via public XCM wrappers must conserve value and settle exactly to the amount actually moved. Any unprivileged account can deploy a `pallet-revive` ERC20 contract with fee-on-transfer/deflationary `transfer()` semantics (returning `true` while moving less than `amount`), then drive XCM programs (`WithdrawAsset`/`DepositAsset`, reserve-transfers) that get credited or paid out based on the nominal `amount` rather than what was truly moved into/out of the shared checking account, letting an attacker drain real value contributed by other legitimate holders of that token, or complete cross-chain transfers backed by funds never actually received.

## Likelihood Explanation
Deploying an arbitrary Solidity/PVM contract via `pallet-revive` and having it recognized by `ERC20Matcher` requires no privileged origin or governance action — any account can deploy a contract at a fresh `AccountKey20` address and immediately have it accepted by `IsLocalAccountKey20`. Exploitation only requires normal XCM extrinsics (`pallet_xcm::execute`, `transfer_assets`, etc.) routed through `ERC20Transactor`, making this highly feasible and repeatable.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the ERC20 balance of the checking account/beneficiary immediately before and after the `IERC20::transfer` call, and use the observed delta rather than the requested `amount` to build `Erc20Credit`/determine success. If the delta is less than `amount`, either fail the transact or credit only the actual delta (mirroring the `Precision::BestEffort` pattern in `substrate/frame/support/src/traits/tokens/fungible/regular.rs`).

## Proof of Concept
1. Deploy a `pallet-revive` ERC20 contract whose `transfer(to, amount)` burns/redirects 5% of `amount` but still returns `true`; it is matched by `ERC20Matcher`/`IsLocalAccountKey20` since it is a local `AccountKey20`.
2. Submit an XCM program with `WithdrawAsset` of `1000` units of this token from the attacker's account. `withdraw_asset_with_surplus` calls `transfer(checking_account, 1000)`, which moves only 950 to the checking account (burning 50) but returns `true`.
3. The code builds `Erc20Credit(1000)` into the XCM holding register — 50 more than the checking account received.
4. A subsequent `DepositAsset` in the same program calls `deposit_asset_with_surplus`, which executes `transfer(beneficiary, 1000)` from the shared checking account; if the checking account holds balance contributed by other users' deposits of the same token, this succeeds, paying 1000 real tokens for only 950 actually deposited — net theft of 50 tokens from the pooled checking account, repeatable to drain further.

impl<
		AssetId: Clone,
		Balance: Clone,
		MatchAssetId: Contains<Location>,
		ConvertAssetId: MaybeEquivalence<Location, AssetId>,
		ConvertBalance: MaybeEquivalence<u128, Balance>,
	> MatchesFungibles<AssetId, Balance>
	for MatchedConvertedConcreteId<AssetId, Balance, MatchAssetId, ConvertAssetId, ConvertBalance>
{
	fn matches_fungibles(a: &Asset) -> result::Result<(AssetId, Balance), MatchError> {
		let (amount, id) = match (&a.fun, &a.id) {
			(Fungible(ref amount), AssetId(ref id)) if MatchAssetId::contains(id) => (amount, id),
			_ => return Err(MatchError::AssetNotHandled),
		};
		let what = ConvertAssetId::convert(id).ok_or(MatchError::AssetIdConversionFailed)?;
		let amount =
			ConvertBalance::convert(amount).ok_or(MatchError::AmountToBalanceConversionFailed)?;
		Ok((what, amount))
	}
}
