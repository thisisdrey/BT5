### Title
Dust-filling a victim's per-account token list desynchronizes tracked collateral/debt set from what the user can ever hold, blocking new deposits/issues and enabling forced liquidation - (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
The Sei OCC bug is a "tracked set vs iterated set" mismatch: validation stops early without confirming that all expected items were visited, so validation passes on a stale/incomplete view. The Metronome analog lives in `Pool.debtPositionOf`/`depositOf`/`debtOf` (`contracts/Pool.sol:227-288`), which compute account health by iterating only over the tracked sets `depositTokensOfAccount` / `debtTokensOfAccount`. These sets are maintained by balance-change hooks in `DepositToken._transfer`/`_mint`/`_burn` and `DebtToken._mint`/`_burn`. Membership in the tracked set is enforced by `onlyIfAdditionWillNotReachMaxTokens`, which caps an account's combined deposit+debt tokens at `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). Because `DepositToken.transfer`/`transferFrom`/`deposit(..., onBehalfOf_)` are callable by any EOA and unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` on a 0→nonzero balance (`contracts/DepositToken.sol:518-520,486-488`), an attacker can forcibly grow a victim's tracked set to the cap. Once full, every operation that would add a new entry reverts with `UserReachedMaxTokens`, so the set of tokens the victim's health check can ever account for is permanently smaller than the set the victim may need — the exact "iterated set ≠ expected set" class.

### Finding Description
`addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens(account_)` (`contracts/Pool.sol:204-220`), which enforces the combined cap (confirmed by `test/Pool.test.ts:1386-1416`, which fills the account with 15 deposit + 15 debt tokens then observes `UserReachedMaxTokens`). There is no opt-out for the recipient:

- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is 0 (`contracts/DepositToken.sol:518-520`). `transfer` and `transferFrom` are public and reachable via any allowance (`contracts/DepositToken.sol:348-376`). Even if the attacker holds no deposit tokens, `deposit(amount_, onBehalfOf_)` lets anyone mint dust to a victim (`contracts/DepositToken.sol:211-237`).
- Once the victim's list is full: (a) `deposit`/`transfer` of any *new* collateral type reverts inside `_mint`/`_transfer` when `addToDepositTokensOfAccount` throws; (b) `DebtToken.issue` reverts inside `_mint` when `addToDebtTokensOfAccount` throws for a synth the victim hasn't borrowed before (`contracts/DebtToken.sol:598-600`).

The invariant that breaks is health-check completeness: `debtPositionOf` is only sound if the tracked set can always reflect every balance the account needs to hold — the same assumption the Sei OCC patch re-established by requiring iterated keys to equal expected keys.

### Impact Explanation
An underwater victim position whose existing collateral cannot be topped up further (e.g., needs a *different*, cheaper collateral or needs to deposit after a price move) is permanently prevented from restoring health; the attacker then calls `Pool.liquidate` (`contracts/Pool.sol:537-596`) as the liquidator and collects `_toLiquidator` plus the liquidation incentive — direct loss of victim collateral value, attacker-profitable. Separately, the victim is permanently blocked from issuing any new synthetic asset (liveness on `issue`/`mint`). This is bounded-cap griefing, not gas/unbounded-loop DoS, and requires no privileged role.

### Likelihood Explanation
Requires the pool to have enough enabled deposit/debt tokens to fill the cap (30 combined). On deployments with < 30 supported tokens total the attack is unreachable; check per-chain `getDepositTokens()`/`getDebtTokens()` counts. Cost is dust amounts of each registered deposit token (or dust underlying deposits). No pause flag blocks `transfer`, and `transferFrom`/`deposit` on behalf of a victim do not require consent.

### Recommendation
Make the victim's list membership consent-based or symmetric: e.g., allow accounts to remove entries themselves (`removeFromDepositTokensOfAccount` callable by the account when balance is dust/zero), exempt the recipient-side `add` when `amount_` is below a dust threshold, or let `deposit`/`issue` of tokens already held proceed (only enforce the cap on *new* entries, which is already the behavior — but also let victims evict attacker-forced entries by transferring dust out, which works today since the sender-removal path is victim-controlled; the missing piece is that victims cannot prevent insertion, so consider a per-account allowlist or a `toggleTokenTracking` escape hatch).

### Proof of Concept
Hardhat, forking the test harness in `test/Pool.test.ts`:

```ts
// given: pool has >= 30 enabled deposit/debt tokens
// attacker fills victim's tracked sets
for (const dt of depositTokens.slice(0, 15)) {
  await depositToken_contract[dt].deposit(1, victim.address) // dust to victim
}
for (const st of synths.slice(0, 15)) {
  // attacker deposits own collateral + issues dust debt? debt can't be pushed to victim,
  // so fill remaining slots with more deposit tokens instead
}
await depositTokenX.deposit(1, victim.address) // 30th entry

// victim's position turns unhealthy (price move)
await masterOracle.updatePrice(met.address, newMetPrice)

// victim tries to deposit NEW collateral type to restore health -> reverts
await expect(depositTokenY.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// attacker liquidates victim and earns incentive
await pool.connect(attacker).liquidate(msEth.address, victim.address, repay, msdMET.address)
```

Caveat: reachability depends on deployment config (≥30 registered tokens); on pools with fewer tokens there is no divergence and no impact. If that condition does not hold on the deployed configuration in scope, this should be downgraded/rejected.
