### No vulnerability found for this question.

Investigation summary: the premise misdescribes how `bandwidth_request.to_shard` is produced and ignores an existing mitigation for exactly this scenario.

- `bandwidth_request.to_shard` is not attacker-controlled data smuggled through receipt size. It is generated by the sender shard's own honest runtime code in `generate_bandwidth_requests`, which iterates `shard_layout.shard_ids()` of the shard layout valid at generation time [1](#0-0) , and each request's `to_shard` is simply that shard id — never something read from an untrusted receipt payload. Receipt size only affects the request's bitmap of requested bandwidth values, not which shard is targeted [2](#0-1) .
- The exact "receiver shard removed by resharding right after the request is made" scenario is explicitly anticipated and mitigated: `generate_bandwidth_request` folds the parent shard's still-buffered receipts into the bandwidth request for its child shard, so a request destined for a shard id about to disappear via a split is represented under the surviving child shard id instead [3](#0-2) .
- Additionally, buffered receipts left in a parent shard's outgoing buffer after resharding are continuously drained every height via `forward_from_buffer`, which walks parent-shard buffers before current-layout buffers until they're empty, independent of any single dropped request [4](#0-3) .
- The `get_shard_index` failure path in `SchedulerBandwidthRequest::new` (scheduler.rs:605-611) only discards requests referencing shard ids that are genuinely stale/nonexistent in the *current* layout used by the scheduler; because of the parent-buffer-folding mechanism above, a legitimate buffered receipt's bandwidth need is still represented under a valid (child) shard id, so this drop does not strand real receipts [5](#0-4) .
- Test coverage (`slow_test_resharding_v3_large_receipts_towards_splitted_shard`) specifically exercises large buffered receipts to a shard that is split at the resharding boundary, and asserts they are still delivered, corroborating that this exact liveness scenario is guarded against in the existing implementation [6](#0-5) .

Since the attacker cannot control `to_shard`, and the code already contains a specific mechanism to prevent bandwidth requests/buffered receipts from being stranded across a shard split, the described exploit path does not hold up against the actual code.
