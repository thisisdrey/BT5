Audit Report

## Title
`submit_delivery_receipt` pays relayer reward and settles `PendingOrder` even when the Ethereum delivery `success` flag is `false` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`snowbridge_pallet_outbound_queue_v2::Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` that carries an explicit `success: bool` field taken from the Ethereum Gateway's `InboundMessageDispatched` event, but the function body never inspects `receipt.success` before paying the relayer reward and removing the `PendingOrder`. [1](#0-0)  The receipt type itself faithfully decodes the `success` field from the on-chain log, confirming the field is available but simply unused. [2](#0-1) 

## Finding Description
`submit_delivery_receipt` is an unprivileged, `ensure_signed` extrinsic that verifies a cryptographic proof for an Ethereum event log, decodes it into a `DeliveryReceipt`, and unconditionally forwards it to `process_delivery_receipt`. [3](#0-2)  Inside `process_delivery_receipt`, the pallet checks the gateway address, resolves the reward beneficiary, looks up the `PendingOrder` by `nonce`, pays `order.fee` via `T::RewardPayment::register_reward` if `order.fee > 0`, and unconditionally calls `<PendingOrders<T>>::remove(nonce)` before emitting `Event::MessageDelivered` — at no point is `receipt.success` read. [4](#0-3)  The module-level doc comment corroborates that the intended flow is "verify proof → fetch pending order → pay reward → remove order," with no mention of a success check. [5](#0-4)  This means any relayer who submits a valid proof for an `InboundMessageDispatched` event with `success = false` (a legitimate outcome recorded on Ethereum when the dispatched command reverts) will still receive the reward and cause the order to be finalized/removed, exactly as if delivery had succeeded.

## Impact Explanation
This matches the "duplicate settlement or payout" / "public underpriced work" impact categories: the pallet pays out `order.fee` to a relayer for a message whose on-chain execution did not actually succeed, and it permanently discards the `PendingOrder` bookkeeping (`<PendingOrders<T>>::remove(nonce)`) with no distinct handling, retry, or refund path for failed deliveries. The exact corrupted values are the `PendingOrders` map entry keyed by `nonce` (incorrectly removed) and the reward balance paid to `reward_account` (incorrectly credited) despite `receipt.success == false`.

## Likelihood Explanation
Any relayer holding a legitimately generated proof of the `InboundMessageDispatched` event — which the Gateway contract emits on every dispatch attempt, whether it succeeds or reverts — can call `submit_delivery_receipt` with no special privilege beyond `ensure_signed`. The only gate is `T::Verifier::verify`, which validates proof authenticity, not the outcome encoded in the event. This is triggerable during ordinary bridge operation whenever an Ethereum-side dispatch fails, with no forged proof or malicious relayer behavior needed.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only invoke `T::RewardPayment::register_reward` and `<PendingOrders<T>>::remove(nonce)` when `receipt.success == true`. For `receipt.success == false`, either remove the order without paying a reward, or retain the order/emit a distinct failure event (e.g. `MessageDeliveryFailed`) so a downstream mechanism (refund to sender, retry, re-issue) can act on the failure instead of treating it as a successful settlement.

## Proof of Concept
1. `do_process_message` inserts a `PendingOrder { nonce, fee, block_number }` for an outbound message. [6](#0-5) 
2. On Ethereum, the Gateway's dispatch of the inner command reverts, and it emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer generates a valid proof for this log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false` correctly. [7](#0-6) 
5. `process_delivery_receipt` proceeds to pay `order.fee` and remove the `PendingOrder`, emitting `Event::MessageDelivered { nonce }` even though delivery actually failed. [8](#0-7)

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
