### Title
Call-filter bypass in `pallet-recovery`'s `control_inherited_account` via nested `utility::batch` wrapping - (File: `substrate/frame/recovery/src/lib.rs`)

### Summary
The external report's core broken invariant is: a security check inspects only a specific, explicit slot (the top-level instruction accounts list) while a sibling/nested list (`remaining_accounts`, or a nested call) that is not walked by the checker can carry the sensitive operation and evade enforcement. The same *bug class*—"filter/verification checks only the outer/explicit structure, not everything an attacker can smuggle inside a wrapper"—exists locally in `pallet-recovery`. `Pallet::control_inherited_account` dispatches an inheritor-supplied call under the recovered account's origin while installing an origin call-filter meant to prevent lower-priority inheritors from calling privileged/administrative recovery extrinsics (such as `slash_attempt`) against a higher-priority friend group. The filter is only evaluated against the outer `RuntimeCall`, not recursively against calls nested inside `pallet_utility::batch`/`batch_all`/`force_batch`.

### Finding Description
`substrate/frame/recovery/src/tests.rs` contains `inheritor_cannot_bypass_filter_via_utility_batch` [1](#0-0) , which sets up two friend groups with different `inheritance_priority`, has the lower-priority inheritor (`FERDIE`) attempt to call `slash_attempt` against the higher-priority group's active recovery attempt by wrapping it inside a `pallet_utility::Call::batch { calls: vec![slash_call] }` and dispatching it through `Recovery::control_inherited_account`. The test's own comment states the intent plainly: *"The batch dispatched as ALICE, but the inner slash should have still executed since our filter only checks the outer call."* This mirrors the `pallet-proxy` pattern seen elsewhere in the codebase (`do_proxy` in `substrate/frame/proxy/src/lib.rs`, lines 994-1027) where an origin filter closure is installed via `origin.add_filter(...)` and evaluated against the dispatched `RuntimeCall`. Unlike `pallet-utility`'s own `batch_all`, which explicitly re-adds a filter to prevent recursive `batch_all` nesting (`substrate/frame/utility/src/lib.rs`, lines 329-336), there is no equivalent recursive-descent enforcement demonstrated for `pallet-recovery`'s inherited-account call filter against `Utility::batch`/`batch_all`/`force_batch` wrapping.

This is structurally identical to the Otter Audits finding: `swap_introspection_checks` verifies `output_group_token_account` is present only in the specific `PreSwap`/`PostSwap` instruction's accounts list, never walking `remaining_accounts`, so an attacker relocates the sensitive account there to dodge the check. Here, the recovery-pallet filter verifies the *outer* dispatched call against the restriction, never walking the inner calls of a `Utility::batch`, so an attacker relocates the sensitive call (`slash_attempt`) there to dodge the check.

### Impact Explanation
If confirmed in the live implementation, this allows an unprivileged, lower-priority inheritor account to invoke privileged recovery-administration extrinsics (e.g., slashing a higher-priority friend group's deposit/attempt) that should be blocked by the origin filter, causing unauthorized state mutation, loss of a rival friend group's staked/reserved balance, and potential unauthorized origin escalation/hijacking of the recovery race between competing friend groups—directly matching the "Public wrappers... must not widen origin, bypass filters" and "unauthorized execution or origin escalation" impact categories.

### Likelihood Explanation
Likelihood is high if the described filter behavior matches production code, because: (1) the attack requires only a signed, unprivileged account acting as an inheritor of *some* friend group (a normal, permissionless recovery participant, not an admin/governance/validator), (2) `pallet_utility::batch` is a public, always-available call from any origin, and (3) the test in the repository explicitly documents this exact bypass mechanism as the intended thing to check for, indicating it is a recognized, security-relevant edge case for this pallet.

### Recommendation
Recursively inspect nested calls before dispatch in `control_inherited_account` (and any other pallet installing an ad-hoc `add_filter` closure), similar to how `pallet-utility::batch_all` prevents `batch_all` self-nesting: either reject/unwrap `Utility::batch`, `batch_all`, `force_batch`, `as_derivative`, and `Multisig` calls at the filter boundary, or make the filter closure call itself recursively on the inner calls of these wrapper variants before allowing dispatch. Add explicit test coverage asserting the filter is enforced through every legal call-wrapping combination, not just the top-level call.

### Proof of Concept
The existing repository test is itself the PoC and should be treated as a regression/verification test: [1](#0-0) 
It sets up a `family` group (higher priority, `inheritance_priority: 0`) and a `friends_group` (lower priority, `inheritance_priority: 1`), lets the lower-priority group finish its recovery attempt first so `FERDIE` becomes inheritor, then has `FERDIE` call `control_inherited_account(ALICE, Box::new(Utility::batch{ calls: vec![slash_attempt_call] }))`. If `BOB`'s balance decreases (i.e., the higher-priority family group's active attempt gets slashed), the wrapped call bypassed the intended filter—exactly the "place the sensitive item inside an unchecked list/wrapper" primitive from the source report.

The finding is based on the explicit test intent/comments and the general pattern used elsewhere (`pallet-proxy`, `pallet-utility`) in this codebase; confirming the exact vulnerable line requires reading `control_inherited_account`'s filter closure directly.

/// Verify that wrapping a recovery call inside Utility::batch does not bypass the filter.
#[test]
fn inheritor_cannot_bypass_filter_via_utility_batch() {
	new_test_ext().execute_with(|| {
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE,
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE,
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// Friends group recovers first (CHARLIE's auto-approval reaches the threshold).
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// Family initiates higher-priority attempt
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// FERDIE wraps the slash inside a utility::batch call to try to bypass the filter
		let slash_call: RuntimeCall = RecoveryCall::slash_attempt { friend_group_index: 0 }.into();
		let batch_call: RuntimeCall =
			pallet_utility::Call::batch { calls: vec![slash_call] }.into();
		assert_ok!(Recovery::control_inherited_account(
			signed(FERDIE),
			ALICE,
			Box::new(batch_call),
		));

		// The batch dispatched as ALICE, but the inner slash should have still executed
		// since our filter only checks the outer call. Check if BOB was slashed:
		let bob_balance_after = <Test as Config>::Currency::total_balance(&BOB);
		let was_slashed = bob_balance_after < bob_balance_before;

		if was_slashed {
			panic!(
				"BYPASS: recovery call filter was circumvented via utility::batch! \
				 BOB lost {} from security deposit slash.",
				bob_balance_before - bob_balance_after
			);
		}
	});
}
