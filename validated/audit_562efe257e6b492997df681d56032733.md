### Title
`nep_141_storage_balance_callback` fails to refund `caller_deposit` when the NEP-141 `storage_balance_of` cross-contract call fails, permanently stranding the relayer's attached deposit - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The ETH-implicit Wallet Contract emulates ERC-20 `transfer` calls by first querying `storage_balance_of` on the target NEP-141 token and, in the callback, deciding whether a `storage_deposit` is required before doing `ft_transfer`. The callback that handles the `storage_balance_of` result checks `env::promise_result(0)` but, unlike the sibling callback `rlp_execute_callback`, does not refund `caller_deposit` on the `PromiseResult::Failed` branch, leaving any attached NEAR deposit stuck in the wallet contract with no path to reclaim it.

### Finding Description
`inner_rlp_execute` constructs a `CallerDeposit` from `env::attached_deposit()` whenever the predecessor is an external (non-self) relayer: [1](#0-0) 

For an `EthEmulationKind::ERC20Transfer`, execution is routed through a `storage_balance_of` call followed by `nep_141_storage_balance_callback`: [2](#0-1) 

Inside that callback, when the `storage_balance_of` promise fails, the function returns immediately with a failure `ExecuteResponse` and never touches `caller_deposit`: [3](#0-2) 

Compare this to `rlp_execute_callback`, which does correctly refund the caller when a downstream cross-contract call fails: [4](#0-3) 

Because `nep_141_storage_balance_callback`'s failure branch drops `caller_deposit` on the floor instead of issuing a `promise_batch_action_transfer` refund like `rlp_execute_callback` does, any NEAR deposit the relayer attached to the `rlp_execute` call (used, per NEP-145, to fund the `storage_deposit` for a not-yet-registered ERC-20 receiver) is permanently retained by the wallet contract account with no code path to return it to the relayer. This mirrors the reported ERC20 class of bug conceptually — a value-moving/compensating action is not gated on checking whether the "transfer" operation it depends on actually succeeded — except here the missing check causes funds to be silently and permanently trapped rather than an invalid transfer being accepted.

### Impact Explanation
Deposits attached by relayers to fund the NEP-145 storage cost of an ERC-20-emulated transfer become permanently unrecoverable whenever the target token contract's `storage_balance_of` call fails or times out (e.g., the token contract is paused, deleted, out of gas, or otherwise reverts). This is a permanent freezing-of-funds bug reachable purely through the ordinary `rlp_execute` entry point used by any eth-implicit-account holder/relayer, without any privileged access.

### Likelihood Explanation
The path is reached whenever a user submits (via any relayer) an ERC-20 `transfer`-emulated Ethereum transaction with an attached NEAR deposit while the target NEP-141 contract's `storage_balance_of` call is failing at execution time (contract paused/deleted/out of gas/panicking). This is not an attacker-controlled precondition per se, but it is a normal failure mode of an external cross-contract call in a permissionless, asynchronous multi-shard system, so it will occur in production under ordinary conditions (e.g., a token contract briefly overloaded or misbehaving) without requiring any malicious actor.

### Recommendation
In `nep_141_storage_balance_callback`, mirror the refund logic used in `rlp_execute_callback`: on `PromiseResult::Failed`, if `caller_deposit` is `Some`, create a refund promise (`env::promise_batch_create` + `env::promise_batch_action_transfer`) back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the failure `ExecuteResponse`.

### Proof of Concept
1. Deploy the Wallet Contract as the global contract for ETH-implicit accounts and fund an eth-implicit account, as in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/emulation.rs` (`test_erc20_emulation`).
2. Have a relayer submit `rlp_execute(target = <nep141_token>, tx_bytes_b64 = <signed ERC20 transfer to an unregistered receiver>)` with a non-zero attached deposit (used to cover `storage_deposit`), while the target token contract is deleted/paused so that `storage_balance_of` fails (e.g., point `target` at an account with no such contract deployed, or a contract engineered to panic on `storage_balance_of`).
3. Observe: `nep_141_storage_balance_callback`'s `PromiseResult::Failed` branch returns `ExecuteResponse{success:false, ...}` and the attached deposit is not sent back anywhere.
4. Query the relayer's account balance and the wallet contract's balance: the deposit remains on the wallet contract account, with no method exposed to recover it. [3](#0-2)

        &mut self,
        token_id: AccountId,

        caller_deposit: Option<CallerDeposit>,

                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),

                }
            },
        };
