### Title
Weight double-counting via non-canonical duplicate signatures in the TVM `ValidateMultiSign` precompile allows multi-sig threshold bypass - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The OrbitChain hack root cause was a bridge vault that failed to enforce that its signature-threshold check counted only genuinely distinct, valid signer approvals — allowing the attacker to satisfy the multi-sig requirement without the intended number of independent authorizations. java-tron's `ValidateMultiSign` TVM precompile has the analogous flaw: its duplicate-signature guard compares the *raw signature bytes* rather than the *recovered signer address*, so a single signer's weight can be counted more than once by resubmitting a byte-varied (e.g. padded or malleable) copy of their own valid signature, letting an attacker satisfy `permission.getThreshold()` with fewer independent signers than the account owner configured.

### Finding Description
`ValidateMultiSign.execute` in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` iterates over the caller-supplied `signatures[]` array and accumulates `totalWeight` for each recovered signer address: [1](#0-0) 

For each signature it computes `recoveredAddr` via `recoverAddrBySign`, then builds `sign = merge(recoveredAddr, sign)` and checks:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;   // exact-duplicate byte match -> skip
  }
  MUtil.checkCPUTime();   // otherwise: only a CPU-time guard, no skip!
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
The dedup logic only skips an entry if the *exact byte-for-byte merged signature* (`recoveredAddr || sign`) has already been seen. It does not dedup purely on `recoveredAddr`. Because signature bytes are extracted with an attacker-controlled length via `extractBytesArray`/`extractSigArray`, an attacker can submit the same underlying 65-byte ECDSA signature twice with different trailing/padding byte lengths (or, more rigorously, an ECDSA-malleable variant `(r, N-s, flipped v)` of the same signature). Both entries recover to the identical `recoveredAddr` via `recoverAddrBySign`, but their `sign` byte arrays differ, so the "already seen" check at line 1093 is false, the entry is **not** skipped, and `weight` for that same address is added to `totalWeight` a second (or further) time.

This precompile is reachable by any unprivileged account: any smart contract can invoke it via `validatemultisign(address,uint256,bytes32,bytes[])`, and any transaction broadcaster can call such a contract via `TriggerSmartContract`.

### Impact Explanation
Any account/contract that relies on this precompile to gate privileged operations (e.g., a custody/treasury/bridge-style contract verifying that an Active permission's multi-sig threshold has been met before authorizing a withdrawal) can be tricked into approving an operation using duplicated weight from a single compromised or self-controlled signer key, instead of the number of independent signers actually required by `permission.getThreshold()`. This is a direct analog of the OrbitChain root cause (insufficient enforcement that threshold approvals come from genuinely distinct, valid signers), and can lead to unauthorized approval of fund transfers or other permissioned operations — i.e., theft of funds or unauthorized account operations, matching the accepted impact classes.

### Likelihood Explanation
Exploitation requires no special privileges: the attacker needs to control (or have) a valid signature from just one key that has non-zero weight under the target permission, and can craft the duplicate byte-length variant of that signature trivially (append padding bytes, since `extractBytesArray`/`Rsv.fromSignature` do not require canonical 65-byte length). This is reachable from a plain `TriggerSmartContract` call, i.e. by any anonymous transaction broadcaster/contract caller, with no reliance on validator/witness compromise, making it directly and easily triggerable.

### Recommendation
Change the dedup check in `ValidateMultiSign.execute` (and audit `BatchValidateSign` for the same pattern) to key exclusively on `recoveredAddr`: once an address has contributed weight, skip it unconditionally for the remainder of the loop, rather than only skipping when the exact signature bytes repeat. Additionally, enforce a canonical, fixed signature length (e.g., exactly 65 bytes) before recovery to eliminate the padding-based duplication vector, and consider rejecting malleable `s` values (`s > N/2`) as is standard practice for canonical ECDSA signatures.

### Proof of Concept
1. Configure an account with an `Active` permission requiring `threshold = 2`, with two keys `key1` (weight 1) and `key2` (weight 1).
2. Attacker controls only `key1`. Compute `sign1 = key1.sign(hash)` (65 bytes).
3. Build a second entry `sign2` = `sign1` with one extra padding byte appended (66 bytes) — `extractBytesArray` will still successfully extract it as a distinct byte array, and `recoverAddrBySign` (via `Rsv.fromSignature`) still recovers the same `key1` address since it only consumes the first 65 bytes.
4. Call `validatemultisign(address, permissionId, dataHash, [sign1, sign2])`.
5. In the loop: for `sign1`, `executedSignList` is empty, so weight 1 is added; for `sign2`, `matrixContains(executedSignList, recoveredAddr)` is true (same address), but `matrixContains(executedSignList, merge(recoveredAddr, sign2))` is false (different byte length/content) — so it is *not* skipped, and weight 1 is added again.
6. `totalWeight` becomes 2, which meets `threshold = 2`, even though only `key1` ever produced a valid signature — bypassing the intended 2-of-N multi-sig requirement with just one signer. [2](#0-1)
