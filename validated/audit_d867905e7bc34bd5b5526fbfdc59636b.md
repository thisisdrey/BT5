### Title
Access key nonce is reset on re-creation instead of preserving prior nonce, enabling replay of old signed transactions - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
The `QuestBoard`/`MultiMerkleDistributor` bug is a class of "identifier/counter resets to a fresh baseline on re-creation, silently reopening state that should have stayed closed off." The nearcore analog is the `AccessKey.nonce` field: NEAR's own documentation states that when an access key is deleted and a new key is added that reuses the *same public key*, the nonce of the new key must be seeded with the nonce of the old key to prevent replay of previously signed transactions [1](#0-0) . The actual `action_add_key`/`add_regular_key` implementation does not honor this invariant: it always initializes the new key's nonce from the current block height, with no reference to any nonce the same public key may have had before it was deleted.

### Finding Description
`AccessKey::nonce` doc-comment on the core type repeats the same requirement: "the nonce of the new access key should be equal to the nonce of the old access key. It's required to avoid replaying old transactions again" [2](#0-1) .

However, the runtime's key-creation path never looks at a prior nonce for the public key being (re)inserted. `action_add_key` only checks whether the key **currently** exists (returning `AddKeyAlreadyExists` if so); if it does not currently exist (e.g., because it was just deleted, possibly in an earlier action of the same transaction/receipt, or in a prior transaction), it proceeds straight to `add_regular_key`/`add_gas_key`: [3](#0-2) 

`add_regular_key` unconditionally overwrites the nonce using `initial_nonce_value(block_height)`, which is purely a function of the current block height, not of any previously used nonce for that key: [4](#0-3) [5](#0-4) 

Because nonces are only bumped when a transaction actually executes (`set_access_key` after successful nonce verification), a user can legitimately sign a transaction with an artificially high nonce (well above `(block_height-1)*1e6`) that is never broadcast/executed. If that access key is later deleted and re-added with the same public key (e.g. as a routine key-rotation "delete stale key, add fresh key" pattern), the new key's nonce resets to a value derived only from the current block height — which is typically far lower than the high nonce used in the old, unexecuted transaction. That previously signed-but-unexecuted transaction now satisfies the nonce-freshness check again (`tx.nonce > access_key.nonce`) and becomes replayable, exactly mirroring the QuestBoard `nextID == 0` overwrite scenario where a re-initialized counter/ID space reopens things that should have stayed permanently invalidated.

### Impact Explanation
If an attacker (or the signer's own leaked/old signed payload) replays such a stale transaction after key recreation, it can execute actions the account owner believed were permanently invalidated — including token transfers, function calls, or `Stake`/`DeleteAccount` actions if the key had `FullAccess` — depending on what the old signed transaction authorized. This is a concrete violation of the double-spend/replay-protection guarantee: authorization escalation / replay of a transaction that the state machine's own nonce monotonicity invariant is supposed to prevent forever.

### Likelihood Explanation
This requires: (1) a signer to have previously signed (but not executed) a transaction with a nonce higher than what a freshly-initialized key at a later block height would have, and (2) the same public key being deleted and re-added later. Key rotation reusing the exact same public key is uncommon operational practice (rotation normally uses a new key pair), and an attacker needs possession of the old signed-but-unexecuted transaction bytes. This lowers likelihood relative to a trivially triggerable bug, but it is fully reachable via ordinary `DeleteKey` + `AddKey` actions available to any account holder, with no privileged/validator/node-operator access required.

### Recommendation
When adding an access key whose public key previously existed on the account (tracked via a tombstone/last-nonce record, or simply disallowing re-use of a deleted key's public key), seed the new key's nonce with `max(initial_nonce_value(block_height), old_nonce)` as the documentation requires, rather than unconditionally reinitializing it from block height in `add_regular_key`/`add_gas_key` in `runtime/runtime/src/access_keys.rs`.

### Proof of Concept
1. Account `alice.near` has `FullAccess` key `K` with current on-chain nonce `1_000_000`.
2. `alice` signs (offline, without broadcasting) `Transfer` transaction `Tx_evil` using key `K` with `nonce = 50_000_000_000` (nonce values are only bounded by `u64`/config sanity checks, not tied to current block height at signing time).
3. Later, at block height `H`, `alice` sends `DeleteKey(K)` followed by `AddKey(K, new_permission)` reusing the same public key `K` (e.g. as part of a permission change).
4. `add_regular_key` sets the new key's nonce to `initial_nonce_value(H) = (H-1) * 1_000_000`, which is far below `50_000_000_000` for any realistic block height.
5. `Tx_evil`, previously "unusable" only because it was superseded logically by intent (not because its nonce had actually been consumed), is now broadcast and passes the nonce check (`50_000_000_000 > (H-1)*1_000_000`), executing against the new key's permissions/state and transferring funds without `alice`'s current consent.

Note: I could not fully trace the exact nonce-comparison predicate in `runtime/runtime/src/verifier.rs` due to iteration limits (grep confirmed matches but the relevant lines were not read in full), so the precise comparison operator (`>` vs `>=`) and any additional nonce-ceiling checks tied to block height at verification time were not directly confirmed from source in this session — this should be verified before treating the PoC as fully proven end-to-end.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

pub(crate) fn action_add_key(
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;
    } else {
        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
