### Title
Missing per-peer buffer quota check in `handle_unsolicited_stacks_messages` allows unbounded tenure-bound message buffering - ([File: stackslib/src/net/unsolicited.rs])

### Summary
`handle_unsolicited_sortition_messages` (unsolicited.rs:639-697) explicitly gates buffering with `self.can_buffer_data_message(...)` at lines 649-662 before calling `buffer_sortition_data_message`, but the parallel tenure-bound handler `handle_unsolicited_stacks_messages` (unsolicited.rs:714-760) calls `self.buffer_stacks_data_message(*event_id, neighbor_key, message.clone())` at line 743 with no equivalent quota check beforehand. This breaks the invariant that "messages buffered per peer == messages within the peer's configured buffer quota" for the tenure-bound code path.

### Finding Description
In the sortition-bound retain closure (unsolicited.rs:646-695), each candidate message is only allowed to proceed to `buffer_sortition_data_message` if `buffer && !self.can_buffer_data_message(*event_id, existing_inbox_slice, message)` evaluates false — i.e., the quota check at line 650 must pass. In the tenure-bound retain closure (unsolicited.rs:720-758), which handles messages such as `StackerDBPushChunk` and `NakamotoBlocksData` that could not be validated immediately (e.g., waiting on the next tenure), the code at lines 726-745 goes straight from `handle_unsolicited_stacks_message` to `self.buffer_stacks_data_message(...)` with no call to `can_buffer_data_message` guarding it. A remote, already-authenticated peer (authentication is required by `authenticate_unsolicited_messages`, unsolicited.rs:580-619, but that only checks the peer is a live authenticated conversation, not any per-message content or quota) can therefore keep sending `StackerDBPushChunk` (or other tenure-bound) messages that `handle_unsolicited_stacks_message` marks `to_buffer = true`, and each will be appended to that peer's `pending_messages` inbox with no bound enforced by this code path, unlike the sibling sortition path.

I was not able to fully inspect the bodies of `can_buffer_data_message`, `buffer_stacks_data_message`, and `buffer_sortition_data_message` (defined elsewhere in `unsolicited.rs`/`p2p.rs`) in this session due to tool-call limits, so I cannot confirm with certainty whether `buffer_stacks_data_message` independently re-implements an equivalent quota check internally. Based strictly on the code visible in the `handle_unsolicited_stacks_messages` function body (lines 714-760), no quota check is invoked in that closure before buffering, which is the asymmetry the question describes.

### Impact Explanation
If `buffer_stacks_data_message` does not itself enforce a quota (unverified), a single authenticated remote peer could grow its buffered-message inbox unbounded by repeatedly sending unsolicited `StackerDBPushChunk` messages that fail immediate validation but are deemed bufferable, causing per-connection memory growth on the victim node. This would match a bounded Critical single-connection memory-growth DoS as described in the question, but confirming this requires reviewing `buffer_stacks_data_message`'s implementation, which was not accessible in this session.

### Likelihood Explanation
Precondition is only that the attacker maintain one authenticated P2P connection (no privileged role, secret, or slot ownership required beyond what's needed to become an authenticated conversation partner) and send messages that the tenure-bound handler judges bufferable. Given the asymmetric code structure clearly visible between the two handlers, this is plausible, but I could not verify the actual runtime behavior of `buffer_stacks_data_message` due to incomplete file exploration.

### Recommendation
Add the same `can_buffer_data_message` quota check to `handle_unsolicited_stacks_messages`'s retain closure (mirroring lines 649-662) before calling `buffer_stacks_data_message`, so both sortition-bound and tenure-bound buffering paths enforce the identical per-peer quota.

### Proof of Concept
A Rust test in `stackslib/src/net/tests/relay/nakamoto.rs` or a new test in `unsolicited.rs` would need to: (1) establish an authenticated peer connection, (2) craft N `StackerDBPushChunk` messages where N exceeds the sortition-bound quota constant used by `can_buffer_data_message`, (3) route them through `handle_unsolicited_stacks_messages` with `buffer = true`, and (4) assert `self.pending_messages.get(&(event_id, neighbor_key)).unwrap().messages.len()` exceeds the quota bound (or grows unbounded), matching the same test structure as would be used against `handle_unsolicited_sortition_messages` to demonstrate the discrepancy.
