### Title
Missing origin/ownership validation in `LinkRepositoryToObjectPool` allows cross-repository object disclosure - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
`LinkRepositoryToObjectPool` accepts any independently-valid `Repository` and any independently-valid `ObjectPool` and links them via the alternates mechanism without verifying that the pool actually originates from, or is otherwise authorized for, the target repository. This mirrors the reported bug class: parameters that are supposed to satisfy strict relationship invariants ("same underlying/maturity", "deployed by the same factory") are assumed to be validated by a trusted off-chain/upstream caller, but the on-chain (server-side) code performs no cross-parameter consistency check.

### Finding Description
The RPC handler only validates each argument in isolation: [1](#0-0) 

`s.locator.ValidateRepository` checks that `repository` is a well-formed, existing repository, and `poolForRequest` (via `objectpool.FromProto`) only checks that the pool path is a valid pool repository: [2](#0-1) [3](#0-2) 

Neither of these checks establishes any relationship between `repository` and the `ObjectPool` being linked — there is no verification that the pool was created from this repository (or a fork/ancestor of it), that both share the same object hash/format, or that they reside on the same storage. The actual linking logic in `Link()`/`getRelativeObjectPath()` simply writes a Git alternates file pointing at the pool's `objects` directory: [4](#0-3) [5](#0-4) 

Since Git alternates make every object in the pool directly readable from the linked repository (via normal fetch/clone/cat-file operations), any caller able to invoke this RPC with a repository they have write access to and an arbitrary but valid pool path can graft that repository onto an unrelated pool, gaining read access to all objects contained in that pool — including objects from repositories that never intended to share them. This is the same insufficient-validation-of-pool-parameters bug class as the external report: creation/linking parameters that must satisfy relationship invariants are not checked at the point where they take effect.

Note: enforcement of "correct" pool-to-repo pairing is expected to happen in the calling layer (e.g., GitLab Rails, which normally only calls this RPC for legitimate fork relationships), analogous to the "provided by the system owner ... validated off-chain" language in the original report. Gitaly itself performs no on-chain/in-process verification.

### Impact Explanation
A caller that can invoke `LinkRepositoryToObjectPool` (reachable through the standard fork-creation flow, or directly via a crafted RPC field) with a repository under their control and a pool path belonging to a different, unrelated repository, can cause that repository to gain persistent read access to all objects in the target pool through Git's alternates mechanism. This is a cross-repository object access vulnerability: object-level access controls (e.g., project visibility) are not enforced at the alternates level once linked, so a repository can be silently backed by pool objects it should not have access to. Additionally, mixing pools/repos with different object hash formats (SHA1 vs SHA256) — also unchecked — is unsupported by Git and can leave the affected repository in an inconsistent/corrupted state, a DoS-style impact on that repository.

### Likelihood Explanation
`LinkRepositoryToObjectPool` is a `MUTATOR` RPC exposed on the standard `ObjectPoolService`, exercised as part of the normal fork-creation workflow (`TestCompleteForkCreationFlow`), so it is reachable by any caller with access to the gRPC surface (typically the internal API layer, but the RPC itself performs no relationship checks). Exploitation only requires knowledge of a valid pool's storage/relative path, which is derivable/guessable from repository naming conventions used elsewhere in the codebase (e.g., `@pools/xx/yy/<hash>.git` layout enforced by `IsPoolRepository`).

### Recommendation
Add server-side verification in `LinkRepositoryToObjectPool` (or in `objectpool.Link`) that:
- The repository and the object pool share the same object hash/format (`ObjectHash`).
- The repository and pool reside on the same storage.
- Ideally, that the pool's recorded/derived origin matches the repository being linked (or the repository is an authorized descendant of that origin), rather than trusting the caller-supplied pairing unconditionally.

### Proof of Concept
1. Attacker creates (or already owns) `Repo A` and, via the standard fork flow, causes `Pool A` to be created from `Repo A` (`CreateObjectPool`).
2. Attacker creates `Repo B` (also under their control) and directly calls `LinkRepositoryToObjectPool` with `Repository = Repo B` and `ObjectPool = Pool X`, where `Pool X` is an existing, unrelated pool belonging to a victim's repository hierarchy (path guessable/known from the deterministic `@pools/<hash>` naming scheme).
3. Since `LinkRepositoryToObjectPool` only validates `Repo B` and `Pool X` independently and never checks their relationship, the call succeeds and writes `Repo B/objects/info/alternates` pointing at `Pool X/objects`.
4. Attacker fetches/clones `Repo B`; all objects present in `Pool X` (including any objects from other pool members that were never explicitly authorized for `Repo B`) become retrievable through `Repo B`.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

func getRelativeObjectPath(ctx context.Context, pool, repo *localrepo.Repo) (string, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting repository path: %w", err)
	}

	relPath, err := filepath.Rel(filepath.Join(repoPath, "objects"), poolPath)
	if err != nil {
		return "", err
	}

	return filepath.Join(relPath, "objects"), nil
}
