### Title
Unbounded array allocation from attacker-controlled length word in `ValidateMultiSign`/`BatchValidateSign` precompiles before TIP-854 activation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` (address `0x...0a`) and `BatchValidateSign` (address `0x...09`) TVM precompiled contracts parse a "count" word directly out of attacker-supplied calldata and use it, unvalidated, to size a Java array (`new byte[len][]`) before any sanity check is performed. This mirrors the Redis RESP bug (ALPINE-CVE-2021-32675): a length/count field taken from an unauthenticated request drives memory allocation before the request is validated.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read `len` from an arbitrary 32-byte word supplied in the precompile's calldata and immediately allocate an array of that size: [1](#0-0) 

`extractSigArray` has the identical pattern: [2](#0-1) 

Both `ValidateMultiSign.execute` and `BatchValidateSign.doExecute` only bound-check the length **before** allocation when `VMConfig.allowTvmSelfdestructRestriction()` (TIP-854) is active; otherwise they call the unguarded `extractBytesArray`/`extractBytes32Array` directly and only check `signatures.length > MAX_SIZE` **after** the array has already been constructed: [3](#0-2) [4](#0-3) 

Since `len = words[offset].intValueSafe()` reads directly from a caller-supplied word, an attacker can set it to `0x7FFFFFFF` regardless of the actual size of the calldata (`getEnergyForData` charges energy based only on `data.length`, not on the embedded `len` value): [5](#0-4) 

The only precondition is `offset <= words.length - 1` (i.e. the word at `offset` must physically exist in the calldata), which requires calldata of just a few words — the `len` value itself can be arbitrarily large independent of calldata size.

### Impact Explanation
A crafted TVM call to precompile `0x...09` or `0x...0a` (reachable from any TriggerSmartContract transaction, or from an unauthenticated/unsigned `triggerConstantContract`/`eth_call` query) causes the node to attempt to allocate an array of up to ~2^31 references before any size limit is enforced. This is a resource-exhaustion vector that can OOM/crash a full node or degrade its ability to serve API/TVM calls — the same class of unauthenticated resource-exhaustion issue described in CVE-2021-32675. It is currently mitigated only when the TIP-854 (`allowTvmSelfdestructRestriction`) chain parameter has been activated via governance; any deployment where that proposal is not yet active remains exposed.

### Likelihood Explanation
High on networks where TIP-854 has not been activated: the precompiles are reachable with a small, cheap TVM call (tiny calldata, low/negative computed energy for the crafted shape), requiring no special privileges — any account (or even an unsigned constant call) can trigger it. The presence of extensive test coverage explicitly built around the "TIP-854" guard (`testTip854RejectsMalformedCalldata`, `testTip854OuterFrameContainment`) confirms the project's own awareness that the unguarded path is unsafe and that the fix is conditional on the proposal flag.

### Recommendation
Move the `sigArraySize`/`addrArraySize` bound checks (against `MAX_SIZE`) so they are unconditionally applied *before* calling `extractSigArray`/`extractBytesArray`/`extractBytes32Array`, independent of `VMConfig.allowTvmSelfdestructRestriction()`. Alternatively, add an intrinsic bound check inside `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` themselves (e.g., reject `len` values that exceed what the actual `data`/`words` length could support, or cap at the contracts' own `MAX_SIZE`) so the fix does not depend on chain-parameter activation state.

### Proof of Concept
1. Craft calldata for `BatchValidateSign` (address `0x...09`) with `words[1]` (the "sig array offset" word) pointing to a small offset (e.g. word index 5), and place at that word index a value of `0x7FFFFFFF`.
2. Ensure the total calldata length is only large enough to satisfy `offset <= words.length - 1` (a handful of 32-byte words), keeping `getEnergyForData` cheap.
3. Invoke the contract via `CALL` from any Solidity contract using `triggerConstantContract` (no signature/fee required) or a signed `TriggerSmartContract` transaction, with `VMConfig.allowTvmSelfdestructRestriction()` not activated (TIP-854 not enabled).
4. Observe `extractBytesArray`/`extractSigArray` execute `new byte[2147483647][]`, driving large memory allocation on the node before the subsequent `signatures.length > MAX_SIZE` check is ever reached.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
