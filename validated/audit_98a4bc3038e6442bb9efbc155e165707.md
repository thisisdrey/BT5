### Title
Attacker-triggered `GlobalContractDoesNotExist` in `DeterministicStateInitAction` commits a phantom zero-balance account while silently dropping the attached deposit with no refund or burn accounting - ([File: runtime/runtime/src/deterministic_account_id.rs])

### Summary
`action_deterministic_state_init` first creates and commits a zero-balance `Account` into `maybe_account` before attempting to deploy the global contract, then calls `use_global_contract` via `deploy_deterministic_account`. If the referenced `GlobalContractIdentifier` does not exist, `result.result` is set to an error and the function returns early at the `if result.result.is_err() { return Ok(()); }` check, before the deposit-refund logic (`check_storage_stake` / `Receipt::new_balance_refund`) ever runs.

### Finding Description
In `runtime/runtime/src/deterministic_account_id.rs`:
- When `maybe_account` is `None`, a new zero-balance account is created via `create_deterministic_account(Balance::ZERO, ...)` and inserted with `maybe_account.insert(new_account)` [1](#0-0) .
- `deploy_deterministic_account` is then called, which invokes `use_global_contract(...)`; if the referenced global contract does not exist, `result.result` becomes `Err(...)` and the function returns `Ok(())` without touching account balance [2](#0-1) .
- Back in `action_deterministic_state_init`, the `if result.result.is_err() { return Ok(()); }` guard fires immediately, entirely skipping the deposit-application/refund block (`check_storage_stake`, `deposit_refund`, and `Receipt::new_balance_refund`) [3](#0-2) .

The net effect: the newly created `Account` (amount = 0) remains in `maybe_account`/`state_update` for the derived `0s...` id, but `action.deposit` — the value attached by the attacker's `DeterministicStateInitAction` — is neither added to the account balance, nor pushed as a refund receipt, nor recorded in `result.tokens_burnt`. This is an unprivileged, fully attacker-controlled path: any client can submit a transaction/receipt with a `DeterministicStateInitAction` whose `state_init.code` is a `GlobalContractIdentifier::AccountId`/`CodeHash` that does not correspond to a deployed global contract, and with `deposit > 0`. No existing signature, nonce, access-key, or action-validation check inspects whether the referenced global contract exists prior to execution — this is only detected at execution time inside `use_global_contract` (per `docs/RuntimeSpec/Actions.md` describing `GlobalContractDoesNotExist` as an **Execution Error**, not a validation error) [4](#0-3) .

### Impact Explanation
This is a value-conservation violation: an attacker's attached deposit disappears from the ledger without appearing in the recipient account's balance, in `tokens_burnt`, or in an outgoing refund receipt. Depending on whether the runtime's balance-conservation check (comparing total incoming vs outgoing balances per receipt/chunk application) is enforced as a hard consensus-level invariant, the consequence is either (a) silent token destruction — a to-value-conservation bug reducible to a "token loss" bounty category, or (b) if the runtime's balance checker does catch the discrepancy, an unrecoverable `BalanceMismatchError`/`StorageInconsistentState` when applying the chunk, which would halt block/chunk production for that shard. Both outcomes are in-scope impacts (permanent fund loss or shard halt). I was not able to fully confirm from the available index whether the balance-conservation check in the runtime treats this class of mismatch as a hard panic versus something silently tolerated; this should be independently verified against the actual balance-checker logic (`runtime/runtime/src/lib.rs` / balance-checking module) before finalizing severity.

### Likelihood Explanation
Trivial and fully reachable by an unprivileged actor: no special permissions, keys, or validator access are required — only the ability to submit a `DeterministicStateInitAction` (directly, or via a delegate/meta-transaction) with a nonexistent `GlobalContractIdentifier` and any nonzero `deposit`. The attack is repeatable at will and costs only the attacker's own deposit plus gas, so the "attacker" effect is self-inflicted loss unless a downstream balance-check failure escalates it into a shard-halting panic affecting others.

### Recommendation
In `action_deterministic_state_init`, when `deploy_deterministic_account` (or `use_global_contract`) sets `result.result` to an error, either:
1. Do not commit the freshly created zero-balance account into `maybe_account`/`state_update` (roll back the "uninit" account creation on failure), and issue a `Receipt::new_balance_refund` for the full `action.deposit` before returning, or
2. If the account creation must remain committed (e.g., for idempotency/lazy-init semantics), explicitly refund `action.deposit` via `Receipt::new_balance_refund(receipt.balance_refund_receiver(), action.deposit)` on this error branch before returning, mirroring the refund logic already present later in the function.

### Proof of Concept
Unit/integration test plan (extends existing `test-loop-tests/src/tests/deterministic_account_id.rs` patterns, e.g. `test_deterministic_state_init_invalid_derived_id`):
1. Set up `TestEnv` without deploying any global contract (or deploy one and reference a different, non-existent `CodeHash`/`AccountId`).
2. Construct a `DeterministicAccountStateInit::V1` whose `code` is a `GlobalContractIdentifier` that does not exist on-chain.
3. Derive the corresponding `0s...` account id and submit a `SignedTransaction::deterministic_state_init` (or via delegate action) with `deposit = Balance::from_near(1)`.
4. Execute via `env.try_execute_tx`, assert the outcome fails with `ActionErrorKind::GlobalContractDoesNotExist` (or equivalent).
5. Assert failure of value conservation: check `env.get_account_state(det_account).amount == 0` (phantom account exists with zero balance), check no refund receipt was generated back to the sender (sender's balance decreased by the full deposit and never recovers it), and check `result.tokens_burnt`/outcome does not record the deposit anywhere. Expected (bug-confirming) assertion: `sender_balance_before - sender_balance_after == deposit + gas_cost` with no corresponding increase in `det_account` balance nor `tokens_burnt`, demonstrating the deposit vanished from `sum(account balances) + tokens_burnt + outstanding_receipts`.
