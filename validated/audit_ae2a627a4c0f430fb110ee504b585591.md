### Title
New Collection Owner Unable to Update Royalty Payee After Transfer — (`aptos-move/framework/aptos-token-objects/sources/aptos_token.move`)

---

### Summary

When a transferable collection (created via `create_fixed_collection_as_owner` / `create_unlimited_collection_as_owner`) is transferred to a new owner via `object::transfer`, the `Collection.creator` field is never updated. All royalty-management and metadata-mutation entry points in `aptos_token.move` gate access via `authorized_borrow_collection`, which checks the immutable `Collection.creator` field rather than the current object owner. As a result, the new owner is permanently locked out of updating the royalty `payee_address`, while the original creator retains the ability to redirect royalties at will.

---

### Finding Description

**Root cause — immutable `creator` field vs. mutable object owner**

`Collection` stores the original creator at construction time and never updates it: [1](#0-0) 

```move
struct Collection has key {
    creator: address,   // set once, never updated
    ...
}
```

`create_collection_internal` writes this field from the deploying signer: [2](#0-1) 

`create_fixed_collection_as_owner` / `create_unlimited_collection_as_owner` explicitly enable ungated transfer so the collection object can be sold or gifted: [3](#0-2) 

After `object::transfer` the `ObjectCore.owner` field is updated to the new owner, but `Collection.creator` remains the original address.

**Broken gate in `authorized_borrow_collection`**

Every royalty and metadata mutation entry point in `aptos_token.move` calls: [4](#0-3) 

```move
inline fun authorized_borrow_collection<T: key>(collection: &Object<T>, creator: &signer): &AptosCollection {
    ...
    assert!(
        collection::creator(*collection) == signer::address_of(creator),
        error::permission_denied(ENOT_CREATOR),
    );
    ...
}
```

This check compares against the **immutable original creator**, not `collection.owner()`. The new owner will always fail this assertion.

**Affected entry points (all use `authorized_borrow_collection`)**

- `set_collection_royalties` / `set_collection_royalties_call` — cannot redirect `Royalty.payee_address`
- `set_collection_description`
- `set_collection_uri` [5](#0-4) 

**Royalty struct — the stale payee** [6](#0-5) 

```move
struct Royalty has copy, drop, key {
    numerator: u64,
    denominator: u64,
    payee_address: address,   // still points to original creator after transfer
}
```

Marketplaces read `royalty::payee_address` and send royalty payments there. After a collection transfer the `payee_address` is frozen at the original creator's address with no way for the new owner to change it.

---

### Impact Explanation

Every secondary-market sale of a token from the transferred collection pays royalties to the **original creator**, not the new owner. The new owner suffers a permanent, ongoing loss of APT (or any fungible asset used as payment) proportional to the royalty rate and trading volume. Additionally, the original creator retains the ability to call `set_collection_royalties` and redirect the payee to any address, including after having sold the collection.

This maps directly to the allowed impact category: *"Direct theft … of APT, fungible assets … or other user-controlled on-chain assets."*

---

### Likelihood Explanation

The `create_fixed_collection_as_owner` and `create_unlimited_collection_as_owner` functions exist precisely to support collection transfers. Any collection created through these paths and subsequently transferred triggers the issue automatically — no special attacker action is required beyond a normal `object::transfer` call. The scenario (creator sells a collection to another party) is a standard NFT market operation.

---

### Recommendation

Replace the `collection::creator()` check in `authorized_borrow_collection` with a check against the current object owner, consistent with how `create_common_with_collection_as_owner` already handles minting authorization:

```move
// current (broken for transferred collections)
assert!(
    collection::creator(*collection) == signer::address_of(creator),
    error::permission_denied(ENOT_CREATOR),
);

// fixed
assert!(
    collection.owner() == signer::address_of(creator),
    error::permission_denied(ENOT_CREATOR),
);
```

Alternatively, add a separate `authorized_borrow_collection_as_owner` path (mirroring the existing minting split) so that both the original creator and the current owner can manage royalties, depending on which creation path was used.

---

### Proof of Concept

```
1. Alice calls create_fixed_collection_as_owner("MyCollection", royalty=5%, payee=Alice).
   → Collection.creator = Alice, Royalty.payee_address = Alice, ObjectCore.owner = Alice.

2. Alice sells the collection: object::transfer(alice, collection, bob).
   → ObjectCore.owner = Bob.
   → Collection.creator = Alice  (unchanged).
   → Royalty.payee_address = Alice  (unchanged).

3. Bob tries to redirect royalties:
   set_collection_royalties_call(bob, collection, 5, 100, bob_address)
   → authorized_borrow_collection checks collection::creator(collection) == bob
   → collection::creator returns Alice ≠ bob  → ABORT (ENOT_CREATOR).

4. A buyer purchases a token from the collection on any royalty-aware marketplace.
   → royalty::payee_address(&royalty) == Alice
   → Royalty payment sent to Alice, not Bob.
   → Bob receives zero royalties despite owning the collection.

5. Alice (original creator, no longer owner) can still call set_collection_royalties
   and redirect payee_address to any address, including after the sale.
```

    inline fun authorized_borrow_collection<T: key>(collection: &Object<T>, creator: &signer): &AptosCollection {
        let collection_address = collection.object_address();
