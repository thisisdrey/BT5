## Title
Attached deposit permanently locked when relayer address-check fails for another eth-implicit target - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

## Summary
The eth-implicit `WalletContract::rlp_execute` entry point is `#[payable]` and accepts an attached deposit from any external caller, tracking it in a `CallerDeposit` struct so it can be refunded if the emulated Ethereum transaction ultimately fails. However, one specific failure branch inside `address_check_callback` returns an error `ExecuteResponse` directly without ever forwarding or refunding the tracked `CallerDeposit`, permanently trapping the attached NEAR in the wallet contract's own balance.

## Finding Description
`rlp_execute` is marked `#[payable]` and captures `env::attached_deposit()` into an `ExecutionContext`, then builds an optional `CallerDeposit { account_id: predecessor_account_id, yocto_near }` via `CallerDeposit::new` whenever the caller is not the wallet itself: [1](#0-0) [2](#0-1) 

For an `EOABaseTokenTransfer` whose target is another eth-implicit account (`address_check: Some(address)`), the flow calls the address registrar and continues in `address_check_callback`, passing along the `caller_deposit`: [3](#0-2) 

Inside `address_check_callback`, if the registrar lookup reveals the target address actually corresponds to an existing named account (`maybe_account_id.is_some()`), and the current relayer is *not* using the wallet's own access key (`env::signer_account_id() != current_account_id`), the function returns a failure `ExecuteResponse` immediately — dropping `caller_deposit` on the floor with no refund promise created: [4](#0-3) 

By contrast, the only place a `CallerDeposit` is ever actually refunded is in `rlp_execute_callback`'s `PromiseResult::Failed` arm: [5](#0-4)  and this branch is never reached for the `address_check_callback` early-return path described above, nor for the sibling `create_ban_relayer_promise`/`ban_relayer` path, which also drops any tracked deposit since `ban_relayer` does not accept or refund `caller_deposit` at all: [6](#0-5) [7](#0-6) 

There is no other withdraw/rescue method on `WalletContract` (its only public/private methods are `get_nonce`, `rlp_execute`, `address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, and `ban_relayer`), so once a deposit is absorbed into the wallet's balance on this failure path, it cannot be recovered through the contract's own logic. This is a direct architectural analog to the reported Solidity issue: a payable entry point whose failure path fails to route funds back out, with no compensating withdraw mechanism.

## Impact Explanation
Funds attached by an external caller (e.g., a relayer fronting gas/fee compensation for an eth-implicit-account transaction, or a user directly calling `rlp_execute`) can become permanently stuck in the target eth-implicit wallet contract's account balance whenever: the transaction is an `EOABaseTokenTransfer` to another eth-implicit address, that address actually resolves to a named account in the registrar, and the relayer submitting the transaction is not using the wallet's own access key. This is a permanent freezing-of-funds condition reachable via an ordinary external call to a deployed (eth-implicit) wallet contract — not requiring any privileged role.

## Likelihood Explanation
This requires a specific but realistic combination: a relayer (not holding a delegated access key for the target wallet) submits an RLP-encoded EOA transfer whose destination decodes to an address that turns out to correspond to an existing named Near account rather than a plain eth-implicit account, with a non-zero deposit attached. This can occur from ordinary usage (e.g. a relayer processing a signed Ethereum-style transaction against a stale/incorrect address-to-account mapping) without any malicious intent, making it a plausible operational occurrence rather than a purely theoretical edge case.

## Recommendation
In `address_check_callback`, when returning the `"Invalid target: target is address corresponding to existing named account_id"` failure, issue a refund promise for `caller_deposit` (mirroring the logic in `rlp_execute_callback`'s `Failed` arm) before returning the `ExecuteResponse`. Similarly, ensure `ban_relayer`/`create_ban_relayer_promise` paths also propagate and refund any pending `caller_deposit` so that a faulty-relayer determination never silently forfeits an external caller's attached deposit. As a general safeguard, ensure every early-return failure path in `rlp_execute`, `address_check_callback`, and `nep_141_storage_balance_callback` refunds `caller_deposit` when present.

## Proof of Concept
1. Deploy an eth-implicit wallet contract W (address A) and fund a relayer account R (not holding an access key on W).
2. Register a named account `bob.near` with the address registrar such that its associated Ethereum address is `0xBEEF...` (i.e., `lookup("0xBEEF...")` returns `Some("bob.near")`).
3. Construct and sign (as the wallet's Ethereum owner) an RLP transaction that is an `EOABaseTokenTransfer` targeting address `0xBEEF...` where the `target` account id passed to `rlp_execute` is some eth-implicit account whose hash matches `0xBEEF...` (triggering `address_check: Some(0xBEEF...)`).
4. R calls `W.rlp_execute(target, tx_bytes_b64)` attaching, e.g., 1 NEAR as deposit; `predecessor_account_id = R`, so `CallerDeposit::new` returns `Some(CallerDeposit { account_id: R, yocto_near: 1 NEAR })`.
5. This triggers the `address_registrar.lookup` cross-call, which returns `Some("bob.near")`, hitting `maybe_account_id.is_some()` branch in `address_check_callback`.
6. Since `env::signer_account_id() != current_account_id` (R submitted the transaction directly, not via W's own access key), the callback returns `ExecuteResponse { success: false, error: Some("Invalid target: ...") }` immediately, at line 168-173 of `lib.rs`, without creating any transfer promise back to R.
7. Result: R's 1 NEAR deposit remains in W's account balance permanently; there is no subsequent call path in `WalletContract` that can move it back to R.
