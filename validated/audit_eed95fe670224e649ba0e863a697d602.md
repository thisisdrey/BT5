### Title
`isPrimary()` gating of pre-receive/post-receive Rails callbacks and quorum-stopping trusts an unauthenticated, client-forgeable `Transaction.Primary` field in the hooks payload - ([File: internal/gitaly/hook/prereceive.go])

### Summary
`GitLabHookManager.PreReceiveHook` / `PostReceiveHook` / `ReferenceTransactionHook` decide whether to run Rails access checks, custom hooks, and reference-counter/vote logic based on `isPrimary(payload)`, which merely reads `payload.Transaction.Primary` out of a client-supplied, unsigned, base64-JSON blob (`GITALY_HOOKS_PAYLOAD`) carried in the RPC's `EnvironmentVariables` field. This is structurally the same bug class as the reported issue: a field that is supposed to describe the *origin/role* of a request (queue origin in the Optimism report; primary/secondary transaction role here) is trusted by downstream privileged logic without being validated against the actual origin of the call.

### Finding Description
`HooksPayload` is serialized purely as base64(JSON) with no integrity protection: [1](#0-0) 

It is decoded from the RPC's environment variables with no signature check: [2](#0-1) 

The `HookService` (`PreReceiveHook`, `PostReceiveHook`, `ReferenceTransactionHook`, `UpdateHook`) is reachable via the same external, token-authenticated gRPC socket used by ordinary clients, as acknowledged directly in Gitaly's own test comments: [3](#0-2) 

`isPrimary` reads the `Primary` field straight out of that unauthenticated payload: [4](#0-3) 

This decides:
- Whether `PreReceiveHook` calls Rails' `/allowed` and `pre_receive` endpoints and runs custom hooks (only executed "on primary"): [5](#0-4) 
- Whether `PostReceiveHook` calls the Rails post-receive endpoint and, more critically, whether it commits/re-opens the storage transaction identified by attacker-controlled `payload.TransactionID`: [6](#0-5) [7](#0-6) 
- Whether `ReferenceTransactionHook` records/updates reference state and votes with Praefect via `m.voteOnTransaction`: [8](#0-7) 

Because `Transaction`, `TransactionID`, `UserDetails` (GL user ID/username/protocol), and the embedded `Repo` (including `GitObjectDirectory`/`GitAlternateObjectDirectories` quarantine paths) all come from this same forgeable payload, an authenticated caller (any client holding the ordinary Gitaly auth token — the same token gitlab-shell/Workhorse use for all RPCs, not a role-restricted "internal-only" credential) can construct a `PreReceiveHookRequest`/`PostReceiveHookRequest`/`ReferenceTransactionHookRequest` with a crafted environment payload that:
- Falsely claims `Primary: false` to suppress the Rails `/allowed` and `pre_receive`/`post_receive` calls and custom hook execution while still driving a real reference-transaction vote, or
- Falsely claims `Primary: true` to force a second, out-of-band pre-receive/post-receive Rails round trip and an early transaction commit for a `TransactionID` guessed/observed from a concurrent legitimate push, or
- Substitutes arbitrary `UserDetails.UserID`/`Username`/`Protocol` values in the request sent to Rails' `/allowed` endpoint, and arbitrary `GitObjectDirectory`/`GitAlternateObjectDirectories` quarantine paths, feeding fabricated "origin" metadata into the access-control decision Rails is asked to make.

This mirrors the reported bug class precisely: an origin/role-describing field is not cross-checked against the mechanism that is supposed to establish it (in the CTC, whether the tx actually came via `enqueue()`; here, whether the call actually originates from the Gitaly-internal hook process on the storage's primary node for a live transaction), so downstream logic (gas/opcode attribution there; access-check gating, hook execution gating, and transaction commit/vote gating here) can be made to evaluate incorrectly.

### Impact Explanation
An attacker with a valid Gitaly auth token (the same credential required for ordinary repository RPCs — not a privileged, internal-only secret) can invoke `HookService` RPCs directly and manipulate the effective role/identity Gitaly believes the call has. Depending on which field is forged, consequences include: bypassing Rails' `pre_receive` access checks for what appears to be a legitimate push (by suppressing them via `Primary: false` while still voting/committing on a real in-flight transaction), causing spurious extra Rails callbacks/commits against a `TransactionID` tied to someone else's concurrent push (cross-transaction interference / potential DoS of that push), or supplying forged `UserDetails`/repository object-directory metadata to the `/allowed` access-check call. This can corrupt the access-control decision or transaction lifecycle for legitimate pushes without the attacker needing to compromise any node.

### Likelihood Explanation
Exploitation requires only an ordinary, authenticated gRPC client capable of calling Gitaly (the same trust level used for regular pushes/fetches) — no leaked internal secret, no MITM, and no privileged/administrative access is needed, since `HookService` is exposed on the same externally-reachable, token-authenticated socket as all other services, as Gitaly's own tests document. The payload format is plain, unauthenticated JSON, so crafting a malicious payload requires no special capability beyond reading the (public, versioned) struct layout.

### Recommendation
Do not trust role/identity/queue-like fields (`Transaction.Primary`, `TransactionID`, `UserDetails`, and the embedded `Repo`) that arrive solely via the client-controlled `EnvironmentVariables` of `HookService` RPCs. Either (a) stop serving `HookService` on the external, client-authenticated socket and restrict it to the internal socket as already flagged in Gitaly's own code comments and issue https://gitlab.com/gitlab-org/gitaly/-/issues/3746, or (b) cryptographically sign/HMAC the `HooksPayload` at creation time (`NewHooksPayload`/`Env()`) using a secret only Gitaly's own hook-invocation path knows, and verify that signature in `HooksPayloadFromEnv` before trusting `Primary`, `TransactionID`, or `UserDetails`, rejecting any hook RPC whose payload fails verification or whose declared transaction/role does not match server-side state.

### Proof of Concept
1. Obtain a valid Gitaly auth token in the same way any legitimate client (gitlab-shell/Workhorse) does (this is not a privileged/internal-only secret; it authenticates all RPCs).
2. Connect directly to Gitaly's externally reachable gRPC endpoint and call `HookService.PostReceiveHook` (or `PreReceiveHook`/`ReferenceTransactionHook`) with a `PostReceiveHookRequest` whose `EnvironmentVariables` contains a self-crafted `GITALY_HOOKS_PAYLOAD=<base64 JSON>` where the JSON directly sets `"transaction": {"id": <observed/guessed TransactionID>, "node": "<any>", "primary": true}` and arbitrary `"user_details"` fields — bypassing `NewHooksPayload`/`.Env()` entirely since no signature ties the payload to a legitimate hook invocation.
3. Observe that `isPrimary(payload)` in `internal/gitaly/hook/transactions.go` (lines 12-17) returns `true` based solely on the forged field, causing `postReceiveHook`/`preReceiveHook` (which call the Rails `/allowed`, `pre_receive`, `post_receive` endpoints and commit the referenced storage transaction) to execute even though the request did not originate from Gitaly's own primary-node hook invocation for that transaction.

I was not able to fully confirm within the available exploration whether Praefect's routing layer independently re-validates or strips a client-supplied `Transaction`/`TransactionID` before a request reaches the `HookService` implementation when passing through Praefect (as opposed to a direct connection to a Gitaly node), so the exact blast radius through a full Praefect-fronted deployment versus a direct Gitaly connection is uncertain and would need further verification.

// HooksPayloadFromEnv extracts the HooksPayload from the given environment
// variables. If no HooksPayload exists, it returns a ErrPayloadNotFound
// error.
func HooksPayloadFromEnv(envs []string) (HooksPayload, error) {
	encoded, ok := lookupEnv(envs, EnvHooksPayload)
	if !ok {
		return HooksPayload{}, ErrPayloadNotFound
	}

	decoded, err := base64.StdEncoding.DecodeString(encoded)
	if err != nil {
		return HooksPayload{}, err
	}

	var jsonPayload jsonHooksPayload
	if err := json.Unmarshal(decoded, &jsonPayload); err != nil {
		return HooksPayload{}, err
	}

	var repo gitalypb.Repository
	err = protojson.Unmarshal([]byte(jsonPayload.Repo), &repo)
	if err != nil {
		return HooksPayload{}, err
	}

	payload := jsonPayload.HooksPayload
	payload.Repo = &repo

	// If no RequestedHooks are passed down to us, then we need to assume
	// that the caller of this hook isn't aware of this field and thus just
	// pretend that he wants to execute all hooks.
	if payload.RequestedHooks == 0 {
		payload.RequestedHooks = AllHooks
	}

	return payload, nil
}

func (p HooksPayload) Env() (string, error) {
	repo, err := protojson.Marshal(p.Repo)
	if err != nil {
		return "", err
	}

	jsonPayload := jsonHooksPayload{HooksPayload: p, Repo: string(repo)}
	marshalled, err := json.Marshal(jsonPayload)
	if err != nil {
		return "", err
	}

	encoded := base64.StdEncoding.EncodeToString(marshalled)

	return fmt.Sprintf("%s=%s", EnvHooksPayload, encoded), nil
}

	var tx storage.Transaction
	if payload.TransactionID > 0 {
		tx, err = m.txRegistry.Get(payload.TransactionID)
		if err != nil {
			return fmt.Errorf("get transaction: %w", err)
		}
	}

	var phase voting.Phase
	switch state {
	// We're voting in preparing state to tell Praefect that the reference changes are ready,
	// although they are not locked yet. At this stage, we can serialize write transactions by
	// acquiring a lock for the transaction and releasing it only when the transaction is
	// committed or aborted. Other transactions must wait for the lock.
	case ReferenceTransactionPreparing:
		phase = voting.Preparing
	// We're voting in prepared state to tell Praefect we've locked the reference changes and
	// queued them for the transaction. We can abort the transaction if needed.
	case ReferenceTransactionPrepared:
		phase = voting.Prepared

		if tx != nil {
			updates, err := parseChanges(objectHash, bytes.NewReader(changes))
			if err != nil {
				return fmt.Errorf("parse changes: %w", err)
			}

			initialValues := map[git.ReferenceName]git.Reference{}
			for reference, update := range updates {
				if update.OldOID != "" {
					initialValues[reference] = git.NewReference(reference, update.OldOID)
				} else {
					initialValues[reference] = git.NewSymbolicReference(reference, update.OldTarget)
				}
			}

			// Only record the initial values of the reference in the prepare step as this
			// change hasn't yet been committed.
			if err := tx.RecordInitialReferenceValues(ctx, initialValues); err != nil {
				return fmt.Errorf("record initial reference value: %w", err)
			}
		}
	// We're also voting in committed state to tell Praefect we've actually persisted the
	// changes. This is necessary as some RPCs fail return errors in the response body rather
	// than as an error code. Praefect can't tell if these RPCs have failed. Voting on committed
	// ensure Praefect sees either a missing vote or that the RPC did commit the changes.
	case ReferenceTransactionCommitted:
		phase = voting.Committed

		if tx != nil {
			updates, err := parseChanges(objectHash, bytes.NewReader(changes))
			if err != nil {
				return fmt.Errorf("parse changes: %w", err)
			}

			if err := tx.UpdateReferences(ctx, updates); err != nil {
				return fmt.Errorf("update references: %w", err)
			}
		}
	default:
		return nil
	}
