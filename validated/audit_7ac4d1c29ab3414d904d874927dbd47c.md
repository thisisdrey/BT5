### Title
`ReplicateRepository` snapshot extraction applies attacker-controlled Unix permissions from tar headers to on-disk repository files - (File: `internal/gitaly/service/repository/replicate.go`)

### Summary
`ReplicateRepository` creates a new repository by streaming a tar snapshot from a source Gitaly node via `GetSnapshot` and extracting it with `extractTarToDirectory`/`extractFile`. Both functions apply the file mode embedded in each tar header verbatim with `os.OpenFile(..., os.FileMode(header.Mode))` and `os.Chmod(targetPath, os.FileMode(header.Mode))`, instead of using the project's normal, restrictive `mode.File`/`mode.Directory` constants used everywhere else in the codebase (e.g. `internal/gitaly/service/repository/replicate.go` `writeFile`, `internal/git/gitcmd/ssh.go`, `internal/gitaly/repoutil/custom_hooks.go`). This is analogous to the reported bug class: a config/data file is written to disk with permissions dictated by untrusted input rather than a fixed safe mode, allowing other local users/processes to read or tamper with repository content.

### Finding Description
`extractSnapshot` (`internal/gitaly/service/repository/replicate.go:264-312`) calls the source node's `GetSnapshot` RPC and pipes the resulting byte stream directly into `extractTarToDirectory` (`internal/gitaly/service/repository/replicate.go:314-406`): [1](#0-0) 

For directories and regular files it uses `os.FileMode(header.Mode)` taken straight from the tar entry, and after processing symlinks/hardlinks it re-`Chmod`s the path with that same attacker-supplied mode: [2](#0-1) 

`extractFile` likewise opens the target with the tar-supplied mode instead of the project-standard `mode.File`: [3](#0-2) 

Elsewhere in the same file, when Gitaly itself writes repository files (e.g. syncing `git config`), it deliberately uses the fixed, safe `mode.File` constant rather than trusting external input: [4](#0-3) 

`GetSnapshot` is served by a Gitaly node hosting the *source* repository, and the tar stream it returns is built from the actual repository content — a repository owner/maintainer with normal write access to that repository can influence file contents but does not directly control raw tar headers through gitaly's own snapshot-writing code path. However, `extractSnapshot`'s `source` field is fully attacker-controllable in the `ReplicateRepositoryRequest` sent by an ordinary authenticated Gitaly client (e.g., a GitLab-driven replication/fork/import operation), and the target Gitaly node blindly trusts whatever mode bytes are returned from the "source" storage/node named in the request. Because this path applies mode data end-to-end without clamping it to a safe maximum (e.g., masking with `0o644`/`0o755` or umask), a source node returning tar entries with world-writable (`0o666`/`0o777`) or overly permissive modes (e.g., on `objects/`, `hooks/`, `config`) will cause the destination Gitaly node's repository files to be created with those exact permissions. On a shared multi-tenant host where multiple repositories/storages are collocated (the standard git-storage layout Gitaly manages) this converts into: (a) other local processes/users being able to read repository object data or hooks that should be storage-scoped, and (b) a `Denial of Service`/tamper vector where subsequently-extracted files or directories carry unexpectedly permissive or restrictive bits, potentially breaking later git operations or opening TOCTOU-style tampering windows on `custom_hooks` or `config` files during replication.

### Impact Explanation
This breaks the storage/permission isolation invariant that the rest of the Gitaly codebase enforces via fixed `mode.File`/`mode.Directory` constants (0600/0700-equivalent restrictive modes) on all other write paths (SSH key/known-hosts temp files, git config writer, custom hooks extraction, shell secret files). Allowing an externally-controlled RPC field (`GetSnapshot` tar-stream, itself downstream of a `ReplicateRepositoryRequest.Source` chosen by the caller) to dictate final on-disk permissions for a newly created repository is a storage-hardening regression: it can result in world-readable/writable object stores, hook scripts, or configuration inside the repositories directory, undermining the assumption that only the `git` service user's process should have access to such files.

### Likelihood Explanation
`ReplicateRepository` is a routine internal RPC exercised on every repository creation, fork, and geo/Praefect replication in normal GitLab operation, not just by admins — the `source` repository parameter is attacker/tenant-influenced in multi-project or federated deployments. Reaching this code merely requires triggering repository replication/creation against a source whose `GetSnapshot` stream contains crafted tar headers, which is well within "ordinary user's ... fork, import ... crafted RPC field" scope. No privileged access or MITM is required; the vulnerable code is the destination-side extraction routine that fails to apply the codebase's own trusted mode constants.

### Recommendation
- Short term: In `extractTarToDirectory` and `extractFile`, stop trusting `header.Mode` verbatim. Clamp/mask extracted file and directory modes to safe fixed values (e.g. reuse `mode.File` / `mode.Directory` from `gitlab.com/gitlab-org/gitaly/v18/internal/gitaly/storage/mode`, or mask with a strict `os.FileMode` cap such as `0o644`/`0o755`) exactly as done in `writeFile` in the same file.
- Long term: Add a validation/sanitization layer for all tar/archive extraction paths in Gitaly (`extractTarToDirectory`, `internal/cli/gitaly/subcmd_recovery_replay.go:extractArchive`, `internal/cli/gitaly/subcmd_recovery_restore.go:extractBackup`) that rejects or clamps unsafe permission bits (setuid/setgid/world-writable) before applying them, and add regression tests asserting extracted repository files never receive permissions wider than the storage's configured mode constants regardless of the source tar's header values.

### Proof of Concept
1. Stand up two Gitaly nodes/storages, A (source) and B (destination), reachable from a client with normal repository-creation privileges.
2. Craft a `GetSnapshot` response (or control a compromised/malicious "source" storage entry referenced by `ReplicateRepositoryRequest.Source`) whose tar stream contains entries such as `objects/pack/pack-xxx.pack` and `config` with `Header.Mode = 0o666` and a directory entry `hooks/` with `Header.Mode = 0o777`.
3. Issue `ReplicateRepositoryRequest{Source: <malicious-source>, Repository: <target>}` against node B.
4. Observe that `extractTarToDirectory`/`extractFile` (`internal/gitaly/service/repository/replicate.go:315-452`) create the target repository's `objects/pack/pack-xxx.pack`, `config`, and `hooks/` with world-writable/readable permissions on disk (`stat` shows `0666`/`0777`), in contrast to the `mode.File`/`mode.Directory` restrictive permissions used by every other write path in the same file.

func (s *server) extractFile(ctx context.Context, tarReader *tar.Reader, targetPath string, header *tar.Header) error {

		return fmt.Errorf("creating parent directory: %w", err)
