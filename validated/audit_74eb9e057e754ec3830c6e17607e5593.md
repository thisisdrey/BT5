### Title
Unbounded/unverified attachment content accepted from remote peer's GET /v2/attachments/{hash} response, bypassing `attachments_max_size` and hash-integrity check - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the Atlas subsystem downloads an attachment from a remote peer via `GET /v2/attachments/{content_hash}`, the response is decoded and inserted into `AtlasDB` without ever checking `AtlasConfig.attachments_max_size` or verifying that the returned content actually hashes to the requested `content_hash`. This lets any peer serving an attachment-download request store arbitrarily large, arbitrary content permanently in the victim's Atlas database.

### Finding Description
The equality the config is supposed to enforce is: `stored content.len() <= atlas_config.attachments_max_size` for every row in `AtlasDB`'s `attachments` table. This is enforced in exactly one place, `AtlasDB::should_keep_attachment` [1](#0-0)  — but that function is only invoked from the local `POST /v2/transactions` path in `posttransaction.rs`, never from the peer-to-peer attachment download path.

The download path is: `AttachmentsDownloader::run` drives `AttachmentsBatchStateMachine`, which eventually calls `AttachmentsBatchStateContext::extend_with_attachments` on the batched HTTP responses: [2](#0-1) 

Here, `response.decode_atlas_get_attachment()` simply hex-decodes JSON into an `Attachment` with no length cap and no hash check: [3](#0-2) [4](#0-3) 

The decoded attachment is inserted straight into `self.attachments` (a `HashSet<Attachment>`), and once the state machine reaches `Done`, every attachment is written unconditionally via `insert_instantiated_attachment`: [5](#0-4) 

`AtlasDB::insert_instantiated_attachment` performs a raw `INSERT OR REPLACE` with no size validation at all: [6](#0-5) 

Critically, there is also no check that the returned `Attachment`'s hash equals the `content_hash` that was originally requested (the request/response pairing in `extend_with_attachments` only keys on the peer URL/request, not on content hash). So a malicious peer selected as a download source for any queued `AttachmentInstance` can respond to `GET /v2/attachments/{requested_hash}` with a `GetAttachmentResponse` containing content of any size and any value — it will be decoded, inserted into the local `HashSet`, and persisted to disk by `insert_instantiated_attachment`, regardless of `attachments_max_size` and regardless of whether it matches the requested hash.

This is repeatable: the malicious peer can serve a new oversized/garbage blob for every attachment instance the victim ever queues (attachment instances arrive continuously from BNS-contract activity processed by `process_atlas_attachment_events`), each insert bypassing the configured cap.

### Impact Explanation
A single unprivileged remote peer that becomes an outbound sync/data-provider peer for the victim node can force unauthenticated, unbounded writes into the victim's `AtlasDB` (`attachments` table), violating the operator-configured `attachments_max_size` invariant with no upper bound enforced anywhere on this path. This is a write of attacker-controlled, arbitrary-size data into persistent node state without authentication or validation, and is repeatable per attachment-instance download cycle, leading to disk exhaustion / unbounded storage growth on the victim node.

### Likelihood Explanation
Precondition is only that the attacker's node be selected as one of the victim's outbound sync peers serving attachment inventory/content — a normal, low-cost, unprivileged peering condition requiring no secret, no StackerDB slot, and no special role. The attack costs the attacker nothing more than running a peer and answering `GET /v2/attachments/{hash}` requests with large/arbitrary bodies; it is fully repeatable for every attachment instance queued by Atlas.

### Recommendation
In `extend_with_attachments` (or immediately in `decode_atlas_get_attachment`/before calling `insert_instantiated_attachment`), enforce `attachment.content.len() as u32 <= atlas_config.attachments_max_size` and reject/deregister peers that violate it (mirroring `AtlasDB::should_keep_attachment`). Additionally verify `attachment.hash() == request.content_hash` before accepting/storing the response, discarding and penalizing peers that return mismatched or oversized content.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs` that:
1. Builds an `AtlasConfig` with a small `attachments_max_size` (e.g. 16 bytes).
2. Constructs a `BatchedRequestsResult<AttachmentRequest>` with one `succeeded` entry whose `StacksHttpResponse` was built from a `GetAttachmentResponse { attachment: Attachment { content: vec![0u8; 1_000_000] } }` (via `decode_atlas_get_attachment`-compatible JSON body).
3. Calls `AttachmentsBatchStateContext::extend_with_attachments` on it and asserts `context.attachments` contains the oversized attachment.
4. Calls `atlas_db.insert_instantiated_attachment(&oversized_attachment)` and asserts `Ok(())` is returned and `atlas_db.find_attachment(&oversized_attachment.hash())` returns `Some` with `content.len() == 1_000_000`, exceeding `attachments_max_size = 16`, proving the cap is never enforced on this path.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

        let tx = self.tx_begin()?;
        tx.execute(

        )?;

            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }

        let payload = String::deserialize(d)?;
