### Title
Unauthenticated forged `BlockValidateResponse`/`NewBurnBlock`/`NewBlock` injection via signer event-receiver HTTP endpoint - (File: libsigner/src/events.rs)

### Summary
The `SignerEventReceiver`'s HTTP handler dispatches any POST to `/proposal_response`, `/new_burn_block`, or `/new_block` straight into `process_event::<T, E>`, which JSON-deserializes the raw request body into `E` and converts it via `TryInto<SignerEvent<T>>` with no authentication, signature, or origin check. Any TCP client that can reach the bound listener can forge a `BlockValidateResponse`/burn-block/Stacks-block event and have it delivered to the signer runloop as if the local, trusted stacks-node had emitted it.

### Finding Description
The broken equality is: the runloop must only ever consume events that the co-located, trusted stacks-node actually dispatched from its own chainstate/validation engine — but `process_event` accepts and forwards any JSON body it can parse into `E`, regardless of source.

Code path: `SignerEventReceiver::next_event` routes by URL to `process_event::<T, BlockValidateResponse>` (or `BurnBlockEvent`/`StacksBlockEvent`) at [1](#0-0) . `process_event` reads the raw HTTP body, acks the request, then does `serde_json::from_slice::<E>(body.as_bytes())` and `json_event.try_into()` with no auth check at all: [2](#0-1) . The `TryFrom` impls for `BlockValidateResponse`, `BurnBlockEvent`, and `StacksBlockEvent` perform a pure field-copy into the corresponding `SignerEvent` variant with no cross-check against any local chainstate or trust anchor: [3](#0-2) [4](#0-3) . The resulting `SignerEvent` is then unconditionally forwarded to every registered consumer channel (i.e., the signer runloop) via `forward_event`: [5](#0-4) .

Unlike the StackerDB chunk path — which requires `chunk.recover_pk()` signature recovery over signed StackerDB data before trusting message contents ( [6](#0-5) ) — the `BlockValidateResponse`, `BurnBlockEvent`, and `StacksBlockEvent` paths have no equivalent signature/auth gate. The only "auth" mentioned anywhere in this subsystem is `auth_password`/`auth_token`, which is checked by the **node's** event-dispatcher HTTP client when it POSTs out, not verified by the **signer's** receiving HTTP server (`tiny_http::Server`) when it accepts inbound connections — the receiving side in `SignerEventReceiver::bind`/`next_event` performs no credential check on any inbound request, per [7](#0-6) .

Attacker's exact message: a raw HTTP POST such as
```
POST /proposal_response HTTP/1.1
Content-Length: <n>

{"result":"Accepted", ... attacker-chosen BlockValidateResponse fields ...}
```
sent to the bound `endpoint` (e.g. `0.0.0.0:30000` per the sample config at [8](#0-7) ) is deserialized and forwarded verbatim as `SignerEvent::BlockValidationResponse(..)` with the attacker's fields intact, exactly matching the same code path a real node's dispatcher would use.

### Impact Explanation
An unprivileged remote party who can reach the signer's event-receiver TCP port can inject an arbitrary, unauthenticated `SignerEvent::BlockValidationResponse`, `SignerEvent::NewBurnBlock`, or `SignerEvent::NewBlock` into the signer's runloop input channel. This is an unauthenticated write into the signer's local event stream/state — the signer's runloop will process this forged event exactly as if the co-located trusted node had emitted it (per the scope boundary, the downstream consensus-decision consequences of that processing are out of scope, but the transport-level injection itself is a Critical unauthenticated write into the signer transport). This is repeatable per message and requires only network reachability to the bound listener address.

### Likelihood Explanation
Preconditions: the signer's event-receiver socket must be reachable by the attacker. The maintainers' own documentation/warning acknowledges this exposure surface (`stacks-signer/src/lib.rs`, warning about "communicating with an external node" — though here the risk is the reverse: an external party communicating with the signer's exposed listener), and the shipped sample config explicitly binds to `0.0.0.0:30000` [8](#0-7) , i.e., all interfaces, not loopback-only. No secret, key, or slot ownership is required — only the ability to open a TCP connection and send a well-formed HTTP POST. This matches the "attacker action" and preconditions asserted in the question and requires no privileged role.

### Recommendation
Require the signer's HTTP event-receiver to authenticate inbound requests (e.g., verify the same `auth_password`/`auth_token` shared secret via a header on every incoming POST, not just rely on the outbound dispatcher having sent it) before calling `process_event`, and/or bind the listener to loopback-only by default and document that exposing it beyond loopback requires an authenticating reverse proxy. At minimum, add an explicit check in `SignerEventReceiver::next_event` (or `process_event`) that rejects requests lacking a valid shared-secret credential before touching `serde_json::from_slice`.

### Proof of Concept
Rust test plan (analogous to existing tests in `libsigner/src/tests/mod.rs`):
1. Construct a `SignerEventReceiver<SignerMessage>` and `Signer::spawn` it bound to `127.0.0.1:<port>` as in `test_status_endpoint` ( [9](#0-8) ).
2. From a separate thread, open a raw `TcpStream` to that port (no auth header, no prior handshake) and send:
   `POST /proposal_response HTTP/1.1\r\nHost: ...\r\nContent-Length: N\r\nConnection: close\r\n\r\n<hand-built BlockValidateResponse JSON with attacker-chosen fields>`.
3. Call `running_signer.stop()` to collect `accepted_events` (as the existing tests do) and assert `accepted_events` contains `SignerEvent::BlockValidationResponse(..)` whose fields equal exactly the attacker-supplied JSON — i.e., no server-side field was validated, recomputed, or rejected.
4. Repeat for `/new_burn_block` and `/new_block` with hand-built `BurnBlockEvent`/`StacksBlockEvent` JSON bodies, asserting the corresponding forged `SignerEvent::NewBurnBlock`/`SignerEvent::NewBlock` is produced.

    fn forward_event(&mut self, ev: SignerEvent<T>) -> bool {
        if self.out_channels.is_empty() {
            // nothing to do
            error!("No channels connected to event receiver");
            false
        } else if self.out_channels.len() == 1 {
            // avoid a clone
            if let Err(e) = self.out_channels[0].send(ev) {
                error!("Failed to send to signer runloop: {:?}", &e);
                return false;
            }
            true

                if let Err(e) = out_channel.send(ev.clone()) {
                    error!("Failed to send to signer runloop #{}: {:?}", i, &e);
                    return false;
                }
            }
            true
        }
    }

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
