Based on the investigation, I found a concrete analog to the "unbounded loop over user-controlled collection" bug class in Gitaly's receive-pack / proc-receive hook handling.

### Title
Unbounded per-reference-update loop in non-atomic proc-receive handling causes O(n) separate Git process invocations per push - (File: internal/gitaly/hook/receivepack/receive_pack.go)

### Summary
The `procReceiveHook` function iterates over `handler.ReferenceUpdates()` — a list fully controlled by the pushing client via `git push` — without any upper bound on its length. In the non-atomic branch, each individual reference update triggers a completely separate, expensive `receivePackReferenceUpdates` call that spawns a new `updateref.New`/`Start`/`Commit` Git transaction and invokes the `update` hook, one reference at a time.

### Finding Description
`procReceiveHook` branches on `handler.Atomic()`: [1](#0-0) 

In the non-atomic case, for every reference update supplied by the client, the code calls `receivePackReferenceUpdates` with a single-element slice, which itself spawns a brand-new reference-transaction updater (`updateref.New`, `Start`, `Commit`) and runs the `update` hook via `hookManager.UpdateHook`: [2](#0-1) 

There is no limit enforced anywhere on the number of `ReferenceUpdates()` a proc-receive handler can carry — that count is derived directly from the ref-update commands sent by the pushing client over `git-receive-pack`. Unlike `ListRefs` or `FindRefsByOID`, which have explicit `limit`/pagination fields in their protobuf definitions, and unlike `UpdateRemoteMirror`, which explicitly batches pushes via `pushBatchSize` [3](#0-2) , this reference-update loop has no batching or cap. Each iteration incurs the full cost of spawning a Git subprocess for the update hook plus a full reference-transaction (Start/Commit) round trip, rather than a single batched transaction as the atomic branch does.

### Impact Explanation
An ordinary authenticated user capable of pushing to a repository (a git push that goes through the non-atomic proc-receive path) can submit a push containing an arbitrarily large number of reference updates. Because each reference update pays the full cost of an independent Git process spawn and reference transaction commit, the per-request cost scales linearly (and with much higher constant factor than the atomic path) with an unbounded, client-controlled quantity. This can exhaust Gitaly server CPU/goroutine/file-descriptor resources for a single RPC, potentially causing denial of service for the Gitaly node handling the push, directly analogous to the reported unbounded loop over user-controlled stakes exhausting gas.

### Likelihood Explanation
This is reachable by any user with push access exercising the proc-receive/non-atomic hook path — no privileged access, leaked token, or malicious peer is required. The reference-update count is entirely attacker-controlled input from a standard `git push`.

### Recommendation
Enforce an explicit maximum number of reference updates processed per proc-receive invocation (mirroring the "10 stakes per user" style cap from the smart-contract fix), and/or batch non-atomic reference updates into grouped transactions similar to the `pushBatchSize` pattern used in `UpdateRemoteMirror`, rather than performing one full Git subprocess + transaction commit per individual reference.

### Proof of Concept
1. As a user with push access, craft a `git push` to a repository configured with a proc-receive hook operating in non-atomic mode, containing a very large number of distinct reference updates (e.g., thousands of new branch refs) in a single push.
2. Observe that `procReceiveHook`'s non-atomic branch invokes `receivePackReferenceUpdates` once per reference update [4](#0-3) , each of which spawns a new `updateref` transaction and hook invocation [5](#0-4) , with no limit on the number of updates accepted, resulting in resource consumption proportional to the attacker-chosen reference count.

func receivePackReferenceUpdates(
	ctx context.Context,
	cfg config.Cfg,
	req gitcmd.ReceivePackRequest,
	repo *localrepo.Repo,
	hookManager hook.Manager,
	updates []hook.ReferenceUpdate,
	stdout, stderr io.Writer,
) (returnedErr error) {
	hooksPayload, err := setupHooksPayloadEnv(ctx, cfg, req, repo, gitcmd.UpdateHook)
	if err != nil {
		return fmt.Errorf("creating hooks payload: %w", err)
	}

	updater, err := updateref.New(ctx, repo, updateref.WithNoDeref())
	if err != nil {
		return fmt.Errorf("spawning ref updater: %w", err)
	}
	defer func() {
		if err := updater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel ref updater: %w", err)
		}
	}()

	if err := updater.Start(); err != nil {
		return fmt.Errorf("start reference transaction: %w", err)
	}

	for _, update := range updates {
		if err := hookManager.UpdateHook(
			ctx,
			req.GetRepository(),
			update.Ref.String(),
			update.OldOID.String(),
			update.NewOID.String(),
			[]string{hooksPayload},
			stdout, stderr,
		); err != nil {
			return fmt.Errorf("running update hook: %w", err)
		}

		if err := updater.Update(update.Ref, update.NewOID, update.OldOID); err != nil {
			return fmt.Errorf("queueing ref to be updated: %w", err)
		}
	}

	if err := updater.Commit(); err != nil {
		return updateError{error: err}
	}

	return nil
}
