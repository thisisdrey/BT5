### Title
`ExchangeInjectContract` lacks slippage/minimum-amount protection, allowing frontrunning to force unfavorable injection terms - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` computes the paired token amount purely from the exchange's current on-chain reserve ratio at execution time, and the `ExchangeInjectContract` protobuf message provides no way for the caller to bound/verify that computed amount. Unlike `ExchangeTransactionContract`, which was hardened with an `expected` (minimum-received) field specifically to prevent this class of issue, `ExchangeInjectContract` never received the same protection. This mirrors the reported Cooler `rollLoan` bug class: a transaction whose economic terms are computed from mutable shared state at execution time, with no way for the sender to enforce the terms they expected when they signed/broadcast the transaction — allowing another party to change that state first (frontrun) and force the victim's transaction to execute under worse terms.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant`: [1](#0-0) 

In `ExchangeInjectActuator.execute`, the amount of the paired token that the caller must supply (`anotherTokenQuant`) is derived at execution time directly from the exchange's live reserve balances: [2](#0-1) 

There is no field in the contract, and no check in `doValidate()`, that lets the sender specify a maximum amount of the paired token they are willing to supply (or a minimum ratio they require). By contrast, `ExchangeTransactionContract` explicitly added an `expected` field and a corresponding validation (`token required must greater than expected`) to guard against exactly this kind of manipulation of the exchange ratio between signing and execution: [3](#0-2) 

Because the exchange's reserve ratio (`firstTokenBalance`/`secondTokenBalance`) can be altered by any other account issuing `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transactions against the same `exchange_id` before the victim's `ExchangeInjectContract` is included in a block, an attacker can observe a pending inject transaction in the mempool, submit a competing transaction with higher fee/priority to shift the ratio, and cause the victim's inject to be executed against the manipulated ratio — exactly analogous to the lender frontrunning `rollLoan` by calling `provideNewTermsForRoll` first to set arbitrary terms that the borrower's transaction is then forced to accept.

### Impact Explanation
A victim broadcasting `ExchangeInjectContract` cannot bound the amount of the paired token they will be forced to contribute. An attacker who frontruns with manipulative `ExchangeTransactionContract`/`ExchangeWithdrawContract`/`ExchangeInjectContract` calls can force the victim to inject at a distorted ratio, extracting value from the victim (effectively a sandwich attack) with no on-chain guardrail to reject the unfavorable execution. This is a direct, unauthorized transfer of value away from the unprivileged transaction sender — a concrete fund-loss impact, reachable by any account able to submit these permissionless exchange contract types.

### Likelihood Explanation
Any account can create competing `Exchange*Contract` transactions against the same `exchange_id`, and mempool visibility plus gas/bandwidth-fee ordering give an attacker a straightforward frontrunning primitive. The lack of an `expected`/bound field is unconditional — every `ExchangeInjectContract` submission is exposed, so exploitation requires no special privilege or preconditions beyond an existing exchange pair with liquidity.

### Recommendation
Add an `expected`/bound field to `ExchangeInjectContract` (mirroring the pattern already used for `ExchangeTransactionContract`), e.g. a maximum-allowed `anotherTokenQuant` (or minimum acceptable exchange rate), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()`, rejecting the transaction if the computed paired-token amount falls outside the caller-specified bound.

### Proof of Concept
1. Attacker monitors the mempool for a victim's `ExchangeInjectContract` targeting `exchange_id = X`, `token_id = A`, `quant = Q`.
2. Attacker submits an `ExchangeTransactionContract` (or `ExchangeWithdrawContract`) against the same `exchange_id = X` with higher fee/priority, shifting `firstTokenBalance`/`secondTokenBalance` significantly.
3. Once the attacker's transaction is applied first, the victim's `ExchangeInjectContract` executes against the new, manipulated ratio in `ExchangeInjectActuator.execute` (lines 60-83), computing an `anotherTokenQuant` far different from what the victim expected when signing.
4. Because `ExchangeInjectContract` has no `expected`/bound parameter, `doValidate()` performs no check to reject this outcome, and the victim's funds are injected at the attacker-favorable ratio.
