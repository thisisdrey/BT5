### Title
Attacker can permanently block a victim from opening new collateral/debt positions by dust-filling `depositTokensOfAccount` to `MAX_TOKENS_PER_USER` - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The Node.js bug class is denial of service via resource exhaustion — each new "connection" consumes a finite per-process slot until the limit is hit and new legitimate connections are rejected. The Metronome analog is `Pool.MAX_TOKENS_PER_USER = 30`: each distinct deposit/debt token an account touches consumes one slot in its per-account enumerable set, and once 30 slots are occupied `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens`, refusing any new "connection" (deposit of a new collateral type, minting of a new synthetic, or inbound token transfer). An unprivileged attacker can cheaply fill a victim's slots by transferring 1 wei of each DepositToken to them.

### Finding Description
`Pool` tracks per-account holdings in `MappedEnumerableSet.AddressSet` sets `depositTokensOfAccount` and `debtTokensOfAccount` (`contracts/storage/PoolStorage.sol`). The modifier `onlyIfAdditionWillNotReachMaxTokens` reverts once the combined length reaches `MAX_TOKENS_PER_USER` (30) (`contracts/Pool.sol` lines 143-148, applied at lines 204 and 216).

`DepositToken._transfer` adds the token to the *recipient's* set whenever the recipient's prior balance is zero and `amount_ > 0` (lines 517-520). The sender-side check `_revertIfLocked(_msgSender, amount_)` only constrains the sender's unlocked balance — there is no minimum amount and no consent from the recipient. So an attacker can:

1. Deposit a dust amount (or already hold) every listed `DepositToken` in the pool.
2. Call `depositToken.transfer(victim, 1)` for each token the victim doesn't yet hold.
3. If the pool has few collaterals, the attacker can also issue dust debt (`DebtToken.issue`) and wait — debt token adds happen on the *minter's* list, so debt-side filling requires the attacker to instead push deposit tokens; with N deposit tokens listed the attacker fills N victim slots, plus the victim's own holdings count toward 30.

Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= 30`:
- `DepositToken.transfer`/`transferFrom`/`deposit(onBehalfOf_ = victim)` for any token the victim doesn't already hold reverts inside `_transfer` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`.
- `DebtToken.issue`/`mint` of a new synthetic reverts the same way.

The victim cannot clear the slots either — removing requires their own balance of that token to hit zero, but they can simply transfer the dust out themselves. However, the attacker can **front-run refills**: whenever the victim empties a slot, the attacker dusts them again for ~gas cost only, keeping the victim pinned at 30 indefinitely (the attacker can even automate this with a contract monitoring transfers). The DoS is therefore sustained for as long as the attacker wishes, mirroring the fd-leak semantics where slots are never reclaimed.

No modifier stops this: `transfer` has no `whenNotPaused`-equivalent recipient check, `seize` (line 343-345) intentionally bypasses nothing that helps the victim, and the MAX check is exactly the mechanism being abused.

### Impact Explanation
Temporary/ongoing freezing of position functionality for a targeted user: the victim cannot deposit new collateral types, cannot mint new synthetic tokens, and cannot receive any deposit token they don't already hold (all such transfers revert). On pools with many listed collaterals (e.g., Metronome Synth deployments with numerous msdTOKENs), a single EOA can keep a victim's account effectively frozen against new activity at near-zero cost (dust is recoverable). Analogous impact to the CVE: a finite resource (30 slots ↔ fd limit) is exhausted by an unprivileged peer, denying service.

### Likelihood Explanation
High reachability for any pool listing ≥ ~30 combined tokens, or fewer if the victim already uses several positions — each fill costs one `transfer` of 1 wei. No privileged role, oracle manipulation, or malicious endpoint is required. The main mitigations are: (a) pools with few collaterals limit the attack to victims who already hold many tokens; (b) the victim can expel dust, but the attacker can re-grief in the same block or by monitoring, and during the filled window all inbound transfers reverts (which can also interfere with liquidation payouts routed to a filled liquidator account or smart-wallet flows like SmartFarmingManager deposits on the victim's behalf).

### Recommendation
Apply the add-slot check only to value-creating actions (deposit/mint) rather than to inbound transfers, or allow transfers to opt out of tracking (e.g., only add to `depositTokensOfAccount` on `_mint`/deposit and on transfer if the recipient opts in), so recipients can't be force-assigned slots. Alternatively, make `addToDepositTokensOfAccount` not revert on transfer-path adds (silently skip tracking, since `depositOf` iterates the tracked set — though this changes accounting semantics). A cheaper remediation: sweep dust back is already possible, so documenting an `Operator.execute` batch that both removes dust tokens and performs the victim's intended deposit atomically prevents re-griefing.

### Proof of Concept
Hardhat fork sketch against a deployed Pool:

```ts
// victim starts with K tokens; attacker fills the rest up to 30
const pool = await ethers.getContractAt("Pool", POOL);
const depositTokens = await pool.getDepositTokens();

for (const dt of depositTokens) {
  const d = await ethers.getContractAt("DepositToken", dt);
  if ((await d.balanceOf(victim)) == 0 &&
      (await pool.getDepositTokensOfAccount(victim)).length +
      (await pool.getDebtTokensOfAccount(victim)).length < 30) {
    // attacker deposits dust then transfers 1 wei of the msdTOKEN
    await underlying.connect(attacker).approve(d.address, 2);
    await d.connect(attacker).deposit(2, attacker.address);
    await d.connect(attacker).transfer(victim, 1); // fills one victim slot
  }
}

// now: any deposit of a new collateral for victim reverts
await expect(
  newDepositToken.connect(anyone).deposit(1000, victim)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// and any transfer of an unheld msdTOKEN to victim reverts
await expect(
  someDepositToken.connect(attacker).transfer(victim, 1)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
```
