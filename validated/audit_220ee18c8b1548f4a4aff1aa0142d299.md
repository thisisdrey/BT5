### Title
Wallet Contract's hardcoded compile-time `CHAIN_ID` enables cross-fork signature replay of RLP-encoded transactions - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs`)

### Summary
The eth-implicit `WalletContract` validates RLP-encoded Ethereum-style transactions against a `CHAIN_ID` constant that is baked into the WASM binary at build time per network (mainnet=397, testnet=398, localnet=399), rather than a chain identifier derived from live NEAR chain state. Combined with a local per-account `nonce` that does not incorporate any block/genesis hash, a `SignedTransaction`-wrapped RLP payload valid on one instance of the chain remains fully valid and replayable on any forked chain that shares the same wasm code and pre-fork state.

### Finding Description
`CHAIN_ID` is read from a generated file at compile time: `pub const CHAIN_ID: u64 = std::include!("CHAIN_ID");` [1](#0-0)  and is produced by the build script with fixed, network-specific values that never change once the contract is compiled: `const MAINNET_CHAIN_ID: u64 = 397;` / `const TESTNET_CHAIN_ID: u64 = 398;` / `const LOCALNET_CHAIN_ID: u64 = 399;` [2](#0-1) .

This constant is the sole chain-binding check performed on a relayer-submitted transaction in `validate_tx_relayer_data`: `if tx.chain_id != Some(CHAIN_ID) { return Err(Error::Relayer(RelayerError::InvalidChainId)); }` [3](#0-2) . The only other replay-protection mechanism is a locally stored, strictly-incrementing `nonce` field on the `WalletContract` struct, which is compared and incremented purely from on-chain storage with no reference to genesis hash, `chain_id()` host function, or any other value that would necessarily diverge across a chain split: `pub nonce: u64` and the nonce-increment logic in `inner_rlp_execute`/`address_check_callback` [4](#0-3) [5](#0-4) .

Note that nearcore's own host function does expose a runtime `chain_id()` value derived from the network's genesis config (`ctx.ext.chain_id()`) [6](#0-5) , but the Wallet Contract does not use it: it exclusively relies on the compiled-in EVM `CHAIN_ID` constant needed for Ethereum RLP/EIP-155-style signing compatibility. Since this constant is embedded in the WASM bytecode itself and the WASM code (and its account state, including `nonce`) is identical on both sides of a chain split at the fork point, this is architecturally the same flaw as the reported hardcoded `SOURCE_IDENTIFIER` in the mock cross-chain messaging bridge: a fixed identifier is used for domain separation instead of one that is guaranteed to diverge across forks.

### Impact Explanation
If NEAR undergoes a contentious hard fork/chain split (uncoordinated fork where two live chains persist with identical genesis/state at the split height and both continue to run the same Wallet Contract WASM), any previously-signed, RLP-encoded transaction targeting a user's eth-implicit account remains valid on the other fork as well, because: (1) `CHAIN_ID` is identical (compiled-in constant, unrelated to which fork it runs on), and (2) `nonce` state is identical immediately post-split. A relayer or any observer who captures a valid signed RLP transaction (these are routinely broadcast/relayed by third-party relayers per the contract's design) can replay it against the sibling chain's copy of the account, causing the same value-moving action (transfers, `FunctionCall`, `AddKey`/`DeleteKey` actions) to be executed a second time on a chain the signer did not intend to affect — a classic hard-fork replay authorization bypass, matching the "authorization escalation … / double-spend/replay" impact category.

### Likelihood Explanation
Requires the same triggering precondition as the external report: an actual blockchain hard fork/chain split, which is rare and outside attacker control, but once it occurs, no contract upgrade or admin action is available to change the compiled-in `CHAIN_ID`, and every already-signed transaction is trivially replayable by any relayer observing it, requiring no special privilege from the signer. This mirrors the Medium severity assigned to the underlying reported issue.

### Recommendation
Use nearcore's runtime `chain_id()` host function (or another value guaranteed to diverge on a fork, e.g. a value tied to genesis hash) instead of, or in combination with, the compile-time constant, and expose an admin/versioning mechanism to update the effective chain identifier used in `validate_tx_relayer_data` without requiring a full contract redeploy, analogous to how the Wormhole implementation in the original report derives its identifier from `chainId()` rather than a hardcoded constant.

### Proof of Concept
1. Deploy the `WalletContract` for an eth-implicit account on NEAR mainnet (compiled with `CHAIN_ID = 397`).
2. Sign an RLP transaction (e.g. a `Transfer`/`FunctionCall` action) with `chain_id: 397` as done in the existing test helper `create_signed_transaction` [7](#0-6) .
3. Submit it via `rlp_execute`; `validate_tx_relayer_data` accepts it because `tx.chain_id == Some(CHAIN_ID)` [3](#0-2) .
4. Simulate a hard fork: clone the exact chain state (including this account, its `nonce`, and the identical WASM bytecode with the same baked-in `CHAIN_ID`) onto a second, independent NEAR network instance.
5. Replay the identical signed RLP transaction bytes on the forked network's copy of the same account. `validate_tx_relayer_data` again succeeds (same `CHAIN_ID`, same starting `nonce`), and the action executes a second time on the unintended chain — demonstrating cross-fork signature replay.
