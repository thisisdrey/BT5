## Finding

The local analog to the "variable balance ERC20" bug class exists in the XCM `ERC20Transactor` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, which bridges XCM asset holding accounting to arbitrary ERC20 contracts executed via `pallet-revive`.

### Title
ERC20Transactor trusts nominal `transfer()` amount instead of verifying actual balance delta, breaking XCM value conservation for fee-on-transfer/rebasing tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` invoke the ERC20's `transfer()` function for the XCM-requested `amount` and treat a `true` boolean return as proof that exactly `amount` tokens moved. Neither function reads `balanceOf()` before/after the call to confirm the actual balance delta, mirroring the exact flaw described in the external report for `EscrowLib.sol`/`LineOfCredit.sol`.

### Finding Description
`Matcher::matches_fungibles(what)` extracts an `(asset_id, amount)` pair directly from the XCM asset descriptor [1](#0-0) . This `asset_id` is any `H160` contract address matched via an `AccountKey20` junction — per the PR that introduced this transactor, "asset ids of the form `{parents: 0, interior: X1(AccountKey20 { key, network })}` will be matched by this transactor and the corresponding `transfer` function will be called in the smart contract whose address is `key`" [2](#0-1) . There is no allowlist restricting which ERC20 contracts qualify — any contract address encoded as `AccountKey20` is accepted by the `Matcher`.

In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall{ to: checking_address, value: amount }` and, if the contract returns `true` without reverting, credits the XCM holding register with a fixed `Erc20Credit(amount)` — the nominal requested amount, not the actual amount that landed in the checking account: [3](#0-2) 

Symmetrically, `deposit_asset_with_surplus` calls `transfer()` for the nominal `amount` from the checking account to the beneficiary and, on a `true` return, reports full success with no verification that the beneficiary's balance increased by `amount`: [4](#0-3) 

For fee-on-transfer tokens, deflationary/rebasing tokens, or any ERC20 whose `transfer()` can return `true` while moving less (or more) than `value`, the pooled `TransfersCheckingAccount` balance diverges from the sum of nominal amounts the XCM ledger believes it holds on behalf of users.

### Impact Explanation
This breaks the "Balances… must conserve value and settle exactly once to the rightful beneficiary and amount" invariant. Because the `TransfersCheckingAccount` is a shared pool backing all XCM-tracked holdings of a given ERC20 asset, a single fee-on-transfer or rebasing token registered under this transactor causes:
- On withdraw: the checking account's real on-chain balance ends up lower than the sum of `Erc20Credit` amounts XCM believes it deposited, creating phantom backing.
- On deposit: beneficiaries can receive less than the nominal amount while the XCM executor and any onward multi-hop message treats the deposit as fully successful, and later withdrawals by other users against the same shared pool can fail or be under-collateralized, causing "permanent user-fund or bridge-state lock" for some accounts.

This is not a validator/relayer/prover assumption failure — it triggers purely through the standard XCM execution path (`TransactAsset`) whenever such a token is registered and moved by any ordinary user.

### Likelihood Explanation
Likelihood is gated only by whether an ERC20 contract with non-standard transfer semantics gets matched by this transactor's `Matcher`. Since the transactor accepts any `AccountKey20`-addressed contract with no code/behavior allowlist, and ERC20 contracts referenced here can be arbitrary user- or governance-deployed contracts on `pallet-revive` (not curated Ethereum mainnet contracts), an unprivileged party deploying (or an existing) fee-on-transfer/rebasing ERC20 and having it registered/used in XCM transfers is sufficient — no malicious node, validator, or admin action is required.

### Recommendation
- In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf()` on the relevant account before and after the `transfer()` call and use the observed delta — not the requested `amount` — as the value credited into `AssetsInHolding`/reported as surplus.
- Alternatively, restrict the `Matcher`/registration path to a governance-curated allowlist of ERC20 contracts known to implement standard, non-fee, non-rebasing transfer semantics, and reject unknown contracts by default.

### Proof of Concept
1. Deploy (or have deployed) an ERC20 contract implementing a fee-on-transfer `transfer()` that returns `true` while delivering `value * 99/100` to the recipient.
2. Its address is encoded as an `AccountKey20` XCM location and matched by `ERC20Transactor`'s `Matcher` with no additional validation, per [2](#0-1) .
3. A user executes an XCM `WithdrawAsset`/`DepositAsset` sequence for `amount` of this token. `withdraw_asset_with_surplus` calls `transfer(checking_address, amount)`, which returns `true` but moves only `amount * 99/100` to `TransfersCheckingAccount`; the code nonetheless credits `Erc20Credit(amount)` into the XCM holding register: [5](#0-4) 
4. Repeating deposits/withdraws accumulates a shortfall between the checking account's real `balanceOf` and the sum of nominal amounts XCM believes are backed, eventually causing legitimate withdrawal attempts by other holders of the same token to fail (`ERC20 contract transfer failed`) once the checking account is drained below the aggregate claimed balance — locking those users' funds.
