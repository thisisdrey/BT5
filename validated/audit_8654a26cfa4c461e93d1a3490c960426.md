### Title
TRC10/TRX bonding-curve exchange price is not split-invariant due to per-call virtual-supply reset and floating-point rounding in `ExchangeProcessor` - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeCapsule.transaction()`, invoked from the permissionless `ExchangeTransactionActuator.execute()`, prices every TRC10⇄TRC10/TRX swap through a Bancor-style relay-token curve. Unlike a real Bancor/AMM implementation, the "relay supply" used to price the swap is **not persisted state** — it is reinitialized to a hard-coded constant on every single call, and the buy/sell amounts are computed with double-precision `Math.pow` on that freshly reset value, then truncated to `long`. This is structurally the same class of flaw as the reported USM `defund()` bug: the pricing function is evaluated on a per-call basis with state that is contracted/reset each time, so redeeming/trading the same total quantity in one large call versus many small calls does not conserve value — the discretization and floating-point rounding compound across calls in a way that is not split-invariant.

### Finding Description
`ExchangeCapsule.transaction()`: [1](#0-0) 
creates a brand-new `ExchangeProcessor` (or `SafeExchangeProcessor`) on every call with `long supply = 1_000_000_000_000_000_000L;` — a fixed constant, not a value carried over from the previous trade against the same `ExchangeCapsule`. Only `firstTokenBalance`/`secondTokenBalance` (the real reserves) persist between calls; the virtual "relay supply" used internally to compute the curve does not.

The actual pricing math: [2](#0-1) 
computes `issuedSupply = -supply*(1 - (1+quant/newBalance)^0.0005)` and `exchangeBalance = balance*((1+supplyQuant/supply)^2000 - 1)` using `double` arithmetic and hard-coded reciprocal exponents `0.0005`/`2000`, each result truncated via a naive `(long)` cast (`SafeExchangeProcessor` truncates via `BigDecimal` `RoundingMode.DOWN` instead, but only when `allowHardenExchangeCalculation()` is enabled, which is off by default and only fixes overflow, not the curve's per-call statelessness): [3](#0-2) [4](#0-3) 

Because the exponentiation constants (`0.0005`, `2000`) are exact reciprocals, the curve is meant to approximate a simple constant-product formula for a symmetric-weight pair, which in exact real arithmetic would be split-invariant (splitting a trade into N slices against the same reserve curve should sum to the same output as one trade). In this implementation, however:
1. The relay supply scratch variable is derived from a constant every call instead of being an integral, monotonically-tracked quantity, so the double-precision `pow` evaluation is re-run from scratch on a huge (`10^18`) scaling constant for every slice instead of once for the whole amount.
2. `Math.pow` on values extremely close to 1 raised to tiny (`0.0005`) or huge (`2000`) exponents is subject to catastrophic cancellation and floating-point rounding error whose magnitude/direction depends on the input `quant/balance` ratio.
3. Reserves (`firstTokenBalance`/`secondTokenBalance`) are mutated and persisted after every call: [5](#0-4) 
so each slice recomputes the curve against updated real reserves but a reset virtual supply, and errors from step (2) compound across N calls instead of being computed once.

This directly mirrors the reported USM flaw: a pricing formula that (a) is evaluated per call against internal state that is contracted/reset each call, and (b) accumulates rounding error, so that splitting one large redemption/swap into many equal small ones diverges from the single-call result — extractable value if the divergence favors the caller.

### Impact Explanation
`ExchangeTransactionActuator` charges zero fee (`calcFee()` returns 0): [6](#0-5) 
so there is no economic friction discouraging an attacker from slicing a large swap into dozens/hundreds of small `ExchangeTransactionContract` transactions against the same `exchangeId`, each independently signed and broadcast — exactly the "64 equal slices" pattern used in the USM PoC. If the per-call floating-point/rounding drift is directionally favorable to the trader for small `quant/newBalance` ratios (plausible given the reset-to-constant virtual supply and `Math.pow` cancellation on near-1 bases), an attacker can drain more of the paired reserve token (TRX or TRC10) from the `ExchangeCapsule` than a single equivalent-size trade would yield, i.e., unauthorized extraction of pooled exchange funds — an unbacked-balance/theft-of-funds outcome.

### Likelihood Explanation
The path is reachable by any account holding TRX/TRC10 tokens via a plain signed `ExchangeTransactionContract`, with no special permission, validator, or admin role required — `ExchangeTransactionActuator.execute()`/`validate()` is a standard actuator invoked from ordinary transaction processing. No fee gates repeated small trades against the same exchange pool, and the reserve balances are mutable, shared, persistent state that any two parties can push into a favorable regime (e.g., low liquidity pools created via `ExchangeCreateActuator`/`ExchangeInjectActuator`) before running the slicing attack.

### Recommendation
Make the exchange pricing curve split-invariant and free of per-call floating-point state resets:
- Track relay/virtual supply as persisted state on the `ExchangeCapsule` itself (or eliminate the virtual-supply detour entirely and compute the constant-product/Bancor formula directly with exact integer/`BigInteger`/`BigDecimal` math, as `ExchangeWithdrawActuator`/`ExchangeInjectActuator` already do for their simpler proportional formulas).
- Replace `Math.pow`-based double arithmetic in `ExchangeProcessor` with a deterministic, exact-rounding fixed-point implementation (already partially done in `SafeExchangeProcessor`), and make the hardened/exact path the only path (retire the legacy `ExchangeProcessor` double-math path via a completed hard fork rather than leaving it gated behind `allowHardenExchangeCalculation` defaulting to off).
- Add differential tests asserting that executing one `ExchangeTransactionContract` of quantity `Q` against a given `ExchangeCapsule` yields the same (or a value never favorable to the caller) aggregate output as executing N `ExchangeTransactionContract`s of quantity `Q/N` sequentially against the same pool, for a range of N and pool sizes, to catch any regression that reintroduces split-variance.

### Proof of Concept
Not independently executed against a live node in this analysis; the following outlines the reachable exploit path derived directly from the code above, structurally identical to the USM PoC's "single vs. sliced" differential:
1. Create an `ExchangeCapsule` via `ExchangeCreateActuator` with a modest TRX/TRC10 reserve pair.
2. As attacker, call `ExchangeTransactionActuator` once with the full `tokenQuant` to record `anotherTokenQuant_single` (single-call baseline), on a forked/duplicated pool state.
3. On the original pool state, issue N separate signed `ExchangeTransactionContract` transactions each with `tokenQuant/N`, summing the `ret.getExchangeReceivedAmount()` across all N calls (`anotherTokenQuant_split`), exactly mirroring the USM attacker's 64-slice `defund()` loop against `ExchangeCapsule.transaction()`/`ExchangeProcessor.exchange()`.
4. Compare `anotherTokenQuant_split` against `anotherTokenQuant_single` and the pool's reserve balances before/after; a positive divergence in the attacker's favor across increasing N (as seen with `ExchangeTransactionActuatorTest`'s existing hardened/non-hardened test scaffolding) demonstrates the exploit, and repeated application against low-liquidity pools would let an attacker drain the paired reserve token from `ExchangeCapsule` without fee cost since `calcFee()` is 0.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
