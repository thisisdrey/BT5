### Title
`GetAttachmentResponse` deserialization bypasses `AtlasConfig.attachments_max_size`, allowing oversized attachments into AtlasDB - ([File: stackslib/src/net/atlas/mod.rs])

### Summary
`GetAttachmentResponse`'s custom `Deserialize` impl decodes a hex-encoded attachment body with no length check against `AtlasConfig.attachments_max_size`, and this size limit is never enforced anywhere downstream in `decode_atlas_get_attachment`, `extend_with_attachments`, or `AtlasDB::insert_instantiated_attachment`. A peer serving `GET /v2/attachments/<hash>` (or a peer that legitimately created an on-chain `AttachmentInstance` whose `content_hash` matches oversized content it controls) can have that oversized `Attachment` accepted and persisted to SQLite, bypassing the node's configured storage cap.

### Finding Description
`GetAttachmentResponse::deserialize` at [1](#0-0)  reads a JSON string, hex-decodes it via `hex_bytes`, and wraps it directly in an `Attachment` with no comparison against `attachments_max_size`. `decode_atlas_get_attachment` in `getattachment.rs` simply calls `serde_json::from_value` into `GetAttachmentResponse` with no post-check [2](#0-1) . A repo-wide search shows `attachments_max_size` is referenced only in `AtlasConfig` definition/validation (`mod.rs`), config parsing (`config/mod.rs`), the config file, and `db.rs`/tests — it is **not** referenced in `download.rs`, the module that owns `extend_with_attachments` and processes fetched attachments before storage. This means the value is validated only as a configuration floor (`AtlasConfig::validate`, requiring `>= ATTACHMENTS_MAX_SIZE_MIN`) but is never compared against the actual `attachment.content.len()` of a downloaded attachment before it is inserted into `AtlasDB` via `insert_instantiated_attachment`.

Because an attacker who legitimately emits a valid `AttachmentInstance` (e.g., via a BNS-style contract call) controls both the content and its `content_hash`, they can announce a hash for arbitrarily large content and later honestly serve that oversized content from `GET /v2/attachments/<hash>` — the served bytes will correctly hash to the announced `content_hash`, so any hash-integrity check the download pipeline performs still passes. The only control meant to stop this is `attachments_max_size`, and that control is not enforced at deserialization or prior to storage.

### Impact Explanation
A malicious/attacker-controlled peer can cause a victim node's `AttachmentsDownloader` to store attachments far larger than the operator's configured `attachments_max_size` into the node's SQLite-backed `AtlasDB`, consuming disk/memory beyond the configured resource bound. This is repeatable per distinct `AttachmentInstance`/hash the attacker registers and serves, giving the attacker a resource-exhaustion primitive against any node that syncs Atlas/BNS attachments from it, matching the "bounded compute DoS on a read endpoint" / resource-bound-bypass category described in scope.

### Likelihood Explanation
Preconditions: the attacker needs only to (1) get an `AttachmentInstance` referencing their oversized content accepted by the network (a normal, permissionless BNS/Atlas contract-call flow), and (2) be selected as (or be) the serving peer for `GET /v2/attachments/<hash>` — achievable by running their own peer, as allowed under the threat model. No secret, admin role, or privileged slot is required. The size of exploitable payload is likely still bounded by whatever generic HTTP message-length cap exists in `httpcore.rs` (not fully confirmed in this investigation — see caveat below), but that generic cap, if present, is unrelated to and much larger than the intended `attachments_max_size` guard (minimum 1 MiB), so the specific control is still meaningfully bypassed.

**Caveat/uncertainty:** I was not able to fully inspect `stackslib/src/net/httpcore.rs` or `stackslib/src/net/atlas/download.rs` line-by-line before the tool budget was exhausted, so I cannot state with certainty whether some other generic HTTP body-size cap (e.g., a `MAX_MESSAGE_LEN`-style constant) bounds the maximum exploitable size, nor confirm the exact code in `download.rs`/`db.rs` that calls `insert_instantiated_attachment`. The repo-wide absence of `attachments_max_size` references in `download.rs`, however, is a reasonably strong signal that the size check is missing from the attachment-acceptance path.

### Recommendation
Enforce `attachments_max_size` at the point content is received/deserialized: either add a length check inside `GetAttachmentResponse::deserialize` (requires access to the configured limit, e.g., via a deserialization seed) or, more practically, add an explicit `attachment.content.len() as u32 > atlas_config.attachments_max_size` check in `extend_with_attachments` (`download.rs`) before the attachment is added to the `HashSet<Attachment>`/passed to `insert_instantiated_attachment`, rejecting and logging any oversized attachment instead of storing it.

### Proof of Concept
In `stackslib/src/net/atlas` tests, construct a `GetAttachmentResponse` JSON payload (`{"...": "<hex string several MB long>"}`) whose hex decodes to content larger than `AtlasConfig::attachments_max_size` (e.g., 1_048_576 + 1 bytes). Feed it through `serde_json::from_value::<GetAttachmentResponse>` (mirroring `decode_atlas_get_attachment`), then call the equivalent of `extend_with_attachments` with a matching `AttachmentInstance` (`content_hash = Hash160::from_data(&content)`), and assert that the resulting `Attachment` is accepted into the pending set / passed to `AtlasDB::insert_instantiated_attachment` despite `content.len() as u32 > atlas_config.attachments_max_size`, with no error returned at any step.

impl<'de> Deserialize<'de> for GetAttachmentResponse {
    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
        let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
        let attachment = Attachment::new(bytes);
        Ok(GetAttachmentResponse { attachment })
    }
}
