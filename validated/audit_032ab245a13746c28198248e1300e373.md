### Title
`git_repository`/`new_git_repository` force `protocol.file.allow=always` for submodule fetches, letting a malicious `.gitmodules` in attacker-controlled repo content read arbitrary local paths - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`git_worker.bzl`'s `update_submodules` invokes `git submodule update --init` with `-c protocol.file.allow=always` unconditionally whenever a `git_repository`/`new_git_repository` rule sets `init_submodules` (or `recursive_init_submodules`) to true. [1](#0-0) 

### Finding Description
Modern Git ships with a protocol allowlist (`protocol.<name>.allow`) that, since the fix for the class of "malicious submodule URL" attacks, defaults `file` transport to `user` (interactive-only) rather than `always` for submodule operations. This hardening exists precisely to stop a hostile repository author from embedding a `.gitmodules` entry such as `submodule.x.url = file:///some/absolute/path` (or an `ext::` helper) that gets silently followed during `git submodule update --init`, letting the *content of the fetched repository* — which is fully attacker-controlled, since the attacker is the one publishing the git repo/mirror/branch/tag being fetched — dictate an arbitrary local filesystem path (or, if `ext::` protocol were allowed, an arbitrary shell command) that Git will clone into the checkout.

Bazel's `git_worker.bzl` explicitly re-enables this disabled transport with `-c protocol.file.allow=always` on every `git submodule update --init` invocation, citing bazel issue #17040 as the reason it is "necessary" for git 2.38.1+. [1](#0-0) 

This is invoked from `_update`, which is the single fetch/checkout entry point used by both `git_repository` and `new_git_repository`: [2](#0-1) 

The bug class mirrors the `c_rehash` CVE: a script/tool consumes untrusted, attacker-supplied content (in `c_rehash`'s case, filenames in a hash-directory; here, the `.gitmodules` file inside a fetched repository tree) and hands it, unsanitized and with a safety mitigation stripped away, to a privileged external interpreter (`git`), which then acts on attacker-chosen paths/commands.

Even when the user pins an exact `commit`, this does not stop the attack: the pinned commit hash only guarantees the victim gets exactly the tree the attacker published — it does not vet the *semantics* of that tree. An attacker who controls (or later compromises) a git remote can publish a commit whose `.gitmodules` references a `file://` (or `ext::`) submodule URL; a victim who fetches that exact commit with `init_submodules = True` will still trigger the forced `protocol.file.allow=always` override, because Bazel injects that flag for every submodule update regardless of what the pinned commit's tree contains.

### Impact Explanation
`git submodule update --init` runs with full host filesystem permissions of the Bazel invocation (repository-rule fetches execute outside Bazel's action sandbox). With `protocol.file.allow=always` forced, a malicious `.gitmodules` submodule URL can point Git at an arbitrary local path (e.g., another user directory, credential store, or CI secrets mount) and have it materialized inside the external repository's checkout tree, which then becomes part of the Bazel workspace under the output base — readable by subsequent build/test actions and potentially exfiltratable through build outputs, logs, or artifacts that leave the machine (e.g., published packages, uploaded caches, or CI artifacts). This is a concrete "read outside the repository / exec root / output base" violation caused by Bazel actively disabling Git's own hardening against this exact class of untrusted-content attack.

### Likelihood Explanation
Reachable whenever a `git_repository`/`new_git_repository` invocation sets `init_submodules = True` or `recursive_init_submodules = True` — a common, default-adjacent configuration for consuming git dependencies with submodules — and the fetched remote (which is by definition external, attacker-served content in the threat model: a compromised or malicious mirror/branch/commit) contains a crafted `.gitmodules`. No credentials, MITM, or victim-machine access are required beyond the attacker being able to publish the git content the victim's build is configured to fetch.

### Recommendation
Do not blanket-force `protocol.file.allow=always`. Scope the override narrowly (e.g., only enable `file` transport for the specific, already-verified local checkout path involved in the Bazel-issue-#17040 workaround, or restrict it to `protocol.file.allow=user` combined with explicit validation that submodule URLs resolve within the already-fetched repository/allowed remotes) so a hostile `.gitmodules` cannot redirect Git to arbitrary local filesystem paths or `ext::`/other dangerous transports.

### Proof of Concept
A `src/test/shell/bazel/starlark_git_repository_test.sh`-style integration test:
1. Create a "malicious" bare git repo whose commit contains a `.gitmodules` with `submodule.leak.url = file:///etc/hostname` (or, in the test harness, an absolute path to a sentinel file created outside `$TEST_TMPDIR`'s intended repo tree) and `submodule.leak.path = leaked`.
2. Define `git_repository(name="g", remote="<malicious_repo>", commit="<pinned_sha>", init_submodules=True)` in `MODULE.bazel`.
3. Run `bazel build @g//...` and confirm that `external/+git_repository+g/leaked/` now contains the contents of the out-of-tree sentinel file, demonstrating that git followed the `file://` submodule URL solely because Bazel forced `protocol.file.allow=always`, contrary to Git's own default protection.

I was unable to verify from the index alone whether newer/older Bazel releases (or the actual upstream `git_worker.bzl` history at commit granularity) have since narrowed this override, since `git blame`/history tooling was unavailable in this session — this should be double-checked against the current `main` branch before filing.

    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

        update_submodules(ctx, git_repo, recursive = True)

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
