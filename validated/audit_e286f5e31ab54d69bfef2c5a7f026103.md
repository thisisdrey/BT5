### Title
Unbounded array allocation in `ValidateMultiSign`/`BatchValidateSign` TVM precompiles via attacker-controlled length word - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` helper methods in `PrecompiledContracts.java` allocate Java arrays sized directly from an attacker-controlled 32-byte word taken from the precompile's raw call data, with no upper bound check on that value before the allocation happens. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` parse the raw call-data of a `CALL` to the fixed precompile addresses into 32-byte words with `DataWord.parseArray`, then treat one of those words as an array length (`words[offset].intValueSafe()`) and immediately allocate an array of that size:

```java
byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
    extractSigArray(words, words[3].intValueSafe() / WORD_SIZE, rawData) :
    extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);
``` [4](#0-3) 

The size check (`sigArraySize > MAX_SIZE`) that is meant to bound this array is only performed when the feature flag `VMConfig.allowTvmSelfdestructRestriction()` is true, and even then it only guards the `extractSigArray`/checked path. [5](#0-4) 

Critically, `extractBytes32Array` (used for the `address[]` parameter of `batchvalidatesign`) is called **unconditionally**, and only its length value is bounds-checked when the same feature flag is active:

```java
byte[][] addresses = extractBytes32Array(
    words, words[2].intValueSafe() / WORD_SIZE);
``` [6](#0-5) 

Inside `extractBytes32Array`/`extractBytesArray`, the length is used directly to allocate a Java array with no comparison against the actual `words.length` or any absolute cap:

```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  for (int i = 0; i < len; i++) {
    bytes32Array[i] = words[offset + i + 1].getData();
  }
  return bytes32Array;
}
``` [1](#0-0) 

This is the same bug class as the docconv advisory: a length value taken from untrusted input is used to size a memory allocation before any validation is performed, so a crafted length can force the process to attempt an excessively large allocation.

The `ValidateMultiSign` and `BatchValidateSign` precompiles are reachable by any TVM contract via a plain `CALL`/`STATICCALL` to the fixed precompile address, gated only by `VMConfig.allowTvmSolidity059()` (a long-activated feature), meaning any unprivileged contract deployer/caller can trigger this code path with fully attacker-controlled call data. [7](#0-6) 

### Impact Explanation
If `VMConfig.allowTvmSelfdestructRestriction()` is not active (e.g., prior to that hard fork's activation, or on any java-tron-derived network/testnet/private chain that has not enabled it), an attacker can set the length word that feeds `extractBytesArray`/`extractBytes32Array` to an arbitrarily large 32-bit value. The resulting `new byte[len][]` allocation (or, for `extractBytes32Array`/`extractSigArray` in the unguarded branch, `new byte[len][32]`/`new byte[len][65]`) can attempt to allocate gigabytes of heap in a single call, throwing an `OutOfMemoryError` during transaction execution. Since precompile execution happens deterministically as part of block application on every full node validating the block, this can crash or destabilize all validating nodes processing the same transaction, resulting in a node-crash/denial-of-service condition (and potential chain-halt risk if enough nodes are affected simultaneously).

### Likelihood Explanation
Reachability requires only that `allowTvmSelfdestructRestriction()` be inactive while `allowTvmSolidity059()` (which gates the precompiles themselves) is active — a plausible configuration for any java-tron-based chain that has enabled Solidity 0.5.9 support (needed to reach the precompiles at all) but not yet enabled the later self-destruct-restriction hard fork, or for any fork/derivative of this codebase where the two flags are toggled independently. I was unable to fully confirm within available time whether `allowTvmSelfdestructRestriction` is unconditionally active by default on the primary java-tron mainnet configuration (its default/activation status is governed by `ProposalUtil`/`DynamicPropertiesStore`, which I located but did not fully trace); this affects whether the vulnerable branch is currently live on the canonical mainnet versus only reachable on chains where that specific proposal has not been passed.

### Recommendation
- Add an unconditional upper bound (e.g., `MAX_SIZE`) check on the decoded length in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves, independent of `VMConfig.allowTvmSelfdestructRestriction()`, before any array allocation occurs.
- Additionally validate `offset + len` against `words.length` before allocation to avoid both the excessive-allocation and the later out-of-bounds read.
- Consider making the size validation logic identical (and equally strict) regardless of feature-flag state, so removal/rollback of a hard fork flag cannot silently reintroduce an unbounded-allocation path.

### Proof of Concept
1. Craft ABI-encoded call data for `batchvalidatesign(bytes32,bytes[],address[])` (or `validatemultisign(...)`) where the offset word for the `address[]` (or `bytes[]`) parameter points to a length word containing a very large value (e.g., `0x7FFFFFFF`), while `VMConfig.allowTvmSelfdestructRestriction()` is inactive.
2. Deploy a trivial contract that performs a raw `CALL` (via inline assembly or a low-level call) to the precompile address (`BatchValidateSign`/`ValidateMultiSign`) with this crafted calldata, supplying enough gas/energy for the call to be dispatched (the energy cost formula for these precompiles is computed from `data.length`, not from the decoded array length, so a compact crafted calldata with a huge embedded length value can pass energy checks cheaply). [8](#0-7) 
3. Broadcast the transaction; when nodes execute it, `extractBytes32Array`/`extractBytesArray` will attempt `new byte[0x7FFFFFFF][]`, causing an `OutOfMemoryError` on the executing node(s).

          bytesLen);
    }
    return bytesArray;
  }
