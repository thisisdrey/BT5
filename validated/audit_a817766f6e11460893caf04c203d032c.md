### Title
Stale learned/reported underlay addresses bypass `lighthouse.remote_allow_list` after policy tightening on reload - (File: remote_list.go)

### Summary
`RemoteList.unlockedCollect` reconstructs the deduplicated address list used for handshakes purely from the cached `learned`/`reported` per-owner entries, filtering only via `unlockedIsBad` (block list). It does not re-invoke `shouldAdd` (which wraps `lighthouse.remote_allow_list`/`remote_allow_ranges`) on cached entries — that check is only applied at insertion time in `unlockedSetV4`/`unlockedSetV6` via the `check` callback, and in `shouldAdd` for DNS-derived static entries.

### Finding Description
Reported/learned addresses are written into a `RemoteList`'s internal `cache` map via `unlockedSetV4`, `unlockedSetV6`, `unlockedSetLearnedV4`, and `unlockedSetLearnedV6` [5](#0-4) . The `unlockedSetV4`/`unlockedSetV6` variants take a `check` function that is expected to filter entries against the currently configured `RemoteAllowList` at the time of write (see `lh.shouldAdd`, `lh.unlockedShouldAddV4/V6` in `lighthouse.go`, which call `lh.GetRemoteAllowList().Allow(...)`) [6](#0-5) .

However, once an address has passed this check and is stored in the cache, `unlockedCollect` — the function that actually produces the list of addresses used for handshakes (`ForEach`, `CopyAddrs`, `Len`) — only excludes addresses present in `badRemotes` via `unlockedIsBad`; it re-adds every cached `learned`/`reported` v4/v6 address unconditionally [7](#0-6) . When an operator tightens `lighthouse.remote_allow_list`/`remote_allow_ranges` via a config reload (`lh.reload`, which atomically swaps `lh.remoteAllowList` — see `lighthouse.go` lines 244-254 in the earlier search) intending to revoke trust in a previously-allowed underlay address/range, any address that was already cached in an existing `RemoteList` before the reload remains in the deduplicated `addrs` slice indefinitely, because the revocation is never propagated to the already-collected cache entries — there is no invalidation of `shouldRebuild`/cache purge tied to a `remoteAllowList` change.

This is structurally identical to the Governance `vote` bug: an authorization decision (`userVotes`/`shouldAdd` check) is captured once, into a value that a later "once-applied" collection/consumption path (`vote`'s tally / `unlockedCollect`'s rebuild) treats as durable, and subsequent changes to the authoritative state (mint/burn votes / `remoteAllowList` reload) are not reconciled back into that cached decision.

### Impact Explanation
If an operator revokes trust for an underlay IP/range via `lighthouse.remote_allow_list` (e.g., after detecting it should no longer be reachable, or after an IP is reassigned to an untrusted network), nebula will continue to attempt handshakes to and accept lighthouse-learned/reported addresses for that IP for any host whose `RemoteList` had already cached it — silently defeating the intended network-level restriction without requiring any attacker action beyond having been reachable/reported before the policy change. This is a firewall/address-trust bypass in the sense that a config-driven access restriction fails to apply retroactively to already-cached remote endpoints.

### Likelihood Explanation
Likelihood is moderate: it requires an admin-driven `remote_allow_list` tightening while existing `RemoteList` caches already contain the now-disallowed address (a routine operational scenario, e.g. reducing scope after suspecting compromise or reassigning subnets), and there is no code path that purges or re-validates `cache` entries against a freshly reloaded `remoteAllowList`.

### Recommendation
When `lighthouse.reload` detects `lighthouse.remote_allow_list` or `lighthouse.remote_allow_ranges` has changed, iterate all `RemoteList`s (via `lh.addrMap`) and either (a) purge/re-filter their `cache` entries against the new `RemoteAllowList`, or (b) have `unlockedCollect` re-apply `r.shouldAdd` to every cached `learned`/`reported` entry (not just DNS-derived `hr.GetAddrs()` entries) on every rebuild, mirroring how `unlockedIsBad` is already re-checked on every collect.

### Proof of Concept
Conceptual repro:
1. Configure `lighthouse.remote_allow_list` to allow `10.0.0.0/8`.
2. Have a peer report/learn an address in `10.0.0.0/8`; this gets stored in the peer's `RemoteList.cache` via `unlockedSetV4`/`unlockedPrependV4`/`unlockedSetLearnedV4`.
3. Reload config, changing `lighthouse.remote_allow_list` to deny `10.0.0.0/8`. `lh.remoteAllowList` is atomically swapped, but the existing `RemoteList.cache` is untouched.
4. Call `ForEach`/`CopyAddrs` on that `RemoteList` (as `handleOutbound` does for handshaking) — `unlockedCollect` still returns the now-disallowed `10.0.0.0/8` address because only `unlockedIsBad` is checked, not `shouldAdd`.
5. nebula will continue to attempt/accept handshakes to that address, defeating the reloaded restriction.

// Rebuild locks and generates the deduplicated address list only if there is work to be done
// There is generally no reason to call this directly but it is safe to do so
func (r *RemoteList) Rebuild(preferredRanges []netip.Prefix) {
	r.Lock()
	defer r.Unlock()

	// Only rebuild if the cache changed
	if r.shouldRebuild {
		r.unlockedCollect()
		r.shouldRebuild = false
	}

	// Always re-sort, preferredRanges can change via HUP
	r.unlockedSort(preferredRanges)
}

	addrs := r.addrs[:0]
	relays := r.relays[:0]

	for _, c := range r.cache {
		if c.v4 != nil {
			if c.v4.learned != nil {
				u := protoV4AddrPortToNetAddrPort(c.v4.learned)
				if !r.unlockedIsBad(u) {
					addrs = append(addrs, u)
				}
			}

			for _, v := range c.v4.reported {
				if v == nil {
					continue
				}
				u := protoV4AddrPortToNetAddrPort(v)
				if !r.unlockedIsBad(u) {
					addrs = append(addrs, u)
				}
			}
		}

		if c.v6 != nil {
			if c.v6.learned != nil {

// unlockedShouldAddV4 checks if to is allowed by our allow list
func (lh *LightHouse) unlockedShouldAddV4(vpnAddr netip.Addr, to *V4AddrPort) bool {
	udpAddr := protoV4AddrPortToNetAddrPort(to)
	allow := lh.GetRemoteAllowList().Allow(vpnAddr, udpAddr.Addr())
	if lh.l.Enabled(context.Background(), logging.LevelTrace) {
		lh.l.Log(context.Background(), logging.LevelTrace, "remoteAllowList.Allow",
			"vpnAddr", vpnAddr,
			"udpAddr", udpAddr,
			"allow", allow,
		)
	}

	if !allow {
		return false
	}

	if lh.myVpnNetworksTable.Contains(udpAddr.Addr()) {
		return false
	}

	return true
}
