### Title
Group-level rate limit check reads a stale, unincremented counter — unrelated user withdraw/borrow flows can collectively bypass the configured group outflow cap - (File: `programs/marginfi/src/utils/general.rs`)

### Summary
`record_withdrawal_outflow` validates every withdraw/borrow against the group's `rate_limiter` counters, but that counter is explicitly documented and implemented as **read-only** during user transactions — it is only mutated later by a privileged off-chain-aggregated call to `update_group_rate_limiter`. This is the same root-cause pattern as the Olympus finding: a value used to gate a condition (endorsement total / here, "remaining rate-limit capacity") is not updated in lock-step with the real-time state it is supposed to represent (votes burned / here, tokens actually withdrawn), so unprivileged users can act repeatedly against the same stale snapshot and collectively exceed the intended limit.

### Finding Description
`record_withdrawal_outflow` in `programs/marginfi/src/utils/general.rs` (lines 464-525) performs the group-level rate-limit check like this: [1](#0-0) 

For each hourly/daily window it computes `group.rate_limiter.hourly.effective_remaining_capacity(clock.unix_timestamp)` and simply compares the *current* transaction's USD value against that number — it never decrements/updates `group.rate_limiter` in the same instruction. This is confirmed by the project's own documentation and test suite: [2](#0-1) 

And explicitly verified by a test named `"(user 2) group rate limiter is read-only during user instructions"`: [3](#0-2) 

The counter is only advanced later, by `update_group_rate_limiter`, called by the `delegate_flow_admin` after off-chain aggregation of `RateLimitFlowEvent`s: [4](#0-3) 

Because the on-chain check in every `lending_account_withdraw` / `lending_account_borrow` / integration withdraw path (`kamino`, `drift`, `juplend`, `solend`) reads the *same unmutated* `remaining` value until the admin settles a batch, any number of withdraw/borrow calls — from the same account or many different unprivileged accounts across the whole group — submitted before the next admin settlement will each independently pass the check as long as each *individual* transaction's outflow is under the configured cap, even though their sum vastly exceeds it. This directly mirrors the Olympus root cause: the gating value (`totalEndorsementsForProposal` / here, "remaining group capacity") is stale relative to the real underlying state (`VOTES.balanceOf` / here, real-time aggregate outflow), so the check permits a condition (proposal activation / here, capacity availability) that should no longer hold.

This is reachable entirely by unprivileged users calling ordinary `lending_account_withdraw`/`lending_account_borrow` (and Kamino/Drift/JupLend/Solend withdraw variants), which are core accounting/borrow/withdraw paths, not privileged-admin-only actions.

### Impact Explanation
The group rate limiter is documented as "a defense if the risk workflow is abused or compromised" and is meant to cap aggregate USD outflow from the group in an hour/day window. Because the check is read-only and only reconciled asynchronously by an off-chain admin process (with up to `~1500` slots / ~10 minutes of allowed lag, per `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS`), unprivileged users can, within that settlement window, submit many withdraw/borrow transactions that are each individually within the cap but collectively far exceed the group's configured hourly/daily outflow limit. This defeats the purpose of the protection during exactly the scenario it is meant to guard against (a compromised or delayed risk process), enabling much larger uncontrolled capital outflow from the group than intended. It does not directly cause insolvency by itself (bank-level rate limits and health checks still apply per bank/account), but it is a genuine unauthorized-state-change/bypass of a protocol-level protection along real, unprivileged, user-reachable withdraw/borrow paths.

### Likelihood Explanation
Likelihood is moderate: it requires the group rate limiter to be enabled and requires either (a) many withdrawals from independent unprivileged accounts within the settlement lag window, or (b) rapid repeated withdrawals from a single account before the off-chain worker aggregates and posts an update. Given documented behavior (tests explicitly demonstrate group state remains unchanged across user borrow/repay calls until an admin batch lands), this is a design-confirmed, not speculative, gap — any group relying on this limiter as a hard cap rather than an advisory metric is exposed for the duration of each settlement cycle.

### Recommendation
Either (1) make the group-level counter update atomically within the same instruction that performs the withdraw/borrow (accepting the group account write-lock/serialization cost this was designed to avoid), or (2) enforce a hard per-transaction/per-slot ceiling in addition to the async aggregate check so that no single settlement window can be exploited to drain more than a bounded multiple of the configured cap, or (3) shrink `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` significantly and require more frequent settlement, and add a compensating conservative "reserved" capacity that is optimistically decremented (even if approximately) at the time of each read-only check to prevent double-spending capacity across the same window before settlement.

### Proof of Concept
This scenario mirrors the project's own test (`"(admin) batched event aggregation - multiple actions then single admin update"`), which demonstrates the exact bypass window: multiple sequential borrows are each individually validated against the same unmutated `group.rate_limiter.hourly.curWindowOutflow`, allowing them to accumulate past the configured hourly limit before the admin settlement call catches up: [5](#0-4) 

In this test, with a configured group hourly cap of `10` USD, actions 1–4 (borrow 3, borrow 2, repay 1, borrow 1 = net outflow of 6) each pass the read-only check independently and are only reconciled afterward by the admin's batched `update_group_rate_limiter` call — proving that, absent the admin settlement, a sequence of unprivileged withdraw/borrow calls can exceed the configured group cap for the entire lag window (up to `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` = 1500 slots) before it is ever enforced against the true aggregate.

### 2. User transaction path

During a withdraw or borrow:

- The bank rate limiter is updated immediately on the writable bank account.
- The group rate limiter is only checked read-only.
- The protocol converts the flow to USD using the instruction price/oracle path.
- If the projected group hourly or daily capacity is exceeded, the user instruction fails.
- A `RateLimitFlowEvent` is emitted for off-chain aggregation.

Important details:

- Flashloans, liquidations, and deleverages skip the normal rate-limit accounting path.
- `RateLimitFlowEvent` is an indexing aid, not a source of truth. Solana log truncation can drop
  events, so the off-chain worker must reconcile gaps instead of assuming no event means no flow.

    // Simulates production flow: multiple user actions happen over a period,
    // admin aggregates all emitted events and calls updateGroupRateLimiter once.
    await setRateLimits({
      bankHourly: usdcNative(1_000),
      bankDaily: new BN(0),
      groupHourly: new BN(10),
      groupDaily: new BN(0),
    });

    const allEvents: RateLimitFlowEvent[] = [];

    // Action 1: Borrow 3 USDC
    const events1 = await borrowUsdcWithEvents(usdcNative(3));
    allEvents.push(...events1);

    // Action 2: Borrow 2 USDC
    const events2 = await borrowUsdcWithEvents(usdcNative(2));
    allEvents.push(...events2);

    // Action 3: Repay 1 USDC
    const events3 = await repayUsdcWithEvents(usdcNative(1));
    allEvents.push(...events3);

    // Action 4: Borrow 1 USDC
    const events4 = await borrowUsdcWithEvents(usdcNative(1));
    allEvents.push(...events4);

    // Verify all events were captured
    assert.equal(allEvents.length, 4, "Should have 4 events total");

    // Admin aggregates all events at once (as would happen in production every ~10 minutes)
    const { totalOutflowUsd, totalInflowUsd } = aggregateFlowEvents(allEvents);
    assert.equal(totalOutflowUsd, 6, "3 + 2 + 1 = 6 USDC outflow");
    assert.equal(totalInflowUsd, 1, "1 USDC inflow");

    // Group state should still be unchanged (read-only during user instructions)
    const groupBeforeAdmin = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    assertBNEqual(groupBeforeAdmin.rateLimiter.hourly.curWindowOutflow, 0);

    // Admin submits both outflow and inflow in a single update
    await adminUpdateGroupRateLimiter({
      outflowUsd: new BN(totalOutflowUsd),
      inflowUsd: new BN(totalInflowUsd),
    });

    // Net outflow = 6 - 1 = 5
    const groupAfterAdmin = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );

pub fn update_group_rate_limiter(
    ctx: Context<UpdateGroupRateLimiter>,
    outflow_usd: Option<u64>,
    inflow_usd: Option<u64>,
    update_seq: u64,
    event_start_slot: u64,
    event_end_slot: u64,
) -> MarginfiResult {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let clock = Clock::get()?;

    check!(
        outflow_usd.is_some() || inflow_usd.is_some(),
        MarginfiError::GroupRateLimiterUpdateEmpty
    );
    validate_event_slots(
        event_start_slot,
        event_end_slot,
        group.rate_limiter_last_admin_update_slot,
    )?;
    check!(
        event_end_slot <= clock.slot,
        MarginfiError::GroupRateLimiterUpdateFutureSlot
    );
    check!(
        clock.slot.saturating_sub(event_end_slot) <= MAX_RATE_LIMIT_UPDATE_LAG_SLOTS,
        MarginfiError::GroupRateLimiterUpdateStale
    );
    check!(
        update_seq == group.rate_limiter_last_admin_update_seq.saturating_add(1),
        MarginfiError::GroupRateLimiterUpdateOutOfOrderSeq
    );

    if let Some(inflow) = inflow_usd {
        check!(
            is_valid_rate_limit_amount(inflow),
            MarginfiError::InvalidConfig
        );
        group
            .rate_limiter
            .record_inflow(inflow, clock.unix_timestamp);
        msg!("Group rate limiter inflow recorded: {} USD", inflow);
    }

    if let Some(outflow) = outflow_usd {
        group
            .rate_limiter
            .try_record_outflow(outflow, clock.unix_timestamp)?;
        msg!("Group rate limiter outflow recorded: {} USD", outflow);
    }
