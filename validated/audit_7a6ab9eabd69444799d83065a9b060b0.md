Confirmed: "receipt atomicity" means a failed receipt (including out-of-gas panics) triggers `state_update.rollback()`, discarding *all* state changes made during that receipt's execution [1](#0-0) . Since every callback that resets `has_in_flight_tx = false` does so as its first statement but that write is part of the same receipt execution, a later panic (e.g. gas exhaustion) in that same callback discards the reset along with everything else, leaving the flag permanently `true`.

### Title
Eth-implicit Wallet Contract can be permanently DoS'd (funds frozen) via a single cheap in-flight-lock that never clears - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The `WalletContract` (the eth-implicit account's `rlp_execute` entry point) guards against concurrent transactions with a boolean `has_in_flight_tx` flag that is set to `true` before dispatching a cross-contract promise and is only ever cleared inside one of the promise's callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). If the scheduled callback fails to execute successfully — most notably by exceeding its allotted gas — the entire receipt (including the `has_in_flight_tx = false` write at its start) is rolled back by the runtime's atomic-receipt-rollback rule, leaving the flag stuck at `true` forever. Because `rlp_execute` unconditionally refuses to start a new transaction whenever `has_in_flight_tx == true`, and there is no other public method to reset it, the wallet becomes permanently unusable, freezing all funds held by that eth-implicit account. This mirrors the reported Buyout bug's core defect: a cheap, unprivileged action can lock a shared, single-instance resource (here, the wallet's "in-flight transaction" slot) with no way for anyone to un-stick it.

### Finding Description
`WalletContract::rlp_execute` checks `has_in_flight_tx` first and immediately returns an error if a transaction is already "in flight" [2](#0-1) . On the success path it sets `self.has_in_flight_tx = true` and returns a cross-contract `Promise` [3](#0-2) .

The flag is only cleared as the very first line of each subsequent callback — `address_check_callback` [4](#0-3) , `nep_141_storage_balance_callback` [5](#0-4) , `rlp_execute_callback` [6](#0-5) , and `ban_relayer` [7](#0-6) . There is no timeout mechanism and no other method that can reset it.

The `nep_141_storage_balance_callback` path is reachable for an emulated ERC-20 transfer whose `target` (the token contract) is attacker-controlled input decoded from the signed RLP transaction, and it deserializes an arbitrary `storage_balance_of` response returned by that contract with `serde_json::from_slice` before doing anything else [8](#0-7) . The static gas budget for this callback chain is fixed at deploy time (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS = 5 Tgas + NEP_141_STORAGE_DEPOSIT_GAS + RLP_EXECUTE_CALLBACK_GAS`, plus `action.gas()`) [9](#0-8) , so a malicious/attacker-deployed token contract can return an oversized or adversarially crafted JSON payload that exhausts that fixed gas budget during parsing, causing the callback to abort with `GasExceeded`.

Per the runtime's own execution model, "a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting" [10](#0-9) , and this rollback is implemented at `Runtime::apply_action_receipt`'s commit/rollback point [1](#0-0) . Because the `has_in_flight_tx = false` write happens inside that same failing receipt, it is discarded along with the rest of the callback's effects, and the flag remains permanently `true`. The nearcore project's own test suite for this contract confirms and relies on the reverse case ("the contract is still usable afterwards" when `rlp_execute` itself, not a callback, fails on insufficient gas) [11](#0-10) , but there is no equivalent test/guard for a callback failing after the flag has already been set to `true`.

### Impact Explanation
Once `has_in_flight_tx` gets stuck at `true`, every future call to `rlp_execute` — from the legitimate owner or any relayer — immediately short-circuits with "transaction already in progress" and never creates a new promise [12](#0-11) . Since ETH-implicit accounts can only be operated through `rlp_execute` (they cannot be assigned a full-access key or use standard NEAR actions directly) [13](#0-12) , this permanently and irrecoverably freezes all NEAR and token balances controlled by that account. This satisfies the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
The attack only requires the account owner (or a relayer acting on their signed intent) to route an ERC-20-style transfer through a token contract that the attacker controls, which is a routine/expected interaction pattern for this wallet (the entire feature exists to let ETH-style tooling interact with arbitrary token contracts). An attacker who deploys such a token contract can unconditionally return an oversized `storage_balance_of` response to trigger the gas-exhaustion rollback; no special privilege, large deposit, or race condition is required — mirroring the "cheap, unprivileged lock with no recovery path" nature of the original Buyout bug.

### Recommendation
- Ensure `has_in_flight_tx` can never get stuck by decoupling the reset from the same fallible receipt, e.g., persist the reset via a separate always-succeeding low-gas step, or use a timeout-based fallback (analogous to `yield_timeout_length_in_blocks`) that force-clears the flag after N blocks if no callback has resolved it.
- Bound the gas consumed by parsing arbitrary cross-contract responses (e.g., cap response size before `serde_json::from_slice`, or reserve a minimum unconditional gas budget sufficient to always execute the flag-reset regardless of parsing outcome).
- Add a privileged/self-service "unstick" method (e.g., callable only by the account owner via a fresh valid RLP transaction with elevated gas) that can force-clear `has_in_flight_tx` after a protocol-defined number of blocks with no resolution.

### Proof of Concept
1. Deploy a malicious contract at some `token_id` account that implements `storage_balance_of` to return a very large JSON payload (e.g., megabytes of padding) instead of a small `Option<StorageBalance>`.
2. Have the ETH-implicit account owner (or a cooperating/tricked relayer) sign and submit an RLP-encoded `ERC20Transfer`-style transaction with `target = token_id`.
3. `rlp_execute` → `inner_rlp_execute` builds the promise chain `storage_balance_of` → `nep_141_storage_balance_callback`, and sets `has_in_flight_tx = true` [14](#0-13) .
4. The malicious contract's oversized response causes `serde_json::from_slice` inside `nep_141_storage_balance_callback` to exceed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, aborting the receipt with `GasExceeded`.
5. Per the runtime's atomic rollback rule [1](#0-0) , the `self.has_in_flight_tx = false` write at the top of the callback is discarded along with everything else in that failed receipt.
6. Any subsequent call to `rlp_execute` on this account now always returns `"transaction already in progress"` and never issues a promise, permanently freezing the account.

(Note: full verification would require compiling and running this scenario in a sandboxed NEAR test environment, e.g., via a Devin session, since exact gas costs of `serde_json::from_slice` for a given payload size were not measured here.)
