### Title
Attached deposit is permanently lost when `address_check_callback` short-circuits on the Address Registrar path - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In the eth-implicit `WalletContract`, `rlp_execute` is `#[payable]`, so any NEAR attached by a caller is deposited into the wallet's own account balance immediately, before execution. To make this safe for external (non-owner) callers, the contract tracks the attached amount as a `CallerDeposit` and threads it through the promise chain so it can be refunded if the underlying cross-contract call fails, exactly as demonstrated by `rlp_execute_callback`'s `PromiseResult::Failed` branch. However, `address_check_callback` — the callback used specifically for EOA-emulated base-token transfers whose target needs an address-registrar lookup — receives the same `caller_deposit: Option<CallerDeposit>` parameter but drops it on every one of its early-return failure paths instead of issuing a refund.

### Finding Description
`inner_rlp_execute` computes `caller_deposit` via `CallerDeposit::new(&context)` for any caller other than the wallet's own account, and only refunds it in `rlp_execute_callback` when the final promise fails: [1](#0-0) 

For the `EOABaseTokenTransfer { address_check: Some(address), .. }` transaction kind, execution instead first calls the address registrar and chains into `address_check_callback`, forwarding `caller_deposit`: [2](#0-1) 

But inside `address_check_callback`, every early-return branch discards `caller_deposit` without refunding it:
- when the registrar call itself fails,
- when the registrar's response fails to deserialize,
- and — most importantly — when the registrar reports the target address maps to an *existing named account* and the caller is not the wallet owner itself (`signer_account_id != current_account_id`): [3](#0-2) 

The `CallerDeposit` type and its intended purpose (refund the external caller's deposit if the emulated call ultimately fails) is documented at: [4](#0-3) 

In all three of these branches, `has_in_flight_tx` is reset and an `ExecuteResponse{success: false, ...}` is returned directly — no `promise_batch_action_transfer` is ever issued for `caller_deposit`, unlike the equivalent failure branch in `rlp_execute_callback`. The last of the three branches (`"Invalid target: target is address corresponding to existing named account_id"`) is fully attacker-controlled and deterministic: any unprivileged caller can construct/relay an RLP-encoded Ethereum base-token transfer whose `to` address resolves (via the on-chain address registrar) to an already-registered named NEAR account, attach NEAR to the `rlp_execute` call, and reliably hit this branch.

### Impact Explanation
Any NEAR value an external, unprivileged caller attaches to `rlp_execute` when the call is routed through `address_check_callback` and any of its failure branches trigger is permanently absorbed into the wallet contract's balance instead of being refunded to the caller. This is a concrete, deterministic loss of funds for an ordinary user/relayer interacting with the eth-implicit wallet contract — directly analogous to the Solidity finding where `msg.value` sent alongside a failing/short-circuiting call path is silently kept by the receiving contract instead of refunded. Because the wallet contract is meant to be broadly deployed for every eth-implicit account, this affects any user of that contract type, not a single victim.

### Likelihood Explanation
High for the "existing named account" branch: a caller only needs to attach a deposit to a `rlp_execute` call whose decoded action is an `EOABaseTokenTransfer` with `address_check: Some(address)`, and choose (or be routed by any relayer to) a target address that the on-chain Address Registrar already maps to a named account — a state fully observable/queryable ahead of time by an attacker or even accidentally hit by a legitimate relayer. No special privileges, races, or malicious validators are required; this is purely a client-facing contract-call bug reachable from an ordinary signed transaction.

### Recommendation
In `address_check_callback`, thread the `caller_deposit` refund logic into every early-return path exactly as done in `rlp_execute_callback`: before returning `ExecuteResponse{success: false, ...}` for the `PromiseResult::Failed` case, the deserialize-error case, and the "target is address corresponding to existing named account_id" case, issue `env::promise_batch_create` + `env::promise_batch_action_transfer` to refund `caller_deposit` (when `Some`), mirroring the pattern already used in `rlp_execute_callback`.

### Proof of Concept
1. Deploy/observe an eth-implicit `WalletContract` and identify (or wait for) a target Ethereum address whose corresponding Near account is already registered as a named account in the on-chain Address Registrar contract.
2. As any external account (not the wallet owner), submit `rlp_execute(target, tx_bytes_b64)` with an attached NEAR deposit, where `tx_bytes_b64` decodes (via `parse_rlp_tx_to_action`/`eth_emulation::try_emulation`) to an `EOABaseTokenTransfer` whose `TargetKind` is `EthImplicit(address)`, forcing `address_check: Some(address)`.
3. `inner_rlp_execute` computes a non-`None` `CallerDeposit` for the caller (since caller != wallet account) and dispatches the registrar lookup, chaining into `address_check_callback` with `caller_deposit` forwarded, per [2](#0-1) .
4. Because the target's address is already a named account and the caller is not `current_account_id`, `address_check_callback` returns `ExecuteResponse{success:false, error: Some("Invalid target: ...")}` at [5](#0-4)  without ever refunding `caller_deposit`.
5. The caller's attached NEAR deposit remains in the wallet contract's balance permanently; observe the caller's account balance dropped by the deposit amount with no compensating refund receipt, in contrast to the refund behavior asserted for the `rlp_execute_callback` failure path (`test_caller_refunds`) at [6](#0-5) .

    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
