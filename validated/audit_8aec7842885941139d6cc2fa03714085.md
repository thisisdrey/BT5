This confirms the invariant described in the question holds: `result.apply(account, access_key)` at `runtime/runtime/src/lib.rs:2266` mutates the access key's nonce immediately during transaction-to-receipt conversion within the same `apply` call, and `set_account`/`set_access_key` (line 2267 onward) persist this to the trie state that gets committed for that chunk — regardless of whether the resulting receipt (`create_receipt_id_from_transaction` at line 2176) is executed immediately or pushed to the delayed queue. The nonce advancement is decoupled from receipt execution entirely. [1](#0-0) [2](#0-1) 

### Analysis

Because the access-key nonce is committed to state as part of the same chunk's `apply` call that converts the transaction into a receipt (not deferred until the receipt executes), a resubmission of the identical signed transaction (same nonce) in chunk N+1 will be checked against the already-advanced `access_key.nonce` via `verify_nonce` at `runtime/runtime/src/verifier.rs:211-236`. Since `Monotonic` mode requires `tx_nonce > current_nonce` (and `Strict` requires exact `+1`), the resubmission's nonce will already equal or be less than the stored nonce, causing `InvalidTxError::InvalidNonce` before any receipt-id computation is reached. [3](#0-2) 

The `create_receipt_id_from_transaction(tx_hash, block_height)` salt difference between chunks is irrelevant here because the fresh resubmission never reaches receipt creation — it is rejected at the nonce-verification stage in `process_transactions`, well before `TxVerdict::Success` would trigger `create_receipt_id_from_transaction` at `runtime/runtime/src/lib.rs:2176`. [4](#0-3) 

The existing test `test_apply_delayed_receipts_local_tx` at `runtime/runtime/src/tests/apply.rs:571` already demonstrates the delayed-receipt mechanics (TX#3's receipt is delayed to a later chunk while the tx itself is fully converted/charged in the earlier chunk), and the nonce/state-mutation code path confirms no double-receipt or nonce-replay is possible.
