## Analysis

I traced the FeeAuction "buy zero assets" bug class — a payout function that unconditionally advances settlement state (bookkeeping) while the actual asset transfer can silently fail or transfer nothing — to a structurally identical pattern in `pallet-broker`'s `do_claim_revenue`.

### Title
Instapool revenue claim burns the contribution record and mutates payout accounting even when the underlying currency transfer fails - (File: `substrate/frame/broker/src/dispatchable_impls.rs`)

### Summary
`Pallet::do_claim_revenue` (invoked by the public, unprivileged `claim_revenue` extrinsic) takes and permanently consumes the caller's `InstaPoolContribution` record and reduces/removes the shared `InstaPoolHistory` payout bookkeeping *before* checking whether the actual `T::Currency::transfer` from the pot account to the claimant succeeded. The transfer result is discarded via `.defensive_ok()`, so a failed transfer never rolls back or blocks the accounting mutation — exactly the same broken invariant as the FeeAuction `_transferOutAssets` bug: settlement state advances unconditionally, independent of whether tokens actually moved.

### Finding Description [1](#0-0) 

Walking through `do_claim_revenue`:
1. `InstaPoolContribution::<T>::take(region)` immediately removes the caller's contribution entry — this is the "ticket" that entitles them to a payout, and it is consumed unconditionally at the start. [2](#0-1) 
2. For each timeslice, `InstaPoolHistory` records are read, `private_contributions` is reduced and the record is updated or removed, and `payout` is accumulated — all before any currency movement occurs. [3](#0-2) 
3. Only after all bookkeeping is finalized does the pallet attempt to actually pay out, and it swallows any error:
```rust
T::Currency::transfer(&Self::account_id(), &contribution.payee, payout, Expendable)
    .defensive_ok();
``` [4](#0-3) 
4. Regardless of transfer outcome, the pallet still emits `RevenueClaimPaid { who, amount: payout, next }` as if payment succeeded. [5](#0-4) 

This mirrors the FeeAuction flaw precisely: `_transferOutAssets` transfers "if balance > 0" but never reverts if nothing was transferred, and the auction's price/state still advances as though the buy succeeded. Here, the entitlement bookkeeping (`InstaPoolContribution`, `InstaPoolHistory.private_contributions`, `maybe_payout`) is consumed/mutated unconditionally, while the actual `Currency::transfer` from the shared pot account (`Self::account_id()`) may fail and is masked by `.defensive_ok()`.

### Impact Explanation
Because the entitlement record is taken (`take`) and the pool history is mutated *before* the transfer is attempted, any transfer failure results in **permanent loss of the claimant's revenue share** with no possibility of retry — the `InstaPoolContribution` is gone and the `InstaPoolHistory.private_contributions`/`maybe_payout` for that timeslice have already been reduced/removed as if the payout had been distributed. The funds remain stuck in the pallet's pot account (`Pallet::account_id()`), unclaimable by anyone, since the bookkeeping that would identify the shortfall is destroyed. This matches the "permanent user-fund lock" and "duplicate/incorrect settlement" impact categories called out in the gate.

### Likelihood Explanation
`claim_revenue` is a fully public, unprivileged, signed-origin extrinsic [6](#0-5) . No malicious peer, validator, collator, or admin is required — any discrepancy between the tracked `maybe_payout` bookkeeping and the actual free balance of the pot account (e.g., from rounding/dust accumulated across many partial `saturating_*` divisions in the payout-splitting math, or from a `Currency::transfer` failure for any other legitimate reason under `Expendable` preservation) silently triggers the bug on the very first affected claim.

### Recommendation
Perform the `T::Currency::transfer` first and propagate its error (`?`) before mutating or removing `InstaPoolContribution`/`InstaPoolHistory`, so a failed transfer aborts the whole extrinsic and leaves the entitlement intact for a retry — analogous to requiring `_transferOutAssets` to revert when the transferred sum is zero. Additionally, avoid emitting `RevenueClaimPaid` unless the transfer actually succeeded.

### Proof of Concept
1. Set up an Instapool contribution such that `InstaPoolHistory` records a `maybe_payout` for a timeslice, but arrange (via the accumulated rounding losses of `saturating_mul`/`checked_div` in the payout split, executed across enough partial claims/timeslices) for `Pallet::account_id()`'s actual free balance to fall short of the sum of outstanding `maybe_payout` entries.
2. Call `Broker::claim_revenue(origin, region_id, max_timeslices)` as the legitimate contributor.
3. Observe: `InstaPoolContribution` is removed, `InstaPoolHistory` for the timeslice is reduced/removed, `Event::RevenueClaimPaid` is emitted — but `T::Currency::transfer` failed internally (swallowed by `.defensive_ok()`), so the claimant's balance is unchanged and their entitlement is permanently gone with no state left to retry the claim.

	pub(crate) fn do_claim_revenue(
		mut region: RegionId,
		max_timeslices: Timeslice,
	) -> DispatchResult {
		ensure!(max_timeslices > 0, Error::<T>::NoClaimTimeslices);
		let mut contribution =
			InstaPoolContribution::<T>::take(region).ok_or(Error::<T>::UnknownContribution)?;
		let contributed_parts = region.mask.count_ones();

		Self::deposit_event(Event::RevenueClaimBegun { region, max_timeslices });

		let mut payout = BalanceOf::<T>::zero();
		let last = region.begin + contribution.length.min(max_timeslices);
		for r in region.begin..last {
			region.begin = r + 1;
			contribution.length.saturating_dec();

			let Some(mut pool_record) = InstaPoolHistory::<T>::get(r) else { continue };
			let Some(total_payout) = pool_record.maybe_payout else { break };
			let p = total_payout
				.saturating_mul(contributed_parts.into())
				.checked_div(&pool_record.private_contributions.into())
				.unwrap_or_default();

			payout.saturating_accrue(p);
			pool_record.private_contributions.saturating_reduce(contributed_parts);

			let remaining_payout = total_payout.saturating_sub(p);
			if !remaining_payout.is_zero() && pool_record.private_contributions > 0 {
				pool_record.maybe_payout = Some(remaining_payout);
				InstaPoolHistory::<T>::insert(r, &pool_record);
			} else {
				InstaPoolHistory::<T>::remove(r);
			}
			if !p.is_zero() {
				Self::deposit_event(Event::RevenueClaimItem { when: r, amount: p });
			}
		}

		if contribution.length > 0 {
			InstaPoolContribution::<T>::insert(region, &contribution);
		}
		T::Currency::transfer(&Self::account_id(), &contribution.payee, payout, Expendable)
			.defensive_ok();
		let next = if last < region.begin + contribution.length { Some(region) } else { None };
		Self::deposit_event(Event::RevenueClaimPaid {
			who: contribution.payee,
			amount: payout,
			next,
		});
		Ok(())
	}
