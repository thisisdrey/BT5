## Title
Insufficient domain separation in the `ValidateMultiSign` precompile allows signature/authorization replay across contracts and chains — (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
TRON exposes the `ValidateMultiSign` precompiled contract (address `0x...0a`) so that any TVM smart contract can verify an off-chain, pre-signed authorization against an on-chain account's active `Permission`/multisig threshold. The signed hash it checks is built as `sha256(address ‖ permissionId ‖ data)`, where `data` is an arbitrary 32-byte value supplied by the calling contract. This mirrors exactly the pattern flagged in the external report: an authorization token/signature that binds only to a user address and a caller-controlled value, with no binding to the destination/consuming contract address, no chain ID, and no expiry baked into the protocol-defined hash scheme.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute()` computes: [1](#0-0) 
and then recovers each signer and checks their weight against the target account's `Permission` via `TransactionCapsule.getWeight`: [2](#0-1) 

The hash that signers must sign to "authorize" an action is `sha256(address, permissionId, data)`. It never incorporates:
- the calling/destination contract's address (`address(this)` of the dApp consuming the approval),
- the chain ID, or
- an expiration time.

This is the same root cause as the Term Finance `TermAuth` finding: the authorization primitive encodes only the subject account and an application-chosen payload, so nothing in the protocol-level scheme prevents the same signed hash+signature pair from being replayed:
1. Against a *different* smart contract on the same TRON network that happens to compute an identical `(address, permissionId, data)` triple for a different, unintended operation, because `ValidateMultiSign` is a generic building block many independent dApps call with the same signature format and no caller-address binding.
2. On a *different* TRON-compatible chain (fork, sidechain, or another chain running java-tron) where the same account address/permission structure exists, since there is no chain ID mixed into the hash.

`TransactionCapsule.getWeight` / `checkWeight`, the same underlying primitive used for real transaction multisig, is bound implicitly to the transaction's own `TransactionId` (which includes tapos ref-block data unique to in-chain history): [3](#0-2) 
But `ValidateMultiSign`'s hash bypasses that protection entirely — it is a bare `sha256` of caller-supplied fields with no chain/contract binding, unlike a real transaction submission.

### Impact Explanation
Because TRON's own precompile-defined authorization hash lacks contract-address and chain-ID domain separation, a signature a user produces to authorize one specific action in one specific contract can be captured and replayed by:
- any other contract on the same chain that reconstructs the same `(address, permissionId, data)` triple to authorize a different, unintended action for that account, potentially enabling unauthorized account operations gated by that account's active permission/threshold, or
- the same signature replayed on a different but address-compatible TRON-based chain.

This maps to "unauthorized account operation" — the account's permission/multisig approval, meant for a single intended contract action, can be reused to approve an action the signer never intended, which is squarely within the accepted impact categories (unauthorized account operation).

### Likelihood Explanation
`ValidateMultiSign` is reachable by any account that deploys or calls a smart contract on TRON (no privileged role required) — it is a public precompile at a fixed address invoked via ordinary `CALL` opcodes from Solidity. Exploitation requires a scenario where two independently-deployed contracts (or the same contract deployed to two chains) compute the same `(address, permissionId, data)` hash for different intended actions, which is plausible given `data` is commonly a simple, low-entropy application-level "action" or "message" hash (e.g., "approve withdrawal of X") without additional binding — exactly the anti-pattern this precompile's fixed hash format encourages, since it gives contract authors no built-in field for contract-address/chain-ID separation.

### Recommendation
Extend the `ValidateMultiSign` (and the account-permission based multisig verification path in general) hash construction to mandatorily include the calling contract's address and `block.chainid`-equivalent chain identifier as part of the hashed payload, e.g. `sha256(address ‖ permissionId ‖ msg.sender/calling contract ‖ chainId ‖ data)`, and document/enforce this so dApps relying on the precompile cannot omit domain separation. Alternatively, provide the calling contract address and chain ID as additional, protocol-enforced inputs to the precompile rather than leaving all domain separation to be manually composed into the caller-supplied `data` field.

### Proof of Concept
1. Contract A calls `ValidateMultiSign(accountAddr, permissionId, dataHash, signatures)` to authorize "action X" for `accountAddr`, where `dataHash = keccak256("withdraw:1000")`.
2. `accountAddr`'s owner signs `sha256(accountAddr ‖ permissionId ‖ dataHash)` off-chain as instructed by Contract A's UI, believing it only authorizes withdrawal via Contract A.
3. Contract B (unrelated, deployed by an attacker) also calls `ValidateMultiSign(accountAddr, permissionId, dataHash, signatures)` — reusing the identical `(accountAddr, permissionId, dataHash)` triple (trivial to construct since `dataHash` is just a hash of a short descriptive string) — and treats a successful `ValidateMultiSign` result as authorization to perform its own action (e.g., transferring `accountAddr`'s TRC-20 balance it manages, or unlocking a vault), which the signer never intended.
4. Because the hash in `PrecompiledContracts.ValidateMultiSign.execute()` never binds to `msg.sender`/calling contract or chain ID, the replayed signature validates successfully in Contract B exactly as in Contract A. [4](#0-3)
