Confirmed: `getWithdrawRewardCost` in `EnergyCost.java` returns a fixed `WITHDRAW_REWARD = 20000` regardless of how much work `withdrawReward` actually performs. This confirms the fixed-cost/unbounded-computation mismatch.

### Title
Unbounded per-cycle reward computation loop lets a single transaction consume excessive computation for fixed energy/fee - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.withdrawReward`/`queryReward` (and the TVM-native counterparts `VoteRewardUtil.withdrawReward`/`queryReward`) compute vote rewards for an account by calling `computeReward(beginCycle, endCycle, accountCapsule)`. When the account's `beginCycle` predates `newRewardCalStartCycle` (i.e. `allowOldRewardOpt` has not kicked in for that account) and `allowOldRewardOpt()` is disabled, `getOldReward` executes a loop bounded only by the number of maintenance cycles that have elapsed since the account last interacted with voting/reward state, with no cap on that range, similar in spirit to the unbounded `fetchUnhealthyAccounts` loop in the reported bug.

### Finding Description
`MortgageService.withdrawReward(byte[] address)` and `MortgageService.queryReward(byte[] address)` compute `computeReward(beginCycle, endCycle, accountCapsule)` [1](#0-0) . Inside `computeReward`, if `beginCycle < newAlgorithmCycle` the old-algorithm path is taken via `getOldReward` [2](#0-1) . When `allowOldRewardOpt()` is not enabled, `getOldReward` runs an explicit unbounded `for (long cycle = begin; cycle < end; cycle++)` loop that performs a DB read (`getReward`/`getWitnessVote`) and iterates the account's full vote list on every single cycle: [3](#0-2) 

`beginCycle`/`endCycle` are per-account values persisted in `DelegationStore` and are only advanced when the account actually calls a reward/vote/freeze/unfreeze/delegate operation [4](#0-3) . If an account votes once and then never triggers any subsequent reward-affecting transaction for a very long time (many maintenance cycles, each cycle being one witness-maintenance period, on the order of hours), `beginCycle` stays frozen far in the past while `currentCycle` (network-wide) keeps advancing every maintenance period. The very first time such a dormant account calls any function that triggers `withdrawReward`/`queryReward` — including `UnfreezeBalanceActuator.execute` [5](#0-4) , `VoteWitnessActuator.countVoteAccount` [6](#0-5) , or the TVM `WITHDRAWREWARD` opcode via `Program.withdrawReward()` [7](#0-6)  — the entire elapsed-cycle range is walked synchronously inside a single block-applying transaction.

Crucially, the TVM entry point charges a fixed, cycle-count-independent energy cost: `getWithdrawRewardCost` always returns the constant `WITHDRAW_REWARD = 20000` [8](#0-7) , and `VoteWitnessProcessor`/`UnfreezeBalanceV2Processor` similarly do not scale gas with the number of elapsed cycles. This decouples the actual computational cost (proportional to the number of maintenance cycles elapsed) from the energy charged, mirroring the reported bug's root cause: an operation whose cost scales with an attacker/user-influenced unbounded quantity (number of accounts in the liquidation bot report; number of elapsed cycles here) is not capped or priced accordingly.

### Impact Explanation
A single ordinary, unprivileged transaction (unfreeze, vote, delegate/undelegate, or a smart contract invoking `WITHDRAWREWARD`/`VOTEWITNESS`) from an account that has been dormant for a long stretch of cycles can force the node to perform a large linear scan over `DelegationStore` reward/vote-count entries during block application, for a flat, underpriced energy fee. Because this executes inside `Manager`'s transaction-processing/block-application path, excessive execution time in one transaction directly impacts block production and can degrade node performance or delay block processing across the network — a resource-exhaustion/DoS class issue reachable by any account holder, not just miscellaneous background jobs.

### Likelihood Explanation
Likelihood depends on how many cycles an account can accumulate without interacting with the network is not artificially bounded in the code path itself (`beginCycle` is only updated by an actual withdraw/vote/freeze action), so an attacker can pre-position an account, let cycles accrue for a long period, then submit one cheap transaction to trigger the full backlog computation. The `allowOldRewardOpt()` flag and the amortized `RewardViCalService` mechanism cover the *new* reward algorithm going forward, but the un-amortized `getOldReward` loop remains reachable for any account whose accumulated backlog predates `newRewardCalStartCycle`, and there is no general cap preventing extreme backlog growth for currently-active or newly affected accounts under other configurations.

### Recommendation
Bound the maximum number of un-amortized cycles that can be computed in a single transaction (e.g., cap `end - begin` and process the remainder incrementally across multiple transactions/maintenance windows), and/or scale the TVM opcode energy costs (`getWithdrawRewardCost`, vote/unfreeze/delegate costs) proportionally to the actual number of cycles processed rather than using a flat constant, consistent with how `RewardViCalService`'s amortized `accumulateWitnessVi` approach already avoids large unbounded backlogs.

### Proof of Concept
1. An account freezes balance and votes for a witness in cycle `N`.
2. The account then remains completely inactive (no unfreeze/vote/delegate/withdraw calls) for a very large number of maintenance cycles `M` (each maintenance cycle ~ a fixed multi-hour period), while `allowOldRewardOpt()` remains disabled and the account's `beginCycle` stays below `newRewardCalStartCycle`.
3. After `M` cycles have elapsed, the account (or an attacker controlling it) submits a single, ordinary `UnfreezeBalanceContract` transaction (or a contract call executing the `WITHDRAWREWARD` opcode).
4. `UnfreezeBalanceActuator.execute` → `MortgageService.withdrawReward` → `computeReward` → `getOldReward` executes the loop `for (long cycle = begin; cycle < end; cycle++) { reward += computeReward(cycle, votes); }` over all `M` cycles [3](#0-2) , while the transaction is only charged the account's normal bandwidth/energy fee (or, via TVM, the fixed 20000-energy `WITHDRAW_REWARD` constant) regardless of `M`.
5. With sufficiently large `M`, this single transaction consumes computation time disproportionate to its cost, delaying processing of the block in which it is included.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }
