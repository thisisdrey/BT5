Based on my research, I found a directly analogous vulnerability in Bazel's Starlark-level patching utility, which shells out to a locally-derived filename that is built from an **attacker-controlled URL path segment**, without quoting it in the assembled command string.

### Title
Command injection via unquoted patch-file path derived from attacker-controlled URL in `patch()` — ([File: tools/build_defs/repo/utils.bzl])

### Summary
`tools/build_defs/repo/utils.bzl`'s `patch()` function is used by `http_archive`, `git_repository`, and Bzlmod module-extension repo rules to apply "remote patches" — patch files fetched from URLs supplied via the `remote_patches` attribute (typically populated with patch URLs served by a registry/mirror for a dependency, i.e., content controlled by whoever hosts that patch, not the root module). The remote patch is downloaded to a local filename derived directly from the URL, then that filename is spliced unquoted into a shell command line executed via `bash -c`.

### Finding Description
`_download_patch` derives the on-disk filename straight from the attacker-supplied URL: [1](#0-0) 

That `patch_path` is later passed as `patchfile` into the "non-native" patch-tool branch, where a shell command string is built with `.format()`. Note that `patch_args` are explicitly single-quoted (`"'%s'" % arg`), but the `patchfile` path is interpolated **without any quoting**, then executed with `bash -c`: [2](#0-1) 

Because `name = patch_url.split("/")[-1]` (in `_download_patch`) takes the raw, undecoded trailing path segment of the URL verbatim as the filename, an attacker who controls the patch URL (a hostile mirror/registry serving a dependency's remote patch, or a `remote_patches` URL from a compromised/malicious upstream) can choose a filename such as `x;touch$IFS.tmp/HACKED#.patch`. Since most filesystems permit `;`, `$`, and other shell metacharacters in filenames, the file is created with that literal name in `.tmp_remote_patches/`, and its path (containing those metacharacters) is substituted unquoted into the `bash -c "<patchtool> <args> < <patchfile>"` command — resulting in arbitrary shell command execution when the patch step runs. This mirrors the `node-df` bug class exactly: user-influenced input concatenated into a shell command string without escaping/quoting.

Note this is reached even when `sha256`/`integrity` on the patch is correctly verified — checksum verification of the patch *content* does nothing to sanitize the *filename* derived from the URL, so the "integrity is binding" invariant does not cover this path.

### Impact Explanation
Arbitrary command execution on the machine running `bazel build`/`bazel fetch`, triggered purely by the contents of a `remote_patches` URL that an attacker controls (a hostile mirror, or any registry/dependency source able to specify a patch URL for a transitively-depended-upon module). This is RCE on the building machine without any local access or credentials, matching the CVSS 8.4 severity of the underlying report.

### Likelihood Explanation
Any repository rule invocation using `remote_patches` with `patch_tool` set to a non-empty value (i.e., the non-native patch path, `_use_native_patch(patch_args)` false, or explicit non-default `patch_tool`) reaches the vulnerable `.format()`-built command. `remote_patches` URLs are exactly the kind of data an untrusted dependency/mirror/registry can supply, satisfying the "hostile origin server" carve-out in the rules (a declared `integrity` hash on the patch content does not protect the filename used to build the shell command).

### Recommendation
Do not derive the local patch filename directly from attacker-controlled URL text; use a fixed/sanitized/opaque local name (e.g., an index or hash-based name) for the downloaded patch file, and always pass file paths to the shell command with proper quoting (as already done for `patch_args`) rather than raw string interpolation.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel/external_patching_test.sh`-style test can:
1. Stand up a local HTTP file server (as the existing `external_patching_test.sh` suite does).
2. Serve a patch file at a URL whose final path segment contains shell metacharacters, e.g. `http://localhost:$port/ok;touch%20HACKED#.patch` (or an unencoded semicolon segment, since `patch_url.split("/")[-1]` does not URL-decode).
3. Configure an `http_archive`/module extension with `remote_patches = {"<that URL>": "<sha256 of patch content>"}` and a non-native `patch_tool` (e.g., `patch_tool = "patch"` with a `patch_args` combination that defeats `_use_native_patch`, or an explicit non-default patch tool).
4. Run `bazel fetch @repo//...` and observe that the injected command runs (e.g., a `HACKED` marker file is created in the working directory), even though the patch content's declared checksum matched. [1](#0-0) [2](#0-1)

def _download_patch(ctx, patch_url, integrity, auth = None):
    name = patch_url.split("/")[-1]
