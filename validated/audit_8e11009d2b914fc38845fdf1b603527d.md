### Title
Dust-transfer griefing of `MAX_TOKENS_PER_USER` bricks withdrawals when the fee collector's token list is filled - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` on the combined per-account list of deposit + debt tokens (`onlyIfAdditionWillNotReachMaxTokens`, `Pool.sol:143-148,204-220`). `DepositToken._transfer` is permissionless (reachable via public `transfer`/`transferFrom`) and unconditionally calls `pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance for that token was zero (`DepositToken.sol:517-520`). There is no opt-out: an attacker can force-add deposit tokens to **any** address's list by sending dust amounts of each listed msdToken. If the attacker fills the `feeCollector`'s list, every `DepositToken.withdraw` that charges a nonzero fee reverts at `_transfer(account_, feeCollector, _fee)` → `addToDepositTokensOfAccount(feeCollector)` → `UserReachedMaxTokens` whenever the collector's balance for that msdToken is 0 — freezing user collateral withdrawals. The same primitive blocks any victim from depositing a new collateral type or minting a new synthetic once their 30 slots are filled. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
- Public entry: `DepositToken.transfer(victim, dust)` (and `transferFrom`). `_transfer` (private, `DepositToken.sol:498`) credits `recipient` and, when `_recipientBalanceBefore == 0 && amount_ > 0`, calls `pool.addToDepositTokensOfAccount(recipient_)` (`DepositToken.sol:518-519`).
- `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` if `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`Pool.sol:144-146`). The revert propagates and rolls back the whole transfer.
- Withdrawal path: `_withdraw` (`DepositToken.sol:536`) sends `_fee` to `pool.feeCollector()` via `_transfer` at line 547 before burning and pulling collateral from Treasury. If the collector's slot count is already 30 and its balance for this msdToken is 0, the transfer reverts → withdrawal reverts → collateral is locked. Since removals require the entry's balance to go to zero, the attacker can re-fill any freed slot with 1 wei in the same block (front-running or post-fee-sweep), making the freeze effectively persistent.
- Secondary impact: a victim whose 30 slots are filled cannot `deposit` into a new collateral (mint path `_mint`/`_transfer` to a 0-balance account reverts at the same `addToDepositTokensOfAccount`) nor take on a new debt token (`DebtToken` issuance calls `addToDebtTokensOfAccount`, same cap). Existing collateral remains withdrawable only when fee == 0 or collector already holds that token.

Invariant broken: liveness — an unprivileged EOA can force a `UserReachedMaxTokens` revert into unrelated users' transfers/withdrawals, a hang-style DoS analogous to the unauthenticated crash/hang in the source report.

### Impact Explanation
Temporary freezing of funds: while the fee collector's list is saturated and withdraw fee > 0, all withdrawals of msdTokens the collector doesn't already hold revert. The collector can free slots by transferring dust out, but the attacker can refill them, so recovery requires a race the defender is not guaranteed to win. Accepted impact class per rules (temporary freezing of funds); it is not a permanent loss, which caps severity below theft/insolvency.

### Likelihood Explanation
- Requires only standard ERC20 transfers of already-listed msdTokens — no privileged role, no oracle manipulation, no malicious infrastructure. Cost is dust amounts of each of up to ~N deposit tokens.
- **Important caveat:** the withdrawal freeze only materializes while the pool's withdraw fee (`depositFee`/withdraw fee used by `quoteWithdrawOut`) is nonzero **and** the collector's balance for the targeted msdToken is 0. If the deployed configuration has fee = 0, the collector-griefing arm collapses and the remaining impact is per-victim slot-filling, which only blocks *new* deposits/mints — existing positions remain withdrawable and liquidatable, so that arm alone is arguably weak. I could not confirm the on-chain fee setting from the indexed code; the deployment JSONs should be checked. The finding stands if any fee tier is nonzero on a live pool.

### Recommendation
- Let accounts "opt out" of forced list additions: keep a per-account set populated only on `deposit`/`issue`, and compute `depositOf`/`debtOf` from explicit registrations, or
- Skip `addToDepositTokensOfAccount` when the recipient is `feeCollector` (or a protocol address), or route fees via a pull/balance-delta at claim time instead of `_transfer`, or
- Add a `removeFromDepositTokensOfAccount`-style escape hatch callable by the account itself (burn/send all dust to clear slots), and/or
- Track fee-collector balances outside the per-account cap (cap should not apply to protocol addresses).

### Proof of Concept
Hardhat (fork or local) outline:

```ts
// setup: pool with >=2 live DepositTokens (msdA, msdB), withdrawFee > 0,
// feeCollector F with 0 balance of msdB.

// 1) Attacker deposits dust of every listed msdToken to self, then
for (const dt of allDepositTokens) {
  await dt.connect(attacker).transfer(victim, 1);           // fills victim's list
  await dt.connect(attacker).transfer(feeCollector, 1);     // fills collector's list
}
expect(await pool.getDepositTokensOfAccount(feeCollector)).to.have.length(30);

// 2) Victim deposit into msdB still works only if msdB already in victim's list;
//    a NEW deposit token deposit reverts:
await expect(msdNew.connect(victim).deposit(amount)).to.be.revertedWithCustomError(
  pool, 'UserReachedMaxTokens');

// 3) Collector-arm: user withdraws msdB (collector balance of msdB == 0, fee > 0)
await expect(msdB.connect(user).withdraw(amount)).to.be.revertedWithCustomError(
  pool, 'UserReachedMaxTokens'); // _transfer(user, feeCollector, fee) fails

// 4) Persistence: keeper/governor moves dust out of collector slot; attacker
//    re-transfers 1 wei of that msdToken in the same block -> slot refilled.
```

If the deployed pools run with zero withdraw fee, step 3 does not reproduce and the residual finding is limited to blocking new deposits/mints for a saturated account; in that configuration this analog should be considered weak/informational rather than a High-severity DoS.

    ) private updateRewardsBeforeTransfer(sender_, recipient_) {

        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
        }

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_recipientBalanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
            pool.removeFromDepositTokensOfAccount(sender_);
        }
