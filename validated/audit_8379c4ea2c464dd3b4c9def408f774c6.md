### Title
Rebasing collateral breaks the msdTOKEN-to-Treasury 1:1 invariant, causing stuck funds or insolvency-style withdrawal race — (`contracts/DepositToken.sol`)

### Summary
`DepositToken` mints `msdTOKEN` 1:1 against the amount of `underlying` received by `Treasury`, and `withdraw` burns `msdTOKEN` and unconditionally pulls that same nominal amount back out via `Treasury.pull`. The code assumes the Treasury's `underlying.balanceOf` only changes through deposits and withdrawals. For a collateral whose balance changes outside of transfers (rebasing tokens), that invariant silently breaks while collateral sits in escrow: after negative rebases the Treasury cannot honor redemptions (withdrawals revert / first-come-first-served drain of remaining backing), and after positive rebases the surplus collateral is stranded because withdrawals only ever pull the recorded `msdTOKEN` amount.

### Finding Description
`DepositToken.deposit` correctly measures the actual received amount (handling fee-on-transfer), then mints `msdTOKEN` accordingly (contracts/DepositToken.sol:225-234). However, redemption assumes a static 1:1 backing:

- `_withdraw` computes `_withdrawn` purely from the `msdTOKEN` amount and calls `_pool.treasury().pull(to_, _withdrawn)` (contracts/DepositToken.sol:545-551).
- `Treasury.pull` performs a plain `underlying().safeTransfer(to_, amount_)` (contracts/Treasury.sol:66-72), which reverts if the Treasury's rebased balance is below `amount_`.

The codebase even encodes this invariant explicitly in the invariant test: `invariant_treasuryBalance` asserts `depositToken.totalSupply() == underlying.balanceOf(treasury)` (test/foundry/DepositToken.invariants.t.sol:98-100). Nothing in the deposit, withdraw, seize, or liquidation paths reconciles drift between `totalSupply` and the actual escrowed balance. The protocol already supports non-standard collateral (fee-on-transfer deposits are explicitly tested in test/DepositToken.test.ts:433-449), so "weird" underlying behavior is within the supported surface.

### Impact Explanation
- **Negative rebase**: Treasury backing < `msdTOKEN` supply. Early withdrawers succeed and drain the remaining collateral; later withdrawers' `withdraw`/`withdrawFrom`/`flashWithdraw`/seize-driven liquidation pulls revert on insufficient balance — a first-come-first-served loss of backing and freezing of remaining users' collateral redemptions.
- **Positive rebase**: surplus underlying accumulates in `Treasury` and is unclaimable by depositors (withdrawals are capped at the `msdTOKEN` amount). `Treasury` has no generic rescue; `claimFromVesper` deliberately subtracts `depositToken.totalSupply()` from reward-token balances (contracts/Treasury.sol:91-99), so the surplus is stranded (governor-recoverable only via migration).

### Likelihood Explanation
Requires a rebasing/balance-mutating token to be a listed collateral — a supported-token/configuration precondition similar to the original Nibiru finding (severity there was Medium for the same reason). Once listed, no privileged action is needed: any EOA calling `deposit` and later `withdraw` after a rebase triggers the breakage; attackers can win the withdrawal race to capture other users' backing. `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists` and the health checks in `unlockedBalanceOf` do not prevent it.

### Recommendation
Either do not list tokens whose balances change outside transfers, or track a per-`DepositToken` internal "shares"/backing accounting: reconcile `underlying.balanceOf(treasury)` against `totalSupply` at withdrawal time (e.g., pro-rata redemption `amount_ * balanceOf(treasury) / totalSupply`), and/or add a governance function to socialize positive/negative rebase deltas.

### Proof of Concept
Foundry-style sketch (reproduces on a fork with a rebasing mock or an elastic-supply token wired as collateral):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
// RebaseERC20: standard ERC20 where `rebase(int256 factor)` multiplies all balances.
// Setup: Pool, Treasury, FeeProvider initialized; depositToken initialized with
// underlying = RebaseERC20; pool.addDepositToken(depositToken); treasury bound to pool.

contract RebaseBreaksTreasuryInvariant is Test {
    function test_negativeRebase_freezesWithdrawals() public {
        // alice and bob each deposit 100e18
        vm.prank(alice); underlying.approve(address(depositToken), 100e18);
        vm.prank(alice); depositToken.deposit(100e18, alice);
        vm.prank(bob);   underlying.approve(address(depositToken), 100e18);
        vm.prank(bob);   depositToken.deposit(100e18, bob);

        assertEq(depositToken.totalSupply(), underlying.balanceOf(address(treasury)));

        // negative rebase: all balances, including Treasury's, shrink 50%
        underlying.rebase(-0.5e18);

        // invariant broken
        assertGt(depositToken.totalSupply(), underlying.balanceOf(address(treasury)));

        // alice (first come) still withdraws her full 100e18 msdTOKEN -> pulls 100
        vm.prank(alice); depositToken.withdraw(100e18, alice);

        // bob's redemption reverts: treasury holds only ~0 after alice's pull
        vm.prank(bob);
        vm.expectRevert(); // SafeERC20 / ERC20 insufficient balance
        depositToken.withdraw(100e18, bob);
    }

    function test_positiveRebase_strandsSurplus() public {
        vm.prank(alice); underlying.approve(address(depositToken), 100e18);
        vm.prank(alice); depositToken.deposit(100e18, alice);

        underlying.rebase(0.5e18); // treasury now holds 150e18, supply still 100e18

        vm.prank(alice); depositToken.withdraw(100e18, alice); // pulls only 100e18
        assertEq(underlying.balanceOf(address(treasury)), 50e18); // stranded
    }
}
```

Key cited code: `deposit` balance-delta mint (contracts/DepositToken.sol:225-234), `_withdraw`/`treasury().pull` (contracts/DepositToken.sol:545-551), `Treasury.pull` plain transfer (contracts/Treasury.sol:66-72), reward-surplus accounting that subtracts `totalSupply` (contracts/Treasury.sol:91-99), and the asserted invariant itself (test/foundry/DepositToken.invariants.t.sol:98-100).
