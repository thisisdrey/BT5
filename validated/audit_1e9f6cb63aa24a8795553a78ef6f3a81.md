### Title
Non-constant-time authorization token comparison enables timing side-channel recovery of the block-proposal auth secret - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
The `/v3/block_proposal` RPC handler compares the client-supplied `authorization` header against the node's configured secret using Rust's default string equality (`!=`), which performs a byte-by-byte, early-exit comparison rather than a constant-time comparison. A remote, unauthenticated attacker who can reach this HTTP endpoint can use statistical timing measurements to incrementally recover the correct `auth_token`/`auth_password` value, exactly the bug class described in the referenced advisory (CVE-2023-41935, non-constant-time nonce/token comparison).

### Finding Description
`RPCBlockProposalRequestHandler::try_parse_request` reads the incoming `authorization` header and checks it against the configured secret with a plain `!=` operator: [1](#0-0) 

```rust
let Some(password) = &self.auth else {
    return Err(Error::Http(400, "Bad Request.".into()));
};
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

`String`/`str` equality in Rust (`PartialEq` for `str`) compares byte-by-byte and returns as soon as a mismatch is found (and also short-circuits on length mismatch). This means the time taken by the comparison is a function of how many leading bytes of the attacker's guess match the true secret. This is architecturally identical to the Jenkins Azure AD plugin flaw: a security-critical secret (here, the `auth_token` configured under `[connection_options]`, documented as securing the `stacks-signer` <-> node channel and gating `/v3/block_proposal` and `/v2/blocks?broadcast=1`) is checked with a non-constant-time comparison. [2](#0-1) 

The identical anti-pattern is repeated in the block-simulation endpoint: [3](#0-2) 

```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

Both handlers are reachable by any remote, unauthenticated party who can open an HTTP connection to the node's RPC port — the whole point of the check is to authenticate that party, so by definition the attacker has no prior credential. Byte-by-byte timing differences (amplified via repeated measurements/statistics, as noted in the advisory) let an attacker incrementally learn the shared secret one byte at a time, without ever needing the node's private key or admin access.

### Impact Explanation
Recovering the `auth_token` is a full authentication bypass for the endpoints it protects: `/v3/block_proposal` (which triggers block validation compute and, per its handling path, participates in miner/signer coordination) and, per the documented use of the same token, `/v2/blocks?broadcast=1` (an unauthenticated/unauthorized *write* path once the token is known). This satisfies the "auth bypass" / "unauthenticated write to state" high/critical impact bar in the rules, since the token is the sole gate protecting these operations, and its compromise removes that gate entirely for a remote attacker.

### Likelihood Explanation
Exploitation requires only network access to the RPC port that already exposes these endpoints (no special role, no node secret, no other party's key). Statistical timing attacks over a network are noisier than local ones, but they are a well-established, practical technique (as reflected by the CVE this scan is modeled on), and repeated/averaged measurements against a fixed secret comparison make byte-by-byte recovery feasible, especially since the secret is a bounded-length operator-chosen token/password rather than a long random value.

### Recommendation
Replace the `!=` string comparisons in `RPCBlockProposalRequestHandler::try_parse_request` (`stackslib/src/net/api/postblock_proposal.rs`) and `RPCNakamotoBlockSimulateRequestHandler::try_parse_request` (`stackslib/src/net/api/blocksimulate.rs`) with a constant-time comparison, e.g. using `subtle::ConstantTimeEq` on the byte representations of both strings (after first checking/handling length in a constant-time-safe manner, or hashing both sides with a fixed-length MAC before comparison). This removes the timing side channel used to reconstruct the shared secret.

### Proof of Concept
1. Configure a node with `[connection_options] auth_token = "<secret>"` to enable `/v3/block_proposal`.
2. From a remote unauthenticated host, send repeated POST requests to `/v3/block_proposal` with candidate `authorization` header values that differ only in the position of the first mismatched byte (e.g., correct prefix of increasing length + wrong byte), measuring response latency for the `if auth_header != password` check at `stackslib/src/net/api/postblock_proposal.rs:1142`.
3. Statistically distinguish "matched N leading bytes" vs "matched N+1 leading bytes" by aggregating many timing samples per candidate, and iteratively extend the guessed prefix byte-by-byte until the full secret is recovered — mirroring the technique described in CVE-2023-41935.
