### Title
Same-block DeleteKey+AddKey nonce rollback allows replay/double-execution of a previously-signed transaction - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
`add_regular_key` reseeds a re-added access key's nonce to `initial_nonce_value(block_height) = (block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` using only the *current* apply-state block height, with no floor tied to the highest nonce that key had actually consumed. Because `verify_nonce`'s `NonceMode::Monotonic` bound check (`tx_nonce >= height * MULTIPLIER` → reject) allows any nonce within the whole `[current_nonce+1, height*MULTIPLIER)` window in a given block, an account owner can pick a nonce for a transaction close to, but above, `(height-1)*MULTIPLIER`, then delete+re-add the same public key later in the same chunk, which resets the stored nonce back below the value already consumed — allowing the original signed transaction to be replayed and re-executed.

### Finding Description
`add_regular_key` (`runtime/runtime/src/access_keys.rs:230-255`) unconditionally sets:
```
access_key.nonce = initial_nonce_value(block_height);
``` [1](#0-0) 
and `initial_nonce_value` computes `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`. [2](#0-1) 

`verify_nonce` (`runtime/runtime/src/verifier.rs:211-237`) only enforces that `tx_nonce > current_nonce` (Monotonic mode) and that `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (the "NonceTooLarge" upper-bound check) — it has no lower bound tied to the key's own usage history, only to the current chunk's block height. [3](#0-2) 

Exploit flow, all within one chunk applied at `apply_state.block_height = H` (this height is what is passed into `action_add_key`/`add_regular_key` for every local receipt executed in that chunk): [4](#0-3) 
1. Attacker's own account A has FullAccess key K whose stored nonce is some low legitimate value `c`.
2. Attacker signs and submits `Transfer` with `tx_nonce = N`, chosen so that `(H-1)*MULTIPLIER < N < H*MULTIPLIER` (well inside the allowed window for block H, but comfortably above `(H-1)*MULTIPLIER`). It passes `verify_nonce` (N > c, N < H*MULTIPLIER) and executes, updating stored `access_key.nonce = N`.
3. In the same chunk, attacker submits a transaction (or the corresponding local receipt) with actions `[DeleteKey(K), AddKey(K)]`, using a nonce `M` with `N < M < H*MULTIPLIER`. `DeleteKey` removes the key/nonce record entirely; `AddKey`'s `action_add_key` → `add_regular_key` then resets the nonce to `initial_nonce_value(H) = (H-1)*MULTIPLIER`, which is **less than** `N`.
4. Attacker now replays the *original, already-signed* `Transfer(tx_nonce = N)` bytes. `verify_nonce` checks `N > current_nonce = (H-1)*MULTIPLIER` — true — and `N < H*MULTIPLIER` — true — so the stale transaction passes and executes a second time.

The bug is that the reseed value is derived purely from the *current* block height rather than from the maximum nonce the key has ever consumed (or the height at which it was actually last used before deletion). The original mitigation comment ("Set default nonce for newly created access key to avoid transaction hash collision", referencing near/nearcore#3779) implicitly assumes the key's prior high-water-mark nonce was set in a *strictly earlier* block, so `(H-1)*MULTIPLIER` would exceed it — this assumption fails when the delete+recreate happens in the *same* block as the high-nonce transaction being replayed.

### Impact Explanation
This enables an account owner to make one of their own signed transactions (e.g., a `Transfer`) execute twice by manipulating their own key's nonce state via `DeleteKey`+`AddKey` in the same chunk. Scoped impact is a double-spend/double-execution of the replayed transaction's value transfer, i.e. loss/inflation of value from whatever account is debited (if `Transfer` deposits from the attacker's own account to a third party, the third party receives double; if the transaction credits the attacker, e.g., via a promise result or receipt logic, this can be abused for token duplication). This falls under "double-spend/replay" and potentially "token inflation" bounty categories.

### Likelihood Explanation
The attacker needs only standard unprivileged capabilities: a funded account with a FullAccess key, ability to sign and submit ordinary `Transfer`, `DeleteKey`, and `AddKey` transactions with self-chosen nonces within the currently valid window. No validator/node/RPC privilege is required. The main precondition is being able to get the `Transfer`, `DeleteKey`, `AddKey` sequence, and the replayed `Transfer`, processed as local receipts within the same chunk/block height, and choosing nonces inside the permitted band `((H-1)*MULTIPLIER, H*MULTIPLIER)`. This is fully controlled by the attacker at signing time (nonces are client-chosen) and is repeatable.

### Recommendation
Do not derive the reseeded nonce purely from the current block height. Either (a) preserve/require the reseeded nonce to be strictly greater than the maximum nonce previously recorded for that public key (track a monotonically non-decreasing "high-water mark" per account, not per currently-live key), or (b) forbid `AddKey` from reusing a public key that was deleted within the same block/chunk without bumping the new nonce baseline above any nonce already used by that key in the current or prior state, or (c) tie `initial_nonce_value` to a value that can never be less than or equal to the maximum nonce value permitted for the account in the current block (e.g., store last max nonce per account across key add/delete cycles).

### Proof of Concept
Runtime apply-path integration test (in the style of `runtime/runtime/src/tests/apply.rs`):
1. Set up an account `alice` with a FullAccess key `K`, and fund it.
2. Apply a chunk at height `H` with the transaction sequence, sharing the same block height:
   - Tx1: `Transfer(deposit=D, receiver=bob)` signed with `K`, `nonce = N` where `(H-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER < N < H*ACCESS_KEY_NONCE_RANGE_MULTIPLIER`.
   - Tx2: `[DeleteKey(K), AddKey(K, FullAccess)]` signed with `K`, `nonce = M` with `N < M < H*MULTIPLIER`.
3. After applying, assert `get_access_key(state, alice, K).nonce == (H-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (i.e., below `N`).
4. Re-submit the original signed Tx1 bytes (same `nonce = N`) in a later apply call (same or subsequent chunk at height `H`).
5. Assert `verify_and_charge_transaction`/apply succeeds again (no `InvalidNonce` error), and assert `bob`'s balance increased by `2*D` while `alice`'s balance decreased by `2*D` (plus fees), proving double execution of the same signed transfer.

    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
