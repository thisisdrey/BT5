## Title
XCMP inbound backpressure drop-threshold silently discards in-flight HRMP messages carrying already-settled asset transfers, causing permanent fund loss with no retry — (`File: cumulus/pallets/xcmp-queue/src/lib.rs`)

### Summary
The external report's core broken invariant is: a receiver-side "pause" gate can revert/reject an in-flight cross-chain message after the sender has already irreversibly committed value, and the protocol offers no automatic retry — permanently stranding funds. The closest verifiable analog in this repository is the XCMP queue's inbound backpressure mechanism in `cumulus/pallets/xcmp-queue/src/lib.rs`. When a sibling parachain's inbound message page arrives while the destination's enqueue capacity is exhausted (`drop_threshold`) or the servicing weight budget for the block is insufficient, the pallet drops the raw HRMP page/batch instead of queuing it, with no on-chain marker, no requeue, and no way for the sender or the affected user to recover the message.

### Finding Description
`Pallet::enqueue_xcmp_messages` computes a `best_batch_footprint` bounded by the configured `drop_threshold` and by available weight, then only enqueues the portion of the batch that fits: [1](#0-0) 

If `best_batch_footprint.msgs_count < xcms.len()`, the function logs an error and returns `Err(())`, and the remaining messages in that batch/page are dropped without a trace beyond a log line: [2](#0-1) 

This is invoked from `handle_xcmp_messages`, the XCMP message handler that processes every inbound HRMP page delivered by the relay chain in a block, and it is explicitly documented as an accepted, silent-drop trade-off: [3](#0-2) 

The pallet does provide a suspend/resume backpressure signal (`suspend_threshold`/`resume_threshold`) intended to stop the sender before `drop_threshold` is reached: [4](#0-3) 

However this signal is asynchronous (round-trip via `ChannelSignal::Suspend`/`Resume` over the same XCMP channel) and is explicitly noted to be potentially too slow: `"It will retry if drop_threshold is not reached, but it could be too late."` and `"future messages may be dropped"`: [5](#0-4) 

Tests confirm the drop is real and produces no compensating state: `xcm_enqueueing_starts_dropping_on_overflow` and `xcm_enqueueing_backpressure_works` show that messages beyond `drop_threshold` simply never appear in the enqueued set: [6](#0-5) [7](#0-6) 

The exact broken invariant: for any XCM message that instructs the destination to mint, unlock, or credit an asset corresponding to value already burned/reserved/locked on the sender side (e.g., a teleport or reserve-asset-transfer XCM built by `pallet-xcm` or asset-hub pallets), the destination-side settlement (`ReceiveTeleportedAsset`/`ReserveAssetDeposited` execution) never happens if the HRMP page is dropped at the queue-ingestion layer, before the `MessageQueue`/`XcmExecutor` ever sees it. Unlike `pallet-message-queue`'s explicit `Unprocessable { permanent: bool }` / `TemporarilyUnprocessable` / `QueuePaused` error taxonomy (which preserves the message for later retry once unpaused — see `substrate/frame/message-queue/src/lib.rs` lines 631-657, 1101-1139), the XCMP drop path never reaches that queue at all; the message is discarded during `handle_xcmp_messages` before enqueueing, so there is no stored page, no error event tied to the specific dropped message, and no retry surface, matching the Wormhole report's "Receiver Failure with no automatic retry — must restart from source chain" pattern, except here there isn't even a source-chain restart mechanism for an already-relayed HRMP page.

### Impact Explanation
Any XCM instruction that debits/burns value on the source chain and credits it on the destination (teleports, reserve transfers, or bridged asset settlement forwarded over XCMP/HRMP) can result in permanent, unrecoverable loss of the credited side if the destination parachain's inbound XCMP channel is congested past `drop_threshold` at the moment the page arrives. This is a "permanent user-fund lock" per the Required Impacts, arising purely from public message-queue congestion (no privileged admin action, no malicious validator/collator required to reproduce the drop condition — only sustained normal or adversarial-but-permissionless message volume from a sibling chain that outpaces the suspend-signal round trip).

### Likelihood Explanation
Reaching `drop_threshold` requires sustained high message volume on a given channel exceeding the configured `suspend_threshold` and outrunning the asynchronous suspend-signal round trip described in the pallet's own comments ("it could be too late"). This is more likely during genuine network congestion, bursty cross-chain activity, or a moderately funded adversary flooding a channel with cheap XCMP messages (delivery fees rise with congestion per `delivery_fee_constants`, but do not prevent a determined actor from pushing past `drop_threshold` before the suspend signal is honored). No validator/collator misbehavior or governance action is needed.

### Recommendation
- Do not silently drop pages/batches at `drop_threshold`; instead, either reject inbound HRMP delivery at the relay-chain/collator level with a receipt the sender chain can observe and act on, or persist dropped payloads (e.g., in an overflow/dead-letter storage keyed by sender+block) so they can be replayed once congestion clears.
- Tighten the suspend/resume handshake so that `suspend_threshold` is enforced synchronously enough (e.g., via relay-chain-level channel capacity limits) that `drop_threshold` is unreachable under normal operation, removing reliance on a "hopefully in time" signal.
- Emit a per-message (not just per-batch) event identifying exactly which XCM(s) were dropped, including enough information (hash of theXCM, sender, HRMP page number) to support off-chain reconciliation/refund tooling.

### Proof of Concept
1. Configure `QueueConfigData { suspend_threshold: N, drop_threshold: N, resume_threshold: N }` such that suspend and drop coincide (as in `xcm_enqueueing_starts_dropping_on_overflow`), or simply flood a channel faster than the suspend signal can propagate.
2. Have the sibling parachain send a teleport/reserve-transfer XCM (value already burned/reserved on that chain) as part of a batch of HRMP messages that exceeds the destination's `drop_threshold` in a single block, as shown in the existing test harness pattern: [8](#0-7) 
3. Observe that `EnqueuedMessages` only contains the first `drop_threshold`-worth of messages; the teleport XCM beyond that cutoff is discarded by `enqueue_xcmp_messages` and never reaches `pallet-message-queue`/`XcmExecutor`, so the corresponding mint/credit on the destination never executes, while the burn/reserve on the source chain already occurred — a permanent value mismatch.

impl<T: Config> OnQueueChanged<ParaId> for Pallet<T> {
	// Suspends/Resumes the queue when certain thresholds are reached.
	fn on_queue_changed(para: ParaId, fp: QueueFootprint) {
		let QueueConfigData { resume_threshold, suspend_threshold, .. } = <QueueConfig<T>>::get();

		let mut suspended_channels = <InboundXcmpSuspended<T>>::get();
		let suspended = suspended_channels.contains(&para);

		if suspended && fp.ready_pages <= resume_threshold {
			if let Err(err) = Self::send_signal(para, ChannelSignal::Resume) {
				tracing::error!(
					target: LOG_TARGET,
					error=?err,
					sibling=?para,
					"defensive: Could not send resumption signal to inbound channel of sibling; channel remains suspended."
				);
			} else {
				suspended_channels.remove(&para);
				<InboundXcmpSuspended<T>>::put(suspended_channels);
			}
		} else if !suspended && fp.ready_pages >= suspend_threshold {
			tracing::warn!(target: LOG_TARGET, sibling=?para, "XCMP queue for sibling is full; suspending channel.");

			if let Err(err) = Self::send_signal(para, ChannelSignal::Suspend) {
				// It will retry if `drop_threshold` is not reached, but it could be too late.
				tracing::error!(
					target: LOG_TARGET, error=?err,
					"defensive: Could not send suspension signal; future messages may be dropped."
				);
			} else if let Err(err) = suspended_channels.try_insert(para) {
				tracing::error!(
					target: LOG_TARGET,
					error=?err,
					sibling=?para,
					"Too many channels suspended; cannot suspend sibling; further messages may be dropped."
				);
			} else {
				<InboundXcmpSuspended<T>>::put(suspended_channels);
			}
		}
	}

#[test]
fn xcm_enqueueing_backpressure_works() {
	let para: ParaId = 1000.into();
	new_test_ext().execute_with(|| {
		assert_ok!(XcmpQueue::update_resume_threshold(Origin::root(), 1));
		assert_ok!(XcmpQueue::update_suspend_threshold(Origin::root(), 3));
		assert_ok!(XcmpQueue::update_drop_threshold(Origin::root(), 5));
		let page = generate_mock_xcm_page(0, 1, XcmEncoding::Simple);

		XcmpQueue::handle_xcmp_messages(repeat((para, 1, page.as_slice())).take(2), Weight::MAX);
		assert_eq!(EnqueuedMessages::get().len(), 2);
		// Not yet suspended:
		assert!(InboundXcmpSuspended::<Test>::get().is_empty());

		XcmpQueue::handle_xcmp_messages(once((para, 1, page.as_slice())), Weight::MAX);
		// Suspended:
		assert_eq!(InboundXcmpSuspended::<Test>::get().iter().collect::<Vec<_>>(), vec![&para]);

		// We want to ignore the defensive panic :)
		let _ = std::panic::catch_unwind(|| {
			// Now enqueueing many more will only work until the drop threshold:
			XcmpQueue::handle_xcmp_messages(
				repeat((para, 1, page.as_slice())).take(10),
				Weight::MAX,
			)
		});
		assert_eq!(EnqueuedMessages::get().len(), 5);

		mock::EnqueueToLocalStorage::<Pallet<Test>>::sweep_queue(para);
		XcmpQueue::handle_xcmp_messages(once((para, 1, page.as_slice())), Weight::MAX);
		// Got resumed:
		assert!(InboundXcmpSuspended::<Test>::get().is_empty());
		// Still resumed:
		XcmpQueue::handle_xcmp_messages(once((para, 1, page.as_slice())), Weight::MAX);
		assert!(InboundXcmpSuspended::<Test>::get().is_empty());
	});
}
