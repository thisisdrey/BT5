### Title
Active permission keys can be granted the `AccountPermissionUpdateContract` operation, allowing a low-security delegated key to seize full Owner control of an account - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` validates a custom Active permission's `operations` bitmap against `DynamicPropertiesStore.getAvailableContractType()`, which by default includes the bit for `AccountPermissionUpdateContract` itself. Nothing in the actuator or in `TransactionCapsule`'s signature-weight check prevents an account owner from delegating the "manage account permissions" capability to a low-threshold Active key. Once that bit is set, any signer holding that Active permission can call `AccountPermissionUpdateContract` and unilaterally rewrite the account's Owner, Witness, and Active permissions — including replacing the Owner key set entirely — bypassing the (typically higher-security) Owner multisig. This mirrors CVE-2022-31168, where insufficient restriction on which entity could grant a privileged capability let a low-privileged actor (bot) escalate to admin.

### Finding Description
`AccountPermissionUpdateActuator.checkPermission()` validates the operations bitmap of a custom Active permission only against the "is this a recognized ContractType" list: [1](#0-0) 

That list, `AVAILABLE_CONTRACT_TYPE`, defaults to a bitmap that includes the bit for `AccountPermissionUpdateContract` (the default hex value is not filtered to exclude it): [2](#0-1) 

By contrast, the *default*, auto-generated Active permission (`ACTIVE_DEFAULT_OPERATIONS`) is built to deliberately exclude `AccountPermissionUpdateContract`, as confirmed by the test that documents this exclusion: [3](#0-2) 

This asymmetry means the exclusion is only enforced for the *auto-generated* default Active permission, not for any custom Active permission an owner explicitly submits via `AccountPermissionUpdateContract`. There is no code path that rejects an Active permission whose `operations` bit for `AccountPermissionUpdateContract` (contract type id 46) is set.

Once such an Active permission exists on an account, the transaction-level authorization check treats it as fully sufficient to invoke `AccountPermissionUpdateContract`: [4](#0-3) [5](#0-4) 

`AccountPermissionUpdateActuator.execute()` then unconditionally overwrites the account's Owner/Witness/Active permission set with whatever the contract specifies — there is no requirement that the new Owner permission retain any relationship to the old one: [6](#0-5) [7](#0-6) 

### Impact Explanation
Accounts commonly configure a high-threshold, multi-key Owner permission for security, while granting a lower-threshold, single-key Active permission to a bot/hot-wallet/automation key for routine operations (transfers, votes, etc.) — trusting that this delegated key cannot touch account-level control. If the account owner ever authorizes an Active permission whose `operations` bitmap includes bit 46 (`AccountPermissionUpdateContract`) — which the system does not block — that low-security Active key becomes equivalent to Owner: it can rewrite the Owner permission's keys/threshold, drop the real owners, and take exclusive control of the account and all its funds, TRX/TRC10/TRC20 balances, staked/voted resources, and witness role if applicable. This is a full account takeover reachable purely from a signed API transaction, matching "unauthorized account operation / theft of funds."

### Likelihood Explanation
Exploitation requires the account owner to grant that specific operation bit to an Active permission (either through misconfiguration, a compromised/malicious integration tool, or a phishing-crafted `AccountPermissionUpdateContract` transaction that the owner signs without noticing the embedded bit in a 32-byte hex blob). Since no validation anywhere blocks this bit for Active permissions, and the field is opaque (raw hex bitmap) making it easy to overlook during signing/review, this is a realistic misconfiguration/social-engineering vector rather than a purely theoretical one, directly analogous to how Zulip bots could be granted admin without additional gating.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly reject the `AccountPermissionUpdateContract` bit (and any other account-control contract types) from being set in an Active permission's `operations`, mirroring the exclusion already applied to `ACTIVE_DEFAULT_OPERATIONS`. Only the Owner permission (`permissionId == 0`) should ever be authorized to invoke `AccountPermissionUpdateContract`.

### Proof of Concept
1. Account `A` has default Owner permission (multisig, e.g., 2-of-2) and wants to delegate routine operations to bot key `B`.
2. Owner signs an `AccountPermissionUpdateContract` transaction adding an Active permission for `B` whose 32-byte `operations` field sets bit 46 (`AccountPermissionUpdateContract`) along with other desired bits — this passes `checkPermission()` because bit 46 is present in `AVAILABLE_CONTRACT_TYPE`.
3. Attacker compromises only key `B` (the low-threshold Active key).
4. Attacker crafts a new `AccountPermissionUpdateContract` transaction with `permission_id = 2` (B's Active permission id), setting `owner_address = A`, and defines a brand-new Owner permission containing only the attacker's key.
5. `TransactionCapsule.validateSignature` → `checkPermission` sees `permissionId != 0`, checks `checkPermissionOperations(permission, contract)` which returns true (bit 46 set), and the transaction is accepted with only `B`'s single signature.
6. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, replacing the multisig Owner permission with the attacker's key — full account takeover.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
