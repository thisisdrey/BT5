Based on the code I reviewed in `stackslib/src/net/atlas/download.rs`, the vulnerability claim is confirmed.

### Title
Atlas attachment gossip content is stored/resolved without verifying it matches the committed content hash - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts the `Attachment` bytes returned by a peer's `GetAttachmentResponse` into `self.attachments` without ever comparing the attachment's actual content hash to the `content_hash` (`X`) that was requested. Any peer selected to serve a `GET /v2/attachments/<X>` request can return arbitrary bytes `B` and have them accepted, stored, and (mis)resolved against whatever hash `B` actually produces rather than `X`.

### Finding Description
The claimed broken equality is: `Hash160::from_data(&response.attachment.content) == request.content_hash` is never checked before storage/resolution.

Tracing the code: in `extend_with_attachments` [1](#0-0) , for each `(request, response)` pair in `results.succeeded`, the code decodes the HTTP body via `response.decode_atlas_get_attachment()` and does `self.attachments.insert(response.attachment)` — there is no reference to `request.content_hash` anywhere in this loop.

This propagates into `AttachmentsDownloader::run`, where the `Done` state drains `context.attachments` and, for each attachment, computes `attachment.hash()` (i.e., the hash of whatever bytes the peer sent), looks up `find_all_attachment_instances(&attachment.hash())`, calls `insert_instantiated_attachment(&attachment)`, and calls `context.attachments_batch.resolve_attachment(&attachment.hash())` [2](#0-1) . All of these operations key off `attachment.hash()` — the hash of the attacker-supplied bytes — never off the original `request.content_hash` that was actually queued in the batch.

The request itself does carry the expected hash: `AttachmentRequest { sources, content_hash: content_hash.clone(), ... }` is built from the on-chain `AttachmentInstance.content_hash` in `get_prioritized_attachments_requests` [3](#0-2) , so the expected value `X` is available at the point of processing the response, but it is discarded — `extend_with_attachments` only has access to `request.content_hash` (via the `request` key in the `succeeded` map) yet never reads it.

Exploit flow: attacker peer is selected as a source in `get_prioritized_attachments_requests` (any peer whose gossiped inventory claims to have the attachment can be selected), the download state machine issues the GET, the attacker responds HTTP 200 with a `GetAttachmentResponse` containing bytes `B` where `hash(B) != X`. `BatchedRequestsState` accepts any 200 response into `succeeded` without hash validation [4](#0-3) . `extend_with_attachments` inserts `B` unchecked. `AttachmentsDownloader::run` stores `B` keyed by `hash(B)` and calls `resolve_attachment(&hash(B))`, which does not match the pending entry for `X` in `attachments_batch`, so the batch entry for `X` remains unresolved forever (until retries exhaust), while `B` is durably persisted in `AtlasDB` under `hash(B)`, a hash no on-chain `AttachmentInstance` ever committed to.

### Impact Explanation
This matches the "High - attachment/BNS mismatch" category: a BNS name's zonefile attachment committed on-chain via hash `X` can never resolve even though a peer "answered" the request, because resolution is keyed by the wrong hash. Additionally, arbitrary attacker-chosen bytes are durably written into `AtlasDB` (via `insert_instantiated_attachment`) under a hash with no corresponding on-chain commitment, wasting storage and allowing a class of unaccountable data injection into the node's attachment store. This is repeatable per attachment instance/content hash and requires no special privilege beyond running a peer and being selected as a download source.

### Likelihood Explanation
Preconditions are modest: an unresolved `AttachmentInstance` (e.g., a BNS name registration/update whose zonefile hasn't yet synced) must be queued, and the attacker's peer must be selected via reliability-scored peer selection (`get_most_reliable_source`/`peers` map) — any outbound-connected peer that advertises the attachment in its inventory response is eligible; no signature, secret, or privileged role is required. The attacker only needs to run a normal P2P peer that answers with a valid-format `GetAttachmentResponse` with wrong content.

### Recommendation
In `extend_with_attachments`, after decoding `response.decode_atlas_get_attachment()`, compute `Hash160::from_data(&response.attachment.content)` and compare it to `request.content_hash`. If they don't match, treat it as a failed/faulty response (bump `report.bump_failed_requests()`, and optionally register the peer as faulty/blocklist it) instead of inserting into `self.attachments`. Only attachments whose hash matches the requested `content_hash` should be inserted into the `HashSet<Attachment>` that later flows into `insert_instantiated_attachment` and `resolve_attachment`.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs`:
1. Construct an `AttachmentsBatchStateContext` with an `AttachmentsBatch` containing one tracked attachment instance with `content_hash = X` (e.g. `Hash160::from_data(b"expected")`).
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map has one entry: key = `AttachmentRequest { content_hash: X, .. }`, value = `Some(StacksHttpResponse)` wrapping a `GetAttachmentResponse { attachment: Attachment { content: b"malicious bytes B".to_vec() } }` where `Hash160::from_data(b"malicious bytes B") != X`.
3. Call `context.extend_with_attachments(&mut results)`, then simulate `AttachmentsDownloader::run`'s `Done` branch (or drive the full `AttachmentsBatchStateMachine` to `Done`) so it drains `context.attachments`, calls `atlasdb.insert_instantiated_attachment(&attachment)`, and `context.attachments_batch.resolve_attachment(&attachment.hash())`.
4. Assert `atlasdb.find_attachment(&X).unwrap()` is `None` (the committed hash is never resolved) while `atlasdb.find_attachment(&Hash160::from_data(b"malicious bytes B")).unwrap()` is `Some(Attachment{content: b"malicious bytes B".to_vec()})`, demonstrating the mismatch is stored/served under the wrong key and the true committed attachment remains permanently unresolved.
