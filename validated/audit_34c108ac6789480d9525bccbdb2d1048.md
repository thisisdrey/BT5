Based on my research, I did not find a Go standard-library analog that faithfully reproduces this bug's root cause. The Sherlock finding is a smart-contract-specific pattern: an unprivileged user supplies a sentinel value (`recipient == address(0)`) at order-creation time with no validation; later, a required cleanup path (`_cancelOrder`'s `safeTransfer`) unconditionally reverts on that sentinel for certain ERC20 tokens (USDT's `_transfer` reverting on zero address), permanently blocking removal of that queue entry; because the admin's only lever is raising a capacity ceiling, the attacker can force that ceiling arbitrarily high until the array becomes too expensive to traverse within the gas limit — a purely economic/state-machine DoS specific to on-chain accounting and token-transfer semantics.

None of the Go HTTP/2, `net/http`, module-cache, or `internal/fuzz` code I inspected exhibits the same shape of vulnerability under the required threat model (unauthenticated/unprivileged input reaching a Go entry point where a *required cleanup/removal operation* is made to permanently and unconditionally fail due to an unvalidated sentinel value, with the only mitigation being to raise a limit that then becomes attacker-exploitable again):

- HTTP/2 server stream accounting (`sc.newStream`/`sc.closeStream` in [1](#0-0) , [2](#0-1) ) always decrements `curClientStreams` on `closeStream`, and there is no user-supplied value that causes `closeStream` itself to unconditionally fail/revert — RST_STREAM and connection resets always force cleanup regardless of any client-controlled field.
- `net/http` `Transport`'s per-host dial queue (`wantConnQueue`, `decConnsPerHost`) in [3](#0-2)  is entirely driven by trusted local client-side logic, not by unauthenticated/attacker-controlled network input, so it doesn't match the "unprivileged attacker" precondition.
- `database/sql`'s connection pool/request queue (`connRequestSet`, `maybeOpenNewConnections`) in [4](#0-3)  is also application/driver-controlled, not attacker-facing.
- The module cache/fetch code (`cacheDir`, `CachePath`, `DownloadDir` in [5](#0-4) ) validates module path/version early (`gover.ModIsValid`, `module.CanonicalVersion`) before any cache operations, so there's no equivalent "zero-value sentinel bypasses validation, later breaks cleanup" pattern; `go clean -modcache` is an unconditional `rm -rf`, not a per-entry accounting/cancel operation that can be blocked by attacker data.
- `internal/fuzz`'s `queue` (`enqueue`/`dequeue`/`grow`) in [6](#0-5)  is local test-tooling state, not reachable by an unprivileged network/module attacker, and dequeue never fails based on element content.

Given the strict rule to avoid stretching an analogy, and that no production Go code path shows an unprivileged-attacker-controlled sentinel value causing a mandatory cleanup/removal operation to permanently and unconditionally fail (thereby letting the attacker force the defender to raise a limit that then becomes exploitable again), I'm reporting no match rather than fabricate a strained analog.

// decConnsPerHost decrements the per-host connection count for key,
// which may in turn give a different waiting goroutine permission to dial.
func (t *Transport) decConnsPerHost(key connectMethodKey) {
	if t.MaxConnsPerHost <= 0 {
		return
	}

	t.connsPerHostMu.Lock()
	defer t.connsPerHostMu.Unlock()
	n := t.connsPerHost[key]
	if n == 0 {
		// Shouldn't happen, but if it does, the counting is buggy and could
		// easily lead to a silent deadlock, so report the problem loudly.
		panic("net/http: internal error: connCount underflow")
	}

	// Can we hand this count to a goroutine still waiting to dial?
	// (Some goroutines on the wait list may have timed out or
	// gotten a connection another way. If they're all gone,
	// we don't want to kick off any spurious dial operations.)
	if q := t.connsPerHostWait[key]; q.len() > 0 {
		done := false
		for q.len() > 0 {
			w := q.popFront()
			if w.waiting() {
				t.startDialConnForLocked(w)
				done = true
				break
			}
		}
		if q.len() == 0 {
			delete(t.connsPerHostWait, key)
		} else {
			// q is a value (like a slice), so we have to store
			// the updated q back into the map.
			t.connsPerHostWait[key] = q
		}
		if done {
			return
		}
	}

	// Otherwise, decrement the recorded count.
	if n--; n == 0 {
		delete(t.connsPerHost, key)
	} else {
		t.connsPerHost[key] = n
	}
}

package fuzz

// queue holds a growable sequence of inputs for fuzzing and minimization.
//
// For now, this is a simple ring buffer
// (https://en.wikipedia.org/wiki/Circular_buffer).
//
// TODO(golang.org/issue/46224): use a prioritization algorithm based on input
// size, previous duration, coverage, and any other metrics that seem useful.
type queue struct {
	// elems holds a ring buffer.
	// The queue is empty when begin = end.
	// The queue is full (until grow is called) when end = begin + N - 1 (mod N)
	// where N = cap(elems).
	elems     []any
	head, len int
}

func (q *queue) cap() int {
	return len(q.elems)
}

func (q *queue) grow() {
	oldCap := q.cap()
	newCap := oldCap * 2
	if newCap == 0 {
		newCap = 8
	}
	newElems := make([]any, newCap)
	oldLen := q.len
	for i := 0; i < oldLen; i++ {
		newElems[i] = q.elems[(q.head+i)%oldCap]
	}
	q.elems = newElems
	q.head = 0
}

func (q *queue) enqueue(e any) {
	if q.len+1 > q.cap() {
		q.grow()
	}
	i := (q.head + q.len) % q.cap()
	q.elems[i] = e
	q.len++
}

func (q *queue) dequeue() (any, bool) {
	if q.len == 0 {
		return nil, false
	}
	e := q.elems[q.head]
	q.elems[q.head] = nil
	q.head = (q.head + 1) % q.cap()
	q.len--
	return e, true
}

func (q *queue) peek() (any, bool) {
	if q.len == 0 {
		return nil, false
	}
	return q.elems[q.head], true
}

func (q *queue) clear() {
	*q = queue{}
}
