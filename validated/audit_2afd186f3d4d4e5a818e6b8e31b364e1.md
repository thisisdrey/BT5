### Title
`Pool.swap` (and `DepositToken.deposit`/`withdraw`) lack a deadline and minimum-output parameter, so delayed/pending transactions execute at stale oracle prices or fees and mint users fewer tokens than intended - (File: contracts/Pool.sol)

### Summary
The referenced DODO issue concerns a user-facing function whose output amount is computed at execution time with no way for the caller to bound how stale the execution can be. The direct Metronome analog is `Pool.swap(ISyntheticToken syntheticTokenIn_, ISyntheticToken syntheticTokenOut_, uint256 amountIn_)`, which prices the swap purely through `masterOracle` at execution time. Its deployed ABI confirms it takes only three parameters — no `minAmountOut` and no `deadline` (`deployments/optimism/Pool.json`, `swap(address,address,uint256)`). The same pattern exists on `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` (`contracts/DepositToken.sol:211`) and `DepositToken.withdraw` (`contracts/DepositToken.sol:406`), where the minted/burned amount is reduced by a fee quoted at execution time via `quoteDepositOut`/`quoteWithdrawOut` with no caller-specified bound.

### Finding Description
- `Pool.swap` burns `amountIn_` of `syntheticTokenIn_` and mints an amount of `syntheticTokenOut_` determined entirely by `masterOracle().quote(...)` and the `swapFee` returned by `FeeProvider.swapFees` at the moment the transaction executes. There is no `minAmountOut` parameter and no `deadline`; the caller can only quote beforehand via `quoteSwapOut`.
- `DepositToken.deposit` pulls `amount_` of underlying into the `Treasury` and mints `_deposited = amount_ - _fee` to `onBehalfOf_` (`contracts/DepositToken.sol:229-234`). The fee is read at execution time; the caller supplies no minimum shares and no deadline.
- By contrast, `SmartFarmingManager.leverage`/`flashRepay` do accept caller-supplied slippage bounds (`depositAmountMin_`, `swapAmountOutMin_`) — see `contracts/SmartFarmingManager.sol:98-103` and `155-162` — but still accept no `deadline`, so a delayed execution can still bind the user to a trade constructed under old prices (slippage bound protects the min, not the intent).
- Concretely: a user signs `pool.swap(msUSD, msBTC, X)` while the oracle reports BTC at $30k. The transaction sits in the public mempool; the oracle updates BTC to $25k (or the `swapFee` for the pair is raised). When mined, the user burns X msUSD but mints materially fewer msBTC than the quote they signed on, with no possibility to revert.

### Impact Explanation
Users lose value through no fault of their own: the burned input is fixed at signing time while the output is priced at an arbitrary future execution time. Any stale-execution output worse than the signed-for quote is a direct, unrecoverable loss of user funds. On `deposit`/`withdraw`, a fee change between signing and execution similarly reduces minted shares / returned collateral without recourse.

### Likelihood Explanation
Requires mempool congestion or a low gas price so the transaction is pending across an oracle price update or a fee change. This is a real-world condition on congested chains (mainnet); on L2s with sequencers it is less common but still possible via delayed inclusion. No privileged role is needed on the attacker side — the harm is environmental rather than adversarial — which matches the DODO report's Medium severity.

### Recommendation
- Add `minAmountOut_` (and optionally `deadline_`) to `Pool.swap`: revert with a slippage error if `_amountOut < minAmountOut_` or `block.timestamp > deadline_`.
- Add `minShares_`/`minOut_` to `DepositToken.deposit`/`withdraw` similarly.
- Add `deadline_` to `SmartFarmingManager.leverage` and `flashRepay` in addition to the existing slippage bounds.

### Proof of Concept
Foundry fork sketch against an existing deployment:

```solidity
// setup: alice holds msUSD, oracle prices msBTC at $P0
uint256 quoteBefore = pool.quoteSwapOut(msUSD, msBTC, amountIn)._amountOut;

// tx is "pending": simulate oracle update before mining
vm.prank(oracleOperatorOrViaPriceFeed);
masterOracle.updatePrice(msBTC, P1); // P1 > P0 (BTC price rises)

// when alice's tx finally executes, she gets less msBTC
uint256 out = pool.swap(msUSD, msBTC, amountIn);
assertLt(out, quoteBefore); // no minOut/deadline to save her
```

Equivalently, increase `feeProvider.updateSwapFee(...)` between signing and execution to show the output dropping below the quoted amount with no revert path. The deposit variant: call `feeProvider.updateDepositFee(f)` before the pending `deposit()` mines and observe `_deposited` shrink (existing test at `test/DepositToken.test.ts:451-472` demonstrates the fee-sensitive mint path).
