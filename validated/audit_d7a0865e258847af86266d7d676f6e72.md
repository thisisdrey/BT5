### Title
Handshake re-key acceptance without signature verification against the already-known public key - (File: `stackslib/src/net/chat.rs`)

### Summary
`ConversationP2P::validate_handshake` only cryptographically verifies an inbound `Handshake` message when the conversation does **not yet** know the peer's public key. Once a public key has already been learned (`self.connection.get_public_key()` returns `Some(_)`), the function skips signature verification entirely and only performs an address/port sanity check — and only for outbound connections. The message is then unconditionally accepted by `handle_handshake`, which calls `update_from_handshake_data`, unconditionally overwriting the connection's/peer's public key with whatever `node_public_key` value the attacker supplied.

### Finding Description
`validate_handshake` branches on whether a public key is already known: [1](#0-0) 

- In the `None` branch (first-time handshake), the code correctly calls `message.verify_secp256k1(&handshake_data.node_public_key)` to prove the sender possesses the private key for the claimed `node_public_key`.
- In the `Some(_)` branch (a public key is already on file for this conversation — i.e., a "re-key"/subsequent handshake), **no signature check is performed at all**. The only guard is an address/port equality check, and that check is gated by `self.stats.outbound`, meaning it is skipped entirely for inbound connections.

After `validate_handshake` returns `Ok(())`, `handle_handshake` proceeds to call `update_from_handshake_data`: [2](#0-1) 

This method unconditionally sets `self.connection.set_public_key(Some(pubk.clone()))` from the attacker-supplied `handshake_data.node_public_key`, without any cryptographic proof that the message was signed by the peer's *previously established* key (or by any key at all, since the new-key verification is also skipped in this branch).

For outbound conversations, the "upgraded" key is even persisted to disk via `Neighbor::load_and_update` / `neighbor.save_update`: [3](#0-2) 

and `PeerDB::update_peer` treats a differing public key as a re-key event and drops the peer's known StackerDB associations: [4](#0-3) 

This breaks the intended equality "the identity recorded for this conversation/neighbor == the identity that actually signed this message." The doc-comment on `handle_handshake` explicitly states the intended invariant that is violated: *"A handshake will only be accepted if we do not yet know the public key of this remote peer, or if it is signed by the current public key."* — the code does not enforce the second half of this contract.

### Impact Explanation
Any party that can inject a `Handshake` message into an existing p2p TCP conversation (the already-connected peer itself, or — for inbound conversations, where the address check is skipped altogether — anyone who can complete a handshake and then send a follow-up bogus one) can force the local node to silently overwrite its record of that peer's cryptographic identity with an arbitrary, unverified public key. This is a direct authentication-bypass/equality violation in the peer-identity protocol: the receiving node's stored identity for the conversation no longer corresponds to anyone who has proven possession of a matching private key. This can be leveraged to spoof/impersonate peer identities in the P2P network, corrupt `PeerDB` state (dropping StackerDB associations for the "re-keyed" slot), and undermine any logic downstream that trusts `ConversationP2P`'s learned public key as an authenticated identity.

### Likelihood Explanation
The bug is reachable by any already-connected peer (which requires only completing an ordinary, unauthenticated first handshake) simply sending a second `Handshake` message with a different (and not necessarily even validly-signed) `node_public_key`. No privileged access, node secret, or other party's key is required — only network access sufficient to establish a normal P2P connection, which is the baseline capability for any peer in this network.

### Recommendation
In the `Some(_)` branch of `validate_handshake`, verify the message signature against the **currently known** public key (`self.connection.get_public_key()`) before allowing any "upgrade," analogous to how the `None` branch verifies against the newly-claimed key. Only if that verification succeeds should the code proceed to accept the new key as an authenticated re-key.

### Proof of Concept
1. Peer A completes a normal handshake with Peer B, so `B.connection.get_public_key() == Some(pubkey_A)`.
2. Peer A (or anyone who can write to that TCP stream) sends a second `Handshake` message whose `node_public_key` field is set to an arbitrary `pubkey_X`, signed with an arbitrary/garbage signature (or even with the wrong private key).
3. `validate_handshake` takes the `Some(_)` branch, performs no `verify_secp256k1` check, and (for an inbound conversation) no address check either, returning `Ok(())`.
4. `handle_handshake` → `update_from_handshake_data` sets `self.connection.set_public_key(Some(pubkey_X))`, and for outbound conversations persists this un-authenticated key change to the `PeerDB` via `Neighbor::load_and_update`/`save_update`, dropping the peer's StackerDB slot associations as a side effect.

Note: I was unable to fully confirm within the available searches whether some other layer (e.g., the initial preamble deserialization/relay path) independently re-verifies this specific message against the previously-established key before dispatch to `handle_authenticated_control_message`; based on the code and comments read, no such independent check was found, but this residual uncertainty should be verified in the full source before remediation.

                // for outbound connections, the self-reported address must match socket address if we already have a public key.

    /// Update connection state from handshake data.
    /// Returns true if we learned a new public key; false if not
    pub fn update_from_handshake_data(
        &mut self,
        preamble: &Preamble,
        handshake_data: &HandshakeData,
    ) -> Result<bool, net_error> {
        let pubk = handshake_data
            .node_public_key
            .to_public_key()
            .map_err(|e| net_error::DeserializeError(e.into()))?;

        self.peer_version = preamble.peer_version;
        self.peer_network_id = preamble.network_id;
        self.peer_services = handshake_data.services;
        self.peer_expire_block_height = handshake_data.expire_block_height;
        self.handshake_addrbytes = handshake_data.addrbytes.clone();
        self.handshake_port = handshake_data.port;
        self.data_url = handshake_data.data_url.clone();

        let mut updated = false;
        let cur_pubk_opt = self.connection.get_public_key();
        if let Some(cur_pubk) = cur_pubk_opt {
            if pubk != cur_pubk {
                debug!(
                    "{:?}: Upgrade key {:?} to {:?} expires {:?}",
                    &self,
                    &to_hex(&cur_pubk.to_bytes_compressed()),
                    &to_hex(&pubk.to_bytes_compressed()),
                    self.peer_expire_block_height
                );
                updated = true;
            }
        }

        self.connection.set_public_key(Some(pubk.clone()));

        Ok(updated)
    }
