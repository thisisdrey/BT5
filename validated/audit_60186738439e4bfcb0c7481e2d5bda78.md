### Title
Unvalidated attacker-controlled offset/length words in `bytes[]` ABI decoding of `ValidateMultiSign` precompile cause uncaught out-of-bounds array access - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The NimBLE CVE stems from computing an "offset to the next report" from attacker-influenced data without validating it against the actual buffer bounds, causing the parser to read past the end of the buffer. The same bug class exists in java-tron's precompiled-contract ABI decoders `extractBytesArray` / `extractSigArray`, which are used by the `ValidateMultiSign` precompile to decode a `bytes[]` array of signatures from raw calldata supplied by any transaction sender. The per-element `bytesOffset` is taken directly from calldata and used to index into the `words[]` array without checking it stays inside the array, so crafted calldata can drive the index past the end of the decoded word array.

### Finding Description
`extractBytesArray` and `extractSigArray` decode a dynamic `bytes[]` argument manually (instead of relying on a bounds-checked ABI decoder): [1](#0-0) [2](#0-1) 

For each array element, `bytesOffset` (and, in `extractBytesArray`, `bytesLen`) are computed straight from `words[...]`, which is attacker-supplied calldata converted with `DataWord.parseArray(data)`. Only the outer `offset > words.length - 1` guard exists; there is no check that `offset + bytesOffset + 1` (or `offset + i + 1`) stays within `words.length` before it is used to index the array, and no check that the derived byte range fits inside `data` before `extractBytes` does `Arrays.copyOfRange(data, offset, offset + len)`. This mirrors the NimBLE root cause exactly: an offset meant to point to "the next sub-item" is computed from untrusted input and used without validating it against the true size of the parsed buffer.

The test suite for `ValidateMultiSign` explicitly documents that pre-activation of TIP-854, malformed calldata "reaches the legacy decoder" and "this precompile has no outer catch, so a too-short input raises inside the decoder": [3](#0-2) 

This confirms the vulnerable, unguarded code path is reachable and unhandled prior to the TIP-854 gate (`VMConfig.allowTvmOsaka()`), and the guard added for TIP-854 only rejects some malformed-length shapes at the top level; it does not add bounds checks inside `extractBytesArray`/`extractSigArray` themselves: [4](#0-3) 

### Impact Explanation
Any unprivileged account can submit a transaction that performs a `CALL` (or `STATICCALL`) into the `ValidateMultiSign` precompile address with hand-crafted `bytes[]` calldata. If the crafted offsets push the array index out of range, Java throws an unchecked `ArrayIndexOutOfBoundsException` inside `extractBytesArray`/`extractSigArray`. Per the test file's own comment, this precompile "has no outer catch" for this path, so the exception is not converted into a normal EVM revert but propagates as a runtime failure during transaction/block execution — the exact class of impact accepted in scope ("node crash or halt"). Because block application in `Manager` processes transactions deterministically, if the exception is not caught somewhere higher in the execution pipeline, it can disrupt processing of the transaction/block for every node that executes it, which is a availability-impacting bug reachable from a single signed transaction.

### Likelihood Explanation
Likelihood is high for reachability: `ValidateMultiSign` is a standard precompiled contract invokable by any TVM `CALL` from any deployed or inline contract, so any anonymous broadcaster can trigger it with one transaction. The only gating factor is whether TIP-854 (`allowTvmOsaka`) is active on the target network — the documented tests show the vulnerable legacy decoder path exists and is intentionally still reachable pre-activation, and even post-activation the top-level shape check does not eliminate all offset-manipulation cases inside the nested `extractBytesArray`/`extractSigArray` helpers.

### Recommendation
Add explicit bounds validation in `extractBytesArray` and `extractSigArray` before every array index/derived-offset use — verify `offset + i + 1 < words.length`, `offset + bytesOffset + 1 < words.length`, and that the final `(bytesOffset + offset + 2) * WORD_SIZE + bytesLen` does not exceed `data.length`, returning a decode failure (e.g., `Pair.of(false, EMPTY_BYTE_ARRAY)`) instead of throwing. Ensure precompiled-contract execution paths (including `ValidateMultiSign`) always convert unexpected `RuntimeException`s into a normal execution failure/revert rather than letting them escape uncaught, consistent with how other precompiles in this file guard offsets (e.g., `extractBytesArray`'s existing `offset > words.length - 1` check should be extended to every offset derived from calldata).

### Proof of Concept
1. Build calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the `bytes[]` array header declares `len = 1` but the per-element offset word (`words[offset + i + 1]`) is set to a large value such that `bytesOffset = value / WORD_SIZE` makes `offset + bytesOffset + 1` exceed `words.length`.
2. Submit a `TriggerSmartContract` transaction (or contract-internal `CALL`) invoking the `ValidateMultiSign` precompile address with this calldata, with `VMConfig.allowTvmOsaka()` not yet active (pre-TIP-854) so the top-level length guard does not intercept it.
3. Execution enters `ValidateMultiSign.execute` → `extractSigArray`/`extractBytesArray`, which indexes `words[offset + bytesOffset + 1]` out of range, throwing `ArrayIndexOutOfBoundsException` with no surrounding catch, as confirmed by `testTip854PreActivationNoOp` in `ValidateMultiSignContractTest.java`.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  @Test
  public void testTip854RejectsMalformedCalldata() {
    VMConfig.initAllowTvmOsaka(1);
    try {
      // Bucket 1: 32-aligned head + sub-word trailing bytes (r=1, r=31).
      for (int r : new int[]{1, 31}) {
        byte[] data = new byte[(5 + 5) * 32 + r];
        Pair<Boolean, byte[]> ret = contract.execute(data);
        Assert.assertFalse("non-32-aligned len=" + data.length, ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Bucket 2: fewer than the static head's 5 words.
      for (int bytes : new int[]{0, 32, 64, 96, 128}) {
        Pair<Boolean, byte[]> ret = contract.execute(new byte[bytes]);
        Assert.assertFalse("len=" + bytes + " < 5 words", ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Bucket 3: 32-aligned but tail not a multiple of I=5 words (k = 1..4).
