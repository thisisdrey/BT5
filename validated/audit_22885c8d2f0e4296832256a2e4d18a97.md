## Analog Vulnerability Found

### Title
Endowment transfer to a precompiled-contract address is executed and left irreversible even when the subsequent `CALL` fails or lacks enough energy - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.callToPrecompiledAddress()` mirrors the Sherlock finding's structural flaw: a state-changing effect (the TRX/TRC10 endowment transfer) is performed unconditionally on the `deposit` repository *before* the call's success is determined, while the code's own inline comment documents that this transfer "is not reversible by rollback." When the subsequent energy check fails, or the precompiled contract itself fails, the caller's stack is pushed with `0` (signaling to the calling contract that the value transfer did not happen, per EVM semantics), yet the balance has already moved and there is no corresponding compensating rollback in that code path.

### Finding Description
In [1](#0-0) , the endowment (native TRX via `MUtil.transfer` or TRC10 via `deposit.addTokenBalance`) is charged to `deposit` immediately, prior to computing `requiredEnergy` and prior to invoking `contract.execute(data)`. The comment directly above this block explicitly states:

```
// Charge for endowment - is not reversible by rollback
```

Immediately after, at [2](#0-1) , if `requiredEnergy > msg.getEnergy().longValue()`, the method refunds zero energy and pushes zero onto the stack — signaling call failure to the calling contract — but **does not call `deposit.commit()`**. Compare this to the success branch at [3](#0-2) , where `deposit.commit()` is only invoked when `out.getLeft()` is `true`.

This is structurally identical to the Teller finding: the "real" effect (fund/asset transfer) is decoupled from the outcome signal (accounting update / return value) that the rest of the system relies on to decide whether the operation actually happened. In the Teller bug, `repayLoanCallback` could revert (paused) while the loan repayment funds had already moved, and the surrounding `try/catch {}` silently absorbed that revert, leaving `totalPrincipalTokensRepaid`/`totalInterestCollected` unbacked by the actual fund movement. Here, a contract invoking a precompiled address with an endowment can end up with the endowment debited from the sender / credited to the target even though the call is reported as failed (stack value `0`), because the explicit "not reversible" charge happens outside of the commit-gated code path that governs whether the rest of the `deposit` child's mutations survive.

### Impact Explanation
Any contract (reachable by an ordinary `TriggerSmartContract` transaction) that performs a `CALL`/`CALLCODE`/`DELEGATECALL` with non-zero value to a precompiled address and races against insufficient energy or a precompile failure would observe: (a) the call reported as failed (`0` returned to the caller), while (b) the balance/token movement persisted. This creates unbacked balances / an inconsistency between the token accounting a calling contract believes occurred (based on the CALL's boolean/0 result) and what actually happened on-chain, directly analogous to the shareholder-loss root cause in the referenced report (funds move, but the value that other code paths rely on to reflect that movement is desynchronized).

### Likelihood Explanation
This is triggerable by any account able to deploy and invoke a smart contract that calls a precompiled address with value and deliberately constrains the gas forwarded (e.g., a `CALL` with a fixed small gas stipend) so that `requiredEnergy > msg.getEnergy()`. No special privilege, validator collusion, or network condition is required — a single crafted transaction from an unprivileged account is sufficient to reach this code path.

### Recommendation
Perform the endowment transfer strictly inside the same commit-gated scope as the rest of `deposit`'s mutations (i.e., only make it durable when `deposit.commit()` is reached), or explicitly discard/reverse the endowment transfer on every early-return / failure branch (the `requiredEnergy` insufficiency branch and the `out.getLeft() == false` branch) so that a failed `CALL` never leaves a committed balance change behind.

### Proof of Concept
1. Deploy a contract `A` with a function that performs `precompiledAddr.call.value(v).gas(g)(data)` where `g` is deliberately set lower than the target precompile's `getEnergyForData(data)` cost.
2. Call this function via a normal `TriggerSmartContract` transaction.
3. Observe: the `CALL` returns `0` (failure) to contract `A`, yet `A`'s (or the caller's) balance reflects the `v` value having been debited/credited per `MUtil.transfer`/`addTokenBalance` at [4](#0-3) , since no rollback/discard of `deposit`'s pending endowment mutation occurs in the insufficient-energy branch at [2](#0-1) .
