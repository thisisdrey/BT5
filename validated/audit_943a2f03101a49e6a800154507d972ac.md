### Title
Case-sensitive certificate blocklist fingerprint comparison allows blocklist bypass - ([File: pki.go], [File: cert/ca_pool.go])

### Summary
`pki.blocklist` fingerprint strings are loaded verbatim from the config file and stored as map keys with no case normalization, while the fingerprints computed at verification time (`Fingerprint()`) are always lowercase hex. If an operator enters a blocklisted fingerprint using uppercase (or mixed-case) hex characters — a common formatting choice for SHA-256 fingerprints — the certificate will silently fail to be recognized as blocklisted, allowing a previously-trusted-but-now-revoked host certificate to continue authenticating and establishing tunnels. This is directly analogous to the reported bug class: a string identifier (address in the report, fingerprint here) that is valid in multiple letter-case representations is compared with a case-sensitive exact match instead of being canonicalized before being used as a security decision key.

### Finding Description
`loadCAPoolFromConfig` reads the blocklist directly from config and calls `BlocklistFingerprint` with the raw string, with no normalization: [1](#0-0) 

`BlocklistFingerprint` and `IsBlocklisted` store/compare the string as-is in a Go map, which is a case-sensitive exact-match data structure: [2](#0-1) 

At verification time, the fingerprint used to test against the blocklist is computed via `c.Fingerprint()`/`CalculateAlternateFingerprint()`, which — per `Certificate.Fingerprint()`'s documented contract ("hex encoded sha256 sum") and Go's `encoding/hex.EncodeToString` behavior — always yields lowercase hex: [3](#0-2) 

`verify()` performs the actual gatekeeping check for every certificate presented in a handshake, comparing the computed (always-lowercase) fingerprint against the blocklist map: [4](#0-3) 

and `VerifyCertificate`/`VerifyCachedCertificate` (used on every handshake and every cached-cert re-check, including for `pki.disconnect_invalid`) rely on the same `IsBlocklisted` lookup for both primary and P256 "alternate" fingerprints: [5](#0-4) 

Because there is no `strings.ToLower()` (or equivalent) normalization applied to the operator-supplied blocklist entries before they are stored as map keys, an admin who pastes a fingerprint from a tool that renders SHA-256 hashes in uppercase (a very common convention, e.g. `sha256sum` on some platforms, various cert tools, and manual transcription) will silently fail to blocklist the intended certificate, with no error or warning logged.

This differs from the DNS server code elsewhere in the same repo, which explicitly normalizes hostnames to lowercase before use as map keys, showing the project is otherwise aware of case-normalization requirements for security/identity-relevant string keys but did not apply the same treatment to the blocklist: [6](#0-5) 

### Impact Explanation
The blocklist is a primary, security-critical mechanism for revoking trust in a certificate without needing to reissue/rotate the entire CA. Per the CHANGELOG, this mechanism was recently hardened specifically to always disconnect blocklisted hosts ("Always disconnect blocklisted hosts, even if `pki.disconnect_invalid` is not set" — #858), underscoring its criticality. A silent, case-based bypass means an operator can believe a compromised or revoked certificate is blocked when in fact it is not, allowing that identity's holder to continue establishing/maintaining a trusted tunnel indefinitely. This is a concrete authentication/revocation bypass with no attacker interaction required beyond possessing the certificate/key that was meant to be revoked.

### Likelihood Explanation
Likelihood is moderate: it requires an operator to enter the blocklist fingerprint in a case that doesn't match the lowercase hex produced by `Fingerprint()`. This is a plausible and easy operational mistake since many tools and manual copy/paste workflows render hex digests in uppercase, and there is no validation, warning, or documentation enforcing lowercase-only entries in `pki.blocklist`. The bug is entirely reachable by a config-level misconfiguration; no attacker action is needed once the mismatch exists — the attacker simply uses the already-issued (but supposedly revoked) certificate as normal.

### Recommendation
Normalize blocklist fingerprints (and the fingerprints being checked) to a canonical case, e.g. lowercase, at the point of `BlocklistFingerprint`/`IsBlocklisted`:
```go
func (ncp *CAPool) BlocklistFingerprint(f string) {
    ncp.certBlocklist[strings.ToLower(f)] = struct{}{}
}

func (ncp *CAPool) IsBlocklisted(fingerprint string) bool {
    _, ok := ncp.certBlocklist[strings.ToLower(fingerprint)]
    return ok
}
```
Additionally, validate `pki.blocklist` entries at config-load time (e.g., confirm they are well-formed hex of the expected length) and log/reject malformed entries so silent misconfigurations are surfaced rather than swallowed.

### Proof of Concept
1. Generate a host certificate and compute its fingerprint via `nebula-cert print` (or `Certificate.Fingerprint()`), e.g. `ab12...ff` (lowercase).
2. In the lighthouse/relay config, set:
   ```yaml
   pki:
     blocklist:
       - "AB12...FF"   # same fingerprint, but uppercase
   ```
3. Start nebula and have the corresponding host attempt a handshake.
4. Observe in `cert/ca_pool.go`'s `verify()` that `ncp.IsBlocklisted(certFp)` returns `false` because the lowercase `certFp` computed from `Fingerprint()` never matches the uppercase key stored in `certBlocklist`, so the handshake succeeds and the "revoked" certificate is trusted, despite the operator's intent to block it.

func (ncp *CAPool) VerifyCertificate(now time.Time, c Certificate) (*CachedCertificate, error) {
	if c == nil {
		return nil, fmt.Errorf("no certificate")
	}
	fp, err := c.Fingerprint()
	if err != nil {
		return nil, fmt.Errorf("could not calculate fingerprint to verify: %w", err)
	}

	signer, err := ncp.verify(c, now, fp, "")
	if err != nil {
		return nil, err
	}

	// Pre nebula v1.10.3 could generate signatures in either high or low s form and validation
	// of signatures allowed for either. Nebula v1.10.3 and beyond clamps signature generation to low-s form
	// but validation still allows for either. Since a change in the signature bytes affects the fingerprint, we
	// need to test both forms until such a time comes that we enforce low-s form on signature validation.
	fp2, err := CalculateAlternateFingerprint(c)
	if err != nil {
		return nil, fmt.Errorf("could not calculate alternate fingerprint to verify: %w", err)
	}
	if fp2 != "" && ncp.IsBlocklisted(fp2) {
		return nil, ErrBlockListed
	}

	cc := CachedCertificate{
		Certificate:       c,
		InvertedGroups:    make(map[string]struct{}),
		Fingerprint:       fp,
		fingerprint2:      fp2,
		signerFingerprint: signer.Fingerprint,
	}

	for _, g := range c.Groups() {
		cc.InvertedGroups[g] = struct{}{}
	}

	return &cc, nil
}

// VerifyCachedCertificate is the same as VerifyCertificate other than it operates on a pre-verified structure and
// is a cheaper operation to perform as a result.
func (ncp *CAPool) VerifyCachedCertificate(now time.Time, c *CachedCertificate) error {
	// Check any available alternate fingerprint forms for this certificate, re P256 high-s/low-s
	if c.fingerprint2 != "" && ncp.IsBlocklisted(c.fingerprint2) {
		return ErrBlockListed
	}

	_, err := ncp.verify(c.Certificate, now, c.Fingerprint, c.signerFingerprint)
	return err
}
