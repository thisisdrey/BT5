### Title
Out-of-bounds read parsing a malformed ZIP64 End-of-Central-Directory Locator offset - (File: third_party/ijar/zip.cc)

### Summary
`FindZip64CentralDirectory()` in `third_party/ijar/zip.cc` reads a 64-bit "zip64 end of central directory offset" field directly out of an attacker-supplied ZIP/JAR file and uses it, unchecked, as a raw pointer offset into the mapped input buffer, then immediately dereferences that pointer to read a fixed-size ZIP64 EOCD record. There is no validation that the offset lies within the mapped file, so a crafted archive can force reads far outside the buffer, analogous to the nvdisasm out-of-bounds read on a malformed ELF file described in CVE-2024-0102.

### Finding Description
`ijar`'s zip reader locates the archive's central directory by scanning backwards from the end of the file for the End-Of-Central-Directory (EOCD) signature [1](#0-0) , and then attempts to locate an optional ZIP64 EOCD record via `FindZip64CentralDirectory()` [2](#0-1) .

When the fixed-offset heuristic fails, the code falls back to reading the ZIP64 EOCD Locator record that immediately precedes the regular EOCD, and pulls a 64-bit "zip64 end of central directory offset" directly from attacker-controlled bytes: [3](#0-2) 

This offset (`zip64_end_of_central_dir_offset`) is added to the base pointer `bytes` and passed straight into `MaybeReadZip64CentralDirectory()` as the `current` pointer to dereference. That function only guards against the pointer being *before* the start of the buffer — it never checks the upper bound against `in_length` (the parameter is explicitly unused, `size_t /*in_length*/`): [4](#0-3) 

It then proceeds to read roughly 52 more bytes (`get_u8le`, `get_u2be` x2, `get_u4be`, `get_u4le`, `get_u8le` x4) from that unchecked location: [5](#0-4) 

Because `zip64_end_of_central_dir_offset` is a full 64-bit value taken verbatim from the file with no range check, an attacker can set it to an arbitrary value (e.g., far beyond the file's actual size, or intentionally within a few bytes of the mapped region's end) to make `current` point outside the `mmap`'d input file, causing an out-of-bounds read the first time `get_u4le(current)` is evaluated in `MaybeReadZip64CentralDirectory`.

This differs from `InputJar::LocateCentralDirectory` (the newer singlejar implementation in `src/tools/singlejar/input_jar.cc`), which uses `mapped_file_.mapped()`/`mapped_file_.offset()` bounds-checking helpers [6](#0-5) . The legacy `ijar` zip reader in `third_party/ijar/zip.cc` has no equivalent containment check for this code path.

### Impact Explanation
`ijar` (interface-jar generation) and its zip-parsing code operate on JAR/ZIP archives that originate from external, attacker-influenced sources — e.g., artifacts fetched by `http_jar`/`http_archive` and precompiled `.jar` dependencies consumed by Java rules. Because the checksum (`sha256`/`integrity`) attributes on `http_archive`/`http_jar` only verify that the downloaded bytes match a pinned hash — they say nothing about the internal structural validity of the archive — any bytes an attacker chooses to publish (and whose hash a developer pins) will pass integrity verification and then be handed to this vulnerable parser. A crafted ZIP64 locator offset can cause an out-of-bounds read of process memory, leading to a crash (denial of service) and potentially information disclosure depending on what memory is mapped adjacent to the archive buffer.

### Likelihood Explanation
Likelihood is moderate-to-high for build pipelines that consume externally-supplied `.jar`/`.zip` archives (e.g., via Maven/`http_jar`/`http_archive`) and process them with `ijar`. The bug requires only a two-field manipulation (ZIP64 EOCD Locator signature check passes, then an arbitrary 8-byte offset), making it trivial to construct once an attacker controls the published archive. No credentials, sandbox escape, or MITM is required — the attacker only needs to be the origin of a dependency archive, and the declared hash simply pins the malicious bytes rather than blocking them.

### Recommendation
In `MaybeReadZip64CentralDirectory()`, validate that `current` and `current + ZIP64_EOCD_FIXED_SIZE` (and, in the locator path, `bytes + zip64_end_of_central_dir_offset`) remain within `[bytes, bytes + in_length)` before dereferencing, returning `false`/failing parsing instead of reading out of bounds. Apply the same offset-bounds validation to `disk_with_zip64_central_directory`/`zip64_end_of_central_dir_offset` before pointer arithmetic in `FindZip64CentralDirectory()`.

### Proof of Concept
Construct a minimal ZIP file consisting of:
1. A valid EOCD record (`0x06054b50`) at the end of the file satisfying `FindZipCentralDirectory`'s comment-length check.
2. Immediately preceding it, a ZIP64 EOCD Locator record (`0x07064b50`) whose `zip64_end_of_central_dir_offset` field is set to a very large 64-bit value (e.g., `0xFFFFFFFFFFFFFF00`).
3. No genuine ZIP64 EOCD record at the fixed offset, forcing `FindZip64CentralDirectory` to take the locator-based path.

Feeding this file to the `ijar` binary (or any Bazel-internal code path invoking `FindZipCentralDirectory`/`FindZip64CentralDirectory` on this file) triggers `get_u4le(bytes + 0xFFFFFFFFFFFFFF00)` in `MaybeReadZip64CentralDirectory`, dereferencing a wild pointer and crashing the process (verifiable via ASan/UBSan or a plain segfault). A `BuildIntegrationTestCase`/shell test can drive this by pointing `http_archive`/`ijar` at such a crafted `.jar` with a pinned `sha256` matching the malicious bytes and observing the crash instead of a parse error.

bool FindZip64CentralDirectory(const u1 *bytes, size_t in_length,
                               const u1 **end_of_central_dir,
                               EndOfCentralDirectoryRecord *cd) {
  // In the absence of a zip64 extensible data sector, the zip64 EOCD is at a
  // fixed offset from the regular central directory.
  if (MaybeReadZip64CentralDirectory(
          bytes, in_length,
          *end_of_central_dir - ZIP64_EOCD_LOCATOR_SIZE - ZIP64_EOCD_FIXED_SIZE,
          end_of_central_dir, cd)) {
    return true;
  }

  // If we couldn't find a zip64 EOCD at a fixed offset, either it doesn't exist
  // or there was a zip64 extensible data sector, so try going through the
  // locator. This approach doesn't work if data was prepended to the archive
  // without updating the offset in the locator.
  const u1 *zip64_locator = *end_of_central_dir - ZIP64_EOCD_LOCATOR_SIZE;
  if (zip64_locator - ZIP64_EOCD_FIXED_SIZE < bytes) {
    return true;
  }
  u4 zip64_locator_signature = get_u4le(zip64_locator);
  if (zip64_locator_signature != ZIP64_EOCD_LOCATOR_SIGNATURE) {
    return true;
  }
  u4 disk_with_zip64_central_directory = get_u4le(zip64_locator);
  u8 zip64_end_of_central_dir_offset = get_u8le(zip64_locator);
  u4 zip64_total_disks = get_u4le(zip64_locator);
  if (MaybeReadZip64CentralDirectory(bytes, in_length,
                                     bytes + zip64_end_of_central_dir_offset,
                                     end_of_central_dir, cd)) {
    // TODO(b/228519294) Add a test for a valid zip64 file with total disks = 0
    if (disk_with_zip64_central_directory != 0 || zip64_total_disks > 1) {
      fprintf(stderr, "multi-disk JAR files are not supported\n");
      return false;
    }
    return true;
  }
  return true;
}

bool FindZipCentralDirectory(const u1 *bytes, size_t in_length, u8 *offset,
                             const u1 **central_dir) {
  static const int MAX_COMMENT_LENGTH = 0xffff;
  static const int CENTRAL_DIR_LOCATOR_SIZE = 22;
  // Maximum distance of start of central dir locator from end of file
  static const int MAX_DELTA = MAX_COMMENT_LENGTH + CENTRAL_DIR_LOCATOR_SIZE;
  const u1* last_pos_to_check = in_length < MAX_DELTA
      ? bytes
      : bytes + (in_length - MAX_DELTA);
  const u1* current;
  bool found = false;

  for (current = bytes + in_length - CENTRAL_DIR_LOCATOR_SIZE;
       current >= last_pos_to_check;
       current-- ) {
    const u1* p = current;
    if (get_u4le(p) != EOCD_SIGNATURE) {
      continue;
    }

    p += 16;  // skip to comment length field
    u2 comment_length = get_u2le(p);

    // Does the comment go exactly till the end of the file?
    if (current + comment_length + CENTRAL_DIR_LOCATOR_SIZE
        != bytes + in_length) {
      continue;
    }

    // Hooray, we found it!
    found = true;
    break;
  }
