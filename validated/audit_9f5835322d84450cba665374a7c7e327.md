## Title
Unbounded array index derived from attacker-controlled precompile calldata causes uncaught exception / node crash in `ValidateMultiSign` and `BatchValidateSign` precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The GSL CVE is caused by computing an array index/offset directly from untrusted (crafted) input data without validating it against the actual buffer bounds, leading to an out-of-bounds access. The same bug-class pattern exists in java-tron's TVM precompiled-contract helpers `extractBytesArray`, `extractSigArray`, and `extractBytes`, which compute byte offsets and lengths from attacker-supplied ABI-encoded calldata and use them directly to index into arrays/slice byte buffers, without full bounds checking before the access.

### Finding Description
`extractBytesArray` and `extractSigArray` read length/offset words directly out of the `DataWord[] words` array that was parsed from the raw precompile input: [1](#0-0) [2](#0-1) 

Only `offset > words.length - 1` is checked up-front; the loop indices `words[offset + i + 1]` and `words[offset + bytesOffset + 1]` are never re-validated against `words.length`, and the derived `bytesOffset`/`bytesLen` values (attacker-controlled, since they come straight from `intValueSafe()` on caller-supplied `DataWord`s) are passed unchecked into `extractBytes`: [3](#0-2) 

`Arrays.copyOfRange(data, offset, offset + len)` will throw `ArrayIndexOutOfBoundsException` if `offset` is negative or beyond `data.length`, or `NegativeArraySizeException`/other unchecked exceptions if `len` is negative or `offset+len` overflows.

These helpers are invoked from `ValidateMultiSign.execute()` and `BatchValidateSign.execute()`/`doExecute()`: [4](#0-3) [5](#0-4) 

Critically, in `ValidateMultiSign.execute()` the calls to `extractSigArray`/`extractBytesArray` (lines 1072-1075) sit **outside** the `try { ... } catch (Throwable t) { ... }` block that wraps the rest of the method (the `try` begins at line 1082), meaning an unchecked exception thrown while computing/copying the byte-array slice propagates out of `execute()` uncaught by this method. `BatchValidateSign.execute()` does wrap `doExecute()` in a `try/catch(Throwable t)` at the outer call site, catching the failure gracefully — so the more exploitable path is `ValidateMultiSign` (opcode reachable via a normal `TriggerSmartContract` CALL to the corresponding precompile address).

Whether an uncaught `RuntimeException` here ultimately just fails the single transaction (caught further up by `VM.play`'s generic `RuntimeException` handler) or destabilizes block processing depends on exception-handling layers in `Program`/`VMActuator`/`Manager` that I was not able to fully trace before running out of tool budget (see "Unknown/uncertain" below). This is the key remaining uncertainty for confirming full node-crash impact versus "just" a failed/aborted transaction (which, while a DoS annoyance, would be lower severity).

### Impact Explanation
If the uncaught exception from `extractBytesArray`/`extractSigArray`/`extractBytes` propagates past the per-opcode/per-call exception boundaries of the TVM interpreter (`VM.play` catches generic `RuntimeException` around each single opcode execution and marks the call reverted/spends all energy), the most likely outcome is a failed/reverted transaction rather than a node crash — this would reduce severity to a griefing/DoS-on-self issue rather than a node-halting bug. However, because the `ValidateMultiSign` call path bypasses the local `Throwable` catch inside `execute()`, if there exists any code path in block validation/`ProcessTransactionsUtils`/`Manager.processTransaction` that does not defensively catch generic `RuntimeException` for constant/trigger-contract calls (e.g., during `getEnergyForData` estimation, or during full-node re-execution for `TriggerConstantContract`/estimateEnergy RPC calls), it could lead to unhandled exceptions surfacing to API callers or, in the worst case, destabilizing block application. I was unable to conclusively confirm this end of the propagation chain in the time available.

### Likelihood Explanation
Any account can trigger this by sending a normal `TriggerSmartContract` transaction (or making an `triggercontract`/`triggerconstantcontract` API call) that performs a `CALL` to the `ValidateMultiSign` precompile address with crafted calldata where the offset/length words are chosen to make `bytesOffset`, `bytesLen`, or the derived index exceed `words.length` or `data.length`. This requires no special privilege, no precompiled ABI validation bypass (the `isValidAbiEncoding` check only runs when `VMConfig.allowTvmOsaka()` is enabled, and even that check does not fully validate every offset/length combination used inside the extraction helpers), and is reachable purely from calldata a caller fully controls.

### Recommendation
- Add explicit bounds validation before every array/byte-buffer access in `extractBytesArray`, `extractSigArray`, and `extractBytes`: verify `offset + i + 1 < words.length`, `offset + bytesOffset + 1 < words.length`, `bytesLen >= 0`, and `(bytesOffset + offset + 2) * WORD_SIZE + bytesLen <= data.length` before calling `Arrays.copyOfRange`.
- Wrap the `extractSigArray`/`extractBytesArray` calls in `ValidateMultiSign.execute()` inside the same `try/catch(Throwable t)` block that already protects the rest of the method (matching the pattern used elsewhere in the file), so malformed calldata safely returns `Pair.of(true, DATA_FALSE)` instead of throwing.
- Add regression/fuzz tests for `ValidateMultiSign` and `BatchValidateSign` with malformed/out-of-range offset and length words to ensure no unchecked exception escapes `execute()`.

### Proof of Concept
1. Deploy or use any contract that performs a low-level `CALL` (or a Solidity precompile-call wrapper) to the `ValidateMultiSign` precompiled contract address, supplying raw ABI-encoded calldata where:
   - word[3] (the `sigArrayOffset`) is crafted so that `words[3].intValueSafe() / WORD_SIZE` combined with the loop index makes `offset + i + 1` exceed `words.length` (fewer trailing words provided than implied by the declared array length `len`), or
   - the length word at that offset (`bytesLen`) is set to a very large or negative-after-overflow value.
2. Broadcast this as a normal signed `TriggerSmartContract` transaction from any account (no special permission required).
3. Execution reaches `PrecompiledContracts.ValidateMultiSign.execute()` → `extractSigArray`/`extractBytesArray` → `words[offset + i + 1]` (out of bounds) or `extractBytes` → `Arrays.copyOfRange(data, offset, offset+len)` (out of bounds / negative size), throwing `ArrayIndexOutOfBoundsException` or `NegativeArraySizeException` outside the local `try/catch(Throwable)` guard.
4. Observe whether the exception is only caught by the generic TVM opcode-level `RuntimeException` handler (transaction fails/reverts, node stays up) — I could not fully verify this boundary in the given time, so the actual blast radius (transaction failure vs. node-level instability) needs to be confirmed by a Devin session with full repo access and the ability to run the node/tests.
