### Title
Relay control-message identity confusion: `RelayFromAddr` is trusted without verifying it matches the authenticated sender's certificate identity - ([File: relay_manager.go])

### Summary
This is a genuine analog to the `tx.origin` bug class described in the report. `tx.origin` fails because it lets a contract accept a *self-declared, forwarded* identity instead of the identity of the party that actually made the immediate authenticated call (`msg.sender`). In Nebula's relay protocol, `handleCreateRelayRequest` does the analogous thing: it uses `RelayFromAddr` (an attacker-controlled field carried inside a `NebulaControl` payload) as the authoritative identity of "who this relay is for," instead of validating it against `h.vpnAddrs` - the cryptographically authenticated identity of the peer that actually sent the message over its verified Noise tunnel.

### Finding Description
`HandleControlMsg` receives a `NebulaControl` message on an already-authenticated tunnel from peer `h` (whose identity was verified during the Noise handshake and bound to `h.vpnAddrs`) [1](#0-0) . It unmarshals attacker-supplied fields `RelayFromAddr`/`RelayToAddr` and only checks that they are non-nil before dispatching to `handleCreateRelayRequest` [2](#0-1) .

Inside `handleCreateRelayRequest`, `from := protoAddrToNetAddr(m.RelayFromAddr)` is treated as the relay-origin identity. When the relay target is "me" (the terminal case), the code installs relay state keyed by `from` and associates it with `h` - the sending HostInfo - without ever checking that `from == h.vpnAddrs[0]`: [3](#0-2) 

Specifically, `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` binds the caller's authenticated `HostInfo h` to a relay-state entry indexed by whatever `from` value the sender chose to put in the payload [4](#0-3) , and the response is echoed back using the same unverified `from`/`target` values [5](#0-4) .

This is structurally identical to the `tx.origin` flaw: `h` (the tunnel peer that cryptographically signed/authenticated this message) is the correct trust anchor - the `msg.sender` equivalent - but the code instead trusts `from`, a value embedded in message content that any authenticated-but-malicious peer fully controls, akin to `tx.origin` being spoofable through an intermediary.

### Impact Explanation
An authenticated (but untrusted/malicious) Nebula peer can send a `CreateRelayRequest` to any node acting as a relay and set `RelayFromAddr` to an arbitrary victim's VPN address instead of its own. Because the relay never verifies `from == h.vpnAddrs[0]`, it will create/overwrite relay routing state (`h.relayState`) keyed to the victim's address and reply with a `CreateRelayResponse` claiming to be that victim, without the true victim's participation or knowledge. This is a remote state-poisoning primitive within the relay subsystem: relay routing metadata that other peers may query/rely on to reach the victim can be corrupted by an unrelated authenticated attacker, potentially misdirecting relayed traffic intended for the victim toward the attacker's session. This matches the "remote state poisoning" / traffic-forgery impact class called out in the validation rules.

### Likelihood Explanation
Any node that can establish a normal, valid Nebula tunnel (i.e., any legitimately certificate-holding but malicious peer, or any peer able to reach a node configured with `relay.am_relay: true`) can trigger this by sending a single crafted `Control`/`NebulaControl_CreateRelayRequest` message with a forged `RelayFromAddr`. No special privilege beyond normal peer status is required, and the check that's missing (`from == h.vpnAddrs[0]`) is absent on every code path in `handleCreateRelayRequest`'s terminal-target branch.

### Recommendation
In `handleCreateRelayRequest` (and symmetrically in `handleCreateRelayResponse`/`EstablishRelay`), verify that the attacker-supplied `RelayFromAddr` matches `h.vpnAddrs` (the authenticated sender's certificate-bound VPN address) before using it as a key for `AddRelay`/`QueryRelayForByIp`/state transitions. If the message is only ever expected to describe the sender's own address in the terminal case, drop it when `from` doesn't match `h.vpnAddrs`, mirroring how `beginHandshake`/`continueHandshake` already refuse self-handshakes and validate certificate-derived addresses [6](#0-5) .

### Proof of Concept
1. Attacker `A` establishes a normal, valid Nebula tunnel to relay node `R` (R has `relay.am_relay: true`).
2. `A` sends `R` a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to victim `V`'s VPN address (not `A`'s own) and `RelayToAddr` set to `R`'s own address [7](#0-6) .
3. `R` sees the target is itself, finds no existing relay for `from=V`, and calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`, where `h` is `A`'s authenticated `HostInfo` - binding `A`'s tunnel to relay state keyed by `V`'s address, with no check that `from` matches `h.vpnAddrs` [4](#0-3) .
4. `R` replies to `A` with `CreateRelayResponse` echoing `relayFrom=V`, completing an "Established" relay entry that misrepresents `A` as `V` in `R`'s relay bookkeeping [8](#0-7) .

Note: I was not able to fully trace, within the remaining investigation budget, every downstream consumer of this poisoned `relayState` entry (e.g., whether third-party lookups such as `QueryVpnAddrsRelayFor` can be tricked into selecting this forged entry when routing traffic to the real `V`) to confirm end-to-end traffic redirection; this would need further tracing in `hostmap.go`'s relay query functions before treating the poisoning as a confirmed traffic-diversion exploit rather than a metadata-integrity violation.

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}

		relay, ok := h.relayState.QueryRelayForByIp(from)
		if !ok {
			logMsg.Error("Relay State not found", "from", from)
			return
		}

		resp := NebulaControl{
			Type:                NebulaControl_CreateRelayResponse,
			ResponderRelayIndex: relay.LocalIndex,
			InitiatorRelayIndex: relay.RemoteIndex,
		}

		if v == cert.Version1 {
			b := from.As4()
			resp.OldRelayFromAddr = binary.BigEndian.Uint32(b[:])
			b = target.As4()
			resp.OldRelayToAddr = binary.BigEndian.Uint32(b[:])
		} else {
			resp.RelayFromAddr = netAddrToProtoAddr(from)
			resp.RelayToAddr = netAddrToProtoAddr(target)
		}

		msg, err := resp.Marshal()
		if err != nil {
			logMsg.Error("relayManager Failed to marshal Control CreateRelayResponse message to create relay", "error", err)
		} else {
			f.SendMessageToHostInfo(header.Control, 0, h, msg, make([]byte, 12), make([]byte, mtu))
			rm.l.Info("send CreateRelayResponse",
				"relayFrom", from,
				"relayTo", target,
				"initiatorRelayIndex", resp.InitiatorRelayIndex,
				"responderRelayIndex", resp.ResponderRelayIndex,
				"vpnAddrs", h.vpnAddrs,
			)
		}
		return
