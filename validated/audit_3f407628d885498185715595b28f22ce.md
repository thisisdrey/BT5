### Title
Unbounded blocking `RateLimiter.acquire()` in the default/QPS rate-limiting strategy causes HTTP/gRPC thread-pool exhaustion and denial of service - ([File: framework/src/main/java/org/tron/core/services/ratelimiter/strategy/QpsStrategy.java])

### Summary
CVE-2025-50334 describes a DoS in Technitium DNS Server's rate-limiting component itself. java-tron has an analogous class of bug: the node's own API rate limiter, which is meant to *protect* the node from overload, instead becomes the DoS vector because its default (and only non-preemptible) blocking mode has no bound on how long a request-handling thread can be held waiting for a permit.

### Finding Description
Every HTTP servlet and every gRPC method is protected at admission time by an `IRateLimiter` chosen in `RateLimiterServlet.service()` [1](#0-0)  and `RateLimiterInterceptor.interceptCall()` [2](#0-1) . Both call `IRateLimiter.acquirePermit()`, which dispatches to either `tryAcquire()` (non-blocking) or `acquire()` (blocking) depending on the `rate.limiter.apiNonBlocking` flag, which **defaults to `false`** [3](#0-2) .

For every endpoint that has no explicit strategy configured — i.e. essentially all endpoints out of the box, since `http = []` and `rpc = []` by default [4](#0-3)  — the fallback is `DefaultBaseQqsAdapter`, which wraps a `QpsStrategy` [5](#0-4) , and `RateLimiterInterceptor.init()` registers exactly this default adapter for every gRPC method at startup [6](#0-5) .

`QpsStrategy.acquire()` and `IPQpsStrategy.acquire()` call the underlying Guava `RateLimiter.acquire()` directly, with **no timeout**:
```java
public boolean acquire() {
  rateLimiter.acquire();
  return true;
}
``` [7](#0-6) [8](#0-7) 

Contrast this with `GlobalPreemptibleStrategy.acquire()`, which explicitly bounds the wait to `DEFAULT_ACQUIRE_TIMEOUT` (2 seconds) and rejects on timeout precisely to avoid "tying up Netty IO / gRPC executor threads" (per its own comment) [9](#0-8) . The QPS-based strategies — which are the *default* for every unconfigured endpoint and the only strategy applied to `GlobalRateLimiter` itself [10](#0-9)  — have no such protection.

Guava's `RateLimiter.acquire()` blocks the calling thread for however long is needed to "pay back" the accumulated deficit of permits; that wait time grows without bound as more callers queue up ahead of it. Because the HTTP servlet thread (Jetty) or gRPC executor thread (`RpcService.initServerBuilder()`, bounded by `parameter.getRpcThreadNum()` or Netty's default executor) is held *inside* `acquire()` for the entire wait, an attacker who simply floods any single endpoint (e.g. any unauthenticated `Wallet` gRPC call or any `/wallet/*` HTTP endpoint) with requests exceeding the configured QPS (default 1000 per endpoint, or the `GlobalRateLimiter`'s 50000 global / 10000 per-IP) causes each excess request's handling thread to block for increasing durations. As long as the attacker keeps the flood going, the queue — and therefore the thread-blocking duration — keeps growing, eventually consuming the entire bounded worker-thread pool and starving all legitimate clients from being served.

### Impact Explanation
This directly matches the "API the node can no longer serve" criterion: any anonymous network client reaching the FullNode's HTTP or gRPC listener can, without any signed transaction or authentication, exhaust the node's request-handling thread pool via the very component intended to prevent overload, rendering `Wallet`/`TronJsonRpcImpl` HTTP, gRPC, and JSON-RPC query paths unavailable to all other clients (validators/SRs relying on the same node for API access, exchanges, wallets, etc.). This is a High-severity denial of service, analogous in root cause to CVE-2025-50334 (rate-limiter itself being the DoS vector).

### Likelihood Explanation
High. The vulnerable path is the **default configuration** — `apiNonBlocking = false` and empty `http`/`rpc` override lists ship as-is in `reference.conf`/`config.conf`. No special privileges, signed transactions, or contract deployment are required; a remote, unauthenticated client can trigger it by simply sending requests at a rate above the per-endpoint/global QPS ceiling.

### Recommendation
- Apply a bounded timeout to `QpsStrategy.acquire()` / `IPQpsStrategy.acquire()` (mirroring `GlobalPreemptibleStrategy`'s `tryAcquire(timeout, unit)` pattern) so blocked requests fail fast with a resource-exhausted error instead of holding a worker thread indefinitely.
- Consider defaulting `rate.limiter.apiNonBlocking` to `true` for a shed-load-first posture, or at minimum document and strongly recommend enabling it in production.
- Decouple permit-waiting from the request-handling thread (e.g. via an async/scheduled retry) so that even long waits don't consume bounded thread-pool capacity.

### Proof of Concept
1. Deploy a FullNode with default `config.conf`/`reference.conf` (`apiNonBlocking = false`, no per-endpoint overrides).
2. From a single unauthenticated client, issue a sustained flood of requests to any HTTP servlet or gRPC method (e.g. `GetAccount` or any `/wallet/*` endpoint) at a rate well above the default per-endpoint 1000 QPS / global 50000 QPS ceilings.
3. Observe that request-handling threads (Jetty worker threads for HTTP, gRPC executor threads) become blocked inside `RateLimiter.acquire()` for increasing durations as the queue grows.
4. Continue the flood; once the bounded thread pool is fully occupied by blocked threads, legitimate requests from other clients time out or are refused, confirming node-wide HTTP/gRPC API denial of service.

*Note: I could not fully verify the exact size/boundedness of Jetty's HTTP thread pool or the default gRPC executor thread count in this codebase (searches for `QueuedThreadPool`/`maxThreads` did not surface the Jetty server thread-pool configuration used by `FullNodeHttpApiService`), so the precise number of concurrent flooding threads required to fully exhaust the pool is not confirmed from the indexed code alone.*

  // Non-blocking: immediately rejects if no permit is available. Used when the
  // apiNonBlocking switch is on, to shed overload instead of tying up Netty IO /
  // gRPC executor threads while waiting for a permit.
  public boolean tryAcquire() {
    return sp.tryAcquire();
  }

  public boolean acquire() {
    try {
      return sp.tryAcquire(DEFAULT_ACQUIRE_TIMEOUT, TimeUnit.SECONDS);
    } catch (InterruptedException e) {
      // Restore the interrupt flag and reject — caller must not release a permit
      // it never acquired.
      logger.error("acquire permit with error: {}", e.getMessage());
      Thread.currentThread().interrupt();
      return false;
    }
  }
