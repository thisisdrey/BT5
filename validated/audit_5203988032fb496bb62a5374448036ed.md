### Title
Peer-controlled `data_url` in Handshake enables SSRF to internal/loopback services via block download (epoch2x) - (File: `stackslib/src/net/download/epoch2x.rs`)

### Summary
The external report describes an SSRF where a redirect target is not validated before the proxy issues an outbound request. The closest analog in this repo is that a remote, unauthenticated-at-the-HTTP-layer peer sets an arbitrary `data_url` field in its P2P `Handshake` message [1](#0-0) , and this URL — decoupled from the peer's actual P2P `addrbytes`/`NeighborKey` that was already vetted by `can_register_peer` — is later used verbatim by this node to originate outbound HTTP connections during block/microblock download (`get_data_url` → `begin_request` → `connect_or_send_http_request`) with no private/loopback-range check at that call site.

### Finding Description
When two Stacks nodes handshake, `HandshakeData.data_url` is taken directly from the wire with only URL-syntax validation, not IP-range validation: `consensus_deserialize` reads the `UrlString` and only validates it "must decode to a URL" / "must be a valid block URL" [2](#0-1) . It is then stored as `convo.data_url` via `update_from_handshake_data` [3](#0-2) .

This `data_url` is subsequently resolved to an IP (`try_decode_data_url_ipaddr` / DNS resolution) and stored in `convo.data_ip` [4](#0-3) . Block-and-microblock downloading fetches this same value with `get_data_url(&nk)`, which simply returns `convo.data_url` if non-empty — with no range check [5](#0-4) , and then queues an HTTP request through `begin_request` → `connect_or_send_http_request` [6](#0-5) [7](#0-6) . Nowhere in this path is `PeerAddress::is_in_private_range()` consulted, unlike the mempool-sync path.

By contrast, the mempool-sync code explicitly guards against this exact scenario: before querying a peer's advertised data URL, it checks `PeerAddress::from_socketaddr(addr).is_in_private_range()` and refuses unless `connection_opts.private_neighbors` is enabled [8](#0-7) . The existence of this guard elsewhere in the codebase, and its absence in the block-download path, the StackerDB `send_request` path (`stackslib/src/net/neighbors/rpc.rs`), and the Atlas attachment-download path (`stackslib/src/net/atlas/download.rs`) — none of which reference `is_in_private_range`/`private_neighbors` — confirms this is an overlooked/inconsistent validation gap rather than an intentional design choice.

Separately, `can_register_peer` only checks whether the peer's P2P `NeighborKey.addrbytes` (the socket address of the inbound/outbound P2P TCP connection) is private [9](#0-8) . It never inspects `HandshakeData.data_url`, which is a logically independent field a legitimate, public-IP peer can set to point anywhere — e.g., `127.0.0.1`, RFC1918 ranges, or a cloud metadata address — and the node will still resolve and connect to it for block/microblock downloads.

### Impact Explanation
A single malicious (or compromised) but otherwise legitimately-connectable Stacks peer can set its `data_url` to an internal address (e.g., a node's own loopback RPC/admin port, another service on the private network, or a link-local metadata endpoint) and steer the victim node's outbound HTTP fetch during block/microblock download to that target. This can be used to probe/reach internal services from a remote, unprivileged network position (classic SSRF impact: internal port/service reachability, potential interaction with unauthenticated local admin endpoints). This matches the "bounded compute DoS on a read endpoint" / SSRF-class impact called out as in-scope (High).

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to first become a P2P neighbor of the victim (routine and easy for a public network) and to be selected as a download source, which happens naturally during normal chain sync when the attacker advertises blocks/microblocks. No additional authentication or privilege is required beyond running a normal Stacks node and completing a handshake — the `data_url` field is attacker-controlled by design in the protocol.

### Recommendation
Apply the same `PeerAddress::is_in_private_range()` (gated by `connection_opts.private_neighbors`) check used in `mempool_sync` to every place a peer-supplied `data_url`/resolved `data_ip` is used to originate an outbound connection: `PeerNetwork::get_data_url`/`begin_request` in `stackslib/src/net/download/epoch2x.rs`, `NeighborRPC::send_request`/`get_peer_host` in `stackslib/src/net/neighbors/rpc.rs`, and the Atlas attachment downloader in `stackslib/src/net/atlas/download.rs`. Ideally centralize the check inside `connect_or_send_http_request` or `HttpPeer::connect_http` so it cannot be bypassed by any future call site.

### Proof of Concept
1. Stand up a malicious node with a normal, publicly-routable P2P `addrbytes` (so it passes `can_register_peer`).
2. In its `Handshake` message, set `HandshakeData.data_url` to `http://127.0.0.1:<victim-internal-port>` (or any internal/private target reachable from the victim's network).
3. Complete the handshake with the victim node; `update_from_handshake_data` stores this URL as `convo.data_url` unchanged.
4. Advertise blocks/microblocks to the victim (or otherwise arrange to be selected as a download source) so that `PeerNetwork::get_data_url` returns the malicious `data_url` and `begin_request`/`connect_or_send_http_request` issues an outbound HTTP GET to `127.0.0.1:<port>` from the victim node — confirmable via `blocked_urls`/logs or by observing traffic to the internal target.

Note: I was not able to fully trace every downstream consumer of `data_url` (e.g., all StackerDB sync call sites in `stackslib/src/net/stackerdb/sync.rs`, which do reference `is_in_private_range`/`private_neighbors` per grep but whose exact enforcement logic I did not read line-by-line) within the tool budget; the block-download path (`epoch2x.rs`) is confirmed to lack the guard, but I could not fully confirm whether Atlas download and StackerDB sync are also vulnerable or already partially mitigated — this should be verified with a full read of `stackslib/src/net/stackerdb/sync.rs` and `stackslib/src/net/atlas/download.rs` in a Devin session with full file access.

    pub fn connect_or_send_http_request(
        &mut self,
        data_url: UrlString,
        addr: SocketAddr,
        request: StacksHttpRequest,
    ) -> Result<usize, NetError> {
        PeerNetwork::with_network_state(self, |ref mut network, ref mut network_state| {
            PeerNetwork::with_http(network, |ref mut network, ref mut http| {
                match http.connect_http(
                    network_state,
                    network,
                    data_url.clone(),
                    addr,
                    Some(request.clone()),
                ) {
                    Ok(event_id) => Ok(event_id),
                    Err(NetError::AlreadyConnected(event_id, _)) => {
                        if let (Some(ref mut convo), Some(ref mut socket)) =
                            http.get_conversation_and_socket(event_id)
                        {
                            convo.send_request(request)?;
                            HttpPeer::saturate_http_socket(socket, convo)?;
                            Ok(event_id)
                        } else {
                            debug!("HTTP failed to connect to {data_url}, {addr:?}");
                            Err(NetError::PeerNotConnected(format!(
                                "HTTP failed to connect to {data_url}, {addr:?}",
                            )))
                        }
                    }
                    Err(e) => Err(e),
                }
            })
        })
    }

        // don't talk to our bind address

            debug!(

            return Err(net_error::Denied);

                &self.local_peer, neighbor_key
