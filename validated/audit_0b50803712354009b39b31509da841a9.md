### Title
Missing Privilege Check Allows Active-Permission Key to Escalate and Silently Replace Account Owner Permission (Multi-Sig Bypass) - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator.execute()` unconditionally overwrites an account's `Owner`, `Witness`, and `Active` permissions from whatever `AccountPermissionUpdateContract` was submitted, with no check that the transaction was authorized specifically by the account's `Owner` permission (`permissionId == 0`). Authorization is instead delegated generically to the same operation-bitmap mechanism (`checkPermissionOperations`) used for any other contract type, so a lower-tier `Active` permission — if it merely has the `AccountPermissionUpdateContract` operation bit enabled — can single-handedly rewrite the account's `Owner` permission, exactly mirroring the CVE-2026-59799 pattern of a security-control-disabling operation reachable without the elevated privilege it is supposed to require.

### Finding Description
Permission authorization for any TRON transaction, including `AccountPermissionUpdateContract`, is resolved in `TransactionCapsule.validateSignature()`/`checkPermission()` [2](#0-1)  and `TransactionCapsule.checkPermission()` [3](#0-2) . If `permissionId != 0` (i.e., an `Active` permission, not `Owner`), the only additional check is `checkPermissionOperations`, which merely tests whether the bit for the contract's `ContractType` is set in that `Active` permission's 32-byte `operations` bitmap [4](#0-3) . There is no special-case exclusion preventing `AccountPermissionUpdateContract` from being one of the contract types delegable to an `Active` permission.

`AccountPermissionUpdateActuator.validate()` further does nothing to require that the specific permission used to sign the transaction is the `Owner` permission before allowing the `Owner` field of the contract to be applied — it only validates the *contents* of the new permissions (key counts, thresholds, witness consistency) [5](#0-4) . `execute()` then calls `account.updatePermissions(owner, witness, actives)` unconditionally and persists it [6](#0-5) .

Consequently, if an account owner ever grants an `Active` key the `AccountPermissionUpdateContract` operation bit (a legitimate-looking convenience, e.g. for automated key-rotation tooling), that single `Active` key — even with a low threshold such as 1 — can submit a transaction that replaces the account's `Owner` permission entirely, evicting the true owner's keys and installing attacker-controlled keys as the new `Owner`, without ever needing to meet the `Owner` permission's threshold. This is the direct analog of the CloudStack bug: a security-control "disable/replace" operation (there: 2FA disable; here: multi-sig `Owner` permission replacement) that should require the highest privilege tier is instead reachable through a lower, delegated privilege tier due to a missing dedicated privilege check in the actuator.

### Impact Explanation
Full account takeover: an attacker who compromises or is granted only an `Active` key with the `AccountPermissionUpdateContract` bit set can overwrite `Owner` (and `Witness`, if applicable) permissions, permanently locking out the legitimate account owner and gaining unilateral control over all account funds, TRC-10/TRC-20 assets, staked TRX, and delegated resources. This satisfies "unauthorized account operation" and "theft/permanent freezing of funds" impact criteria.

### Likelihood Explanation
Exploitation requires only that the target account's `Owner` has, at some point, configured an `Active` permission with the `AccountPermissionUpdateContract` operation bit enabled — a plausible operational pattern for exchanges/custodians using tiered key management for automation, since nothing in the actuator or documentation-enforced code path prevents it. Once such a permission exists, exploitation is a single signed transaction from an unprivileged holder of that `Active` key, requiring no special node privilege, race condition, or additional preconditions.

### Recommendation
Add an explicit privilege check in `AccountPermissionUpdateActuator.validate()`/`execute()` requiring that the contract's `permissionId` used for signing equals `0` (the account's `Owner` permission) whenever the `Owner` permission is being modified, rather than relying solely on the generic per-contract-type operations bitmap used for ordinary contract types. Alternatively, exclude `AccountPermissionUpdateContract` from the set of contract types that can ever be enabled in an `Active` permission's operations bitmap (reject it during `checkPermission` in `AccountPermissionUpdateActuator`), so permission structure changes always require `Owner`-level signature weight.

### Proof of Concept
1. Account `A` (owner key `K_owner`) sets up an `Active` permission `P_active` with threshold 1, containing key `K_active`, and includes the `AccountPermissionUpdateContract` bit in `P_active.operations` (a legitimate-looking setup for automation).
2. Attacker who controls only `K_active` (e.g., via a compromised automation service) builds an `AccountPermissionUpdateContract` for account `A` that sets a brand-new `Owner` permission containing only the attacker's key, signs it with `K_active`, and sets `permission_id = P_active`'s id in the transaction.
3. `TransactionCapsule.checkPermission()` passes because `checkPermissionOperations` finds the `AccountPermissionUpdateContract` bit set in `P_active` [3](#0-2) .
4. `AccountPermissionUpdateActuator.execute()` applies the new `Owner` permission unconditionally [6](#0-5) , giving the attacker full `Owner`-level control of account `A`, locking out `K_owner`.

    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);

    if (account == null) {
      if (permissionId == 0) {

      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);

    if (weight >= permission.getThreshold()) {

    }
    return false;
  }

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
