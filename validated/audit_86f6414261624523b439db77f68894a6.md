### Title
Unbounded array allocation from attacker-controlled length in TVM precompiled-contract input parsing can cause node OutOfMemoryError DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.java` contains several helper methods (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) that read a "count/length" word directly out of the raw calldata passed to a precompiled contract and immediately use it to allocate a Java array, with no upper bound check against a sane maximum or against the actual remaining size of the input buffer. ### Finding Description
Each of these helpers derives `len` from a single 32-byte word supplied by the caller (`words[offset].intValueSafe()`), then immediately does `new byte[len][]` before performing any validation that `len` is consistent with the length of the actual input `data`/`words` array:

```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    ...
}
``` [1](#0-0) 

`extractBytesArray` and `extractSigArray` follow the identical pattern, reading `len` from a word inside attacker-supplied `words` and allocating `new byte[len][]` before the inner loop attempts to index past the actual `data`/`words` bounds. [2](#0-1) [3](#0-2) 

This is structurally the same bug class as CVE-2021-40941: a size/count value taken from untrusted, attacker-controlled input is used to size an allocator (`AP4_Array::EnsureCapacity` in Bento4 / `new byte[len][]` here) without first bounding it to what the surrounding data could plausibly contain, so a single crafted input can request an allocation many gigabytes in size and trigger `OutOfMemoryError`.

The `words` array itself is the `DataWord[]`-chunked representation of the raw `byte[] data` passed into a `PrecompiledContract.execute(byte[] data)` call. That `data` is completely attacker controlled: it is the CALL/STATICCALL input to a precompiled-contract address, reachable from any smart contract executed by the TVM in response to a `TriggerSmartContract` transaction broadcast by any unprivileged account — no special privilege is required to reach `execute()` and thus these array-extraction helpers.

Because `intValueSafe()` only guards against throwing on conversion (clamping/interpreting the word as an `int`), an attacker can set the length word to a very large positive value (up to `Integer.MAX_VALUE`), causing `new byte[Integer.MAX_VALUE][]` (an array of ~2 billion object references, ~16GB+ just for the reference array before any element allocation) to be attempted on the node executing the transaction.

### Impact Explanation
`OutOfMemoryError` is a JVM `Error`, not a checked `Exception`. Depending on where it propagates in the TVM execution stack, it can escape narrow `catch (Exception e)` or `catch (ContractExeException e)` blocks used elsewhere in the VM/actuator code, causing the executing thread (and potentially the whole full node / SR node process, since the JVM heap is shared) to crash or become unresponsive. Because this is reachable via a single unprivileged, unsigned-cost-bounded transaction (subject only to normal energy/fee accounting, which does not model allocation size for this code path), any user with enough TRX for a `TriggerSmartContract` fee can attempt to crash or degrade the availability of nodes that execute the transaction — this qualifies as a High severity node crash / denial-of-service condition, consistent with the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Likelihood is high for the code paths that call these three helpers: an attacker only needs to invoke, from a deployed contract, whichever precompiled-contract address consumes `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (these are used to parse Ed25519/ZK-related structured precompile inputs) with a length word set to a large value. No special network position, key material, or SR/witness status is required — it is purely a matter of crafting the calldata for the CALL to that precompiled address.

### Recommendation
- In `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against a strict upper bound derived from the actual size of `data`/`words` (e.g., `len` must not exceed `(data.length - minimal per-item size) / itemSize`) before allocating any array.
- Reject with an execution failure/exception (charged energy, not crash) rather than allocating when the declared length is inconsistent with the available input size, mirroring the pattern already used elsewhere in the VM (e.g., `checkMemorySize` in `EnergyCost.java`).
- Consider centralizing an "ABI array length sanity check" utility (similar to `isValidAbiEncoding`) and applying it uniformly to every precompiled-contract input parser that reads a count/length field from untrusted data.

### Proof of Concept
1. Deploy a trivial contract that performs a `STATICCALL`/`CALL` to the precompiled-contract address whose `execute()` method internally calls `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (these are invoked from the batch-signature/zk-proof style precompiles in `PrecompiledContracts.java`).
2. Craft the calldata so that the length word read at the relevant `offset` (i.e., `words[offset]`) is set to a very large value, e.g. `0x7fffffff`.
3. Broadcast a normal `TriggerSmartContract` transaction invoking this call with sufficient `feeLimit` to reach the vulnerable code before hitting an energy-based rejection.
4. Observe the executing node attempt `new byte[0x7fffffff][]`, exhausting the JVM heap and throwing `OutOfMemoryError`, which can crash or hang the node's transaction-processing thread.

Note: Due to indexing limits, the exact precompiled-contract `execute()` method(s) that invoke `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (i.e., which precompile address/opcode reaches them, and whether any additional length-vs-data-size check exists immediately after the allocation in those specific call sites) could not be fully traced in this session. A Devin session with full file access would be needed to confirm the exact reachable precompile address and rule out any pre-existing guard immediately following the allocation.
