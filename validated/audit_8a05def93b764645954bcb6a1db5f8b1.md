### Title
Unbounded `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` multiplication in `/v2/fees/transaction` handler can overflow/panic on attacker-supplied `u64::MAX` - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
The `/v2/fees/transaction` RPC endpoint accepts an attacker-controlled `estimated_len: Option<u64>` field with no upper bound check, and later multiplies it unchecked by `MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length`. A remote unauthenticated caller can supply `estimated_len: u64::MAX` to trigger this multiplication with no size cap enforced beforehand.

### Finding Description
In `try_parse_request` [1](#0-0) , `estimated_len` is computed as `std::cmp::max(body.estimated_len.unwrap_or(0), payload_data.len() as u64)`, meaning any `u64` value supplied by the client that is larger than the actual decoded payload length is used verbatim — there is no upper bound, no comparison against `MAX_PAYLOAD_LEN`, and no cap based on real transaction sizes. This value flows unchanged into `try_handle_request`, which forwards it to `estimate_tx_fee_from_cost_and_length` [2](#0-1) , where the fault line performs plain (unchecked) multiplication:

```
let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;
``` [3](#0-2) 

The only preceding validation is the HTTP body length check (`content_len > 0 && content_len < MAX_PAYLOAD_LEN`) and JSON content-type check [4](#0-3)  — these bound the size of the raw HTTP body/JSON text, not the numeric value of the `estimated_len` field itself, which is a JSON number and can be `u64::MAX` (`18446744073709551615`) regardless of body length. Nothing in the code path checks `body.estimated_len` against any ceiling before the `max()` call or before the multiplication.

Whether this manifests as a panic or silent wraparound depends on the build's `overflow-checks` setting (debug profile panics on overflow by default; release profile wraps silently unless `overflow-checks = true` is set in `Cargo.toml`). I was unable to confirm from the available files whether `overflow-checks` is explicitly enabled for release builds in this repo's `Cargo.toml`, so the panic-vs-wrap behavior in production builds is uncertain. In a debug/test build, the reachable arithmetic overflow will panic within the request handler thread; if it wraps in release, the resulting `minimum_fee` becomes a nonsensical small/garbage value that gets served as the canonical minimum fee floor in the JSON response.

### Impact Explanation
This endpoint is reached with no authentication requirement (no RPC secret, no peer key) since it's a documented public `/v2` RPC path handled through the standard HTTP RPC dispatch and `RPCRequestHandler` trait, reachable by any remote client that can open an RPC connection. If the build panics on overflow, a single crafted HTTP POST crashes the thread handling that request (and potentially the whole node process depending on panic-handling/unwind configuration) — matching the "remote crash/unauthenticated DoS from few messages" Critical category. If the build instead wraps, the endpoint silently returns a corrupted `minimum_fee`/`fee` value to any caller (e.g., a wallet), which is a correctness/non-canonical-data-served issue but less severe than a crash.

### Likelihood Explanation
No preconditions beyond network reachability to the node's RPC port are required — no secret, no valid session, no special peer status. Attacker cost is a single crafted JSON body: `{"estimated_len": 18446744073709551615, "transaction_payload": "<valid hex payload>"}`. The `transaction_payload` field must decode via `TransactionPayload::consensus_deserialize`, which is achievable with a minimal valid payload (attacker fully controls this). The attack is trivially repeatable per request.

### Recommendation
Bound `estimated_len` explicitly (e.g., clamp to `MAX_PAYLOAD_LEN` or another sane maximum transaction-size constant) in `try_parse_request` before storing it, and/or use `checked_mul`/`saturating_mul` in `estimate_tx_fee_from_cost_and_length` when computing `minimum_fee`, returning a `400 Bad Request` if the value is out of range instead of allowing unchecked arithmetic on attacker-supplied input.

3. Invokes `RPCPostFeeRateRequestHandler::try_parse_request` followed by `try_handle_request` (or the full request dispatch) with a configured fee estimator/cost estimator (`rpc_args.get_estimators_ref()` returning `Some`).
4. Asserts that the handler returns a bounded HTTP error response (e.g., 400) rather than panicking, by running the test under `overflow-checks = true` (debug profile) and observing whether `estimate_tx_fee_from_cost_and_length`'s line `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` panics with "attempt to multiply with overflow" at `stackslib/src/net/api/postfeerate.rs:112`.
