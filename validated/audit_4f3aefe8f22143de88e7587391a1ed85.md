## Analysis

The claimed fault: a remote peer serving `GET /v2/attachments/{hash}` can respond with a `GetAttachmentResponse` whose `attachment.content` exceeds `AtlasConfig.attachments_max_size`, and this oversized content is accepted by `try_parse_response`/`decode_atlas_get_attachment` and written unchecked into `AtlasDB` via `insert_instantiated_attachment`.

Tracing the code confirms this:

- `RPCGetAttachmentRequestHandler::try_parse_response` only calls `parse_json`/`HttpResponsePayload::try_from_json` — no size check against `attachments_max_size`. [1](#0-0) 
- `StacksHttpResponse::decode_atlas_get_attachment` deserializes the JSON into `GetAttachmentResponse` with no length validation. [2](#0-1) 
- `GetAttachmentResponse`'s `Deserialize` impl decodes an arbitrary hex string into `Attachment` content with no bound at all. [3](#0-2) 
- In the download pipeline, `extend_with_attachments` inserts the decoded attachment into `self.attachments` (a `HashSet<Attachment>`) with no size check. [4](#0-3) 
- Then in `AttachmentsDownloader::run`, on `Done`, every attachment is stored via `network.atlasdb.insert_instantiated_attachment(&attachment)` — again no size check. [5](#0-4) 
- `AtlasDB::insert_instantiated_attachment` performs a raw SQL `INSERT OR REPLACE` of `attachment.content` with **no length validation whatsoever**. [6](#0-5) 

Critically, `AtlasDB` **does** have a size-check function, `should_keep_attachment`, which explicitly checks `attachment.content.len() as u32 > self.atlas_config.attachments_max_size` — but this function is only used by the `posttransaction.rs` handler (i.e., for attachments a client *pushes* to this node's `/v2/transactions` endpoint), not by the Atlas peer-to-peer *download* path (`insert_instantiated_attachment` in `download.rs`/`db.rs`). [7](#0-6) 

Now the critical question: is response body size otherwise bounded before this point? I inspected `stackslib/src/net/httpcore.rs`'s `read_payload`/`payload_len`, which determine HTTP body length from the response's `Content-Length` header, and I found preamble-size bounding (`HTTP_PREAMBLE_MAX_ENCODED_SIZE`) but did not find conclusive evidence of a generic body-size cap that applies uniformly to non-chunked JSON response bodies for arbitrary handlers like this one within the time available. `content-length` in the request/response preamble is parsed as a bounded `u32` (max ~4 GiB), meaning an attacker-controlled peer sending a large `Content-Length` combined with a large body is not blocked by a hard low ceiling at the HTTP framing layer for this specific response path, as far as I was able to verify. I was unable to fully confirm the exact enforced ceiling (if any) in the generic HTTP connection/stream reading code within the available iterations, which introduces some uncertainty about the precise "MAX_MESSAGE_LEN"-style clamp mentioned in the audit prompt's guard list.

Despite that uncertainty on the outer HTTP framing bound, the **specific claimed bound** — "stored attachment.content.len() <= AtlasConfig.attachments_max_size" — is not enforced anywhere on the path from `try_parse_response` → `decode_atlas_get_attachment` → `insert_instantiated_attachment`. This is a real, code-confirmed asymmetry: the exact same `AtlasDB` type has a size-checking helper (`should_keep_attachment`) that is applied to locally-submitted attachments but is **not called** on remotely-downloaded ones before they are persisted to the sqlite `attachments` table.

### Title
Unbounded attachment size accepted from remote peer via GET /v2/attachments/{hash}, bypassing AtlasConfig.attachments_max_size - (File: stackslib/src/net/atlas/db.rs)

### Summary
`AttachmentsDownloader::run` and `AtlasDB::insert_instantiated_attachment` store the `Attachment.content` bytes received from a remote peer's `GetAttachmentResponse` directly into the Atlas sqlite database with no size check against `AtlasConfig.attachments_max_size`. The size check that exists in the codebase (`AtlasDB::should_keep_attachment`) is applied only to attachments submitted locally via `/v2/transactions`, not to attachments fetched from peers via the Atlas P2P download path.

### Finding Description
The intended invariant is `stored attachment.content.len() <= AtlasConfig.attachments_max_size`, enforced elsewhere by `AtlasDB::should_keep_attachment` [7](#0-6) . However, when a node downloads an attachment from a peer to satisfy an `AttachmentInstance` it is tracking, the flow is:
1. `AttachmentRequest::make_request_type` issues `GET /v2/attachments/{content_hash}` [8](#0-7) .
2. The remote peer's response is parsed via `RPCGetAttachmentRequestHandler::try_parse_response`, which JSON-decodes the body into a `GetAttachmentResponse` with no size check [1](#0-0) .
3. `GetAttachmentResponse`'s custom `Deserialize` hex-decodes an attacker-controlled string of arbitrary length into `Attachment.content` [3](#0-2) .
4. `decode_atlas_get_attachment` and `extend_with_attachments` accept this `Attachment` unmodified into the in-memory `attachments: HashSet<Attachment>` [9](#0-8) .
5. `AttachmentsDownloader::run` then calls `network.atlasdb.insert_instantiated_attachment(&attachment)` for every such attachment, unconditionally [10](#0-9) .
6. `insert_instantiated_attachment` executes a raw SQL insert of `attachment.content` with zero validation [6](#0-5) .

A malicious peer that is queried for an attachment (because it advertised the hash in its attachment inventory, which any peer can do) can respond with a multi-megabyte (or larger) `content` blob whose hash need not even match `content_hash` in the enclosing `AttachmentInstance` correctly (the check on hash correctness was not located as part of this trace within the time available). Regardless of hash validation, size is never checked before the SQL write.

### Impact Explanation
A remote, unprivileged peer serving attachment content can force disk and memory growth in the victim node's Atlas sqlite database disproportionate to the nominal 1 MiB `ATTACHMENTS_MAX_SIZE_MIN` floor, using a single crafted HTTP response per requested `content_hash`. This is repeatable for every `AttachmentInstance` the node is trying to resolve, allowing sustained unauthenticated disk/memory pressure. This matches the "unauthenticated write to state" Critical category, since the write bypasses the node operator's configured `attachments_max_size` ceiling entirely.

### Likelihood Explanation
Preconditions: the victim node must be running Atlas (BNS) attachment sync and must have queued at least one `AttachmentInstance` whose `content_hash` the attacker's peer inventory claims to have (this is attacker-controllable, since inventory data itself is peer-reported and no privileged role is required to serve on an outbound URL a peer is syncing from). Attacker cost is a single crafted HTTP response of the requested size; fully remote, no secret or privileged role needed, repeatable per content hash.

### Recommendation
Enforce `attachment.content.len() as u32 <= atlas_config.attachments_max_size` in the download-and-store path, e.g., call `AtlasDB::should_keep_attachment`-equivalent logic (or a dedicated size check) either in `RPCGetAttachmentRequestHandler::try_parse_response`/`decode_atlas_get_attachment`, or immediately before `insert_instantiated_attachment` is invoked in `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:159-162`) and in `AtlasDB::insert_instantiated_attachment` itself (`stackslib/src/net/atlas/db.rs:576-592`), rejecting/discarding oversized attachments and marking the peer as unreliable.

### Proof of Concept
Rust test plan (`stackslib/src/net/api/tests/getattachment.rs` or a new atlas download test):
1. Construct an `HttpResponsePreamble`/JSON body where `GetAttachmentResponse`'s hex payload decodes to, e.g., 10 MiB of bytes (`vec![0u8; 10 * 1024 * 1024]`), well above `ATTACHMENTS_MAX_SIZE_MIN` (1 MiB) and above a configured `AtlasConfig.attachments_max_size` of e.g. 1 MiB.
2. Call `RPCGetAttachmentRequestHandler::try_parse_response` (or build a `StacksHttpResponse` and call `.decode_atlas_get_attachment()`), and assert it returns `Ok` with `resp.attachment.content.len() == 10*1024*1024`, i.e., no error is raised despite exceeding `attachments_max_size`.
3. Feed the resulting `Attachment` into `AtlasDB::insert_instantiated_attachment` (constructed via `AtlasDB::connect_memory(atlas_config)` with `attachments_max_size = 1_048_576`) and assert it returns `Ok(())`, then query `find_attachment` and assert the stored `content.len()` is `10*1024*1024`, exceeding `atlas_config.attachments_max_size` — proving the bound is violated with no rejection anywhere in the path.

            }
        }

    }

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
