### Title
Denial of Service via Division-by-Zero in Resource Window-Size Calculation - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`)

### Summary
`ResourceProcessor.increaseV2()` and its sibling `unDelegateIncreaseV2()` compute a new bandwidth/energy "window size" by dividing an accumulated `BigInteger` numerator by a locally derived `newUsage` (or `newOwnerUsage`) value using `BigInteger.divide()` (via the `divideCeilExact` helper), without first checking that the divisor is non-zero. This mirrors the FreeRDP bug class: an attacker-influenced integer combination collapses a divisor to zero, and the raw division throws before any guard can catch it.

### Finding Description
`increaseV2()` is used by the hardened (`hardenCalculation()`) resource-accounting path for freeze-v2/delegation-based bandwidth and energy usage tracking: [1](#0-0) 

`newUsage` is derived from `getUsage(averageLastUsage, oldWindowSize, averageUsage, this.windowSize)`, an integer computation that truncates toward zero: [2](#0-1) 

The code only special-cases the situation where `remainUsage == 0` (an *early* usage snapshot), and returns before reaching the division: [3](#0-2) 

However, `newUsage`, the actual divisor used a few lines later, is a *different* quantity (combining old and new usage across two different window sizes) and is never checked for zero before being fed into `BigInteger.valueOf(newUsage)` as a division denominator: [4](#0-3) 

Because both `getUsage()` calls use truncating integer division (`usage * windowSize / precision`), it is possible for `remainUsage` (computed with `oldWindowSize`) to be non-zero while `newUsage` (computed with the current `windowSize` and different `usage`/`averageUsage` inputs) rounds down to exactly zero for small delegated amounts near the resolution boundary of `precision`. When that happens, `BigInteger.divide(BigInteger.ZERO)` throws an uncaught `ArithmeticException`.

The same unguarded pattern of dividing by a computed-but-unchecked value recurs in `unDelegateIncreaseV2` (`divideCeilExact(bi, BigInteger.valueOf(newOwnerUsage))`, guarded only for the `newOwnerUsage == 0` early branch) and in `getNewWindowSize`, which divides by `newUsage` with no zero-check at all: [5](#0-4) 

These accounting routines are invoked from bandwidth/energy consumption and delegation/un-delegation code paths (`increase`, `unDelegateIncrease`/`unDelegateIncreaseV2`) that execute during ordinary `DelegateResourceContract`/`UnDelegateResourceContract`/transfer transactions reachable by any unprivileged account — directly analogous to the FreeRDP report where an unprivileged client-supplied parameter combination (`nBlockAlign`, `nChannels`) zeroed a divisor (`bs`) feeding an unguarded modulo, crashing the server process.

### Impact Explanation
An `ArithmeticException: / by zero` thrown from these accounting helpers during block application (as part of processing a `DelegateResourceContract`/`UnDelegateResourceContract` transaction) is not caught by a dedicated handler at these call sites. If uncaught further up the stack in `Manager`'s transaction/block processing, it can abort processing of the block/transaction, degrading node availability and potentially causing consensus-relevant nodes to diverge or halt on transactions that reliably trigger the divide-by-zero — a Denial of Service impacting the whole node's ability to process transactions, matching the required "node crash or halt" criterion.

### Likelihood Explanation
Reaching this state requires crafting specific small `frozen`/`delegated` resource amounts so that integer truncation drives `newUsage` (or `newOwnerUsage`) to exactly zero while the other branch condition (`remainUsage == 0`) is not triggered first. This is a `hardenCalculation()`-gated path, so it depends on that feature flag being active in the target network; the underlying non-hardened arithmetic (plain `long` division, `getUsage`) has the same shape but does not throw on zero (integer `/` by zero on longs does throw too, actually — note `long / 0` also throws `ArithmeticException` in Java, so the non-hardened branch is equally exposed). This raises the likelihood since it does not require the harden flag specifically, but does require exact-timing/amount conditions that an attacker can iteratively construct off-chain before broadcasting the triggering transaction.

### Recommendation
Add explicit zero-guards immediately before every division in `ResourceProcessor` that uses a runtime-computed divisor (`newUsage`, `newOwnerUsage`, `windowSize`, `denominator` in `divideCeil`/`divideCeilExact`/`getNewWindowSize`), returning a safe default (e.g., 0 or the previous window size) when the divisor evaluates to zero, consistent with the existing `remainUsage == 0` guard pattern.

### Proof of Concept
Exact reproduction requires locating account resource state (`accountCapsule.getWindowSize`/`getWindowSizeV2`, prior usage) and a delegated-resource amount such that `getUsage(averageLastUsage, oldWindowSize, averageUsage, this.windowSize)` truncates to 0 while `remainUsage != 0`, then broadcasting a `DelegateResourceContract`/`UnDelegateResourceContract` transaction touching that account through `increaseV2`/`unDelegateIncreaseV2`. I was not able to fully confirm end-to-end whether an exception thrown here propagates uncaught all the way through `Manager` block processing (this would require tracing every caller of `ResourceProcessor.increase`/`unDelegateIncrease` and their exception handling in `TransactionTrace`/`Manager`, which I could not complete within the available investigation). This should be validated with a live/dynamic test (e.g., via a Devin session) crafting the precise resource amounts and confirming the resulting exception's propagation and effect on block processing.

  private long getNewWindowSize(long lastUsage, long lastWindowSize, long usage,
