### Title
Unstaked QUIC connections are keyed by attacker-controlled Pubkey instead of source IP in `SwQos::cache_new_connection`, allowing per-IP connection-limit evasion - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
`SwQos::cache_new_connection` builds the `ConnectionTable` key via `ConnectionTableKey::new(remote_addr.ip(), conn_context.remote_pubkey)` unconditionally for both staked and unstaked peers, rather than forcing `ConnectionTableKey::IP` for `ConnectionPeerType::Unstaked`. Because the QUIC client TLS certificate always carries a self-signed, freely-generatable pubkey regardless of stake, an attacker can present a distinct ephemeral pubkey per connection from a single source IP and have each connection keyed independently in `unstaked_connection_table`, bypassing the intended per-IP `max_connections_per_unstaked_peer` limit.

### Finding Description
`ConnectionTableKey::new` maps any `Some(pubkey)` to `ConnectionTableKey::Pubkey(pubkey)` and only falls back to `ConnectionTableKey::IP(ip)` when `maybe_pubkey` is `None`: [1](#0-0) 

`SwQos::cache_new_connection` calls this with `conn_context.remote_pubkey` for *every* peer type, without special-casing `ConnectionPeerType::Unstaked` to force IP-keying: [2](#0-1) 

`SwQos::try_add_connection` routes `ConnectionPeerType::Unstaked` connections into `prune_unstaked_connections_and_add_new_connection` → `cache_new_connection` against the shared `unstaked_connection_table`, using the same pubkey-based key derivation: [3](#0-2) 

Inside `ConnectionTable`, the `max_connections_per_peer` cap (here `max_connections_per_unstaked_peer`) is enforced **per key** in the `IndexMap<ConnectionTableKey, Vec<ConnectionEntry<S>>>`, not globally. This is explicitly demonstrated by the existing unit test showing that distinct pubkey keys let the table exceed `max_connections_per_peer` in aggregate (only global pruning via `total_size`/`max_unstaked_connections` bounds it): [4](#0-3) 

Since the client TLS certificate's pubkey is self-signed and unauthenticated by any stake requirement for unstaked traffic (that is precisely why `get_connection_stake` returns `None` → `ConnectionPeerType::Unstaked` for these peers), an attacker can generate a fresh ed25519 keypair/self-signed cert per QUIC connection at negligible cost while keeping the same source IP. Each such connection is keyed under a distinct `ConnectionTableKey::Pubkey`, so the attacker is capped only by `max_connections_per_unstaked_peer` *per fabricated identity*, and by `max_unstaked_connections` globally — not by any per-IP limit. This lets one IP acquire a disproportionate share (up to the entire global cap) of `unstaked_connection_table` slots, triggering `prune_unstaked_connection_table`'s `prune_oldest` eviction of legitimate unrelated unstaked peers' connections.

### Impact Explanation
This breaks the intended QoS invariant that unstaked (free, unauthenticated) traffic is rate-limited per source IP, since IP is the only real anti-sybil signal available for unstaked clients (pubkeys are free to mint). A single machine can now: (1) hog nearly all of `max_unstaked_connections` slots in the leader's TPU unstaked table, and (2) force eviction/DoS of other legitimate unstaked peers via `prune_oldest`, degrading connection availability for all unstaked participants of the network — this is a QoS/rate-limit evasion issue in the Agave bounty sense (unbounded resource capture via connection-table flooding).

### Likelihood Explanation
Fully reachable by an unprivileged remote attacker: no stake, no gossip/config access, and no crafted snapshots required — only opening many QUIC connections to the leader's public TPU/TPU-forward port, each with a freshly generated self-signed client certificate/keypair (trivial and cheap). The vulnerable call path (`setup_connection` → `SwQos::try_add_connection` → `prune_unstaked_connections_and_add_new_connection` → `cache_new_connection` → `ConnectionTable::try_add_connection(ConnectionTableKey::new(ip, remote_pubkey))`) is exercised on every incoming unstaked QUIC connection, making this fully repeatable.

### Recommendation
In `SwQos::cache_new_connection` (and anywhere else `ConnectionTableKey::new` is invoked for the unstaked path), force `ConnectionTableKey::IP(remote_addr.ip())` when `conn_context.peer_type()` is `ConnectionPeerType::Unstaked`, and only use `ConnectionTableKey::Pubkey` for `ConnectionPeerType::Staked` (where the pubkey has been validated against real stake in `staked_nodes`). This restores per-IP enforcement of `max_connections_per_unstaked_peer` for the only class of peer where pubkey identity is unauthenticated.

### Proof of Concept
```rust
// streamer/src/nonblocking/quic.rs (extend existing test module)
#[test]
fn test_unstaked_pubkey_keying_bypasses_per_ip_limit() {
    use std::net::Ipv4Addr;
    agave_logger::setup();
    let cancel = CancellationToken::new();
    let mut table = ConnectionTable::new(ConnectionTableType::Unstaked, cancel);
    let stats = Arc::new(StreamerStats::default());
    let max_connections_per_unstaked_peer = 10;
    let same_ip = IpAddr::V4(Ipv4Addr::new(1, 2, 3, 4));

    // Attacker opens 100 connections from ONE IP, each with a distinct
    // self-signed (fake, free) pubkey - simulating the vulnerable
    // ConnectionTableKey::new(ip, Some(fresh_pubkey)) call for unstaked peers.
    for i in 0..100u64 {
        let fake_pubkey = Pubkey::new_unique(); // free per-connection identity
        table
            .try_add_connection(
                ConnectionTableKey::new(same_ip, Some(fake_pubkey)),
                0,
                ClientConnectionTracker::new(stats.clone(), 1000).unwrap(),
                None,
                ConnectionPeerType::Unstaked,
                Arc::new(AtomicU64::new(i)),
                max_connections_per_unstaked_peer,
                || Arc::new(NullStreamerCounter {}),
            )
            .unwrap();
    }

    // BUG: total_size for this single IP grows unbounded (100), far exceeding
    // max_connections_per_unstaked_peer (10), because each connection is keyed
    // by a distinct Pubkey instead of the shared IP.
    assert_eq!(table.total_size, 100);

    // Expected (fixed) behavior: connections from one IP should be keyed by
    // ConnectionTableKey::IP regardless of claimed pubkey when peer_type is
    // Unstaked, capping total_size at max_connections_per_unstaked_peer.
}
```
This test currently passes with `total_size == 100`, proving the per-IP cap is not enforced when unstaked connections are keyed by attacker-supplied pubkeys; after the recommended fix (forcing `ConnectionTableKey::IP` for `Unstaked`), it should fail to add beyond `max_connections_per_unstaked_peer` entries for the same IP.
