### Title
Integer-underflow bounds check in ijar's ZIP parser allows out-of-bounds read from a crafted local-header offset - (File: `third_party/ijar/zip.cc`)

### Summary
Bazel's ijar tool parses ZIP/JAR files by trusting a central-directory-supplied `local_header_offset` (extendable to 64 bits via the Zip64 extra field) to compute a pointer into the memory-mapped input file, then validates remaining bytes using a subtraction that can underflow, defeating the bounds check and allowing the parser to read past the mapped file.

### Finding Description
`InputZipFile::ProcessNext` uses the (attacker-controlled) `offset` value returned by `ProcessCentralDirEntry` to directly compute the input cursor:

```cpp
p = zipdata_in_ + in_offset_ + offset;
if (EnsureRemaining(4, "signature") < 0) {
  return false;
}
``` [1](#0-0) 

`offset` is read straight from the central directory header as a raw 32-bit field, extendable to a full 64-bit value through the Zip64 extra field, with no validation that it is `<= in_length` before being added to the base pointer: [2](#0-1) 

The subsequent bounds check, `EnsureRemaining`, computes the "remaining bytes" using unsigned subtraction:
```cpp
int EnsureRemaining(size_t n, const char *state) {
  size_t in_offset = p - zipdata_in_;
  size_t remaining = input_file_->Length() - in_offset;
  if (n > remaining) {
    return error(...);
  }
  return 0;
}
``` [3](#0-2) 

If the crafted `offset` pushes `p` beyond `zipdata_in_ + input_file_->Length()`, `in_offset` exceeds `Length()`, and `remaining = Length() - in_offset` underflows (both are `size_t`), wrapping to a huge value. The `n > remaining` check therefore incorrectly succeeds, and `get_u4le(p)` and later field reads dereference memory outside the mapped file — analogous to the erofs bug where an unchecked cluster offset field is trusted and used to index into buffers/pages without validating it lies in the legal range, leading to an out-of-bounds read/crash.

This is the same bug class as CVE-2023-54132: a struct field taken from untrusted, attacker-supplied content is used to compute an address/offset for subsequent parsing without first validating that the field is within the legitimate range, and the "safety" check that exists is defeated by unsigned-integer wraparound rather than being absent outright.

### Impact Explanation
A maliciously crafted `.jar`/`.zip` file processed by ijar (e.g., a prebuilt jar fetched via `http_jar`/`http_file`/`java_import`, whose bytes are attacker-authored and whose sha256/integrity the attacker computes and publishes themselves) can trigger an out-of-bounds read of the memory-mapped file, causing a crash (denial of service for that build invocation) or, depending on memory layout, disclosure of adjacent process memory content into subsequent parsing/error paths. The sha256/integrity check on the download only guarantees byte-for-byte fidelity of the attacker's chosen content — it does nothing to stop a parser bug in the bytes that were legitimately downloaded.

### Likelihood Explanation
Reaching this code only requires that ijar process an attacker-supplied jar; this happens automatically whenever Bazel builds an interface jar from a `java_import`-style dependency or any jar produced from an external, attacker-influenced source. Crafting a central-directory entry with an out-of-range `local_header_offset` (optionally amplified through a Zip64 extra field to guarantee overflow past the file end) requires only a hex editor / small Python script — no privileged access is needed, matching the "unprivileged attacker publishes content a victim's build consumes" threat model.

### Recommendation
Validate `offset` (and the resulting `compressed_size`/`uncompressed_size`/`file_name_length`/`extra_field_length` fields extracted from the central directory and Zip64 extra field) against `input_file_->Length()` immediately after they are read, before they are used to derive pointers. In `EnsureRemaining`, guard against underflow explicitly, e.g., reject when `p < zipdata_in_ || (size_t)(p - zipdata_in_) > input_file_->Length()` prior to computing `remaining`, and treat any offset/size field that would place `p` outside `[zipdata_in_, zipdata_in_ + Length())` as a hard parse error rather than relying on a post-hoc subtraction that can wrap.

### Proof of Concept
Construct a ZIP/JAR whose single central directory entry has:
- `local_header_offset` field set to `0xFFFFFFFF` (triggering Zip64 extension) and a Zip64 extra field with `attr64(2)` (the offset attribute) set to a value larger than the file's total length (e.g., `file_length + 0x1000`).
- A valid central directory / EOCD so `FindZipCentralDirectory` succeeds.

Feed this file to `InputZipFile::Open()` → `ProcessNext()`. The computed `p = zipdata_in_ + in_offset_ + offset` will point past the mapped region; `EnsureRemaining(4, "signature")` will underflow `remaining` and pass, and `get_u4le(p)` will read out-of-bounds memory, which can be observed as a crash (SIGSEGV) under a memory-safety tool (ASan) or via a JUnit/integration test that runs `ijar` (or `singlejar`, which follows a similar pattern in `src/tools/singlejar`) on such a crafted jar and asserts the process does not crash and instead reports a clean parse error.
