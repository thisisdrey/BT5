### Title
Downloaded `Attachment` content is never verified against the requested `AttachmentRequest.content_hash` before being stored and resolved - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts whatever `Attachment` a peer returns for a `/v2/attachments/:hash` request into `self.attachments` without ever checking that the returned `attachment.hash()` equals the `content_hash` of the `AttachmentRequest` that was sent. In `AttachmentsDownloader::run`'s `Done` branch, the hash used for `find_all_attachment_instances` and `resolve_attachment` is recomputed from the attacker-controlled bytes (`attachment.hash()`), not the originally requested `content_hash`. A malicious source peer for a request can thus answer with unrelated (but internally hash-consistent) attachment bytes.

### Finding Description
`AttachmentRequest` carries the specific `content_hash` `H` that is being requested via the URL `/v2/attachments/{content_hash}` [1](#0-0) . When the batched HTTP request completes, `extend_with_attachments` decodes the JSON response and unconditionally inserts the returned `Attachment` into `self.attachments`, with no comparison against `request.content_hash`: [2](#0-1) 

`decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) only performs JSON parsing of `GetAttachmentResponse { attachment }` — no hash equality check is done there either [3](#0-2) . The server-side handler (`RPCGetAttachmentRequestHandler::try_handle_request`) looks up `attachment_hash` from the URL path in its own DB and returns whatever `Attachment` row it finds for that hash [4](#0-3) , so a malicious node fully controls what URL path (`content_hash`) it registers into its own atlas DB ahead of time, and can therefore be selected as a source for request `H`, yet respond with an `Attachment` whose bytes hash to some other value `Y != H` (e.g. by returning a stale/garbage local row, or a locally crafted DB entry it created for its own reasons) — nothing on the client side enforces `attachment.hash() == H`.

Finally, in `AttachmentsDownloader::run`, the `Done` branch computes and uses `attachment.hash()` (i.e., `hash(Y)`, not `H`) to look up matching `AttachmentInstance` rows and to mark resolution: [5](#0-4) 

Because `resolve_attachment` is called with `attachment.hash()` rather than the tracked `content_hash` `H` of the request that was actually satisfied, the specific `AttachmentInstance` awaiting `H` is never marked resolved by this response (it will be endlessly retried/never resolved from this peer's perspective), while `insert_instantiated_attachment` stores the peer-supplied bytes under `hash(Y)` regardless of whether any `AttachmentInstance.content_hash` equals `Y`. `find_all_attachment_instances` only returns rows literally matching `Y` [6](#0-5) , which is a mechanical hash lookup and cannot be spoofed to "pair" with `H`'s instance unless `Y == H`'s stored value already exists as an unresolved instance for a *different* attachment slot — meaning the practical effect is not a hash-collision forgery (that would require breaking Hash160), but a request/response mismatch: the requested slot `H` silently fails to resolve, and unrelated valid attachment content for hash `Y` can be inserted/orphaned without ever having been legitimately requested for that hash in this batch.

### Impact Explanation
A malicious peer chosen as a download source for `AttachmentRequest{content_hash: H}` can return arbitrary attachment content whose hash `Y != H`. Effects:
- The `AttachmentsBatch` entry for `H` is never resolved by this exchange (the wrong hash is passed to `resolve_attachment`), causing repeated retries/backoff for that legitimate BNS attachment slot — a bounded, low-severity availability degradation for a specific name's attachment resolution, not a crash or unauthenticated write of forged canonical state.
- `insert_instantiated_attachment` stores content under `Y` even when no instance requested `Y` in this batch, growing `attachments` table with content not tied to any pending instance (orphan storage), though this is bounded by whatever content the attacker legitimately possesses (not arbitrary/attacker-chosen bytes matching an already-existing target hash, since Hash160 preimage/collision resistance still holds — the attacker cannot pick `Y` to equal an existing instance's `content_hash` unless they already know a preimage for it, which for legitimately-known content is not a security violation).

This does not achieve the "High" impact described in the question (serving forged data as canonical BNS data) because the actual pairing performed by `find_all_attachment_instances`/`resolve_attachment` is still keyed by a genuine hash match — the attacker cannot forge content matching an arbitrary target hash without breaking Hash160. The realistic impact is a peer-triggerable resolution stall for specific attachments and minor orphan-row storage growth, not attachment/BNS data corruption or mismatch serving.

### Likelihood Explanation
Trivial to trigger: any peer configured as an outbound sync peer that is selected as a source for a given `AttachmentRequest` can supply this response with zero cost, and it is fully repeatable per request/session. No privileged role, secret, or signature check is bypassed because none exists on this specific equality (request hash vs. response hash) to begin with.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), after decoding `response.attachment`, explicitly verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; treat a mismatch as a failed/faulty response (bump failed-request counters / mark peer unreliable) rather than silently accepting it. This restores the intended invariant that only content matching the requested hash is stored and used to resolve that specific `AttachmentInstance`.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs`:
1. Construct an `AttachmentRequest` with `content_hash = H` (e.g., hash of `b"expected"`).
2. Build a `BatchedRequestsResult<AttachmentRequest>` where `succeeded` maps this request to a `StacksHttpResponse` whose JSON body is `GetAttachmentResponse { attachment: Attachment::new(b"unexpected".to_vec()) }` (so `attachment.hash() = Y != H`).
3. Call `AttachmentsBatchStateContext::extend_with_attachments` with this result.
4. Assert that `context.attachments` contains the `Y`-hashed attachment despite it not matching `H` — demonstrating no `H == attachment.hash()` check exists — and that a subsequent simulated `run()`-style call to `context.attachments_batch.resolve_attachment(&attachment.hash())` resolves nothing under `H`, leaving `H`'s `AttachmentInstance` perpetually unresolved by this exchange.

    ) -> AttachmentsBatchStateContext {

            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }

impl StacksHttpResponse {
    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
            .map_err(|_e| NetError::DeserializeError("Failed to load from JSON".to_string()))?;
        Ok(resp)
    }
