### Title
Unbounded prefix-truncation loop over attacker-controlled `tx_replay_set` causes bounded compute DoS - (File: libsigner/src/v0/signer_state.rs)

### Summary
`GlobalStateEvaluator::find_majority_prefix_replay_set` performs a truncation loop that, for every one of up to ~L elements in the largest submitted `tx_replay_set`, rescans the entire `tx_replay_sets` HashMap and calls `Vec::starts_with` (an O(L) comparison of `StacksTransaction` values) against every candidate. A single legitimately-slotted signer can submit a `StateMachineUpdate` whose `tx_replay_set` contains as many `StacksTransaction` entries as fit under the 2MB `STATE_MACHINE_UPDATE_MAX_SIZE` cap, driving this function toward O(N·L²) work with no additional cap enforced in `signer_state.rs` itself.

### Finding Description
`find_majority_prefix_replay_set` (libsigner/src/v0/signer_state.rs lines 196-275) is reached from `GlobalStateEvaluator::determine_global_state` [1](#0-0)  whenever no exact `tx_replay_set` agreement exists among signers, which is a normal, attacker-inducible condition (other signers simply submit different or empty sets).

Once no exact match is found, the code:
1. Sorts all distinct replay sets, then picks the largest as the initial `candidate_prefix` [2](#0-1) .
2. Enters a `while !candidate_prefix.is_empty()` loop that pops one element per iteration and, on every iteration, rescans the *entire* `tx_replay_sets` map calling `replay_set.0.starts_with(&candidate_prefix)` [3](#0-2) .

The only externally enforced bound on the size of a single `tx_replay_set` is the overall StackerDB chunk/message size cap `STATE_MACHINE_UPDATE_MAX_SIZE = 2 * 1024 * 1024` bytes [4](#0-3) . There is no additional cap in `signer_state.rs` on the number of `StacksTransaction` entries inside a `ReplayTransactionSet`, nor on the number of pop/rescan iterations performed. `ReplayTransactionSet` is a plain wrapper around `Vec<StacksTransaction>` [5](#0-4)  with no length validation applied before it reaches `find_majority_prefix_replay_set`.

An attacker who legitimately owns one signer's StackerDB slot can craft a `StateMachineUpdate` whose `tx_replay_set` is populated with the maximum number of distinct (or near-distinct, differing only near the end) `StacksTransaction` values that fit in 2MB — potentially thousands of entries for small transactions. Once accepted via `insert_update` (which only checks that the address is a known signer, not the content size) [6](#0-5) , every subsequent call to `determine_global_state`/`get_global_tx_replay_set` re-executes the O(N·L²)-scale truncation loop against this oversized candidate, since other signers' shorter/empty sets keep failing to reach majority quickly.

### Impact Explanation
Every node evaluating global signer state (any node/signer that ingests this StackerDB slot's updates) repeatedly performs a large amount of CPU work per state re-evaluation, which is triggered on ordinary signer-update processing. This matches the "bounded compute DoS on a read/evaluation path" category — bounded because the total input size is capped by the 2MB message limit, but the quadratic-ish blow-up (large L combined with N rescans and O(L) `starts_with`/`StacksTransaction` equality comparisons per rescan) still produces a disproportionate CPU cost relative to a legitimate, small-N/small-L input, and this cost is paid repeatedly (once per re-evaluation) for as long as the malicious update remains the largest set with no majority.

### Likelihood Explanation
Precondition: attacker must hold one legitimate signer slot for the active reward cycle — a moderate but achievable bar since it's a normal, permitted signer role, not a privileged/admin capability. No secrets, no other peer's key, and no exact majority collusion are required; the attack works simply by other signers naturally disagreeing (common in transient states). Attacker cost is a single StackerDB chunk write within the existing 2MB size limit, and the effect is repeatable on every re-evaluation cycle as long as the oversized update remains posted.

### Recommendation
Enforce an explicit maximum number of transactions (and/or maximum candidate-prefix length) allowed inside a single `ReplayTransactionSet`/`tx_replay_set` independent of the raw byte-size cap, rejecting or truncating updates that exceed it before they are inserted via `insert_update`. Additionally, consider replacing the linear rescan-per-pop truncation strategy with an approach that computes common-prefix lengths across all sets in a single pass (e.g., a trie or incremental agreement count) so the algorithm scales linearly in total input size rather than quadratically.

### Proof of Concept
Rust unit test in `libsigner/src/v0/signer_state.rs` test module:
1. Construct several `StacksAddress`/weight pairs (`address_weights`) simulating ~100 signers.
2. Build one `StateMachineUpdate` for the attacker-controlled address with a `tx_replay_set` containing N large, distinct `StacksTransaction`s (as many as fit under `STATE_MACHINE_UPDATE_MAX_SIZE`, e.g., several thousand minimal transactions).
3. Build the remaining signer updates with empty or short, differing `tx_replay_set`s so no exact agreement is reached at lines 205-209.
4. Call `GlobalStateEvaluator::determine_global_state()` (which reaches `find_majority_prefix_replay_set`) and measure wall-clock time.
5. Compare against a baseline run with small, similarly-sized-but-short replay sets, asserting that time grows superlinearly with N, demonstrating the missing bound on `candidate_prefix` length/iteration count referenced at lines 254-264.
