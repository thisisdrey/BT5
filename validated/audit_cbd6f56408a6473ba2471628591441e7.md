### Title
Unprivileged dust-transfer griefing fills an account's `MAX_TOKENS_PER_USER` list, bricking deposits, withdrawals and liquidations that route through `feeCollector` - (File: contracts/Pool.sol)

### Summary
`Pool` tracks per-account holdings in `depositTokensOfAccount` / `debtTokensOfAccount` and enforces a hard cap of `MAX_TOKENS_PER_USER = 30` inside `onlyIfAdditionWillNotReachMaxTokens` (contracts/Pool.sol:79, 143-148). `DepositToken._transfer` and `DepositToken._mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero (contracts/DepositToken.sol:486-488, 518-520). Because `DepositToken.transfer/transferFrom` are permissionless, any EOA can push dust of every deposit token in a pool into a chosen account — most importantly the pool's `feeCollector` — until its list hits the cap. Once `feeCollector`'s list is full, every protocol operation that tries to mint or transfer a fee in a deposit token the `feeCollector` does not already hold reverts with `UserReachedMaxTokens`, causing a protocol-wide temporary denial of service analogous to the authenticated-DoS class of CVE-2018-2769, but reachable by an unprivileged attacker.

### Finding Description
The cap check lives in `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`, both guarded by `onlyIfAdditionWillNotReachMaxTokens` (contracts/Pool.sol:204-220). Three public flows force a new entry into `feeCollector`'s list:

- `DepositToken.deposit` → `_mint(_pool.feeCollector(), _fee)` at contracts/DepositToken.sol:231 (requires `depositFee > 0` in `FeeProvider`).
- `DepositToken.withdraw` → `_withdraw` → `_transfer(account_, _pool.feeCollector(), _fee)` at contracts/DepositToken.sol:547 (requires `withdrawFee > 0`).
- `Pool.liquidate` → `depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee)` at contracts/Pool.sol:591-593 (requires `protocolFee > 0` from `feeProvider.liquidationFees()`).

`_mint`/`_transfer` add the recipient to `depositTokensOfAccount` only when `_balanceBefore == 0` (DepositToken.sol:486, 518), so the attack sequence is:

1. Attacker deposits a minimal amount of each of the pool's collateral types to obtain dust `msdTOKEN` balances (or uses flash-obtained underlying via `NativeTokenGateway`/`VesperGateway`).
2. Attacker calls `DepositToken.transfer(feeCollector, 1 wei)` for each distinct deposit token the `feeCollector` doesn't yet hold, until `depositTokensOfAccount.length(feeCollector) + debtTokensOfAccount.length(feeCollector) == 30`.
3. From then on, any `deposit`, `withdraw`, or `liquidate` whose fee is denominated in a deposit token absent from `feeCollector`'s list reverts inside `addToDepositTokensOfAccount` → `UserReachedMaxTokens`, reverting the entire transaction.

No modifier stops this: `transfer` only checks `_revertIfLocked` on the *sender's* balance (DepositToken.sol:348-354), and the cap is applied to the recipient with no opt-out. The same primitive can grief individual users (blocking them from receiving new collateral types via `deposit(onBehalfOf_)` or transfers), but the `feeCollector` variant is the strongest since it halts core pool functions for everyone.

### Impact Explanation
While the attack persists, for every deposit token missing from `feeCollector`'s list: user collateral withdrawals revert (temporary freezing of user funds, since `withdraw` burns and sends the fee in one transaction), new deposits revert, and — most critically — `Pool.liquidate` reverts whenever `protocolFee > 0`, preventing liquidation of unhealthy positions and allowing bad debt to accrue against the protocol (solvency/liveness invariant break). The DoS is temporary rather than permanent: the governor can `sweep` the `feeCollector`'s deposit token balances to zero to free list slots, or fees can be set to zero. However, an attacker can cheaply re-fill freed slots and there is no self-serve recovery path, so the freeze lasts until privileged intervention.

### Likelihood Explanation
Reachable by any unprivileged EOA at a cost of dust amounts of each collateral plus gas; `transfer` requires only an unlocked sender balance. The main precondition is numeric: filling the list requires at least 30 distinct deposit token types in the pool (debt token entries cannot be pushed to a third party — they are only added on `DebtToken` mints to the issuer's own account), and at least one fee parameter (`depositFee`, `withdrawFee`, or `protocolFee`) must be non-zero for the revert path to trigger. Whether any deployed pool lists ≥30 collaterals could not be fully confirmed from the index; if pools have fewer deposit tokens, the residual impact is per-user griefing that blocks *receipt of new token types* (not withdrawal of existing funds), which is materially weaker. The feeCollector variant should be validated against deployed `getDepositTokens()` lengths.

### Recommendation
Do not apply `MAX_TOKENS_PER_USER` accounting to `feeCollector` (or protocol-owned addresses generally), or make `addToDepositTokensOfAccount` failure non-fatal for fee minting — e.g., accrue fees to `Treasury`/a dedicated accounting variable instead of minting deposit tokens to a list-capped account. Alternatively, gate `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` on a per-account opt-out, or exempt the recipient-side addition when the recipient is `feeCollector` since it never opens debt positions.

### Proof of Concept
Hardhat (TypeScript) outline:

```ts
// setup: pool with >= 30 DepositTokens DT[0..29], depositFee = e.g. 0.25e16, withdrawFee > 0
const feeCollector = await poolRegistry.feeCollector();

// 1. attacker acquires dust of each deposit token
for (const dt of depositTokens) {
  await underlying(dt).approve(dt.address, MIN);
  await dt.deposit(MIN, attacker.address);          // mints dust msdTOKEN to attacker
}

// 2. fill feeCollector's list to MAX_TOKENS_PER_USER
for (const dt of depositTokens.slice(0, 30)) {
  await dt.transfer(feeCollector, 1);               // addToDepositTokensOfAccount(feeCollector)
}
expect(await pool.getDepositTokensOfAccount(feeCollector)).to.have.length(30);

// 3a. deposit in a collateral type feeCollector doesn't hold reverts
await expect(otherDepositToken.deposit(amount, alice.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3b. withdraw reverts -> user funds temporarily frozen
await expect(otherDepositToken.connect(bob).withdraw(bobBal, bob.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3c. liquidation reverts when protocolFee > 0
await expect(pool.liquidate(msSynthetic, victim.address, repayAmt, otherDepositToken.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Key assertions: step 2 succeeds because `DepositToken.transfer` (contracts/DepositToken.sol:348) only checks the sender's unlocked balance; steps 3a–3c revert inside `Pool.addToDepositTokensOfAccount` (contracts/Pool.sol:216) reached from `_mint`/`_transfer`/`seize` (DepositToken.sol:231, 487, 519; Pool.sol:592).
