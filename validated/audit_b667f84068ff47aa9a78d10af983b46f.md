### Title
Attacker can permanently DoS liquidations and fee-bearing withdrawals by filling the feeCollector's token list to `MAX_TOKENS_PER_USER` - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the Squads "stuck state" invariant bug (`remove_member` succeeding only because the `keys.len()==0` state was assumed unreachable), Metronome assumes the per-account token list invariant (`debt + deposit tokens < 30`) can never be forced on an account that does not cooperate. Because `DepositToken.deposit(amount_, onBehalfOf_)` and `DepositToken.transfer` let any EOA push a new deposit-token entry onto an arbitrary account's `depositTokensOfAccount` list, an attacker can fill the `feeCollector`'s list to `MAX_TOKENS_PER_USER = 30`. Every `Pool.liquidate` call that collects a non-zero `protocolLiquidationFee`, and every `DepositToken.withdraw` with a non-zero `withdrawFee`, then permanently reverts inside `addToDepositTokensOfAccount`.

### Finding Description
`Pool.addToDepositTokensOfAccount` reverts when the recipient already has 30 tokens:

```solidity
// contracts/Pool.sol:143-148
modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}
```

Any deposit-token receipt (mint via `deposit(..., onBehalfOf_)`, `transfer`, `seize`) registers the token when `balanceBefore == 0`:

```solidity
// contracts/DepositToken.sol:517-520
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

`Pool.liquidate` seizes the protocol fee to `feeCollector`:

```solidity
// contracts/Pool.sol:591-593
if (_fee > 0) {
    depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee);
}
```

and `DepositToken._withdraw` transfers the withdraw fee the same way (`DepositToken.sol:546-548`). If the `feeCollector`'s list is full and it does not already hold that deposit token, the inner `seize`/`_transfer` reverts with `UserReachedMaxTokens`, reverting the whole liquidation or withdrawal.

Unlike the `Ms` invariant in the report, there is no recovery: `feeCollector` is a contract that has no mechanism to transfer dust msdTokens out of its list, and `removeFromDepositTokensOfAccount` can only be triggered by the token itself when the balance reaches zero — which requires a transfer the feeCollector cannot initiate.

### Impact Explanation
- All liquidations through `Pool.liquidate` revert permanently whenever `protocolLiquidationFee > 0` (or whenever the seized deposit token is new to the feeCollector), freezing the protocol's only bad-debt remediation path and leading to protocol insolvency as positions go underwater.
- All `withdraw`/`withdrawFrom` calls on deposit tokens with a non-zero `withdrawFee` revert, permanently freezing user collateral for every user who does not already... (reverts for all users, since the fee transfer to `feeCollector` fails regardless of the withdrawer's own list).

### Likelihood Explanation
Feasibility depends on the deployed pool having enough registered collateral types for the attacker's deposits to push `feeCollector` to 30 combined entries (debt tokens cannot be transferred, so only deposit-token entries are attacker-controllable). The attacker needs at most ~30 dust deposits (`deposit(1 wei, feeCollector)` per token) plus balance-growth transfers for tokens the feeCollector already holds. The cost is negligible. Note: if the deployed configuration registers fewer than ~30 deposit tokens, the list cannot be filled and this vector is unreachable — this must be checked against the live `getDepositTokens()` count. Once filled, the attack cannot be undone without an upgrade.

### Recommendation
- Do not revert inside `addToDepositTokensOfAccount` for protocol-internal recipients; bypass the per-account list cap for `feeCollector` (e.g., check `if (account_ == feeCollector) skip tracking` or track the feeCollector in a separate structure).
- Alternatively, allow listing beyond the cap to succeed silently (return early instead of revert) so that receipt of a 31st token does not DoS the transaction — the list is only an accounting convenience for `debtPositionOf`/`depositOf` iteration.
- Give `feeCollector` a `sweep`/`rescue` function able to call `transfer` on msdTokens, allowing list entries to be shed.

### Proof of Concept
```solidity
// Foundry fork test (pool with >= 30 registered DepositTokens, protocolLiquidationFee > 0)
function test_liquidationDoS_viaFeeCollectorTokenList() public {
    IPool pool = IPool(POOL);
    address feeCollector = pool.poolRegistry().feeCollector();

    // 1. Attacker fills feeCollector's deposit token list to MAX_TOKENS_PER_USER
    address[] memory dtokens = pool.getDepositTokens();
    for (uint i; i < dtokens.length && pool.getDepositTokensOfAccount(feeCollector).length < 30; ++i) {
        DepositToken dt = DepositToken(dtokens[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1e6);
        vm.startPrank(attacker);
        underlying.approve(address(dt), 1e6);
        dt.deposit(1e6, feeCollector); // registers token on feeCollector
        vm.stopPrank();
    }
    assertEq(pool.debtTokensOfAccount.length(feeCollector)
           + pool.depositTokensOfAccount.length(feeCollector), 30);

    // 2. Any liquidation that charges a protocol fee now reverts
    vm.prank(liquidator);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    pool.liquidate(msEth, victim, amountToRepay, msdMET);

    // 3. Any withdraw with withdrawFee > 0 also reverts (fee transfer to feeCollector fails)
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    msdMET.withdraw(1e18, victim);
}
```

Uncertainty: the PoC requires the deployed pool to have enough registered deposit tokens to reach the 30-entry cap for `feeCollector` (debt tokens are non-transferable). If the live pool registers fewer collateral types than needed, the attack is not reachable on that deployment and this finding should be downgraded to a latent design flaw.
