### Title
Unbounded, unfallbacked external call to the stSTX admin-controlled ratio contract freezes price resolution for all stSTX-based assets - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar`'s oracle callcode transformation for stSTX makes a hard, non-fallback external call to a RESTRICTED third-party contract (`block-info-nakamoto-ststx-ratio-v2`) that it does not own. Any normal admin action on that external contract (upgrade/migration, pause, or removal of `get-ststx-ratio-v3`) that causes the call to fail, revert, or return a degenerate value permanently blocks price resolution — and therefore blocks collateral operations, borrowing, and health checks — for every stSTX-derived asset (stSTX, zstSTX, zstSTXbtc), freezing user funds tied to those positions. This mirrors the Convex `BaseRewardPool` pattern where an external, restricted admin's routine action (adding reward tokens) forces a downstream call (`claimRewards`) to always fail, permanently blocking `pullFromLocker`. [1](#0-0) 

### Finding Description
`call-ststx-ratio` performs a direct `contract-call?` into an external, RESTRICTED-admin-owned contract with no error handling, no fallback price source, and no bound/sanity check on the returned ratio: [2](#0-1) 

This function is consumed unconditionally by `resolve-ststx`, which itself `unwrap!`s the result into `ERR-ORACLE-CALLCODE` on any failure: [3](#0-2) 

`resolve-ststx` is the single price-transformation path for three registered assets: the raw `stSTX` asset (`CALLCODE-STSTX`), the `zstSTX` vault token (`CALLCODE-ZSTSTX`, which chains `resolve-ststx` before applying the liquidity index), and any other consumer of the staking ratio: [4](#0-3) 

`price-resolve` (the function driving all market-side price lookups used for collateral validation, egroup/LTV checks, and liquidation notional calculations) calls `resolve-callcode`, and any `try!`/`unwrap!` failure inside that chain aborts the entire transaction with `ERR-ORACLE-CALLCODE` or a runtime panic: [5](#0-4) 

Because `market.clar` has no circuit breaker, cached fallback, or DAO-settable override for the stSTX ratio source, if the external contract's operator (per the audit convention this counterparty is RESTRICTED, not TRUSTED) performs an ordinary administrative action — deploying a new ratio contract version and deprecating/pausing the old `get-ststx-ratio-v3` function, or the function beginning to revert under some internal condition of that external protocol — every call into `call-ststx-ratio` reverts. This makes `price-resolve` for stSTX/zstSTX (and derivatively zstSTXbtc paths that reuse the same STX/stSTX price) permanently fail.

### Impact Explanation
Since collateral additions, borrow validation, and liquidation notional evaluation all route through `get-egroup`/`get-notional-evaluation`, which in turn require `price-resolve` for every asset in a user's position mask, a user holding stSTX, zstSTX, or zstSTXbtc as collateral or debt cannot:
- Add or remove collateral (health-check path requires price for all masked assets),
- Borrow against or repay debt requiring a post-operation health check,
- Be liquidated (liquidators also need the price to compute notional/penalty).

This is a **temporary freezing of funds** (High) for any account holding these three assets, and could escalate to insolvency risk if bad debt cannot be liquidated while the price feed is broken — landing squarely on the "market entry points and health checks" / "oracle resolution and callcode transforms" areas explicitly in scope.

### Likelihood Explanation
Likelihood is low-to-medium, matching the judged severity of the referenced Convex issue (accepted as Medium with duplicates due to "extremely low likelihood" but real, restricted-admin-triggerable harm). The stSTX ratio provider is external and out of Zest's control; any legitimate reason for that provider to redeploy, deprecate, or temporarily disable `get-ststx-ratio-v3` (version migrations are common in Stacks liquid-staking protocols) triggers this permanently until Zest's DAO ships a patched oracle path.

### Recommendation
- Wrap `call-ststx-ratio` in a fallback: on failure, fall back to a DAO-settable cached/last-known-good ratio (with staleness bounds), rather than reverting the entire price resolution.
- Add sanity bounds (min/max) on the returned ratio value before using it, so a degenerate or manipulated value (e.g., 0 or absurdly large) is rejected without permanently bricking the callcode path.
- Provide a DAO-governed emergency override/circuit-breaker for the stSTX ratio source, analogous to the existing `max-confidence-ratio`/pause mechanisms already present for Pyth confidence and liquidation pausing.

### Proof of Concept
1. External stSTX protocol operator (RESTRICTED per audit convention) deploys `block-info-nakamoto-ststx-ratio-v2` v2 (or newer) and deprecates/removes `get-ststx-ratio-v3` on the old contract address hardcoded in `call-ststx-ratio`, or that entry point begins reverting due to an internal state change (pause, migration, admin key action).
2. Any user calls `collateral-add`/`borrow`/`liquidate` involving stSTX, zstSTX, or zstSTXbtc.
3. `price-resolve` → `resolve-callcode` → `resolve-ststx` → `call-ststx-ratio` reverts (contract-call target function no longer callable/behaves unexpectedly).
4. The transaction reverts with `ERR-ORACLE-CALLCODE`/panic for every operation touching these assets, for as long as the external ratio contract remains broken — freezing the affected users' positions. [2](#0-1) [6](#0-5) [5](#0-4)
