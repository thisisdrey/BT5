### Title
Integer-overflow bypass of the Exchange balance-limit safeguard when `AllowHardenExchangeCalculation` is disabled - (File: actuator/src/main/java/org/tron/core/actuator/AbstractExchangeActuator.java)

### Summary
`ExchangeTransactionActuator` and `ExchangeWithdrawActuator` (java-tron's on-chain DEX/Exchange actuators, reachable by any unprivileged order placer) rely on `addExact`/`subtractExact` helpers defined in `AbstractExchangeActuator` to protect balance arithmetic from overflow. These helpers only perform overflow-checked math when the committee-gated flag `allowHardenExchangeCalculation` is enabled; otherwise they silently fall back to raw, unchecked `long` `+`/`-` operators. This mirrors the report's root cause pattern — a safeguard (here, overflow-safe arithmetic protecting an explicit `ExchangeBalanceLimit` guardrail) exists in the codebase but is not uniformly enforced on the path an ordinary user can reach, allowing the guardrail to be silently defeated.

### Finding Description
`AbstractExchangeActuator` defines: [1](#0-0) 

`allowHarden()` reflects the dynamic property `allowHardenExchangeCalculation`, and `addExact`/`subtractExact` conditionally use `StrictMathWrapper` (checked) math only when that flag is on; otherwise plain, unchecked `long` arithmetic is used, which silently wraps on overflow instead of throwing.

`ExchangeTransactionActuator.doValidate()` uses this same conditional `addExact` to enforce the exchange pool's guardrail (`ExchangeBalanceLimit`): [2](#0-1) 

If `allowHardenExchangeCalculation` is not enabled (the default state before the committee opts in), `tokenBalance = addExact(tokenBalance, tokenQuant)` performs unchecked addition. An unprivileged order placer can submit an `ExchangeTransactionContract` with a `quant` large enough (close to `Long.MAX_VALUE - tokenBalance`) to overflow this sum, wrapping it into a small or negative value that trivially passes the `tokenBalance > balanceLimit` check — completely defeating the guardrail that is supposed to bound how much can be traded into an exchange pool in a single transaction.

The same conditional, unsafe arithmetic is then used in `execute()` when actually mutating account and exchange-pool balances: [3](#0-2) 
and in `ExchangeCapsule.transaction()`, where the non-hardened path also uses unchecked `+`/`-` for updating pool reserves: [4](#0-3) 

Only the hardened path (`hardenedCalc == true`) uses `StrictMathWrapper.addExact/subtractExact` and explicitly rejects negative resulting balances: [5](#0-4) 

This confirms the safety mechanism (checked math + non-negative balance invariant) is a real fix that the project added for exactly this class of bug, but it is only active when the `allowHardenExchangeCalculation` committee proposal is turned on — the actuators still expose the legacy unchecked-arithmetic path by default, exactly analogous to the external report's pattern where a safeguard mechanism exists but a specific reachable path (there: `ArbitraryCallsProposal` + `AddPartyCardsAuthority`; here: `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` while hardened mode is off) is not covered by it.

### Impact Explanation
An attacker who can place exchange orders (any account with a small TRX/asset balance for fees) can craft a `quant` value that overflows the `addExact` guardrail check in `doValidate()`, bypassing the intended `ExchangeBalanceLimit`, and then cause `ExchangeCapsule.transaction()`/actuator `execute()` to wrap pool and account balances using unchecked arithmetic. This can corrupt the Exchange's `firstTokenBalance`/`secondTokenBalance` accounting (an on-chain AMM-like pool holding real TRX/TRC10 reserves), producing balances that no longer match actual backing reserves — an unbacked-balance condition that can be leveraged to drain the pool of other users' locked value, satisfying the "unbacked balance / theft of funds" impact bar.

### Likelihood Explanation
The precondition — `allowHardenExchangeCalculation` not yet enabled by the committee — represents the historical/default state of this feature (it is a committee-gated hardening flag added on top of pre-existing Exchange logic), and any order placer can broadcast an `ExchangeTransactionContract`/`ExchangeWithdrawContract` with attacker-chosen `quant`/`expected` fields without any special permission. The overflow itself requires large quant magnitudes, but no additional access control, multi-party collusion, or malicious-operator assumption is required, unlike the excluded classes (malicious SR/witness/committee, p2p). Exploitability is contingent on the flag's on-chain state at time of attack, which I was not able to directly confirm as default-off in this session (the default initialization for `allowHardenExchangeCalculation` in `DynamicPropertiesStore` was not read due to tool-call exhaustion) — this is the main remaining uncertainty.

### Recommendation
Remove the `allowHarden()` conditional bypass in `AbstractExchangeActuator.addExact/subtractExact` so that overflow-checked arithmetic and the non-negative-balance invariant enforced by `SafeExchangeProcessor`/hardened `ExchangeCapsule.transaction()` are applied unconditionally to all Exchange balance mutations and to the `ExchangeBalanceLimit` guardrail check in `ExchangeTransactionActuator.doValidate()`, regardless of the `allowHardenExchangeCalculation` flag state.

### Proof of Concept
Conceptual reproduction (could not be executed in this read-only session; recommend validating with a Devin session that can run the existing `framework/src/test/java/org/tron/core/actuator/ExchangeTransactionActuatorTest.java` harness):
1. Ensure `allowHardenExchangeCalculation` is left at its default (disabled) value in `DynamicPropertiesStore`.
2. Create an Exchange pair with a large `firstTokenBalance` close to `Long.MAX_VALUE - X` for a small `X`.
3. Submit an `ExchangeTransactionContract` with `tokenQuant` set so that `tokenBalance + tokenQuant` in `ExchangeTransactionActuator.doValidate()` (line ~202) overflows `long`, producing a small/negative wrapped value that passes the `tokenBalance > balanceLimit` check.
4. Observe `execute()` / `ExchangeCapsule.transaction()` update pool and account balances using the same unchecked arithmetic, producing balances inconsistent with actual token reserves.
