### Title
Stale Signature-Verification Cache in `Manager.getVerifyTxs` Bypasses Post-Revocation Permission Checks — ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
`Manager.getVerifyTxs` marks a block's transaction as `setVerified(true)` whenever a transaction with an identical signature already exists in the node's `pendingTransactions` pool for the same owner address, skipping full signature/permission re-validation at block-application time. `TransactionCapsule.validatePubSignature` then short-circuits entirely when `isVerified` is `true`, returning success without re-checking the signature against the current account permission set held in `AccountStore`.

### Finding Description
`TransactionCapsule` caches a boolean `isVerified` flag, and `validatePubSignature` skips re-verifying the signature against the current `AccountStore`/`Permission` state whenever that flag is already `true`: [1](#0-0) 

`Manager.getVerifyTxs` sets this flag preemptively for any incoming block transaction whose signature bytes match a transaction of the same owner address already sitting in `pendingTransactions` — i.e., a transaction the node verified earlier, at an earlier point in chain state: [2](#0-1) 

This is the same bug class as the reported analog: an authorization decision (here, permission/signature validity, analogous to the "admin role") is snapshotted once (when the transaction first entered `pendingTransactions`, verified against the account's permission set at that time) and cached (`isVerified=true`, analogous to `SESSION_POOL[sid]['role']`). Just as the external report's `heartbeat` handler in `socket/main.py` refreshes only `last_seen_at` while leaving `role` stale, `getVerifyTxs` refreshes only signature-byte equality while leaving the underlying permission validity unrefreshed. If the owner's account permissions are changed between the time the transaction was accepted into the pool (verified under the old permission set) and the time the block containing it is applied (`applyBlock`), the stale `isVerified=true` flag causes `validatePubSignature` to accept the transaction without re-checking it against the now-current `Permission`/key set in `AccountStore`.

Concretely: a user broadcasts transaction T (e.g. a `TransferContract`) signed by key K under the account's current owner permission. T enters the node's `pendingTransactions` and is verified (`isVerified` becomes true via normal processing). The user then broadcasts an `AccountPermissionUpdateContract` that removes key K from the owner permission (revokes K's signing rights) — this executes and commits in an earlier block or earlier in the same block. When a later block contains T again (re-broadcast, or the same T remains referenced), `getVerifyTxs` compares its signature bytes to the pooled entry, finds a match, and calls `capsule.setVerified(true)` — causing `validatePubSignature` to bypass re-validation of T's signature against the now-revoked permission set entirely.

This mirrors the reported vulnerability's core defect precisely: caching an authorization/verification result indexed by object identity/signature bytes rather than re-deriving it from current on-chain state (`AccountStore`) at the moment of actual authorization consumption, exactly as `SESSION_POOL`'s role field was cached instead of being re-fetched from the DB at each privileged operation.

### Impact Explanation
If exploitable, this allows a transaction signed under a permission set that has since been revoked (e.g., an owner key removed via `AccountPermissionUpdateActuator`) to still be treated as validly signed at block-application time, resulting in unauthorized account operations (transfers, contract calls, resource operations) executed by a key that should no longer have signing authority over the account — a direct violation of the account-permission model (CWE-863: Incorrect Authorization, CWE-613: Insufficient Session/Verification Expiration).

### Likelihood Explanation
Exploitability depends on the precise conditions under which `pendingTransactions` retains transactions across permission changes and whether `getVerifyTxs`'s owner-address + signature-byte match can be triggered by an attacker without the node performing an intervening full re-validation elsewhere in `applyBlock`/`processTransaction`. I was not able to fully trace whether `processTransaction` performs an independent, unconditional permission re-check elsewhere in the same call path (e.g., inside individual actuators' `validate()`, which do re-read `AccountStore` for other checks) that would still catch a revoked-key signature via a different mechanism, or whether `pendingTransactions` is cleared/pruned aggressively enough (e.g., on each new block) to make the matching window impractically small. This uncertainty affects confidence in real-world exploitability and should be verified with a live trace of `processTransaction`/`applyBlock`.

### Recommendation
Do not treat a byte-identical signature as sufficient proof of continued authorization. `getVerifyTxs`/`isVerified` caching should be invalidated whenever the owner account's `Permission` set has changed since the transaction was first verified (e.g., track a permission-version or last-updated block number on `AccountCapsule` and compare it before reusing `isVerified`), or simply drop this optimization and always re-verify signatures against the current `AccountStore` state at `applyBlock` time.

### Proof of Concept
1. Account A signs transaction T1 with key K (K is currently in A's owner `Permission`). T1 is broadcast and enters `pendingTransactions`, is verified, `isVerified=true`.
2. Account A broadcasts and confirms `AccountPermissionUpdateContract` removing K from A's owner permission (via `AccountPermissionUpdateActuator.execute`, updating `AccountStore`). [3](#0-2) 
3. A block arrives containing a transaction with the same owner address and identical signature bytes as T1 (re-included/re-ordered T1).
4. `Manager.getVerifyTxs` matches this transaction against the pooled T1 entry via `isSameSig`, and calls `capsule.setVerified(true)`. [4](#0-3) 
5. At block application, `TransactionCapsule.validatePubSignature` sees `isVerified==true` and returns success without re-deriving the permission from the current (post-revocation) `AccountStore` state, allowing the transaction signed by the now-unauthorized key K to be executed against A's account. [1](#0-0) 

Full confirmation of end-to-end exploitability requires tracing `applyBlock`/`processTransaction` to verify no other independent permission check intercepts this path before execution.

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }

  public List<TransactionCapsule> getVerifyTxs(BlockCapsule block) {

    if (pendingTransactions.size() == 0) {
      return block.getTransactions();
    }

    List<TransactionCapsule> txs = new ArrayList<>();
    Map<String, TransactionCapsule> txMap = new HashMap<>();
    Set<String> multiAddresses = new HashSet<>(ownerAddressSet);

    pendingTransactions.forEach(capsule -> {
      String txId = Hex.toHexString(capsule.getTransactionId().getBytes());
      if (isMultiSignTransaction(capsule.getInstance())) {
        String address = Hex.toHexString(capsule.getOwnerAddress());
        multiAddresses.add(address);
      } else {
        txMap.put(txId, capsule);
      }
    });

    block.getTransactions().forEach(capsule -> {
      String address = Hex.toHexString(capsule.getOwnerAddress());
      String txId = Hex.toHexString(capsule.getTransactionId().getBytes());
      if (multiAddresses.contains(address) || !isSameSig(capsule, txMap.get(txId))) {
        txs.add(capsule);
      } else {
        capsule.setVerified(true);
      }
    });

    return txs;
  }
