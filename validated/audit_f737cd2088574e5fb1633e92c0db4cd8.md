### Title
Atomic self-unpause + liquidate allows liquidators to bypass any grace period and liquidate accounts the instant a protocol pause ends - (File: `programs/marginfi/src/instructions/marginfi_group/panic_unpause_permissionless.rs`, `programs/marginfi/src/instructions/marginfi_group/propagate_fee_state.rs`, `programs/marginfi/src/instructions/marginfi_account/liquidate.rs`)

### Summary
When the protocol is under a `panic_pause`, `LendingAccountLiquidate`, `LendingAccountRepay`, `LendingAccountDeposit`, and `LendingAccountWithdraw` are all blocked, exactly like Notional's `PauseRouter`. Unlike a manual patch upgrade, marginfi's pause auto-expires and can be lifted by *anyone* via `panic_unpause_permissionless`, and the group's cached pause flag can also be refreshed by *anyone* via `propagate_fee_state`. Because both of these plus `LendingAccountLiquidate` require no special authorization beyond a liquidator's own account signer, a liquidator can pack `panic_unpause_permissionless` → `propagate_fee_state` → `LendingAccountLiquidate` into a single atomic transaction. There is no grace period after unpausing, so an account that became unhealthy while repay/deposit were blocked during the pause can be liquidated in the exact same transaction that lifts the pause — before the affected user has any chance to submit a repayment or top-up.

### Finding Description
`PanicState::unpause()` clears the pause flag immediately and unconditionally with no cooldown: [1](#0-0) 

`panic_unpause_permissionless` requires no signer authorization at all beyond the `fee_state` PDA itself, and can be invoked by any actor once the pause window has expired: [2](#0-1) 

`propagate_fee_state`'s `PropagateFee` accounts are explicitly documented as permissionless and callable against any group, and immediately syncs the group's cached `panic_state_cache` from the (now unpaused) `FeeState`: [3](#0-2) 

`LendingAccountLiquidate` only checks the group's cached pause state, which is now stale-refreshed by the same attacker in the prior instruction: [4](#0-3) 

Meanwhile `LendingAccountRepay` (and deposit/withdraw) are gated the same way, blocking the user from fixing their position while paused and requiring a *separate* transaction to react to the unpause, which cannot possibly land in the same slot as the attacker's bundled unpause+liquidate transaction: [5](#0-4) 

While a bank is paused, oracle price feeds are not frozen — only user-initiated bank operations are blocked (per `guides/ADMIN/BANK_STATE.md` and `PERMISSIONS_AND_ROLES.md`), so an account's health can silently deteriorate below the maintenance threshold during the pause window while the user has no recourse to repay or add collateral: [6](#0-5) 

This is a stronger variant of the Notional M-17 pattern: rather than merely frontrunning the user's repayment transaction in the block after unpause, an attacker can atomically compose the unpause and the liquidation into one transaction, guaranteeing the liquidation executes before any user-submitted repair transaction can even be constructed (since the user cannot know the pause has ended before it actually ends on-chain).

### Impact Explanation
An account whose health degraded during a protocol-wide pause (oracle prices moved while repay/deposit were blocked) can be unfairly liquidated by any liquidator the instant the pause ends, with zero opportunity for the account owner to repay debt or post collateral first. This is a material, low-cost loss of user funds (liquidation bonus/penalty extracted from the victim's collateral) achievable by any address holding a liquidator marginfi account, matching Sherlock's criteria for a valid (Medium, per the referenced judgment) severity finding.

### Likelihood Explanation
This requires: (1) a protocol pause occurring (rate-limited to 3/day, 4 consecutive, 6h duration) and (2) at least one account becoming liquidatable during that window due to price movement. Given marginfi's pause is intended for emergencies and can last up to 6 hours, and oracles keep updating during the pause, this is a realistic, non-"stars must align" scenario — the same conditions accepted as valid-Medium in the referenced Notional judgment apply here, arguably more directly because the liquidation and unpause can be bundled atomically by the same actor.

### Recommendation
Introduce a short grace period after `panic_unpause` / `panic_unpause_permissionless` during which `LendingAccountLiquidate` (and equivalent integration liquidation paths) remain blocked while repay/deposit/withdraw are re-enabled immediately, mirroring the Notional-accepted mitigation. Alternatively, disallow bundling `panic_unpause_permissionless`/`propagate_fee_state` with `LendingAccountLiquidate` in the same transaction, or require a minimum number of slots between the pause-clearing instruction and any liquidation against a given account.

### Proof of Concept
1. Protocol pause is active (`panic_pause` triggered by `global_fee_admin`/`pause_delegate_admin`); an account's health deteriorates below maintenance threshold due to oracle price movement while deposit/repay are blocked (`FailsIfPausedOrReduceState` / `ProtocolPaused` checks in `deposit.rs`/`repay.rs`).
2. Pause duration (`PanicState::PAUSE_DURATION_SECONDS` = 6h) elapses, making `panic_unpause_permissionless` callable by anyone.
3. Attacker (acting as liquidator) submits a single transaction containing, in order:
   - `panic_unpause_permissionless` (no signer authorization required beyond fee_state PDA) — clears `pause_flags` on `FeeState`.
   - `propagate_fee_state` (fully permissionless per its own doc comment) — syncs `MarginfiGroup.panic_state_cache` to reflect unpaused.
   - `LendingAccountLiquidate` against the target unhealthy account — passes its `!group.load()?.is_protocol_paused()` constraint because the cache was just refreshed in the prior instruction.
4. The liquidation executes atomically in the same transaction/slot that ends the pause, with no possibility for the victim to have submitted a repay/deposit transaction beforehand.

pub fn panic_unpause_permissionless(ctx: Context<PanicUnpausePermissionless>) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_mut()?;
    let current_timestamp = Clock::get()?.unix_timestamp;

    require!(
        fee_state.panic_state.is_paused_flag(),
        crate::errors::MarginfiError::ProtocolNotPaused
    );

    require!(
        fee_state.panic_state.is_expired(current_timestamp),
        crate::errors::MarginfiError::PauseLimitExceeded
    );

    msg!(
        "Permissionlessly unpaused at: {} (expired {}s)",
        current_timestamp,
        current_timestamp - fee_state.panic_state.pause_start_timestamp
    );

    fee_state.panic_state.unpause();

    Ok(())
}
```

#[derive(Accounts)]
pub struct PropagateFee<'info> {
    // Note: there is just one FeeState per program, so no further check is required.
    #[account(
        seeds = [FEE_STATE_SEED.as_bytes()],
        bump,
    )]
    pub fee_state: AccountLoader<'info, FeeState>,

    /// Any group, this ix is permisionless and can propagate the fee to any group
    #[account(mut)]
    pub marginfi_group: AccountLoader<'info, MarginfiGroup>,
}

pub fn propagate_fee(ctx: Context<PropagateFee>) -> Result<()> {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let fee_state = ctx.accounts.fee_state.load()?;

    group.fee_state_cache.global_fee_wallet = fee_state.global_fee_wallet;
    group.fee_state_cache.program_fee_fixed = fee_state.program_fee_fixed;
    group.fee_state_cache.program_fee_rate = fee_state.program_fee_rate;

    let clock = Clock::get()?;
    group.fee_state_cache.last_update = clock.unix_timestamp;

    group
        .panic_state_cache
        .update_from_panic_state(&fee_state.panic_state, clock.unix_timestamp);
```
