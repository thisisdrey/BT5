### Title
Retroactive Bank Risk-Tier Change Permanently Blocks Withdrawals for Existing Accounts - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
The reported Kamino bug is caused by a mismatch between a value cached on a user obligation (its elevation group) and a mutable admin-controlled configuration list (the reserve's valid elevation groups). When the admin narrows the valid set, existing obligations referencing the now-invalid value become permanently unable to pass validation, freezing them. Marginfi has a structurally identical pattern with `Bank.config.risk_tier`: existing accounts can accumulate multiple isolated-tier liabilities that were legal at the time they were opened, but a later, routine admin re-tiering of any one of those banks retroactively invalidates the account's liability composition and every future normal operation (not just new borrows) is blocked by the same live-state check.

### Finding Description
`Bank::configure` allows the group admin to change `config.risk_tier` between `Collateral` and `Isolated` at any time via `lending_pool_configure_bank`, with no validation against any existing obligations that reference that bank: [1](#0-0) 

The isolated-tier invariant is re-evaluated from **live** bank state (not any value cached on the account) every time `check_account_risk_tiers` runs: [2](#0-1) 

This check aggregates **all active liability balances across all banks in the account**, not just the bank being acted on. It fails with `IsolatedAccountIllegalState` if the account has more than one isolated liability, or one isolated liability plus any other liability — a state that becomes reachable purely because the admin flipped an existing bank from `Collateral` to `Isolated` (or vice versa) after users had already opened otherwise-legal combinations of borrows.

Crucially, this check is folded into the account's *init health* check, `check_account_init_health` (referenced explicitly in the liquidation code as "includes isolated-tier check"): [3](#0-2) 

`check_account_init_health` is invoked on ordinary, non-receivership withdrawals — i.e., a user withdrawing their own healthy, unrelated collateral: [4](#0-3) 

The same is documented as an acknowledged, un-authoritative edge case for the indexer flag: "Not authoritative due to a variety of edge cases, such as a Bank being configured from Collateral -> Isolated after the user deposits": [5](#0-4) 

So the exact bug class from the report reproduces: a value that is validated against a live, admin-mutable configuration (elevation-group membership / risk tier) rather than being fixed at the time the position was opened, with no grandfathering for pre-existing state.

### Impact Explanation
Once an admin retiers a bank that an existing account is borrowing from (a normal risk-management action, not an exploit), any account holding that liability alongside another liability becomes unable to pass `check_account_risk_tiers` on any future ordinary withdrawal, since the check inspects the account's entire liability set, not just the position being withdrawn. This blocks legitimate withdrawals of unrelated, healthy collateral — a permanent lock on funds for the affected user unless the admin reverts the risk-tier change or the account is put into receivership by a liquidator (which bypasses normal health checks). This matches the report's required impact bar: unintended permanent lock/freeze of user funds caused by a mismatch between cached/implied obligation state and a mutable admin configuration.

### Likelihood Explanation
This requires the group admin to change a bank's `risk_tier` while accounts already hold multiple liabilities involving that bank — a foreseeable, non-malicious admin action for ongoing risk management (exactly analogous to the reserve owner removing an elevation-group entry in the original report). It requires no attacker; it is triggered by routine protocol operations plus pre-existing legitimate user state, making it a realistic operational hazard rather than a purely theoretical one.

### Recommendation
Do not evaluate `check_account_risk_tiers` purely against live bank config for pre-existing positions. Either (a) grandfather existing liability combinations that were legal when opened by skipping the isolated-tier constraint on withdrawals/repayments that do not increase risk, restricting the check to borrow-opening flows only, or (b) exclude the isolated-tier check from `check_account_init_health` when the transaction does not add a new liability, so risk-tier changes cannot retroactively block withdrawals of unrelated healthy collateral.

### Proof of Concept
1. Admin creates Bank A (`Collateral`) and Bank B (`Collateral`).
2. User deposits collateral and opens borrows against both Bank A and Bank B — legal under `check_account_risk_tiers` since neither is isolated.
3. Admin later calls `lending_pool_configure_bank` on Bank B, setting `risk_tier = Isolated` (a legitimate risk-tightening action, e.g. due to a liquidity/oracle concern) — [6](#0-5) .
4. User now attempts to withdraw excess healthy collateral from an unrelated Bank C position. `lending_account_withdraw` calls `check_account_init_health`, which internally runs `check_account_risk_tiers` over the whole account, sees `isolated_risk_count == 1` and `total_liability_balances == 2` (Bank A + Bank B), and returns `IsolatedAccountIllegalState` — [7](#0-6) .
5. The user cannot withdraw any collateral through the normal path until the admin reverts Bank B's risk tier or a third-party liquidator initiates receivership, demonstrating an admin-configuration-induced fund lock analogous to the reported elevation-group DOS.

/// Check the isolated-risk-tier constraint (internal helper).
fn check_account_risk_tiers<'info>(
    marginfi_account: &MarginfiAccount,
    remaining_ais: &'info [AccountInfo<'info>],
) -> MarginfiResult {
    let mut isolated_risk_count = 0;
    let mut total_liability_balances = 0;

    let mut account_index = 0usize;
    for balance in marginfi_account
        .lending_account
        .balances
        .iter()
        .filter(|b| b.is_active())
    {
        // Load bank to read risk tier and remaining account count
        let bank_ai = remaining_ais
            .get(account_index)
            .ok_or(MarginfiError::InvalidBankAccount)?;
        let bank_al = AccountLoader::<Bank>::try_from(bank_ai)?;
        let bank = bank_al.load()?;

        check_eq!(
            balance.bank_pk,
            *bank_ai.key,
            MarginfiError::InvalidBankAccount
        );

        let num_accounts = get_remaining_accounts_per_bank(&bank)?;

        if !balance.is_empty(BalanceSide::Liabilities) {
            total_liability_balances += 1;
            if bank.config.risk_tier == RiskTier::Isolated {
                isolated_risk_count += 1;
                if isolated_risk_count > 1 {
                    break;
                }
            }
        }

        account_index += num_accounts;
    }

    check!(
        isolated_risk_count == 0 || total_liability_balances == 1,
        MarginfiError::IsolatedAccountIllegalState
    );

    Ok(())
}
