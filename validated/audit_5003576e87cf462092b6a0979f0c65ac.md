### Title
Unsafe truncating `BigInteger.longValue()` cast in `MarketUtils.multiplyAndDivide()` can silently corrupt market order settlement amounts - (File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java)

### Summary
`MarketUtils.multiplyAndDivide(long a, long b, long c, boolean disableMath)` first attempts an overflow-checked `multiplyExact`/`floorDiv`, but when that overflows it falls back to a `BigInteger` computation and returns `aBig.multiply(bBig).divide(cBig).longValue()` — using the truncating `longValue()` instead of the overflow-checked `longValueExact()`. This mirrors the reported Angle Protocol bug class (unsafe cast of an arithmetic result to a smaller/bounded type instead of using a safe/checked cast), but here it lands in java-tron's on-chain TRC10 order-matching arithmetic that any unprivileged account can trigger via `MarketSellAssetContract`.

### Finding Description
`multiplyAndDivide` is defined as: [1](#0-0) 

Elsewhere in the codebase, the same category of "big multiply/divide of user-controlled quantities" is done safely — e.g. `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate paths use `longValueExact()` (which throws `ArithmeticException` on truncation) and the calling actuators explicitly catch `ArithmeticException` and fail the transaction: [2](#0-1) 

By contrast, `multiplyAndDivide` is called directly by `MarketSellAssetActuator.matchSingleOrder()` with user/order-book-controlled quantities (`takerSellRemainQuantity`, `makerSellQuantity`, `makerBuyQuantity`, `makerSellRemainQuantity`) to compute how many tokens are actually delivered to taker and maker during order matching: [3](#0-2) [4](#0-3) 

These quantities are only bounded by `dynamicStore.getMarketQuantityLimit()` at order-creation validation time: [5](#0-4) 

If `a * b` (as computed via `BigInteger`) does not fit into a `long` even after the intended division by `c`, or if a maker/taker order combination is crafted such that the multiply-then-divide result silently wraps, `longValue()` (unlike `longValueExact()`) will **not** throw — it returns the low 64 bits of the true mathematical result. That truncated (and potentially negative, since sign is taken from the low bits) value is then used directly to set balances/asset amounts for both parties (`accountCapsule.addAssetAmountV2`, `setSellTokenQuantityRemain`, etc.) with no downstream sanity check that the settled amount matches the expected price ratio.

### Impact Explanation
Because the truncated result is used as the actual amount of TRX/TRC10 tokens transferred between the taker and maker order owners, an attacker who can construct maker and taker orders (both of which are createable by any unprivileged account issuing `MarketSellAssetContract` transactions, since TRON's on-chain DEX allows any two accounts to place orders that get matched) could engineer sell/buy quantities near the `long`/`BigInteger` boundary such that the fallback path returns a wrapped (possibly negative or drastically smaller/larger) settlement quantity instead of throwing. This can result in:
- Tokens credited to an account that do not correspond to the actual value exchanged (unbacked balance / theft of funds), or
- A negative or zero settlement amount being silently accepted, corrupting order book and account state,
- Divergence between nodes if the intermediate quantities differ due to prior state (leading to non-determinism/consensus risk if reached differently across nodes — though same computation, deterministic; primary risk is fund accounting corruption).

This satisfies the Medium+ bar: unauthorized/incorrect asset settlement reachable purely through ordinary account-signed `MarketSellAssetContract` transactions, without any privileged role.

### Likelihood Explanation
Reaching the overflow fallback branch requires carefully chosen large sell/buy token quantities near the `long` overflow boundary combined with matching orders in the order book — both are achievable by an ordinary user since `MarketSellAssetContract.sellTokenQuantity`/`buyTokenQuantity` are only capped by `dynamicStore.getMarketQuantityLimit()` (a runtime-configurable committee parameter, not hard-coded to a small safe value) rather than any arithmetic-safety-derived bound. I was not able to fully confirm the exact configured value of `MARKET_QUANTITY_LIMIT` from `DynamicPropertiesStore.java` in this session (search located the property but not its default/most likely value), so I cannot state with certainty that the default configuration allows quantities large enough to trigger the truncating fallback versus always fitting cleanly in the `multiplyExact`/`floorDiv` happy path. This uncertainty affects the likelihood assessment but not the root-cause validity of the unsafe cast itself.

### Recommendation
In `MarketUtils.multiplyAndDivide`, replace `.longValue()` with `.longValueExact()` in the `BigInteger` fallback path (mirroring the safe pattern already used in `ExchangeWithdrawActuator`/`ExchangeInjectActuator`), and ensure callers in `MarketSellAssetActuator` catch `ArithmeticException` from this path and fail the transaction (`ContractExeException`) rather than allowing a silently wrong quantity to be applied to account balances.

### Proof of Concept
Not independently executable in this session — reproducing the exact overflow boundary requires confirming the live value of `getMarketQuantityLimit()` and constructing matching maker/taker orders whose `BigInteger` product/quotient exceeds `Long.MAX_VALUE`/`Long.MIN_VALUE` after the `multiplyExact` fast path throws, at which point `.longValue()` in `MarketUtils.multiplyAndDivide` (chainbase/.../MarketUtils.java:264-277) returns a truncated/wrapped value instead of throwing, and that value is applied as the settled quantity in `MarketSellAssetActuator.matchSingleOrder` (actuator/.../MarketSellAssetActuator.java:382-463).

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
