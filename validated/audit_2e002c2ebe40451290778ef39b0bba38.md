### Title
Attachment content is stored keyed by its own hash without verifying it matches the requested `content_hash`, allowing a malicious peer to poison an unrelated hash slot and permanently block BNS attachment resolution - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's `GetAttachmentResponse` via `decode_atlas_get_attachment` and inserts `response.attachment` into `self.attachments` with no check that `Attachment::hash()` equals the `content_hash` that was actually requested from that peer. Because `AttachmentsDownloader::run` later stores the attachment keyed by its own self-computed hash (`attachment.hash()`), a malicious/unreliable peer can return arbitrary content for any request and it gets accepted, stored under a wrong (attacker-controlled) hash key, while the originally requested `content_hash` never gets its content, permanently starving that BNS name resolution.

### Finding Description
`extend_with_attachments` iterates `results.succeeded`, which pairs each `AttachmentRequest` (which carries the requested `content_hash`) with the peer's raw `StacksHttpResponse`: [1](#0-0) 

The response is decoded with `decode_atlas_get_attachment`, which only performs JSON parsing — it never compares `Hash160::from_data(&attachment.content)` against the `request`'s `content_hash`: [2](#0-1) 

The accepted (and unvalidated) `response.attachment` is inserted directly into `self.attachments`, discarding all association with the original request/its `content_hash`: [3](#0-2) 

Downstream, `AttachmentsDownloader::run` drains `context.attachments` and, for each one, re-derives the hash from the attacker-supplied content itself (`attachment.hash()`), looks up any `AttachmentInstance`s waiting on *that* hash, and unconditionally stores it via `insert_instantiated_attachment`: [4](#0-3) 

`insert_instantiated_attachment` writes `(attachment.hash(), attachment.content)` into the `attachments` table and marks any `attachment_instances` row with `content_hash = attachment.hash()` as available: [5](#0-4) 

`Attachment::hash()` is simply `Hash160::from_data(&self.content)`: [6](#0-5) 

Because the hash is derived from the attacker-controlled content itself rather than validated against the requested hash, a malicious peer selected as an outbound sync peer can respond to a request for `content_hash = H(legit)` with `Attachment{content: b"evil"}`. That response is accepted unconditionally, hashed to `H(evil)`, and stored/marked-available under `H(evil)` — a hash nobody asked about and that may collide with (poison) a different, legitimate pending `AttachmentInstance` if one happens to exist for `H(evil)`, or simply be wasted storage. Critically, the `AttachmentInstance` that legitimately committed to `H(legit)` on-chain is never resolved by this response, because the code never checks that the returned content actually satisfies the request it was fetched for. The peer can repeat this for every attachment request it receives, indefinitely starving resolution of any name update whose attachment it is asked to serve, since the reliability report is incremented as `bump_successful_requests()` regardless of hash correctness, keeping the malicious peer "reliable" and preferred for future requests.

Existing guards that fail to catch this: there is no cryptographic tie between `AttachmentRequest.content_hash` and the decoded `GetAttachmentResponse.attachment`; `decode_atlas_get_attachment` only validates JSON well-formedness; and `insert_instantiated_attachment`/`find_all_attachment_instances` trust the self-derived hash rather than the requested one.

### Impact Explanation
A remote, unprivileged peer that is selected as an outbound Atlas-sync source (via `get_outbound_sync_peers`/`get_data_url`, no privileged role required) can cause the node to (a) silently fail to resolve legitimate, on-chain-committed BNS attachments (the specific requested `content_hash` is never satisfied, and its `AttachmentInstance` stays unresolved/unavailable indefinitely) and (b) insert arbitrary attacker content into the node's Atlas attachments table keyed by attacker-chosen hash, which could mark unrelated legitimate `attachment_instances` rows (any with the same hash) as resolved with attacker content. This matches "attachment/BNS mismatch" under the High severity category: legitimate name updates never resolve via `/v2/attachments/{committed_hash}` even though the content was announced by a confirmed on-chain transaction, and the node treats attacker-served, non-matching content as if it satisfied a request.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to run an ordinary Stacks peer that gets included in `network.get_outbound_sync_peers()` for the target node (standard peer discovery, no key/secret/StackerDB slot needed) and answer `GET /v2/attachments/{hash}` requests with a crafted JSON body. No signature or MAC protects the HTTP attachment response. The attack is trivially repeatable per request/per batch and costs nothing beyond running a peer. This is a straightforward, always-reachable RPC round-trip already exercised by normal Atlas sync logic.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment` succeeds, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; treat a mismatch as a failed request (`report.bump_failed_requests()` and optionally penalize/blacklist the peer) instead of a success. Preserve the request's `content_hash` alongside the attachment (e.g., store as `HashMap<Hash160, Attachment>` keyed by the requested hash) so downstream code in `AttachmentsDownloader::run` can also assert the invariant defensively.

### Proof of Concept
Rust test in `stackslib/src/net/atlas` (mirroring existing tests in `stackslib/src/net/atlas/tests.rs`):
1. Construct an `AttachmentsBatchStateContext` with one peer entry (via `AttachmentsBatchStateContext::new`).
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains one `(AttachmentRequest { content_hash: Hash160::from_data(b"legit"), .. }, Some(response))`, where `response` is a `StacksHttpResponse` whose body JSON-decodes (via `decode_atlas_get_attachment`) to `GetAttachmentResponse { attachment: Attachment::new(b"evil".to_vec()) }`.
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert `context.attachments` contains the `Attachment::new(b"evil".to_vec())` entry (proving it was accepted) and that no entry with `hash() == Hash160::from_data(b"legit")` exists in `context.attachments`.
5. Simulate `AttachmentsDownloader::run`'s drain loop calling `atlasdb.insert_instantiated_attachment(&attachment)` and then `atlasdb.find_attachment(&Hash160::from_data(b"legit"))`, asserting it is still `None`/unresolved, proving the legitimately requested hash was never satisfied despite a "successful" response and a bumped reliability score.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }

impl StacksHttpResponse {
    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
            .map_err(|_e| NetError::DeserializeError("Failed to load from JSON".to_string()))?;
        Ok(resp)
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
