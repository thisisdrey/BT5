### Title
StackerDB chunk signatures do not bind to the target contract, enabling cross-contract chunk replay by a legitimate signer - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the digest signed and verified for every StackerDB chunk write — only commits to `slot_id`, `slot_version`, and `data_hash`. It never includes the target StackerDB's contract identifier (`QualifiedContractIdentifier`). Because the same signer key/address owns the identical slot index across multiple sibling StackerDB contracts (e.g. `signers-0-0`, `signers-0-1`, `signers-0-2`, one per `MessageSlotID`, all sharing the same slot assignment from `.signers`), a chunk validly signed for one contract passes signature verification when replayed against a different sibling contract at the same slot.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`verify()`/`sign()` operate solely on this digest, with no contract binding: [2](#0-1) 

On the write path, `StackerDBs::try_replace_chunk` looks up the slot's expected signer *by contract + slot_id* and checks `slot_desc.verify(&slot_validation.signer)`, but the signature itself never proves the chunk was intended for *that* contract — only that it was intended for *that slot_id/version/hash* combination: [3](#0-2) 

The same pattern exists on the P2P push/gossip path in `validate_received_chunk`, which resolves the signer via `get_slot_signer(smart_contract_id, data.slot_id)` and then verifies the same contract-agnostic digest: [4](#0-3) 

Critically, the signer-slot assignment is shared across all sibling per-message-type contracts within a signer set: every `signers-{set}-{message_id}` contract calls the same underlying page lookup, so a given signer occupies the *same slot_id* in every sibling contract for that reward cycle/signer-set: [5](#0-4) [6](#0-5) 

This is confirmed by `MessageSlotID::stacker_db_contract`, which derives sibling contracts for the same reward cycle differing only in a message-type index (`X` in `signers-0-X`): [7](#0-6) 

Consequently, a signer who legitimately owns slot `N` and produces a valid `(slot_id, slot_version, data_hash)` signature for contract A (e.g. `signers-0-1`, `BlockResponse`) can resubmit the identical `StackerDBChunkData` (same slot_id, version, sig, data) to a different sibling contract B (e.g. `signers-0-2`, `StateMachineUpdate`) via the write endpoint. Since that signer owns the same slot_id in B, and the signature check only validates `(slot_id, slot_version, data_hash)` against the recovered address, `try_replace_chunk`/`validate_received_chunk` will accept and store it as canonical data for contract B, even though it was never intended for that message type/contract.

The equality broken here mirrors the external report's bug class: an implicit binding (here, "which contract/type this signed data is for") is never checked/enforced by the cryptographic evidence, so a value accompanying the evidence (the target contract) can diverge from what was actually authenticated.

### Impact Explanation
This allows a registered signer (using only their own key — no other party's key or admin role needed) to write arbitrary already-signed payloads into a StackerDB contract other than the one intended, causing the node to serve/gossip that chunk as canonical state for the wrong message-type/contract. Downstream consumers (other signers, relayers, miners reading `signers-*-*` contracts) may misinterpret cross-contract replayed data, get confused about the current state-machine/BlockResponse/BlockPreCommit views, or have stale/foreign signed payloads propagate network-wide via `StackerDBChunkInv`/push-chunk gossip. This matches "serving non-canonical state as canonical" / unauthorized write across StackerDB boundaries.

### Likelihood Explanation
Requires only a normal, currently-registered signer (not an admin, not another party's key) and standard use of the public HTTP write endpoint (`POST /v2/stackerdb/:principal/:contract_name/chunks`) or the P2P StackerDBPushChunk path, both remote and unauthenticated beyond having a valid signer slot. No race condition or privileged access is needed — only that the resubmitted `slot_version` be higher than the current version at the target contract's slot, which the attacker fully controls.

### Recommendation
Bind the signed digest to the target StackerDB contract identity, e.g. include the `QualifiedContractIdentifier` (or a stable hash/index of it) in `SlotMetadata::auth_digest()`, so a signature over slot data for contract A cannot be replayed as valid for contract B. This mirrors the report's recommendation to validate that an auxiliary identifier (there, `_tokenTypeIndex`; here, the contract identifier) matches the value implied by the authenticated evidence.

### Proof of Concept
1. Registered signer S owns slot `5` in both `signers-0-1` (BlockResponse) and `signers-0-2` (StateMachineUpdate) for the current reward cycle (guaranteed by shared slot-assignment logic in `signers.clar`/`signers-0-xxx.clar`).
2. S crafts `StackerDBChunkData { slot_id: 5, slot_version: V, data: payload }` and signs it — this only commits to `(5, V, hash(payload))`.
3. S legitimately POSTs it to `/v2/stackerdb/<S>/signers-0-1/chunks`; it is accepted.
4. S then POSTs the identical `slot_id/slot_version/sig/data` to `/v2/stackerdb/<S>/signers-0-2/chunks` (a different message-type contract) with `slot_version` above the current version there.
5. `try_replace_chunk` for `signers-0-2` looks up the slot-5 signer (S), calls `slot_desc.verify(&S)`, which succeeds because the digest never referenced the contract — the chunk is stored as canonical StateMachineUpdate data even though it was authenticated only for BlockResponse.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
