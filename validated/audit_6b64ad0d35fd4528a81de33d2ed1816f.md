### Title
Unbounded HTTP response body buffering in `run_http_request` allows unauthenticated memory-amplification DoS against StackerDB clients - (`libsigner/src/http.rs`, `libsigner/src/session.rs`)

### Summary
`StackerDBSession::get_latest_chunks()` enforces `SIGNERS_STACKERDB_CHUNK_SIZE`/`STACKERDB_MAX_CHUNK_SIZE` only after the entire HTTP response body has already been read into memory. The underlying transport function `run_http_request` calls `sock.read_to_end(&mut buf)` with no size cap, and for non-chunked bodies `decode_http_body` simply does `buf.to_vec()` with no limit either, so a malicious StackerDB host can send an arbitrarily large `HTTP/1.1 200 OK` body and force the requesting client to buffer it all before the size check ever runs.

### Finding Description
The claimed equality — "bytes buffered before size-check == the enforced chunk-size limit" — does not hold. Tracing the GET path:

- `StackerDBSession::get_latest_chunks()` calls `self.rpc_request("GET", &path, None, &[])`, which calls `run_http_request(sock, ...)`. [1](#0-0) 

- `run_http_request` writes the request, then reads the *entire* response with no bound: `sock.read_to_end(&mut buf)?;`. There is no length check performed during or immediately after this read. [2](#0-1) 

- After parsing headers, `decode_http_body` is called on the remaining bytes. For a non-chunked response (no `Transfer-Encoding: chunked` header, which the attacker fully controls), it does `buf.to_vec()` — again with no size limit. Only the chunked-encoding branch enforces `MAX_MESSAGE_LEN` via `HttpChunkedTransferReader`. [3](#0-2) 

- Only after `run_http_request` returns the fully-materialized `Vec<u8>` does `get_latest_chunks()` check `if body_bytes.len() > limit { None } else { Some(body_bytes) }`. [4](#0-3) 

Thus the size check is strictly post-hoc: it can only discard an oversized chunk after the full body (bounded only by what the attacker chooses to send, e.g. hundreds of MB or GB) has already been allocated and copied into the client's heap via `Vec<u8>` growth in `read_to_end`. No `Content-Length` cap, no incremental read cap, and no streaming size check exists anywhere on this non-chunked path. `get_chunks()` (the non-latest variant) has no size check at all.

### Impact Explanation
A remote StackerDB replica host (any node the signer/client connects to for `list_chunks`/`get_chunks`/`get_latest_chunks`/`put_chunk` — i.e., any operator running a node, since this is a normal RPC session and not privileged) can respond to a single GET request with an oversized body and force unbounded memory allocation on the calling client (e.g., a signer process) per request, and this is fully repeatable on every request/reconnect. This is an unauthenticated, single-message memory-amplification DoS against the client, matching the Critical category ("remote crash/unauthenticated DoS from few messages").

### Likelihood Explanation
No special privileges, secrets, or slot ownership are required by the malicious responder — it only needs to be the host that the `StackerDBSession` connects to and respond to a GET request. This is a standard interaction pattern (clients query StackerDB replicas across the network), the attack costs the attacker only the bytes they choose to send, and it is trivially repeatable on every call.

### Recommendation
Bound the response read in `run_http_request` by wrapping `sock` in a limited reader (e.g., `Read::take(MAX_MESSAGE_LEN or the caller-specific chunk limit)`) before calling `read_to_end`, so the socket read itself aborts once the limit is exceeded rather than after buffering the full body. Also apply an explicit size cap to the non-chunked branch of `decode_http_body`, not just the chunked-transfer-encoding branch.

### Proof of Concept
```rust
// libsigner/src/http.rs (test) or a new integration test
use std::net::TcpListener;
use std::io::Write;
use std::thread;

#[test]
fn oversized_body_is_fully_buffered_before_limit_check() {
    let listener = TcpListener::bind("127.0.0.1:0").unwrap();
    let addr = listener.local_addr().unwrap();
    let big_len = 50 * 1024 * 1024; // 50MB, >> SIGNERS_STACKERDB_CHUNK_SIZE

    thread::spawn(move || {
        let (mut stream, _) = listener.accept().unwrap();
        let mut resp = format!("HTTP/1.1 200 OK\r\nContent-Length: {big_len}\r\n\r\n").into_bytes();
        resp.extend(std::iter::repeat(b'A').take(big_len));
        stream.write_all(&resp).unwrap();
    });

    let mut sock = std::net::TcpStream::connect(addr).unwrap();
    let result = run_http_request(&mut sock, "127.0.0.1", "GET", "/", None, &[]).unwrap();
    // Assertion: the full 50MB body was buffered and returned BEFORE
    // any chunk-size limit (SIGNERS_STACKERDB_CHUNK_SIZE / STACKERDB_MAX_CHUNK_SIZE)
    // was ever checked -- proving the discard in get_latest_chunks() happens too late
    // to bound memory usage during the read.
    assert_eq!(result.len(), big_len);
}
```
This demonstrates that `run_http_request`'s `sock.read_to_end(&mut buf)` fully materializes an oversized body in memory before `get_latest_chunks()`'s `body_bytes.len() > limit` check ever runs, confirming the memory-amplification path.

pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
