### Title
`RepositoryImpl::calculateGlobalEnergyLimit()` never applies the V2 fractional-weight formula, diverging from `EnergyProcessor::calculateGlobalEnergyLimit()` used for actual resource accounting - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()`, which backs the TVM's view of an account's total energy quota (via `getAccountLeftEnergyFromFreeze`), always computes the energy limit using the legacy formula with integer-floored `energyWeight = frozeBalance / TRX_PRECISION`. In contrast, `EnergyProcessor.calculateGlobalEnergyLimit()`, which is the source of truth for actual on-chain energy accounting (`useEnergy`), switches to `calculateGlobalEnergyLimitV2()` — using a fractional `energyWeight = (double) frozeBalance / TRX_PRECISION` (or the hardened `calculateGlobalLimitV2` BigInteger form) — whenever `supportUnfreezeDelay()` is active. This is the same "two formulas for one logical quantity" pattern as the JOJO `getTRate()`/`accrueRate()` bug: one code path never picked up the newer, more precise formula.

### Finding Description
`EnergyProcessor.calculateGlobalEnergyLimit()` explicitly forks on the chain parameter: [1](#0-0) 
When `supportUnfreezeDelay()` is enabled it calls `calculateGlobalEnergyLimitV2`, which preserves fractional weight for balances that are not exact multiples of `TRX_PRECISION`: [2](#0-1) 

By contrast, `RepositoryImpl.calculateGlobalEnergyLimit()` — used inside the TVM execution path — contains no such fork and always floors the weight via integer division `frozeBalance / TRX_PRECISION`: [3](#0-2) 

This method is invoked from `getAccountLeftEnergyFromFreeze`, which is reachable for every smart-contract call where the contract has `consumeUserResourcePercent < 100` (i.e., the contract creator shares energy cost with the caller): [4](#0-3) [5](#0-4) 

Any unprivileged account can trigger this path by simply calling (`TriggerSmartContract`) any deployed contract that has `consumeUserResourcePercent < 100`, an extremely common, unprivileged, single-signed-transaction-reachable configuration.

### Impact Explanation
Once `supportUnfreezeDelay` is enabled on-chain (a hard-fork-controlled feature switch, not attacker-controlled but globally activatable), `EnergyProcessor` (the actual resource-consumption bookkeeping used by `useEnergy`) computes the contract creator's global energy limit with fractional-weight precision, while `RepositoryImpl.calculateGlobalEnergyLimit`, used during VM execution to determine `originEnergyLeft`/`creatorEnergyLimit` for splitting energy costs between caller and contract owner (`VMActuator.getTotalEnergyLimitWithFixRatio` / `getTotalEnergyLimitWithFloatRatio`), keeps using the legacy floored formula. This produces a biased (generally lower, due to floor truncation of `frozeBalance/TRX_PRECISION`) creator energy limit estimate at the point where a contract call's energy cost is being apportioned, versus the real accounting figure enforced later by `EnergyProcessor`. The result is an inconsistent, and for balances not an exact multiple of `TRX_PRECISION`, systematically incorrect distribution of energy consumption cost between the calling account and the contract's origin/creator account — potentially causing callers to be overcharged for energy that should have been drawn from the contract creator's frozen energy, or vice versa. Because this affects the energy-fee accounting reachable from every ordinary smart-contract invocation, it is a Medium-severity, broadly reachable billing/accounting correctness bug.

### Likelihood Explanation
The divergent code path executes automatically and deterministically on mainnet once the `supportUnfreezeDelay` hard fork parameter is turned on (a normal, already-supported configuration flag checked throughout the codebase, e.g., in `ResourceProcessor.increase`). No special privilege is needed by the transaction sender — any contract call to a contract configured with `consumeUserResourcePercent < 100` and non-round frozen energy balances on the creator side triggers the miscalculation. This makes the bug consistently and trivially reachable by any anonymous API client / order-placer.

### Recommendation
Make `RepositoryImpl.calculateGlobalEnergyLimit()` consistent with `EnergyProcessor.calculateGlobalEnergyLimit()`/`calculateGlobalEnergyLimitV2()`: check `getDynamicPropertiesStore().supportUnfreezeDelay()` in `RepositoryImpl` and delegate to the same fractional/hardened V2 formula used by `EnergyProcessor`, ideally by extracting a single shared implementation (e.g., via `ResourceProcessor`) that both `EnergyProcessor` and `RepositoryImpl` call, eliminating duplicate/divergent formulas entirely.

### Proof of Concept
1. Enable `supportUnfreezeDelay` (the relevant chain parameter/hard fork) on a test network.
2. Deploy a contract with `consumeUserResourcePercent` set to e.g. 50, owned by account `Creator`.
3. Freeze for `Creator` a `FrozenBalanceForEnergy` that is **not** an exact multiple of `TRX_PRECISION` (e.g., `1_500_000` sun when `TRX_PRECISION = 1_000_000`).
4. Compare:
   - `EnergyProcessor.calculateGlobalEnergyLimit(Creator)` (actual accounting; uses `calculateGlobalEnergyLimitV2` with fractional weight `1.5`).
   - `RepositoryImpl.calculateGlobalEnergyLimit(Creator)` (TVM path used in `getAccountLeftEnergyFromFreeze` during `getTotalEnergyLimitWithFixRatio`), which floors weight to `1` via `frozeBalance / TRX_PRECISION`.
5. Observe the two results differ (as already demonstrated for the analogous V1/V2 divergence in `framework/src/test/java/org/tron/core/db/CalculateGlobalLimitHardenTest.java` `testV1FlooredWeightVsV2FractionalWeight`, lines 235-263, which shows 25 vs 37 for a 1.5×`TRX_PRECISION` frozen balance) — confirming the same class of formula bias reaches an energy-fee-splitting decision inside the TVM execution path while the ledger's real energy accounting uses the corrected value.   public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {

    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  @Test
  public void testV1FlooredWeightVsV2FractionalWeight() {
    dbManager.getDynamicPropertiesStore().saveTotalEnergyCurrentLimit(50_000_000_000L);
    dbManager.getDynamicPropertiesStore().saveTotalEnergyWeight(2_000_000_000L);
    long frozeBalance = 1_500_000L; // 1.5 x TRX_PRECISION

    dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(1);

    // V1 path
    dbManager.getDynamicPropertiesStore().saveUnfreezeDelayDays(0);
    ownerCapsule.setFrozenForEnergy(frozeBalance, 0L);
    dbManager.getAccountStore().put(ownerCapsule.getAddress().toByteArray(), ownerCapsule);
    long v1New = energyProcessor.calculateGlobalEnergyLimit(ownerCapsule);

    // Legacy V1 expectation: floor(1.5) * 25.0 = 1 * 25 = 25
    Assert.assertEquals(25L, v1New);

    // V2 path with the same balance keeps the fractional weight
    long v2New = energyProcessor.calculateGlobalEnergyLimitV2(frozeBalance);
    // Legacy V2 expectation: 1.5 * 25.0 = 37.5 -> 37
    Assert.assertEquals(37L, v2New);

    // And both must match their respective legacy doubles
    dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(0);
    long v1Old = energyProcessor.calculateGlobalEnergyLimit(ownerCapsule);
    long v2Old = energyProcessor.calculateGlobalEnergyLimitV2(frozeBalance);
    Assert.assertEquals(v1Old, v1New);
    Assert.assertEquals(v2Old, v2New);
  }
