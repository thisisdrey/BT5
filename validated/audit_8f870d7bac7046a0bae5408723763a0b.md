### Title
Unbounded, unpaginated `GetAssetIssueList` / `GetAssetIssueByAccount` / `GetAssetIssueListByName` query APIs can be forced into memory-exhausting responses as the number of issued assets grows - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`Wallet.getAssetIssueList()`, `Wallet.getAssetIssueByAccount()`, and `Wallet.getAssetIssueListByName()` all call `getAllAssetIssues()` on the asset-issue store and then iterate the *entire* result set to build a single in-memory `AssetIssueList` protobuf response, with no offset/limit bound, unlike the sibling `getAssetIssueList(offset, limit)` API. These unbounded methods are wired directly into HTTP servlets (`GetAssetIssueListServlet`, `GetAssetIssueListByNameServlet`) and gRPC/JSON-RPC-adjacent `WalletSolidityApi`/`WalletApi`/`WalletPBFTApi` endpoints, so any anonymous API client can trigger full-table scans and full in-memory materialization of every asset ever issued on the network.

### Finding Description
`Wallet.getAssetIssueList()` fetches the complete list via `getAssetIssueStoreFinal(...).getAllAssetIssues()` and iterates it with `.forEach(...)` to add every entry to the response builder, with no `limit`: [1](#0-0) 

The same unbounded pattern repeats in `getAssetIssueByAccount()`: [2](#0-1) 

and in `getAssetIssueListByName()`: [3](#0-2) 

By contrast, the paginated variant `getAssetIssueList(offset, limit)` correctly bounds results and even clamps the limit via `ASSET_ISSUE_COUNT_LIMIT_MAX` in `AssetIssueStore`: [4](#0-3) 

The unbounded APIs are reachable by any anonymous HTTP client with no authentication: [5](#0-4) 

and via gRPC `WalletSolidityApi.getAssetIssueList` / `getAssetIssueByAccount` and the `WalletApi` equivalents: [6](#0-5) 

The number of asset issues on-chain is grown by broadcasting `AssetIssueContract` transactions handled by `AssetIssueActuator`, which persists a new `AssetIssueCapsule` into `AssetIssueStore`/`AssetIssueV2Store` on every successful execution: [7](#0-6) 

Each account is limited to issuing exactly one asset over its lifetime (enforced in `validate()`), and issuance costs the `AssetIssueFee` dynamic parameter paid by the owner account: [8](#0-7) 

This constraint means growing the asset table requires funding many distinct accounts (one asset per account), which raises the cost of the attack but does not eliminate it as a scalability/DoS concern for the always-unpaginated read paths, since the store only grows monotonically over the life of the chain (no asset deletion mechanism was found) and every future full-node/solidity-node operator inherits the accumulated dataset regardless of who created it.

### Impact Explanation
As the total number of issued assets increases, `getAssetIssueList()`, `getAssetIssueByAccount()`, and `getAssetIssueListByName()` degrade linearly and unboundedly: each call performs a full LevelDB/RocksDB iterator scan, deserializes every `AssetIssueCapsule`, runs `BandwidthProcessor.updateUsage()` per item, and serializes the entire set into one protobuf/JSON response. A sufficiently large asset-issue table causes large heap allocations and long-held CPU/GC pauses on every hit to these public, unauthenticated endpoints, degrading or crashing the API-serving process (full node, solidity node, or PBFT node) for all legitimate callers — this matches the "API the node can no longer serve" acceptance criterion. Because the underlying data only accumulates over time (assets are not deleted), this is not a transient condition; it worsens monotonically as long as the chain operates and any accounts continue to issue assets.

### Likelihood Explanation
Likelihood is moderate. Triggering the vulnerable state requires an attacker (or organic network growth) to accumulate enough `AssetIssueContract` entries to make the full-scan response large; because each account may issue only one asset and must pay `AssetIssueFee`, this is not free, but it is far cheaper than comparable smart-contract-storage DoS vectors since it is a native, fee-bounded, always-available transaction type usable by any funded account — no special privileges are required. An attacker with moderate capital (funding many low-balance accounts, each paying the fixed issuance fee once) can inflate the store size over time. Once inflated, every call to the unbounded read APIs by any anonymous client reproduces the DoS effect indefinitely, since the paginated alternative exists but does not replace or gate the unbounded ones.

### Recommendation
- Deprecate or remove the unbounded `getAssetIssueList()`, `getAssetIssueByAccount()`, and `getAssetIssueListByName()` code paths (and their HTTP/gRPC exposures), or internally cap them the same way `getAssetIssueList(offset, limit)` is capped via `ASSET_ISSUE_COUNT_LIMIT_MAX`.
- Add pagination parameters to `getAssetIssueByAccount` and `getAssetIssueListByName`, mirroring `AssetIssueStore.getAssetIssuesPaginated`.
- Consider indexing by owner/name (e.g., secondary key on owner address) instead of scanning and filtering the entire `AssetIssueStore` per request.

### Proof of Concept
1. Fund N distinct accounts, each above the `AssetIssueFee` threshold read from `DynamicPropertiesStore.getAssetIssueFee()`.
2. From each account, broadcast one `AssetIssueContract` transaction (processed by `AssetIssueActuator.execute`), growing `AssetIssueStore`/`AssetIssueV2Store` by one entry each, respecting the "one asset per account" rule enforced in `AssetIssueActuator.validate()`.
3. Repeat until the store contains a large number of entries (tens of thousands+).
4. As an anonymous client, call `GET /wallet/getassetissuelist` (routed to `GetAssetIssueListServlet` → `Wallet.getAssetIssueList()`) or the gRPC `WalletSolidity.GetAssetIssueList`/`GetAssetIssueByAccount` endpoints repeatedly.
5. Observe that each call forces a full iteration and in-memory materialization/serialization of the entire asset-issue table with no size limit, causing elevated latency/memory pressure proportional to table size, degrading the node's ability to serve other API requests.

    if (accountAddress == null || accountAddress.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getOwnerAddress().equals(accountAddress))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }
