### Title
Replay window is only updated after decryption completes, allowing a duplicated packet to be processed twice - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay check into two separate, lock-scoped steps around the actual cryptographic/decryption work: `window.Check` is evaluated and released, then `dKey.DecryptDanger` runs *without* holding `decryptLock`, and only afterward is `window.Update` called to actually record the message counter as seen. This mirrors the Maverick finding where the authoritative state (the liquidity bin) is only "moved"/committed after the swap executes rather than atomically with the check, leaving a window where a second observer can race the update and get treated as if the state hadn't changed yet.

### Finding Description
`Decrypt` performs:
1. `decryptLock.Lock(); Check(counter); decryptLock.Unlock()`
2. `DecryptDanger(...)` (no lock held)
3. `decryptLock.Lock(); Update(counter); decryptLock.Unlock()` [1](#0-0) 

Because the lock is released between `Check` and the actual `Update`, the replay-window bit for `messageCounter` is not committed until step 3, well after decryption of the packet's payload has already happened. If two copies of the same encrypted packet (same `messageCounter`) are handed to the reader/decryption path concurrently — e.g. via nebula's multi-routine UDP/tun readers, `q int` in `readOutsidePackets`, or simple network-level duplication of a captured UDP datagram — both goroutines can pass `Check` before either calls `Update`, because neither has recorded the counter yet. Both then run `DecryptDanger` successfully (it's a valid, previously-seen ciphertext, so AEAD decryption succeeds for both), and only the second `Update` call correctly returns `false`/`ErrAlreadySeen`. By that point the plaintext payload has already been produced and (depending on caller order) may already have been delivered to the tun device / forwarded, i.e., the "protection" is applied to bookkeeping only after the sensitive operation (decryption/delivery) already occurred — exactly the same "commit-after-action" ordering bug as bins moving only after the swap.

`readOutsidePackets` is invoked per reader routine (`q int`) and dispatches straight into `ConnectionState.Decrypt`/`VerifyRelay` for both regular and relayed message paths: [2](#0-1) [3](#0-2) 

The underlying replay-window primitive (`Bits.Check`/`Bits.Update`) itself has no atomicity guarantee across the two calls — it is a plain read vs. read-modify-write pair, and `ConnectionState` relies entirely on `decryptLock` scoping to serialize them, which it does not do across the decrypt call: [4](#0-3) [5](#0-4) 

### Impact Explanation
A duplicated/replayed on-path packet can be decrypted and passed to the upper layers twice within the race window before `Update` commits the counter, i.e. this is a nonce/replay-handling bypass in the data-plane traffic layer rather than a mere log/metric duplication. This is not a full authentication bypass (the AEAD key material must already be valid, i.e. a real established tunnel is required), but it undermines the anti-replay guarantee nebula explicitly documents and tests around message counters, letting an attacker who can duplicate a captured UDP datagram get double-processing of a single wire packet.

### Likelihood Explanation
Requires an on-path/network attacker who can duplicate a legitimate encrypted UDP datagram (or naturally-duplicated delivery, e.g. via multiple listener routines or network-level retransmission) and deliver both copies close enough in time to land inside the `Check`→`Update` window while `decryptLock` is unheld during `DecryptDanger`. No CA-signed certificate or authenticated-peer status is needed beyond passively capturing/replaying ciphertext already on the wire, matching the same "narrow timing window, real but niche" profile that the original Maverick issue was judged as Medium severity for.

### Recommendation
Hold `decryptLock` for the entire `Check` → `DecryptDanger` → `Update` sequence (or otherwise reserve the counter slot atomically before decrypting, rolling back on decryption failure) so the replay-window state is committed atomically with the decision to proceed, closing the same "commit only after the action" race that made the Maverick bin-movement bug exploitable.

### Proof of Concept
1. Establish a nebula tunnel between two hosts.
2. Capture one legitimate encrypted data packet (`header.Message`) with counter `N`.
3. Send two copies of this exact packet to the receiving host's UDP listener nearly simultaneously (e.g., via `sendto` twice back-to-back, or by exploiting multiple reader routines when `listen.routines`/`tun.routines` > 1).
4. Both goroutines call `ConnectionState.Decrypt`; because `decryptLock` is released after `Check` and re-acquired only for `Update`, both can pass `Check(N)` before either calls `Update(N)`.
5. Both successfully run `DecryptDanger` and produce plaintext; only the losing goroutine's later `Update(N)` returns `ErrAlreadySeen`, but by then its plaintext has already been produced/handled, demonstrating double-processing of a single replayed wire packet analogous to exploiting the delayed-commit window in the Maverick bin-movement bug.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// updateSlow handles jumps, in-window backfill, dupes, and out-of-window.
func (b *Bits) updateSlow(l *slog.Logger, i uint64) bool {
	// If i is a jump, adjust the window, record lost, update current, and return true
	if i > b.current {
		end := i
		if end > b.current+b.length {
			end = b.current + b.length
		}
		count := end - b.current
		startPos := (b.current + 1) & b.lengthMask

		var lost int64
		if b.current >= b.length {
			// Steady state: every cleared slot is past warmup, so any unset
			// bit we evict is a lost packet from the previous cycle.
			wasSet := b.clearRange(startPos, count)
			lost = int64(count) - int64(wasSet)
		} else {
			// Warmup (the very first window). Some cleared slots represent
			// packets <= length where eviction is not "lost" in the usual
			// sense. This branch is taken at most once per connection so we
			// don't bother optimizing it.
			for n := b.current + 1; n <= end; n++ {
				if !b.get(n) && n > b.length {
					lost++
				}
			}
			b.clearRange(startPos, count)
		}

		// Anything past the new window can never be backfilled, so it's lost.
		if i > b.current+b.length {
			lost += int64(i - b.current - b.length)
		}
		b.lostCounter.Inc(lost)

		b.set(i)
		b.current = i
		return true
	}
