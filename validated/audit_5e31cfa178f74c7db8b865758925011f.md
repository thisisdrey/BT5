### Title
Cross-contract StackerDB signature replay due to missing StackerDB identifier in signed digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest for a StackerDB chunk as `sha512/256(slot_id || slot_version || data_hash)` and omits the smart-contract identifier (`QualifiedContractIdentifier`) of the StackerDB the chunk is being written to [1](#0-0) . Because the same signer address is assigned the *same* `slot_id` across multiple independent StackerDB replicas (the `.signers-{0,1}-{message_id}` family of contracts, for `message_id` in `0..SIGNER_SLOTS_PER_USER`, all derived from the same underlying per-cycle signer ordering) [2](#0-1) , a validly-signed chunk observed on one contract/lane can be replayed verbatim (same `slot_id`, `slot_version`, `sig`, `data`) into a different contract/lane for the same signer, and the signature check will still pass because it never bound the message to a specific StackerDB contract. This is the direct analog of the reported bug class: a signature scheme lacking a discriminator (function selector / destination context) that is supposed to keep two operations distinct.

### Finding Description
`SlotMetadata::sign`/`verify` compute the authenticated digest solely from `(slot_id, slot_version, data_hash)` [3](#0-2) . The write path, `StackerDBTx::try_replace_chunk`, looks up the expected signer address for a `(smart_contract, slot_id)` pair and calls `slot_desc.verify(&slot_validation.signer)`, but the contract identity is used only to select which address to check against — it is never mixed into the signed bytes themselves [4](#0-3) . The same pattern is repeated on the read/gossip-validation path in `StackerDBSync::validate_received_chunk`, which also resolves the expected `addr` per-contract but verifies against the contract-agnostic digest [5](#0-4) .

Because signer-slot assignment for a given `signer_set` (reward-cycle parity) is identical across every `.signers-{signer_set}-{message_id}` contract — confirmed by the test asserting the exact same slot list is returned by `stackerdb-get-signer-slots` for every `message_id` in `0..SIGNER_SLOTS_PER_USER` for a given `signer_set` [2](#0-1)  — the same signer address owns `slot_id` `N` in every one of those parallel StackerDB instances simultaneously. A chunk that a signer legitimately produced and signed for one message lane (e.g., a `BlockResponse`/`MockSignature` chunk on `.signers-1-1`) carries a signature that is equally valid, byte-for-byte, on any other lane contract for the same signer_set (e.g. `.signers-1-2`, used for `StateMachineUpdate`). An unprivileged network peer that observes the legitimate `StackerDBChunkData` (slot_id, slot_version, sig, data) can resubmit it — either via the unauthenticated HTTP `POST /v2/stackerdb/.../chunks` path (`poststackerdbchunk.rs`) or via unsolicited P2P push (`StackerDBPushChunkData`, processed in `relay.rs`) — against the *other* contract's slot, and `try_replace_chunk`/`validate_received_chunk` will accept it as long as the target replica's stored version for that slot is lower than the replayed `slot_version` (which is trivially true for a fresh/independent replica).

This breaks the equality "signed-for-context A" vs "accepted-as-valid-for-context B": the node's per-slot signature check authenticates *who* wrote a chunk, but not *which StackerDB/message-lane* it was authorized for.

### Impact Explanation
A successfully replayed chunk is stored via `insert_chunk`/`try_replace_chunk` and then unconditionally rebroadcast network-wide in `PeerNetwork::process_stacker_db_chunks`, which wraps the accepted chunk in `StacksMessageType::StackerDBPushChunk` and calls `self.p2p.broadcast_message(...)` [6](#0-5) . This means an attacker with no signing key can cause forged/mismatched data (data belonging to one message-lane's schema, e.g. a serialized `BlockResponse`, deserialized under a `StateMachineUpdate` slot, or vice versa) to be written into a StackerDB replica it was never authorized for, and have every honest node in the network propagate and store that same mismatched chunk. Consumers that read the StackerDB events, such as the state-machine evaluator in `stackerdb_listener.rs`, attempt to interpret chunk bytes according to the lane they were fetched from [7](#0-6) ; a cross-lane replay can silently overwrite a slot with data of the wrong schema (deserialization will typically fail cleanly given the leading type-prefix byte in `SignerMessage`'s codec, but the chunk write, storage, and network-wide propagation still succeed as an unauthorized, forged write with no legitimate authorization for that specific StackerDB). This qualifies as an unauthenticated write to StackerDB state plus network-wide propagation of forged data.

### Likelihood Explanation
Exploitation requires only observing one legitimate, publicly-broadcast StackerDB chunk (chunks are gossiped and readable via the public HTTP StackerDB API) and resubmitting it against a sibling contract; no private key or elevated privilege is needed. The precondition — identical slot assignment for the same signer across all `.signers-{set}-{message_id}` contracts for one cycle parity — is structural (enforced by `stackerdb-get-signer-slots-page` reading the same underlying list, per `signers.clar`) rather than incidental, making the attack reliably reproducible for any active signer set.

### Recommendation
Include a per-StackerDB domain separator in the signed digest — e.g., mix the `QualifiedContractIdentifier` (or a stable numeric StackerDB/message-lane identifier) into `SlotMetadata::auth_digest()` — so that a signature produced for one StackerDB contract cannot be replayed as valid for a different StackerDB contract, even when the same signer occupies the same `slot_id` in both. This mirrors the recommended fix for the reported issue: bind the signature to the specific authorized destination/context rather than relying solely on externally-tracked per-contract signer-address bookkeeping.

### Proof of Concept
1. Observe a validly-signed `StackerDBChunkData { slot_id: N, slot_version: V, sig, data }` broadcast for contract `.signers-1-1` (owned by signer address `A` at slot `N`).
2. Confirm via `stackerdb-get-signer-slots` that `.signers-1-2` (same `signer_set=1`) assigns the same address `A` to the same `slot_id` `N` [2](#0-1) .
3. Resubmit the identical chunk (same `slot_id`, `slot_version`, `sig`, `data`) either via `POST /v2/stackerdb/<contract=.signers-1-2>/chunks` or via a `StackerDBPushChunkData` P2P message with `contract_id = .signers-1-2`.
4. `try_replace_chunk`/`validate_received_chunk` verify `slot_desc.verify(&slot_validation.signer)` against `.signers-1-2`'s configured signer for slot `N`, which is the same address `A`; verification succeeds because `auth_digest()` never included the contract identifier, and the chunk is stored and rebroadcast [8](#0-7) [9](#0-8) .

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
