### Title
Dust-size debt positions become permanently unliquidatable due to the interaction between `maxLiquidable` and `debtFloorInUsd` — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two constraints simultaneously: a liquidator may repay at most `maxLiquidable` (50%) of the position's debt, and any non-zero remaining debt after repayment must be `>= debtFloorInUsd`. These constraints are mutually exclusive for any position whose total debt is `< 2 * debtFloorInUsd`. A borrower can therefore open a small, under-collateralized position that no liquidator can ever close, forcing the pool to absorb the resulting bad debt. This is the Metronome analog of the CVE-2018-2805 bug class: a reachable, repeatable denial of a protocol component (liquidation) triggered by unprivileged input.

### Finding Description
In `Pool.liquidate`, the repay amount is capped by `maxLiquidable` (initialized to `0.5e18` = 50%): [1](#0-0) 

Immediately after, the function reverts if the remaining debt is non-zero and below `debtFloorInUsd`: [2](#0-1) 

Combining the two:
- `amountToRepay_ <= debtBalance * 0.5`, so `remaining = debtBalance - amountToRepay_ >= debtBalance * 0.5 > 0`.
- `remaining` must therefore satisfy `remaining >= debtFloorInUsd`, which requires `debtBalance * 0.5 >= debtFloorInUsd`, i.e. `debtBalance >= 2 * debtFloorInUsd`.
- Full repayment (`remaining == 0`) is impossible because `amountToRepay_ = debtBalance` would make `wadDiv(debtBalance) = 1e18 > maxLiquidable` and hit `AmountGreaterThanMaxLiquidable`.

Any account whose debt in a given synthetic token is below `2 * debtFloorInUsd` reverts on every liquidation attempt regardless of how unhealthy it is. There is no alternative close path: `DebtToken.repay`/`repayAll` only burn the caller's own synthetic tokens and cannot reduce a third party's debt, and `DepositToken.seize` is only callable through `liquidate`. `quoteLiquidateMax` has the same defect — it caps at `maxLiquidable` without checking the floor, so even the "max" quote produces a reverting liquidation.

### Impact Explanation
Protocol insolvency via permanently stuck bad debt. A borrower whose position goes underwater while its per-synthetic debt is below `2 * debtFloorInUsd` can never be liquidated. The collateral backing that debt stays locked in the pool's `DepositToken`, the `DebtToken` balance keeps accruing interest via `accrueInterest`, and the protocol's collateralization invariant (`depositOf >= debtOf` coverage) degrades with no recourse. An attacker can mass-create such dust positions across accounts, each of which is individually unliquidatable, converting a natural price decline into guaranteed bad debt for the pool. This breaks the liquidation-bounds invariant and the solvency invariant — the same "complete DOS of the component" outcome as the reference CVE.

### Likelihood Explanation
Fully reachable by an unprivileged EOA: deposit collateral, call `DebtToken.issue`/`Pool` mint path to borrow just under `2 * debtFloorInUsd`, and wait for interest accrual or a routine price move to push the position below the health factor. No privileged role, oracle manipulation, or special timing is needed; even positions created innocently (small borrowers) become unliquidatable once their debt decays below the threshold. The only cost is the dust collateral deposited.

### Recommendation
In `Pool.liquidate`, exempt full-debt repayments from the `maxLiquidable` cap (e.g., `if (amountToRepay_ != _debtTokenBalance && amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) revert`), or clamp the floor check so that a repay that clears the entire debt is always permitted. Alternatively, enforce `debtFloorInUsd` as a minimum at borrow time in `DebtToken.issue`/`Pool.mint` so positions below `2 * debtFloorInUsd` cannot exist.

### Proof of Concept
Foundry/Hardhat sketch on a pool fork (debtFloor e.g. set to a non-zero USD value):

```solidity
// setup: pool with depositToken (msdToken) and debtToken (msSynth), debtFloorInUsd = F
address victim = makeAddr("victim");

// 1. victim deposits small collateral and borrows debt D with F/2 < D < 2*F
depositToken.mint(victim, collateralAmt);           // via pool deposit path
vm.prank(victim);
debtToken.issue(synthAmt, victim);                  // debt D in [F, 2F)

// 2. push position underwater (drop underlying oracle price, or let interest accrue)
oracle.setPrice(underlying, price / 2);
debtToken.accrueInterest();
(bool healthy,,,,) = pool.debtPositionOf(victim);
assert(!healthy);

// 3. every liquidation attempt reverts
uint256 debt = debtToken.balanceOf(victim);
vm.expectRevert(Pool.AmountGreaterThanMaxLiquidable.selector);
pool.liquidate(synth, victim, debt, depositToken);           // full repay blocked by cap

vm.expectRevert(Pool.RemainingDebtIsLowerThanTheFloor.selector);
pool.liquidate(synth, victim, debt * pool.maxLiquidable() / 1e18, depositToken); // leaves dust < floor

// any amountToRepay in (0, debt*0.5] leaves remaining in (debt*0.5, debt) ⊂ (0, F) when debt < 2F
// => position is permanently unliquidatable
```

For `debt < 2 * debtFloorInUsd`, all branches of `liquidate` revert, demonstrating the liveness break.
