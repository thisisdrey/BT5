### Title
Time-of-check/time-of-use gap in the anti-replay window lets a duplicated packet bypass replay protection - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` check the replay window (`window.Check`), release the lock, perform the (comparatively expensive) AEAD decryption, and only afterward re-acquire the lock to actually record the counter (`window.Update`). Because the counter is not reserved atomically with the check, two copies of the same encrypted packet arriving on different reader queues at nearly the same time can both pass `Check`, both decrypt successfully (AEAD decryption of identical ciphertext with the same counter is deterministic), and both be forwarded to the local tun interface before either call to `Update` records the counter — exactly the same class of bug as the Optimism `gasleft()` check/call gap: a value is validated, work is done, and only afterward is the state that made the validation meaningful actually committed.

### Finding Description
`Decrypt` and `VerifyRelay` in `connection_state.go` follow this pattern:
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
if !result { return nil, ErrAlreadySeen }

out, err = cs.dKey.DecryptDanger(...)   // expensive AEAD work, done without the lock held
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)  // counter is only *recorded* here
cs.decryptLock.Unlock()
if !result { return nil, ErrAlreadySeen }
``` [2](#0-1) 

`Bits.Check` only inspects whether the bit for `messageCounter` is already set; it does not set it. `Bits.Update` is the only call that actually marks the counter as seen. [3](#0-2) 

Multiple independent UDP reader goroutines (one per `f.routines` queue, via SO_REUSEPORT sockets) call `readOutsidePackets` → `Decrypt`/`VerifyRelay` concurrently for packets belonging to the same `hostinfo`/`ConnectionState`. [1](#0-0) [4](#0-3) 

If an attacker on the network path captures one legitimate encrypted packet and re-injects a duplicate copy of it (a trivial network-layer action requiring no cert, no key, and no privileged position — the same "malicious user" precondition as the original report), the two copies can land on two different reader queues at (nearly) the same instant:
1. Goroutine A calls `Check(counter)` → true (not yet marked).
2. Goroutine B calls `Check(counter)` → true (still not yet marked, A hasn't called `Update` yet).
3. Both A and B successfully `DecryptDanger` the identical ciphertext (same nonce/counter → same deterministic plaintext).
4. Both proceed past `Decrypt` and are handed to `handleOutsideMessagePacket`, which firewall-checks and writes the plaintext to the tun device: `f.readers[q].Write(out)` — this happens fully outside `decryptLock`. [5](#0-4) 
5. Only afterward does each goroutine call `Update`; the second `Update` call correctly returns `false`/`ErrAlreadySeen`, but by then the duplicate plaintext has already been delivered to the local network stack — the anti-replay window failed to prevent the replay it exists to stop.

This mirrors the report's root cause precisely: a "sufficient" check is performed, but the actual state mutation/consumption that the check was meant to gate happens later, after other work, leaving a window where the checked property no longer holds by the time it matters.

The project's own `CHANGELOG.md` documents that this exact class of issue (replay-window races) has previously required fixes — "Lock replay window updates so concurrent readers can't corrupt it" (#1802) and "Advance the replay window on relayed packets..." (#1751) — confirming replay-window concurrency is a recognized, previously-patched risk area, but the check/update split analyzed here remains present in both `Decrypt` and `VerifyRelay`. [6](#0-5) 

### Impact Explanation
This is a concrete traffic-replay bypass: duplicated ciphertext for a message that should be replay-rejected can be decrypted and delivered to the tun device (and, for relay frames, forwarded onward to the target) more than once, defeating the purpose of the `Bits` anti-replay window. Depending on payload semantics (e.g., duplicated application-layer commands, DNS queries, or other idempotency-sensitive traffic passed over the tunnel), this can cause duplicate processing of attacker-replayed traffic at the receiving application, and for relayed traffic can cause duplicate forwarding through `handleOutsideRelayPacket`.

### Likelihood Explanation
The precondition is only the ability to capture and re-inject (duplicate) one legitimate ciphertext packet on the network path — no valid certificate or any privileged position is required, matching the "no CA-signed certificate" attacker model. Triggering the race reliably requires the duplicate to arrive on a different reader queue within the narrow window between `Check` and `Update` on another goroutine, which is timing-dependent, but the codebase explicitly runs `f.routines` concurrent UDP reader goroutines that all funnel into the same per-connection `decryptLock`/`window`, so genuine concurrent processing of the same counter is a supported runtime configuration rather than a theoretical edge case.

### Recommendation
Merge the check and the update into a single atomic operation performed under one lock acquisition — i.e., have the first successful "claim" of a counter (bit-set) happen before or atomically with the decision to proceed to decryption, not after. Concretely, `Decrypt`/`VerifyRelay` should call a combined `CheckAndReserve`-style method that sets the bit while still holding `decryptLock`, before releasing the lock to perform `DecryptDanger`; if decryption then fails, the reservation should be rolled back (or, since decryption failure with a bad counter is not security-relevant, simply not rolled back) rather than re-checking availability afterward.

### Proof of Concept
1. Establish a working Nebula tunnel between two nodes with `listen.routines` (or default `f.routines`) > 1 so multiple UDP reader queues are active. [7](#0-6) 
2. Capture one legitimate encrypted `header.Message` UDP packet sent to the receiving node (e.g., with a packet sniffer/tap on the underlay network).
3. Re-inject two copies of the identical captured UDP datagram to the receiver's underlay UDP port(s) as close together in time as possible, ideally targeting the two socket queues bound via SO_REUSEPORT so the kernel dispatches them to different reader goroutines.
4. Observe on the receiving node's tun interface (or via `assertUdpPacket`-style test scaffolding as used in `e2e/tunnels_test.go`) whether the plaintext payload is delivered to the tun device more than once, versus the expected single delivery with the duplicate dropped as `ErrAlreadySeen`. [8](#0-7)  A reliable reproduction requires timing the two injected copies to land inside the `Check`→`Update` gap in `Decrypt`/`VerifyRelay`. [2](#0-1)

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (f *Interface) handleOutsideMessagePacket(hostinfo *HostInfo, out []byte, packet []byte, fwPacket *firewall.Packet, nb []byte, q int, localCache firewall.ConntrackCache) {
	err := newPacket(out, true, fwPacket)
	if err != nil {
		hostinfo.logger(f.l).Warn("Error while validating inbound packet",
			"error", err,
			"packet", out,
		)
		return
	}

	dropReason := f.firewall.Drop(*fwPacket, true, hostinfo, f.pki.GetCAPool(), localCache)
	if dropReason != nil {
		// NOTE: We give `packet` as the `out` here since we already decrypted from it and we don't need it anymore
		// This gives us a buffer to build the reject packet in
		f.rejectOutside(out, hostinfo.ConnectionState, hostinfo, nb, packet, q)
		if f.l.Enabled(context.Background(), slog.LevelDebug) {
			hostinfo.logger(f.l).Debug("dropping inbound packet",
				"fwPacket", fwPacket,
				"reason", dropReason,
			)
		}
		return
	}

	_, err = f.readers[q].Write(out)
	if err != nil {
		f.l.Error("Failed to write to tun", "error", err)
	}
}
