### Title
`unbond` extrinsics in `pallet-staking`, `pallet-staking-async`, and `pallet-nomination-pools` compute unlock era from the era observed at execution time with no user-supplied deadline, extending lock duration on delayed inclusion - ([File: substrate/frame/staking/src/pallet/impls.rs])

### Summary
The external report's core broken invariant is: a time/epoch-anchored lock-extension calculation reads a *mutable, execution-time* clock (`nextEpoch()`/timestamp) instead of a value the user committed to, so any inclusion delay across an epoch boundary silently extends the lock by a full extra epoch, with no `deadline`/`latestUnlockTime` parameter to bound this. The same broken invariant exists in Polkadot SDK's staking pallets, where `unbond` computes the unlocking-chunk era as `current_era (read at execution) + BondingDuration`, and the caller has no way to cap the era at which they are willing to be locked.

### Finding Description
`do_unbond` in `pallet-staking` reads the era live at execution time and adds `BondingDuration` to compute the unlock era for the newly created `UnlockChunk`: [1](#0-0) 

The equivalent logic exists in `pallet-staking-async`'s `unbond` path: [2](#0-1) 

and in `pallet-nomination-pools::unbond`, which delegates through `T::StakeAdapter::current_era()`: [3](#0-2) 

In all three cases, `era`/`unbond_era` is derived from whatever `CurrentEra` happens to be *when the block executing the extrinsic is authored*, not from a value the signer chose or bounded when they signed the transaction. `CurrentEra` advances autonomously via session rotation (`trigger_new_era` in staking, `plan_new_era` in staking-async), completely independent of and asynchronous to any individual user's extrinsic submission: [4](#0-3) [5](#0-4) 

If a user submits `unbond` expecting `current_era = N` (and therefore an unlock era of `N + BondingDuration`), but the transaction is not included until after the chain has already rotated into era `N+1` (due to congestion, low tip/fee, mempool eviction and resubmission, or simply being submitted near an era boundary), the resulting unlock era becomes `N+1 + BondingDuration` — one full era (hours) longer than the user intended, with no mechanism to reject the extrinsic if this threshold is crossed. Exactly analogous to the report's `nextUnlockTime()` jump caused by delayed execution crossing an epoch boundary, this is a corruption of the *effective unlock era* value written into `UnlockChunk.era` / pool `unbonding_eras`.

### Impact Explanation
This matches the report's "temporary freeze of funds" class: an unprivileged, honest user's stake is locked for longer than they intended without any way to bound or cancel it. Because `BondingDuration` for validators/nominators is on the order of multiple hours to days depending on the runtime configuration (e.g. `BondingDuration = 2` eras of `SessionsPerEra × session length`), and this affects both direct `Staking::unbond` and `NominationPools::unbond` (the latter being the exact functional analog of the report's "stake MagicLP for rewards, then lock/unlock" flow), the impact is a temporary but material fund lock extension for an unprivileged actor's own funds — no malicious peer, validator, or governance actor required.

### Likelihood Explanation
Likelihood is non-trivial but bounded: it only manifests for transactions submitted close to an era-boundary (last block(s) of the current era) under congestion or fee/inclusion delay, similar to the report's reasoning that this is "not a targeted attack" but "a constant probabilistic leak." Given eras rotate on the order of hours and inclusion delays of even a few blocks near the boundary can flip `CurrentEra`, this can occur under normal network conditions without any adversarial behavior, consistent with the accepted-scope criteria (implementation bug degrading intended user-facing behavior, not requiring a malicious actor).

### Recommendation
Add an optional caller-supplied upper bound (e.g. `max_unbond_era` / `deadline_era`) to `unbond` (and `pallet-nomination-pools::unbond`) that is checked against the era actually observed at execution time; reject with an error (e.g. `Error::<T>::DeadlineExceeded`) if the computed `era` (`current_era + BondingDuration`) would exceed the caller's specified bound, mirroring how AMM-style `deadline` parameters guard against stale execution.

### Proof of Concept
1. User A calls `Staking::unbond(amount)` while `CurrentEra = N`, expecting `UnlockChunk.era = N + BondingDuration`.
2. The transaction sits in the transaction pool because of a fee spike / network congestion near the era boundary.
3. Before A's transaction is included, `on_initialize`/`new_session` triggers `try_trigger_new_era`, calling `trigger_new_era`, which bumps `CurrentEra` to `N+1`: [6](#0-5) 
4. A's transaction is finally included; `do_unbond` now reads `CurrentEra::<T>::get() == N+1` and creates `UnlockChunk { value, era: N+1+BondingDuration }`: [1](#0-0) 
5. A's funds are now locked one full era longer than intended, and A had no parameter available on the `unbond` call to prevent this or abort execution.
