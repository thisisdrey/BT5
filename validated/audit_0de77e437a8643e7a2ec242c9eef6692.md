### Title
Uninitialized `accountIndexOf` treated as zero instead of `INITIAL_INDEX` lets an attacker accrue rewards equal to their full token balance per fresh account - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The SQLite CVE class is "incorrect error handling when rewriting state" — a fallback/edge path produces wrong results. The analog in Metronome is `RewardsDistributor._calculateTokenDelta`: when a user's stored `accountIndexOf` is `0` (never initialized), the code only substitutes `INITIAL_INDEX` if the token index is *strictly greater* than `INITIAL_INDEX`. While the token index is still exactly `INITIAL_INDEX` (before any rewards have accrued), the uninitialized account keeps index `0`, producing `_deltaIndex = 1e18` and `_tokensDelta = balance` — i.e., every fresh account is credited reward tokens equal to its whole DepositToken/DebtToken balance.

### Finding Description
In `contracts/RewardsDistributor.sol:217-231`:

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a reward token's speed is first enabled, `_updateTokenSpeed` initializes `tokenStates[token_] = {index: INITIAL_INDEX, timestamp: now}` (`lines 296-299`). Before `block.timestamp` advances past that timestamp, `_calculateTokenIndex` returns no new index (`_deltaTimestamps == 0`), so the index remains exactly `INITIAL_INDEX`.

Any account whose `accountIndexOf` is `0` (which is *all* accounts that held or received the token before rewards were activated — `updateBeforeMintOrBurn`/`updateBeforeTransfer` skip updates while `index == 0`, lines 175-192) falls into the gap: the `> INITIAL_INDEX` guard does not fire, `_accountIndex` stays `0`, and `_tokensDelta = balance.wadMul(1e18) = balance`.

Attacker path (fully unprivileged):
1. Deposit underlying via `DepositToken.deposit` before the governor enables reward speed (index still `0`, no index write).
2. Wait for `updateTokenSpeed(token, speed > 0)` — this sets `index = INITIAL_INDEX`.
3. In any block before the index advances, call `claimRewards(account, [token])` — public, nonReentrant only. `_updateTokensAccruedOf` accrues `tokensAccruedOf[account] += balance`.
4. Repeatably: transfer the DepositToken balance to a fresh attacker address via `DepositToken.transfer`. `updateBeforeTransfer` calls `_updateTokensAccruedOf` for `to_`, whose index is `0`, adding another `balance` to `tokensAccruedOf[to_]` — this can be repeated across a chain of fresh addresses with the same tokens, each hop crediting `balance` again.
5. `claimRewards` calls `_transferRewardIfEnoughTokens`, which pays out up to the distributor's entire `rewardToken` balance.

### Impact Explanation
Theft of unclaimed yield: the distributor's `rewardToken` balance (e.g., VSP rewards destined for all depositors/borrowers) can be fully drained by an unprivileged attacker using only public entry points and self-transfers. The drain is limited per hop only by the attacker's token balance, but is repeatable across fresh recipient addresses, so with modest capital the whole contract balance is extractable — after which legitimate users' accrued rewards can never be paid.

### Likelihood Explanation
Likelihood depends on the distributor holding reward tokens and the token index sitting at `INITIAL_INDEX` — the window between `updateTokenSpeed` enabling a token and the next timestamp in which rewards accrue. However, the multiplicative repeat via `updateBeforeTransfer` on fresh accounts means a single account is not required to exploit during that window for the *first* hop; additionally, any account created later whose index was never written remains vulnerable whenever `tokenStates[token].index` is reset or a new token is added. The attacker needs only an EOA and standard deposit/transfer calls; no privileged role, oracle manipulation, or malicious endpoint is required. The required precondition (rewards enabled on a token that has holders with uninitialized indexes) is the normal deployment/configuration sequence, not an edge case.

### Recommendation
Change the fallback condition in `_calculateTokenDelta` to handle the equality case:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

or, more robustly, treat `_accountIndex == 0` as `_accountIndex = _tokenIndex` (no accrual for accounts with no recorded index). Also consider writing `accountIndexOf` eagerly in `updateBeforeMintOrBurn`/`updateBeforeTransfer` even when `tokenStates[token_].index == 0`, so no account ever carries a sentinel `0` index into a live reward window.

### Proof of Concept
Hardhat/fork sketch (assumes pool, msdUSDC DepositToken, RewardsDistributor with rewardToken funded):

```ts
// Pre: governor funded distributor with rewardToken; reward speed not yet set.
await usdc.approve(msdUSDC.address, amount)
await msdUSDC.deposit(amount, attacker.address) // index==0 → no index write

// Governor enables rewards
await rewardsDistributor.connect(governor).updateTokenSpeed(msdUSDC.address, speed)

// Same timestamp: index still INITIAL_INDEX
await rewardsDistributor.connect(attacker).claimRewards(attacker.address, [msdUSDC.address])
// tokensAccruedOf[attacker] == amount (deltaIndex = 1e18)

// Amplify: transfer msdUSDC to fresh EOA, claim again
await msdUSDC.connect(attacker).transfer(fresh.address, amount)
await rewardsDistributor.connect(attacker).claimRewards(fresh.address, [msdUSDC.address])
// fresh is credited `amount` again; repeat across EOAs to drain rewardToken balance
```

Expected: `rewardToken.balanceOf(rewardsDistributor)` is drained to attacker-controlled EOAs while legitimate users' `claimable` can no longer be paid (`_transferRewardIfEnoughTokens` no-ops on insufficient balance).

Caveat: I could not fully verify via the index whether `DepositToken.transfer` always routes through `updateBeforeTransfer` before the balance move (it is declared in `IDepositToken`/`IRewardsDistributor` and invoked per the comments at `contracts/RewardsDistributor.sol:186`), and whether reward speeds are enabled on the deployed configuration — a fork test should confirm both, but the logic bug in `_calculateTokenDelta` stands on its own.
