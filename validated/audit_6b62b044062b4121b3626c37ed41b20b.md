### Title
Unprivileged attacker can fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` sets via dust transfers, reverting all future deposits, transfers-in and debt issuance to the victim with `UserReachedMaxTokens` — (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount()` and `Pool.addToDebtTokensOfAccount()` enforce `MAX_TOKENS_PER_USER = 30`, but any holder of a `DepositToken` can force entries into an arbitrary victim's set simply by `transfer()`-ing a dust amount to them. `DepositToken._transfer()` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero. Once the combined set size reaches 30, every subsequent operation that would add a *new* token to the victim's account reverts — including the victim's own first-time `deposit()` into a collateral they don't hold yet, incoming `transfer()`/`transferFrom()` of any msdToken they don't hold, and `DebtToken.issue(..., to_=victim)`. This is the same bug class as CVE-2019-1010239: an exceptional state (account's token list is full) is handled by reverting instead of being checked/skipped, producing a denial of service.

Relevant code:
- `Pool.sol:79` `MAX_TOKENS_PER_USER = 30`, `Pool.sol:143-148` `onlyIfAdditionWillNotReachMaxTokens` reverts `UserReachedMaxTokens`, `Pool.sol:216-220` `addToDepositTokensOfAccount` (caller-authenticated only as "is a deposit token", no consent from `account_`).
- `DepositToken.sol:517-520` `_transfer` auto-adds on recipient's first receive; `DepositToken.sol:485-488` `_mint` auto-adds on first deposit.

### Finding Description
The invariant broken is liveness: the protocol assumes an account can always receive collateral/deposit tokens, but an attacker can unilaterally push the victim's `depositTokensOfAccount` list to the cap without any consent check. There is no opt-in mechanism, no minimum-amount check, and no way for `account_` to reject an addition. Removal only happens when the balance goes to zero (`DepositToken.sol:522-525`, `DepositToken.sol:459-462`), so the victim must spend gas to shuffle dust out — and the attacker can refill entries in the same or a follow-up transaction (front-running the victim's deposit), giving a repeatable griefing loop for the cost of dust collateral across at most 30 tokens.

Concretely:
1. Attacker deposits dust into each of the pool's `N` deposit tokens (or acquires dust msdTokens).
2. Attacker calls `msdToken_i.transfer(victim, 1 wei)` for each token `i` the victim doesn't hold. Each call hits `DepositToken._transfer` → `pool.addToDepositTokensOfAccount(victim)`, filling the victim's list to 30 (combined with debt tokens if needed — the attacker can also `issue(1 wei, victim)` on each debt token to fill `debtTokensOfAccount`, since `issue` mints the debt position to an arbitrary `to_`).
3. Any subsequent `deposit(amount, victim)` / `transfer(..., victim, ...)` / `issue(..., victim)` involving a token not already in the victim's list reverts in `onlyIfAdditionWillNotReachMaxTokens` with `UserReachedMaxTokens`, even though the revert happens *after* the pull of underlying collateral is only avoided because the mint reverts before `addToDepositTokensOfAccount` — the user-facing result is the deposit/issuance path is unusable.

Note the check ordering in `_mint`: `DepositToken.sol:476` checks `maxTotalSupply` and mutates `balanceOf`, then `pool.addToDepositTokensOfAccount` reverts, rolling back the whole deposit. There is no path to deposit a new collateral type while the victim's list is full.

### Impact Explanation
Temporary freezing of funds / liveness denial against a targeted account: while the victim's token list is saturated, they cannot deposit into any collateral they don't already hold, cannot receive any msdToken they don't already hold, and cannot be issued debt in a new synthetic — i.e., they cannot open or rebalance a position using new collateral types. For an account that is near-liquidation and needs to add a *different* collateral to restore health, this directly blocks the rescue path, which can convert a temporary freeze into a forced liquidation loss. The attack is cheap (dust of ≤30 registered tokens), repeatable (attacker can re-fill after the victim clears entries), and works on the deployed configuration since none of `whenNotPaused`, `nonReentrant`, or `onlyIfDepositTokenExists` stop it — the victim's consent is never required anywhere in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`.

### Likelihood Explanation
Requires no privileged role: the attacker only needs dust amounts of the pool's listed deposit tokens (obtainable by depositing dust or buying msdTokens on the market) plus optional dust debt issuance to their own account forwarded via `issue(amount, victim)` — note `DebtToken.issue`/`flashIssue` mint the position to an arbitrary `to_`, so `addToDebtTokensOfAccount(victim)` is also attacker-controlled. Gas cost is ~30 cheap ERC-20 transfers. Main limitations: (a) bounded by the number of registered deposit + debt tokens in the pool — if fewer than 30 exist, the cap can't be reached by this vector alone; (b) the victim can self-recover by transferring dust entries out, so the DoS must be sustained by re-griefing. Given pools on mainnet/optimism/base list numerous collaterals (USDC, DAI, WETH, WBTC, vaUSDC, vaETH, vaOP, sfrxETH, etc.) plus debt tokens, reaching 30 combined entries is realistic or near-realistic; even partial filling raises the victim's gas costs and blocks tokens beyond the remaining slots.

### Recommendation
- Make additions to `depositTokensOfAccount`/`debtTokensOfAccount` opt-in or skip-on-full instead of revert: e.g., in `addToDepositTokensOfAccount`, return early (no-op) when the account is at `MAX_TOKENS_PER_USER` rather than reverting, and make `depositOf`/`debtOf` iterate over tracked tokens only (untracked tokens would be excluded from health, which must be weighed against letting users hold untracked collateral).
- Alternatively, enforce a meaningful minimum first-transfer/first-deposit amount per token so dust cannot cheaply occupy slots.
- Alternatively, allow the account itself (or anyone) to remove a token entry when its balance is below a dust threshold, not only at exactly zero.
- If keeping the revert, document that positions must be rescued only via collateral types already held, and consider tracking the account's set in a way that ignores balances below a floor.

### Proof of Concept
Foundry/Hardhat fork sketch (against a deployed pool with ≥ a few registered deposit tokens; use smock or real tokens on a mainnet fork):

```solidity
// Setup: pool with registered deposit tokens msdA, msdB, ..., msdN
// Victim holds nothing or only some tokens.
address victim = makeAddr("victim");

// 1. Attacker obtains dust of each deposit token
for (uint i; i < depositTokens.length; ++i) {
    IDepositToken dt = IDepositToken(depositTokens[i]);
    IERC20 underlying = dt.underlying();
    deal(address(underlying), attacker, 1e6);
    underlying.approve(address(dt), 1e6);
    dt.deposit(1, attacker);          // mint dust msdToken to attacker
}

// 2. Fill victim's list with dust transfers (repeat with debt issuance if needed)
for (uint i; i < depositTokens.length; ++i) {
    IDepositToken dt = IDepositToken(depositTokens[i]);
    vm.prank(attacker);
    dt.transfer(victim, 1);           // adds dt to depositTokensOfAccount[victim]
}
// If debt tokens are needed to reach 30:
for (uint i; i < debtTokens.length; ++i) {
    IDebtToken dbt = IDebtToken(debtTokens[i]);
    // attacker has collateral; issue dust debt directly to victim
    vm.prank(attacker);
    dbt.issue(1, victim);             // adds dbt to debtTokensOfAccount[victim]
}
assertEq(pool.getDepositTokensOfAccount(victim).length
       + pool.getDebtTokensOfAccount(victim).length, 30);

// 3. Victim can no longer deposit a collateral they don't already hold
vm.startPrank(victim);
IERC20 underlyingNew = IDepositToken(newDepositToken).underlying();
deal(address(underlyingNew), victim, 100e18);
underlyingNew.approve(address(newDepositToken), 100e18);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
IDepositToken(newDepositToken).deposit(100e18, victim);   // reverts

// 4. Incoming transfer of a token the victim doesn't hold also reverts
vm.prank(attacker);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
IDepositToken(newDepositToken).transfer(victim, 1);
```

Observed behavior matches `Pool.test.ts` "should revert when reach max tokens" (test/Pool.test.ts:1386-1416), which confirms `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined list hits 30 — the finding is that this cap is reachable *by a third party* via ordinary `transfer()`/`issue()` calls against an unconsenting victim.
