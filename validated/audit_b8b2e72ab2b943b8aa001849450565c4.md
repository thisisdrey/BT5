### Title
Eth-implicit Wallet Contract trusts unvalidated cross-contract return data to decide whether to spend NEAR on `storage_deposit`, letting a malicious "token" contract repeatedly siphon funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::nep_141_storage_balance_callback` decides whether to spend `NEP_141_STORAGE_DEPOSIT_AMOUNT` of the wallet's own NEAR balance based solely on the JSON payload returned by an externally-controlled contract (`storage_balance_of`), rather than on any protocol-guaranteed fact. A malicious `target` "token" contract can always report that the receiver is unregistered, forcing the wallet contract to pay an extra `storage_deposit` to the attacker's contract on every emulated ERC-20 transfer, exactly mirroring the NFTX pattern of trusting untrustworthy return data from an external call to control fund movement.

### Finding Description
When an eth-implicit account performs an emulated ERC-20 transfer, `inner_rlp_execute` calls the target token contract's `storage_balance_of` and routes the result to `nep_141_storage_balance_callback`: [1](#0-0) 

The callback deserializes the *content* of the promise's successful return value (not merely whether the call succeeded) into `maybe_storage_balance: Option<StorageBalance>`, and this attacker-controlled value alone determines whether an additional `storage_deposit` call carrying `NEP_141_STORAGE_DEPOSIT_AMOUNT` NEAR is made: [2](#0-1) [3](#0-2) 

Since `token_id` (the `target` account) is an arbitrary, attacker-deployable contract, the attacker fully controls the body of `storage_balance_of`'s response. By always returning `null` (i.e., `None`) regardless of the real registration state, the malicious contract forces the wallet into the `None` branch every time, which issues a `Promise::new(token_id).function_call("storage_deposit", ..., NEP_141_STORAGE_DEPOSIT_AMOUNT, ...)` that pays `NEP_141_STORAGE_DEPOSIT_AMOUNT` yoctoNEAR directly to the attacker's contract account — funds drawn from the wallet contract's own balance, not from any user-supplied deposit earmarked for this purpose. This is the same root cause as the referenced NFTX bug: the contract "assumes the returned data is truthful" and uses it to decide whether to move funds, instead of relying only on facts it can trust (e.g., the actual on-chain storage state or the success/failure of the call).

### Impact Explanation
Every emulated ERC-20 transfer routed through such a malicious token contract results in an unconditional, unrecoverable transfer of `NEP_141_STORAGE_DEPOSIT_AMOUNT` (1,250 microNEAR) from the wallet contract's account balance to the attacker's contract, with no compensating benefit to the wallet owner. Because this triggers on every transfer call, it constitutes repeated, concrete theft of the wallet owner's NEAR funds and is a genuine loss of funds vulnerability.

### Likelihood Explanation
Reachable by any ordinary user: an eth-implicit wallet owner (or a relayer submitting on their behalf) simply needs to sign/submit an RLP transaction whose `to` address resolves to a malicious "token" contract implementing a spoofed `storage_balance_of`. No validator, network, or privileged access is required — only a deployed contract acting as the ERC-20 target, i.e., an unprivileged "malicious receiver" role analogous to the original finding.

### Recommendation
Do not trust the deserialized business data returned from `storage_balance_of` to authorize spending the wallet's own NEAR. Instead, treat only the presence of an actual on-chain, previously-confirmed registration (or require the caller/registrar-level source of truth rather than a self-reported balance) as authoritative, or bound how much can be spent per call/require it to come from funds explicitly provided by the caller for this purpose rather than the wallet's residual balance.

### Proof of Concept
1. Attacker deploys a NEAR contract with a `storage_balance_of` method that always returns `null`, and any other methods needed to appear NEP-141-like.
2. Attacker gets a user's eth-implicit wallet to sign an `ERC20Transfer` RLP transaction with `target` set to this malicious contract (e.g., by presenting it as a legitimate token to a user/relayer).
3. `inner_rlp_execute` builds the `storage_balance_of` promise chain and calls `nep_141_storage_balance_callback` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:433-458`).
4. The callback parses `PromiseResult::Successful(value)` into `None` (lines 203-221) and, believing the receiver is unregistered, issues a `storage_deposit` call attaching `NEP_141_STORAGE_DEPOSIT_AMOUNT` to the malicious contract (lines 224-269), transferring real NEAR out of the wallet contract's balance on every such transfer call, regardless of the receiver's actual registration status.
