### Title
Wallet Contract fails to refund `caller_deposit` when the Address Registrar cross-contract call fails, permanently locking user funds in the contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
This is analogous to the Stargate `sgReceive()` bug class: a `require`/failure path on a hardcoded external dependency (there, the Stargate router; here, the hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` contract) causes tokens already transferred into the contract to be stranded, because the failure-handling branch does not return the deposit to its rightful owner.

### Finding Description
The Wallet Contract's `rlp_execute` flow attaches a `caller_deposit` (tracked via `CallerDeposit::new`, which records the predecessor's attached NEAR whenever the predecessor differs from the contract account) so that if a downstream cross-contract call fails, the deposit can be refunded [1](#0-0) .

For the `EOABaseTokenTransfer` path with an `address_check`, `inner_rlp_execute` calls out to a hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` contract (`address-map.near`) via `address_registrar.lookup(...)`, chaining the result into `address_check_callback` and forwarding `caller_deposit` through [2](#0-1) .

In `address_check_callback`, when the registrar cross-contract call fails (`PromiseResult::Failed`), the function immediately returns an `ExecuteResponse` with `success: false` and does **not** refund `caller_deposit` — contrast this with `rlp_execute_callback`, which explicitly creates a refund promise back to `caller_deposit.account_id` when its own promise fails: [3](#0-2)  versus the refund logic at [4](#0-3) .

The registrar lookup call can fail for reasons entirely outside the wallet-contract's control — e.g., if `address-map.near` is redeployed/migrated to a different account, deleted, or its `lookup` method signature/ABI changes — exactly the "router redeployment" scenario described in the external Stargate report, where a hardcoded, externally-controlled dependency address becomes stale and callbacks revert/fail.

### Impact Explanation
When this failure occurs, any NEAR that was attached by the predecessor (tracked as `caller_deposit`) is not sent back and instead remains locked in the Wallet Contract's account balance, from which the legitimate owner has no protocol path to recover it (the eth-implicit account can only act through `rlp_execute`, and this code path never returns the funds). This is a permanent freezing/loss of user funds, matching the class of impact required.

### Likelihood Explanation
Triggering this requires a failure of the cross-contract call to the hardcoded `ADDRESS_REGISTRAR_ACCOUNT_ID` contract — plausible if that contract is redeployed to a new account, deleted, upgraded incompatibly, or simply out of gas/panics during `lookup`. This is not attacker-controlled in the general case (unless an attacker can also influence the registrar contract), so likelihood depends on operational stability of `address-map.near`, similar to the original report's assessment that likelihood is hard to estimate but the risk is real given it's an external, upgradeable dependency.

### Recommendation
In `address_check_callback`'s `PromiseResult::Failed` branch, mirror the refund logic used in `rlp_execute_callback`: if `caller_deposit` is `Some`, create a transfer promise back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before (or as part of) returning the failure `ExecuteResponse`.

### Proof of Concept
Not independently reproduced in this analysis (would require simulating a registrar contract failure, e.g., pointing `ADDRESS_REGISTRAR_ACCOUNT_ID` at a nonexistent/incompatible account and calling `rlp_execute` with an `EOABaseTokenTransfer` carrying a non-zero `caller_deposit`, then observing that `address_check_callback`'s failure path does not emit a refund transfer). This is noted as unverified/uncertain and would need to be confirmed with a live test-loop or sandbox test.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
