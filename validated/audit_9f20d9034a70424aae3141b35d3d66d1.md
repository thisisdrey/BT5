### Title
Naive floating-point proportional-share reward distribution allows aggregate voter payouts to diverge from the recorded reward pot - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
The Size Sealed Auction bug computes what the seller receives with one rounding formula and what each bidder is later refunded with a *different* rounding formula. Because the two computations are performed independently and rounded down separately, the sum of amounts owed to bidders can exceed (or diverge from) what was actually collected, so the last claimant on a shared pot cannot be paid. java-tron's witness voting-reward distribution has the same structural pattern: a single shared reward pot recorded once per witness/cycle is later split among an arbitrary number of independent voters, each computed with its own rounding step, with no invariant tying the sum of individual payouts back to the recorded pot.

### Finding Description
`MortgageService.payReward()` records a single aggregate reward value per witness per cycle: [1](#0-0) 

That aggregate value is later split among every voter who voted for that witness in that cycle, independently, in `computeReward(long cycle, List<Pair<byte[], Long>> votes)`: [2](#0-1) 

Each voter's share is computed as `voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;`, using Java `double` arithmetic and a truncating cast to `long`, executed **separately for every voter** who calls `withdrawReward`/`queryReward`. Unlike the newer VI-based algorithm (`getWitnessVi`/`accumulateWitnessVi`), which uses a floor-rounded, monotonic "reward-per-share" accumulator specifically designed so that the sum of all floor-rounded individual claims never exceeds the recorded total, the old per-cycle `computeReward(cycle, votes)` path has no such invariant: it recomputes each voter's proportional share from scratch using floating-point division and multiplication, and the rounding error for each voter is independent of every other voter's rounding error.

This path is still reachable for any cycle prior to `newRewardAlgorithmEffectiveCycle` via `getOldReward`: [3](#0-2) [4](#0-3) 

and it is also duplicated verbatim (same double-based per-voter computation) in the TVM-native `VoteRewardUtil.computeReward`, reachable from any smart contract that calls the TVM `withdrawReward`/`queryReward`/`voteWitness` opcodes: [5](#0-4) 

Both `MortgageService.adjustAllowance` and `VoteRewardUtil.adjustAllowance` simply add the computed reward to the target account's `allowance` field, which is later converted 1:1 into spendable TRX balance on `WithdrawRewardProcessor.execute` — there is no per-cycle "remaining pot" counter that decrements as each voter claims, and no reconciliation check that the sum of all individually-rounded claims for a given witness/cycle does not exceed `delegationStore.getReward(cycle, srAddress)`.

### Impact Explanation
Because voter reward shares are computed independently with `double` (floating point) rounding rather than a floor-consistent, pot-decrementing scheme, the aggregate amount minted into voter `allowance` fields for a single witness/cycle reward can systematically diverge from the recorded `totalReward` for that witness/cycle. Any voter's `allowance` created this way is later paid out as real, spendable TRX balance via `WithdrawRewardProcessor`/`adjustBalance`, so a positive divergence effectively mints unbacked TRX balance across the many independent voters of a popular witness, while a negative divergence causes some voters to be silently short-paid relative to their proportional entitlement. This maps to the "unbacked balance"/"theft or permanent freezing of funds" impact class, reachable purely by ordinary account holders casting votes and calling withdraw/query reward — no privileged role required.

### Likelihood Explanation
Any account can vote for witnesses and call withdraw/query-reward operations (`WithdrawRewardProcessor`, `MortgageService.withdrawReward`), and the affected old-algorithm code path is still exercised for any cycle prior to `newRewardAlgorithmEffectiveCycle`, and unconditionally in the TVM-native `VoteRewardUtil` duplicate. Because the divergence is driven by ordinary floating-point rounding rather than a rare edge case, it will occur whenever a witness has many small-vote-count voters splitting a shared reward pool — a routine, easily reachable condition, not a contrived adversarial setup.

### Recommendation
Replace the double-based per-voter proportional computation in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` and its duplicate in `VoteRewardUtil.computeReward` with the same floor-rounded, invariant-preserving "reward-per-share" (Vi) accumulator technique already used for the new reward algorithm, ensuring the sum of all individually-rounded voter claims for a given witness/cycle can never exceed the recorded `totalReward`. Alternatively, track and decrement a "remaining reward" counter per witness/cycle as each voter withdraws, and clamp/cap individual payouts to the remaining balance, analogous to fixing the aggregation error identified in the SizeSealed report by tracking `filledQuote` explicitly rather than recomputing amounts from an intermediate rounded price for every party.

### Proof of Concept
1. Set up a witness `W` in a cycle with a recorded reward `totalReward = R` via `delegationStore.addReward(cycle, W, R)` (as done in `MortgageService.payReward`).
2. Have `N` different accounts vote for `W` with vote counts chosen so that `userVote / totalVote` are values that do not divide evenly in binary floating point (e.g., votes of 1, 1, 1 out of a `totalVote` of 3, or other irrational-in-binary fractions).
3. Have each of the `N` accounts independently call `withdrawReward` (via `MortgageService.withdrawReward` or the TVM `withdrawReward` opcode backed by `VoteRewardUtil`/`WithdrawRewardProcessor`).
4. Sum the `allowance` increments granted to all `N` accounts for cycle `cycle` and compare to `R`. Because each account's share is computed independently as `(long) (voteRate * totalReward)` with `voteRate` computed in `double` precision, the summed payouts can be shown (via constructed vote distributions and repeated runs, similar to the referenced report's Foundry PoC methodology) to diverge from `R`, unlike the floor-consistent Vi-based path used after `newRewardAlgorithmEffectiveCycle`.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
