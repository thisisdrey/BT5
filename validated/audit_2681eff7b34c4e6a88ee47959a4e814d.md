## Analog Found

### Title
Unauthenticated `RecvError` packets allow a spoofing attacker to force last-minute tunnel/handshake teardown - ([File: outside.go])

### Summary
The report describes a "last-minute cancellation" bug class: an actor is allowed to unilaterally abort a process right at its critical finalization boundary, forcing the system into a worse fallback state (reserve price or null settlement) instead of the intended outcome. In nebula, the same bug class appears in the handling of `header.RecvError` control packets, which are processed as plaintext, unauthenticated messages and can tear down an established tunnel or in-flight handshake at any moment, including the instant before/after completion.

### Finding Description
`RecvError` is dispatched directly out of the unencrypted packet-type switch, before any AEAD/authentication step is applied: [1](#0-0) 

Unlike `header.Message` traffic, which must pass `ConnectionState.Decrypt` (AEAD verification) before being acted on, `RecvError` packets skip decryption entirely. The handler `handleRecvError` accepts the packet as authoritative and closes the tunnel purely based on a UDP source-address comparison to the currently known remote: [2](#0-1) 

The only "authentication" is `hr.IsValid() && hr != addr` — i.e., it only checks that the claimed source UDP address matches the hostinfo's currently known remote address. Since UDP source addresses are trivially spoofable (and the `RemoteIndex` field needed to target a specific hostinfo travels in cleartext in the header of every other packet on the wire, per `header.H.Parse`), an attacker who can observe or guess a valid `(RemoteIndex, remoteAddr)` pair can forge a `RecvError` packet at will. There is no cryptographic binding (no AEAD, no signature, no cert) tying the `RecvError` sender to a real, previously-authenticated peer.

`handleRecvError` immediately calls `f.closeTunnel(hostinfo)` and also deletes the corresponding pending handshake entry via `f.handshakeManager.DeleteHostInfo(hostinfo)` — exactly analogous to canceling a bid at `timestamp == listingEnd`: an attacker can time the forged `RecvError` to arrive right as a handshake is about to complete (or right after), aborting the process and forcing the victims to restart the handshake from scratch (the "null" auction outcome), repeatedly, as a low-cost unauthenticated DoS/state-poisoning primitive.

There is a rate-limiting gate (`sendRecvErrorConfig.ShouldRecvError` / `acceptRecvErrorConfig.ShouldRecvError`) referenced in `outside.go` and `interface.go`, but based on the code inspected, this is a throttling mechanism, not a cryptographic authentication mechanism — it does not verify that the sender possesses any secret material or CA-signed certificate. I was not able to fully inspect the implementation of `ShouldRecvError`/`RecvErrorConfig` within the available index, so I cannot rule out additional mitigations (e.g., stricter per-source rate limits) inside that type; this should be verified directly in `interface.go` if precise bounds on exploitability are needed.

### Impact Explanation
An attacker with no valid CA-signed certificate, and without needing to be a valid peer/lighthouse/relay, can:
- Repeatedly force teardown of active tunnels and abort in-progress handshakes between two legitimate, fully-authenticated nebula nodes, by spoofing the UDP source address of one party and replaying/forging a `RecvError` header with an observed `RemoteIndex`.
- Time this to coincide with handshake completion, mirroring the reserve-price/null-settlement pattern in the report: instead of a clean, authenticated tunnel establishment, the attacker forces perpetual restart/degraded availability (remote state poisoning / DoS), without ever needing to break the Noise handshake or certificate verification itself.

This is a remote, unauthenticated denial-of-service / state-poisoning primitive against the tunnel lifecycle, reachable by any attacker capable of spoofing UDP source addresses and observing the cleartext `RemoteIndex` field carried on every packet.

### Likelihood Explanation
Likelihood is moderate-to-high in networks where UDP source spoofing is possible (many networks do not enforce strict source-address validation / BCP38), and where the attacker is on-path or can observe traffic to learn `RemoteIndex` values (which are sent in cleartext on every packet, per `header.H`). No cryptographic secret is required to construct a valid-looking `RecvError` packet.

### Recommendation
- Do not allow `RecvError` (or any control message that tears down state) to be honored based solely on a cleartext, unauthenticated source-address match.
- Either authenticate `RecvError` cryptographically (e.g., require it to be sent inside the encrypted tunnel envelope like `CloseTunnel` is, per `outside.go:164-166` and validated by `TestCloseTunnelAuthenticated`), or add a challenge/response and stricter rate limiting keyed by unforgeable state (e.g., require a valid AEAD-authenticated confirmation before tearing down an active `ConnectionState`).
- If backward compatibility requires keeping `RecvError` unauthenticated, at minimum add a buffer/debounce window around handshake completion so that a `RecvError` arriving within that window cannot immediately erase a hostinfo that just became `ConnectionState != nil`, analogous to the `MIN_LENGTH_BID_EXPIRY` buffer recommended in the report.

### Proof of Concept
1. Observe or capture any packet traversing between two nebula nodes A and B to learn `RemoteIndex` (cleartext in `header.H`) associated with B's tunnel to A, and A's currently known UDP remote address for B.
2. Craft a UDP packet with header `Type = header.RecvError`, `RemoteIndex` = the observed index, spoofing the source address to match B's known remote address, and send it to A.
3. `readOutsidePackets` routes it directly to `handleRecvError` without any decryption/authentication step (`outside.go:81-84`).
4. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, sees the (spoofed) source address matches `hostinfo.GetRemote()`, and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` (`outside.go:563-575`), tearing down the tunnel/pending handshake with no cryptographic proof of legitimacy.
5. Repeating this at the moment a legitimate handshake is about to complete forces perpetual restart, denying service or poisoning the connection state — the network analog of forcing the "auction" (handshake) to null out via last-minute unauthenticated cancellation.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
